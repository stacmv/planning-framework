# Dev Docs: Бюджет Manual-кейсов по size tier

## Архитектура

### Где живут данные

- `skills/pf-size-tiers/SKILL.md` — единственный источник таблицы бюджета
  (`trivial` 0-1, `small` ≤2, `medium` ≤3, `large` ≤5, потолок 5
  безусловно) и закрытого словаря `Manual reason` (5 значений). Остальные
  места (`pf-test-plan`, `pf-check`, `test/lib.sh`) ссылаются на него, а не
  дублируют значения — тот же принцип, что уже используется для
  size-tier-таблиц вообще.
- `skills/pf-test-plan/SKILL.md` Steps 4a-4d — вся enforcement-логика:
  валидация причины (4a) → подсчёт и сверка с бюджетом (4b) → automation
  pass (4c) → 3-вариантный гейт (4d). Вставлены между существующими Step 4
  (Status Tracker) и Step 5 (Known Issues) — чистая вставка, остальные шаги
  не тронуты.
- `skills/pf-check/SKILL.md` — тот же бюджет и словарь проверяются ещё раз,
  но не через вызов инструмента, а как ещё один пункт текстового промпта
  "Claude review path" (тот же LLM-ревьюер, что уже механически считает
  строки и сверяет tier-бюджет по количеству, просто добавлена ещё одна
  проверка). Это даёт защиту от хендэдита `test_plan.md` в обход
  `/pf-test-plan`.

### Конвенция `Manual reason` — решение, принятое во время реализации

**Ни `brd.md`, ни первая версия `test_plan.md` не специфицировали, где
именно в `test_plan.md` записывается причина.** Решение, принятое здесь
(и зафиксированное в `pf-size-tiers/SKILL.md`): колонка `Remarks` Status
Tracker для `Manual`-строки обязана начинаться с `Manual reason: <value>`,
опционально с произвольным текстом после. Переиспользует существующую
колонку (без изменения структуры таблицы) — так же, как `Auto`-строки уже
несут `Harness: ...` в том же `Remarks`. Альтернатива (отдельная колонка в
таблице) была бы более явной, но потребовала бы менять шаблон Status
Tracker и его парсеры во всех местах, которые его уже читают
(`pf-execute`, `pf-close`, `pf-test`) — решение сознательно взяло меньший
blast radius.

### Automation pass — отдельный sub-agent, не оркестратор

Step 4c диспатчит отдельного sub-agent, а не переписывает `test_plan.md`
силами оркестрирующей сессии. Это тот же паттерн, что уже используют
`pf-test-plan`/`pf-impl-plan` для черновой генерации документов ("do not
read/draft yourself — dispatch a sub-agent"). Sub-agent для
недостающего харнесса **не сам** добавляет задачу в
`implementation_plan.md` — он только называет, что нужно, в своей
summary; сама задача попадает в план на следующем касании планирования
(см. `user_docs.md` — расхождение между этими двумя вещами было найдено
review'ом `user_docs.md` и исправлено там же).

## Известная ловушка: `pipefail` + `grep -q` на живом продюсере

**Найдено и исправлено во время `/pf-test`, задокументировано как CR-004 в
`code_review.md`.** `test/lib.sh` включает `set -uo pipefail`. Паттерн
`multi_line_producer_function | grep -qiE 'pattern'` под `pipefail`
может вернуть **ложный fail**, даже когда `grep` реально нашёл совпадение:
`-q` завершает `grep` сразу при первом совпадении, продюсер (всё ещё
работающий цикл `while ... done < <(...)`) получает `SIGPIPE` при попытке
писать дальше, и `pipefail` репортит статус пайплайна по **продюсеру**
(ненулевой, killed by signal), а не по `grep` (который был бы 0).
Воспроизведено эмпирически (`PIPESTATUS` показывал `[141, 0]` — продюсер
убит, grep реально нашёл совпадение) — не гипотетическая проблема.

**Правило на будущее для любого нового `test/*.sh` в этом репозитории:**
не пайпить результат многострочной функции-продюсера напрямую в
`grep -q`/`grep -l`/`head` (что угодно, что может завершиться раньше, чем
продюсер допишет весь вывод). Либо захватывать вывод в переменную сначала
(`rows="$(producer)"; printf '%s' "$rows" | grep -q ...`), либо
использовать `grep -c`/plain `grep` (читают весь ввод до конца, не
завершаются досрочно). `pf_count_manual_in_tracker` (пайпит в `awk`, читает весь ввод для
подсчёта) и `TC-016`'s `grep -c .` в `test/manual-budget.sh` уже безопасны
по этой же причине — они не заканчиваются раньше продюсера. (TC-018 этот
паттерн не использует вовсе — считает через `pf_count_manual_in_tracker`
напрямую, тоже безопасно, но по другой причине.)

## Известные ограничения (не исправлены в этой issue)

- **Пробел в маршрутизации `/pf`.** `skills/pf/SKILL.md`'s таблицы
  переходов не содержат строки "`code_review.md` complete,
  `manual_test_checklist.md` not complete" → `/pf-test` — прыгают сразу с
  `CODE_REVIEW` на `TESTING`. Проверено: пробел идентичен во **всех трёх**
  таблицах (`feat`, `improve`, `bug`), не только в improve, как можно было
  бы подумать по тому, что именно эта issue — `improve`-типа. Обнаружено
  при прохождении этой issue через собственный пайплайн фреймворка; не
  исправлено здесь — баг самого `/pf`, вне охвата этой issue, реальный
  next step (`/pf-test`) был очевиден из `pf-test/SKILL.md`'s
  собственного prerequisite-гейта и из таблицы пайплайна `pf-size-tiers`.
  Кандидат в отдельную issue.
- **CR-001/CR-002/CR-003 (`wont-fix` в `code_review.md`).** CR-001 —
  заявленный P1-баг извлечения `Manual reason` при пояснительном тексте,
  эмпирически опровергнут (glob `[^a-z-]*` — не regex, работает корректно).
  CR-002 — фикстуры не покрывают явный кейс "reason с пояснительным
  текстом" (coverage-only, не баг). CR-003 — неоднородная нотация бюджета
  в таблице (`0-1` vs `≤N`), без функционального эффекта.
- **`20260806-feat-product-test-plan` (отдельная issue, ещё не
  реализована).** Вариант гейта "отложить избыток" сейчас — чисто
  информационная запись в `test_plan.md`, без реестра долга и без гейтов
  `/pf-qa`/`/pf-close` вокруг него. Эта половина дизайна сознательно вне
