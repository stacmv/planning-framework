## 1. Overview

Три технических блока реализуют BRD:

1. Новое поле `reviewers` в frontmatter `prompt.md` — хранит выбор ревьюера на артефакт.
2. `pf-check` учится читать это поле и вызывать Codex вместо/вместе с Claude.
3. Новый скилл `pf-codereview` — жёсткий гейт ревью кода между `/pf-execute` и `/pf-test`.

Оба механизма ревью (документы и код) используют один и тот же способ вызова Codex (§4) и один и тот же принцип: ревьюер только находит замечания, исправляет их всегда Claude-сабагент (§7).

## 2. `prompt.md` frontmatter — `reviewers`

```yaml
reviewers:
  brd: claude
  specs: claude
  test_plan: claude
  implementation_plan: claude
  code: claude
```

- Один ключ на каждый документ, который реально производит пайплайн **этого** issue (см. таблицу пайплайнов в `pf-size-tiers`): `feat` — brd/specs/test_plan/implementation_plan; `improve` — brd/test_plan/implementation_plan (нет specs); `bug` — analysis/test_plan/implementation_plan (ключ называется `analysis`, не `brd`); `trivial` — единственный ключ `notes` вместо brd/specs/implementation_plan. Ключ `code` присутствует всегда, при любом типе и тире.
- Допустимые значения: `claude`, `codex`, `both`.
- Значение по умолчанию для каждого ключа — `claude` (сохраняет сегодняшнее поведение для тех, кто полем не пользуется).
- Пишется один раз гардой из §3 и больше никогда не редактируется никаким `pf-*` скиллом.

## 3. Гарда назначения ревьюеров (по образцу гарды `size_tier`)

- Срабатывает там же и в тот же момент, где сегодня уже спрашивается `size_tier`: в `pf-brd` (для `feat`/`improve`) и в `/pf` перед написанием `analysis.md` (для `bug`, см. `pf-size-tiers`, «Tier confirmation for bug issues»).
- Если поле `reviewers` в `prompt.md` отсутствует — спросить пользователя (`AskUserQuestion`) выбор ревьюера для каждого применимого ключа (см. §2 про набор ключей по типу/тиру), рекомендуя `claude` везде («сохраняет сегодняшнее поведение»). Записать ответ в `prompt.md`.
- Для `trivial`-тира ключи — `notes`, `test_plan`, `code` (нет brd/specs/implementation_plan, т.к. они не производятся отдельно).

## 4. Механизм вызова Codex

Цепочка обнаружения, единая для документов (§5) и кода (§6):

1. Проверить, доступен ли в этой установке Claude Code глобальный плагин `codex` (его скиллы `codex:setup`/`codex:rescue` присутствуют в списке доступных скиллов).
2. Если плагин доступен — вызвать `codex:setup` (он сам проверяет готовность CLI и, если CLI не установлен, а `npm` доступен, сам предлагает пользователю установить — этот шаг не дублируется). После того как CLI готов, ревью выполняется тем же скриптом, которым пользуется команда `/codex:review` (`codex-companion.mjs review`, режим `--wait`, без интерактивных пауз), с базовой веткой/областью, подходящей под конкретный вызов (весь целевой документ для §5; diff issue-ветки от родителя для §6).
3. Если плагин недоступен в этой установке — спросить пользователя, ставить ли его; при отказе — вызывать `codex exec` напрямую через Bash (сырой CLI, без обёртки плагина), передав ему промпт-эквивалент §5/§6 и забрав stdout как текст ревью.
4. Если после всего этого Codex реально недоступен (CLI не установлен/не авторизован даже после предложений) — молча использовать Claude вместо Codex для этого артефакта, отметив в выдаче замечаний: «Codex недоступен — ревью выполнено Claude».

**Нормализация замечаний.** Ответ плагина соответствует `review-output.schema.json`: `verdict`, `summary`, `findings[].severity ∈ {critical, high, medium, low}`. Соответствие приоритетам, которыми уже пользуется `pf-check`: `critical`/`high` → **P0**, `medium` → **P1**, `low` → **P2**. Сырой ответ `codex exec` (без схемы) приоритетам не сопоставляется — показывается пользователю как есть, отдельным блоком «Codex findings (unstructured)».

## 5. Ревью документов — изменения в `pf-check`

- Перед диспетчеризацией сабагента анализа читать `reviewers.<ключ-документа>` из `prompt.md`.
- `claude` — поведение не меняется (сегодняшний Claude-сабагент).
- `codex` — вместо Claude-сабагента выполняется цепочка §4 с эквивалентным промптом (тот же TARGET и список предшественников, та же группировка по P0/P1/P2 — с сопоставлением severity по §4).
- `both` — выполняются оба ревью, их замечания объединяются в один список для пользователя, каждое подписано источником (`[Claude]` / `[Codex]`), группировка по P0/P1/P2 сохраняется. Автоматического разрешения противоречий нет (см. `brd.md`).
- Три опции гейта (Fix now / I'll fix manually / Skip and continue) не меняются. «Fix now» всегда диспетчеризует Claude fix-сабагент (§7) независимо от того, кто нашёл замечания.

## 6. Новый скилл `pf-codereview`

- Новый файл `skills/pf-codereview/SKILL.md`.
- **Точка запуска:** после завершения `/pf-execute`, до `/pf-test`. `/pf` направляет сюда следующим шагом, когда все задачи `implementation_plan.md` отмечены выполненными.
- **Входной гейт:** `implementation_plan.md` должен быть complete (та же механическая проверка, что использует `/pf-execute` для своих предусловий).
- **Что ревьюится:** diff issue-ветки относительно родительской ветки (`git diff <parent>...HEAD`) — не весь working tree, а именно то, что изменено в рамках issue. Родитель определяется тем же способом, что уже использует `/pf-close` (не изобретать вторую логику детекции).
- **Выбор ревьюера:** `reviewers.code` из `prompt.md`, то же поведение claude/codex/both, что в §5, тот же механизм вызова Codex (§4).
- **Артефакт:** `docs/issues/open/<ISSUE-ID>/code_review.md` — `verdict: PASS|FAIL` (по образцу `qa_report.md`) + список замечаний, сгруппированных по P0/P1/P2 (с подписями `[Claude]`/`[Codex]`, если `both`).
- **Жёсткий гейт — без «Skip and continue»:** пока остаётся открытым хотя бы одно P0/P1-замечание, доступны только «Fix now» (Claude fix-сабагент правит диф, затем ревью перезапускается автоматически) и «I'll fix manually, then re-run /pf-codereview». Цикл повторяется до `verdict: PASS`. Если замечаний нет или только P2 — сразу `verdict: PASS`.
- `/pf-test`'s входной гейт получает дополнительное условие (по аналогии с уже существующей проверкой `test_plan.md`): `code_review.md` должен существовать и иметь `verdict: PASS`; иначе — «code_review.md (PASS) is required. Run /pf-codereview first.»

## 7. Fix-сабагент — всегда Claude

И для документов (§5, «Fix now»), и для кода (§6) правки в файлы вносит только Claude-сабагент (Agent tool, general-purpose) — точно так же, как сегодня работает fix-flow `pf-check`. Codex никогда не получает право записи в репозиторий, независимо от того, кто нашёл замечание.

## 8. Обновления `pf-size-tiers`

- В список документов, к которым применяется критерий «stage complete» (раздел Scope), добавляется `code_review.md`.
- В таблицу пайплайнов добавляется стадия код-ревью между IMPL_PLAN/`/pf-execute` и TESTING — для всех типов issue (`feat`/`improve`/`bug`) и всех тиров, включая `trivial` (код-ревью не зависит от тира документов — замечания есть замечания, а не проза, которую нужно сокращать под бюджет).

## 10. Расширяемость на будущее

Значение ревьюера — открытый строковый enum (`claude`/`codex`, в будущем `human`), а не булев флаг. Добавление `human` в будущем — это третья ветка в цепочке §4 плюс расширение списка допустимых значений; формат поля `reviewers`, логика гейтов `pf-check`/`pf-codereview` и уже сделанный выбор в существующих issue при этом не меняются.
