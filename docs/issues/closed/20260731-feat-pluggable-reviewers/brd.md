# Business Requirements Document: Pluggable Reviewers (Claude / Codex) for Documents and Code

## Overview

Сегодня единственный механизм ревью в Planning Framework — это ревью PF-документов (BRD, specs, test_plan, implementation_plan), которое всегда выполняет Claude. Кода реализации это ревью вообще не касается — после `/pf-execute` issue сразу идёт на тестирование без отдельного шага проверки кода.

Эта фича вводит выбор ревьюера — Claude, Codex, или оба сразу — для каждого артефакта issue (четырёх планировочных документов и кода реализации), плюс новый шаг ревью кода, который сегодня отсутствует. Выбор делается один раз при создании issue и действует до его закрытия.

Абстракция ревьюера при этом не должна быть жёстко привязана только к двум движкам: в будущем предполагается добавить третий тип — ревью человеком через внешний сервис (асинхронно, по образцу существующего инструмента `codereview-tool`). Эта фича его не реализует, но не должна архитектурно исключать такое расширение.

## Goals

- Пользователь может назначить ревьюера — Claude, Codex, или оба — отдельно для каждого из пяти артефактов issue: BRD, specs, test_plan, implementation_plan, код.
- Ревью документов происходит там же, где оно происходит сегодня — по одному разу на документ.
- Появляется новый шаг ревью кода реализации — после того как код написан, до начала тестирования.
- Если Codex недоступен на текущей машине, ревью этого артефакта тихо продолжается силами Claude — работа пользователя не блокируется недоступностью стороннего сервиса.
- Абстракция «ревьюер» не привязана намертво к двум вариантам — добавление третьего типа (человек) в будущем не должно требовать пересмотра уже сделанного выбора для существующих issue.

## Non-Goals

- Ревью человеком (через внешний сервис/очередь) в этой фиче не реализуется — только не должно быть архитектурно исключено на будущее.
- Автоматическое разрешение конфликта между вердиктами двух ревьюеров — если Claude и Codex разошлись во мнениях, оба замечания просто передаются автору на рассмотрение, как и сегодня для одного ревьюера; никакого арбитра между ними не вводится.
- Изменение выбора ревьюера после создания issue — выбор фиксируется один раз при создании и действует до закрытия issue.
- Изменение самих требований к содержанию документов или кода — фича меняет только то, кто и когда их проверяет, а не что должно быть в них написано/реализовано.

## User Stories

1. **Как пользователь, создающий issue**, я хочу для каждого планировочного документа (BRD, specs, test_plan, implementation_plan) выбрать ревьюера — Claude, Codex или оба — чтобы получать взгляд Codex в дополнение к Claude или вместо него, с автоматическим переключением на Claude, если Codex недоступен на этой машине.
2. **Как пользователь, только что закончивший реализацию issue**, я хочу пройти отдельный шаг ревью кода (с тем же выбором ревьюера, что и для документов) перед началом тестирования, чтобы код получал такую же проверку, какую сегодня уже получают документы.

## Business Rules

### Выбор ревьюера
- Ревьюер назначается отдельно для каждого из пяти артефактов: BRD, specs, test_plan, implementation_plan, код.
- Для каждого артефакта доступны три варианта: только Claude, только Codex, либо оба сразу.
- Выбор делается один раз, при создании issue, и фиксируется на весь его жизненный цикл — изменить его позже (например, перед конкретным шагом ревью) нельзя.
- Дефолт (если пользователь не указал иное) — только Claude, чтобы поведение framework для тех, кто не пользуется этой возможностью, не менялось.

### Ревью документов
- Ревью документа происходит в той же точке пайплайна, где оно происходит сегодня (по одному документу за раз, после его написания), но исполняется тем ревьюером (или обоими), который назначен на этот документ.

### Новый шаг ревью кода
- После завершения реализации, но до начала тестирования, появляется новый обязательный шаг ревью кода — по аналогии с сегодняшним ревью документов.
- Этот шаг — жёсткий гейт: issue не переходит к тестированию, пока замечания ревью кода не закрыты (закрыты = учтены/исправлены автором), точно так же, как сегодня работает гейт ревью документов.

### Поведение при недоступности Codex
- Если для артефакта назначен Codex (единолично или вместе с Claude), но Codex недоступен на текущей машине, пользователю предлагается настроить его; при отказе пользователя framework автоматически проводит ревью силами Claude вместо Codex для этого артефакта — без ошибки и без блокировки работы.

### Оба ревьюера на одном артефакте
- Если на артефакт назначены оба ревьюера, оба проходят ревью независимо, и оба набора замечаний агрегируются и передаются автору документа/кода на рассмотрение и исправление — так же, как сегодня работает ревью с одним ревьюером.
- Framework не пытается автоматически разрешить противоречия между вердиктами двух ревьюеров — окончательное решение всегда за автором/пользователем.

### Расширяемость на будущее
- Набор типов ревьюера («Claude», «Codex», в перспективе «человек через внешний сервис») не должен быть зашит так, что добавление нового типа требует ломать или мигрировать уже сделанный для существующих issue выбор.

## Acceptance Criteria

- [ ] При создании issue пользователь может выбрать ревьюера (Claude / Codex / оба) отдельно для BRD, specs, test_plan, implementation_plan и кода; по умолчанию — Claude.
- [ ] Выбор ревьюера сохраняется как часть issue и используется на протяжении всего его жизненного цикла; изменить его после создания issue штатным способом нельзя.
- [ ] Каждый планировочный документ проходит ревью в существующей точке пайплайна, силами назначенного на него ревьюера (или обоих).
- [ ] После реализации и до начала тестирования появляется новый шаг ревью кода, использующий тот же выбор ревьюера, что и документы.
- [ ] Новый шаг ревью кода — блокирующий гейт: тестирование не начинается, пока замечания ревью кода не закрыты, аналогично сегодняшнему гейту ревью документов.
- [ ] Если Codex назначен, но недоступен на машине, пользователю предлагается его настроить; при отказе ревью того же артефакта тихо выполняется силами Claude, без блокировки и без ошибки.
- [ ] Назначение только Codex (без Claude) на любой артефакт — валидный выбор.
- [ ] Если на артефакт назначены оба ревьюера, замечания обоих агрегируются и передаются автору на рассмотрение; framework не разрешает противоречия между ревьюерами автоматически.
- [ ] Ни один из вышеуказанных пунктов не меняет сами требования к содержанию документов или кода — только то, кто и когда их проверяет.
