Две задачи из плана недели 31, объединённые в один issue: обе меняют Manual Test UI (`tools/manual-test-ui/`) и подготовку ручного тестирования.

- `planning-framework: manual-test должен подготавливать все тестовые данные/файлы или создавать скрипты для инициализации тестового кейса`
- `planning-framework: на базе manual test UI сделать project explorer для просмотра CLAUDE.md (включая вложенные), Memory, PF-документов (BRD, SPECS, etc.)`

---

## Часть A — подготовка тестового кейса

### Проблема

Сейчас `manual_test_checklist.md` даёт тестировщику только прозаический список **Prerequisites**, а инструкция «How to use» прямо говорит: «если не можешь выполнить предусловие — остановись и спроси разработчика» (`skills/pf-test/SKILL.md`, шаг 5.3). Подготовка среды целиком лежит на человеке, который по замыслу того же документа «ничего не знает о внутреннем устройстве проекта». Ручной прогон упирается в предусловия ещё до первого шага.

### Что делаем

1. **`/pf-test-plan`** — для каждого Manual TC заполняет поле **Test Data** (оно уже есть в шаблоне тест-кейса, `skills/pf-test-plan/SKILL.md:69`): какие файлы/фикстуры нужны кейсу.
2. **`/pf-test`** — на основе этого порождает `docs/issues/open/<ISSUE-ID>/test-data/`:
   - исходные фикстуры — файлами, под git;
   - `setup.mjs` — идемпотентный Node-скрипт подготовки.
3. **Manual Test UI** — кнопка «Подготовить тестовый кейс» рядом с TC (и одна на issue целиком).

### Решения, принятые до начала работы (не переспрашивать)

- **Формат скрипта:** Node (`setup.mjs`), не bash/ps1. Node уже обязателен для `make test-ui`, один файл работает на всех платформах, тестировщик может запустить и руками: `node setup.mjs TC-003`.
- **Гранулярность:** один скрипт на issue, цель — аргумент. `node setup.mjs` без аргументов готовит всё; `node setup.mjs TC-003` — только этот кейс. Общий prelude не дублируется.
- **Идемпотентность:** каждый запуск приводит кейс в заданное состояние с нуля (сносит свою рабочую копию и создаёт заново). Кнопка «Подготовить» = кнопка «Сбросить». Отдельного teardown нет.
- **Граница ответственности:** файлы и фикстуры. Подъём сервисов, БД, аккаунты остаются текстом в Prerequisites — скрипт их не трогает.
- **Куда пишет скрипт — важно:** исходные фикстуры и сам скрипт лежат в `docs/issues/<ID>/test-data/` под git, но **рабочую копию скрипт разворачивает во временном каталоге вне репозитория**. Причина: если скрипт создаёт файлы внутри репозитория, рабочее дерево становится грязным, а UI отказывает в `checkout` при грязном дереве (`tools/manual-test-ui/README.md`) и `/pf-qa` падает на той же проверке (`skills/pf-qa/SKILL.md`, Important Notes). Путь рабочей копии скрипт печатает, UI его показывает.
- **Исполнение сервером:** путь жёстко whitelist-ится — сервер запускает только `docs/issues/{open,closed}/<ID>/test-data/setup.mjs`, без shell, с подтверждением как у `checkout`, с таймаутом, показом stdout/stderr и кода возврата. Клиент не передаёт произвольный путь.

## Часть B — project explorer по ролям

### Проблема

UI сегодня умеет ровно один экран — чек-лист. Всё остальное (BRD, spec, `CLAUDE.md`, память агента) читается только из редактора, хотя контекст нужен ровно в тот момент, когда смотришь на тест-кейс.

### Что делаем

UI становится **role-first**: три вкладки верхнего уровня, содержимое разложено по стадиям пайплайна, за которые роль отвечает. Текущий экран чек-листа становится одним из экранов вкладки «Тестировщик».

| Вкладка | Содержимое |
| --- | --- |
| **Аналитик** | `prompt.md` · `brd.md` · `analysis.md` · `notes.md` · `PLANNING.md` · `docs/planning/decisions.md` |
| **Разработчик** | `specs.md` · `implementation_plan.md` · `CLAUDE.md` (корневой + все вложенные) · Memory · `docs/planning/session-log.md` · `docs/planning/implementation-plan.md` |
| **Тестировщик (QA)** | `test_plan.md` · `manual_test_checklist.md` (текущий экран) · `qa_report.md` · `.qa-workflow.md` · кнопка «Подготовить тестовый кейс» из части A |

### Решения, принятые до начала работы (не переспрашивать)

- **Строго read-only.** Единственный записывающий путь в UI остаётся прежним — точечный патч чек-листа. Правка BRD/specs через веб-форму обошла бы гейты пайплайна и `/pf-check`.
- **Свой минимальный markdown-рендерер**, без npm-зависимостей: заголовки, списки, таблицы, код, ссылки, frontmatter, с экранированием HTML. Принцип «No database, no npm dependencies» из `tools/manual-test-ui/README.md` не нарушается. Таблицы обязательны — в PF-документах они везде.
- **Memory** — это `~/.claude/projects/<путь-проекта-с-дефисами>/memory/*.md` плюс `MEMORY.md`, то есть **вне репозитория**. Требуется точечно расширить путевую валидацию сервера ровно на этот один префикс; сегодня сервер жёстко заперт в каталоге проекта (защита от path traversal), и эта защита должна остаться для всего остального.
- **Аудитория вкладки «Тестировщик»** — владелец проекта в роли QA, не внешний тестировщик. Поэтому внутреннюю терминологию на вкладке скрывать не нужно. Запрет на жаргон из `skills/pf-test/SKILL.md` («Critical: … Do not include … BRD, specs.md, /pf …») продолжает действовать **только** для содержимого самого `manual_test_checklist.md`, который уходит наружу.
- **Роли — верхний уровень всего UI**, а не отдельный раздел внутри explorer'а. Одно связное приложение вместо двух навигаций в одном окне.
- Explorer работает для всех проектов из `projects.json`, как и текущий список issue.
