# User Docs — сходимость ревью и честность отчётов стадий

**Issue:** 20260806-improve-codereview-convergence
**Дата:** 2026-08-13

Что изменилось для того, кто пользуется фреймворком: новое поле в `prompt.md`,
новый формат отчёта ревью, новый блокирующий гейт перед передачей в ревью, и
несколько мест, где стадия теперь останавливается вместо того, чтобы отчитаться
об успехе.

Ниже — только пользовательская сторона. Устройство проверок и обоснования
решений — в `dev_docs.md`.

---

## Как получить изменения

Скиллы копируются в проект командой `make converge TARGET=/path/to/project`;
установленные копии в `~/.claude/skills/` обновляются через `make update-skills`
(или `/pf-update`). До обновления пайплайн работает по-старому — правки живут в
файлах скиллов, а не в коде проекта.

---

## Новое поле `review_rounds` в `prompt.md`

Необязательное. Задаёт бюджет раундов код-ревью для этой issue; при отсутствии
поля используется **3**.

```yaml
---
doc_language: Russian
size_tier: large
review_rounds: 3
roles:
  code: { write: claude, review: [claude, codex] }
---
```

Бюджет — **триггер эскалации, а не потолок для выдачи `PASS`**. Разница
существенна:

- Раунд, закончившийся чисто, закрывает цикл как `PASS` независимо от своего
  номера — четвёртый и пятый раунд тоже могут дать `PASS`, если в них ничего не
  найдено.
- Раунд, на котором бюджет исчерпан и остались открытые замечания высшей или
  средней важности, **не** даёт `PASS` и **не** запускает следующий раунд:
  оставшиеся замечания становятся задачами `implementation_plan.md`, и issue
  возвращается на `/pf-execute`.

## Что теперь делает `/pf-codereview`

### Ранний возврат в первом раунде

Если первый раунд нашёл **три и более** блокирующих замечания, цикл исправлений
не запускается вовсе. Это трактуется как «реализация не готова»: замечания
становятся задачами плана, issue уходит на `/pf-execute`. При нуле, одном или
двух блокирующих замечаниях всё идёт как раньше.

### Раунд второй и далее проверяет две вещи, а не одну

Каждый раунд после первого обязан и убедиться, что блокирующие замечания
прошлого раунда действительно закрыты, и **отревьюить собственный дифф
исправлений** на новые проблемы. Раньше вторая половина не требовалась, и правки
уезжали неотревьюенными.

### Отчёт стал журналом, а не перезаписываемым списком

`code_review.md` больше не хранит находки в секциях `### P0` / `### P1` / `### P2`,
которые переписывались на каждом прогоне. Вместо них — таблица со строками, у
каждой из которых устойчивый идентификатор:

| ID | Round | Priority | Description | Follow-up Issue | State |
|---|---|---|---|---|---|
| CR-001 | 1 | P0 | `load_config()` молча возвращает пустой конфиг при отсутствующем файле | | fixed |
| CR-002 | 1 | P2 | имя переменной `x` в `parse_line()` непонятно | | wont-fix |
| CR-003 | 2 | P1 | предупреждение о неизвестном ключе не печатается | 20260901-improve-config-warnings | deferred |

Правила чтения:

- Идентификатор `CR-NNN` присваивается один раз и не переиспользуется.
- Последующий прогон делает с таблицей ровно одно из трёх: дописывает новую
  строку, обновляет ячейку `State` существующей, либо заполняет её пустую ячейку
  `Follow-up Issue`. Идентификатор, номер раунда и описание не переписываются
  никогда.
- `State` принимает ровно шесть значений: `open` (начальное) и пять
  терминальных — `fixed`, `accepted-risk`, `deferred`, `wont-fix`,
  `duplicate-of CR-NNN`.
- Перед вердиктом `PASS` у каждой строки обязано быть непустое `State`. Пустая
  ячейка — нарушение; явный `open` — нет, это настоящее значение (но открытое
  замечание высшей или средней важности `PASS` не даёт).

**Что это даёт.** Замечание больше не может исчезнуть между раундами молча. В
исходном инциденте, из-за которого issue и заведена, замечание низшей важности из
первого раунда никто не починил и никто не заметил пропажи вплоть до седьмого.

### Замечание обязано называть сценарий отказа

Замечание высшей или средней важности теперь обязано назвать конкретный сценарий
отказа: вход или состояние → неверный выход, падение, регрессия или нарушение
заявленного требования.

Замечание без такого сценария **понижается в важности** до низшей — отдельным
явным шагом, с записью причины, видимой в самом отчёте. Второго признака
блокировки (флага вида «блокирует / не блокирует» рядом с важностью) не
вводится: важность остаётся единственной осью, которую читает гейт.

Практически это значит, что стилистическая придирка больше не останавливает
пайплайн, а настоящий дефект — останавливает, и решение видно и оспоримо.

### Вынос замечания в отдельную issue

Замечание **средней** важности можно разрешить, заведя отдельную follow-up issue:
состояние строки становится `deferred`, а идентификатор новой issue записывается
в колонку `Follow-up Issue` той же строки. Несвязанный `deferred` неотличим от
молча выброшенного замечания, поэтому ссылка обязательна.

Для замечаний **высшей** важности этот путь недоступен ни при каких условиях.

Обратите внимание: это не третий вариант ответа на вопрос гейта. Гейт
`/pf-codereview` по-прежнему предлагает ровно два варианта — исправить сейчас
либо исправить самостоятельно и перезапустить. Вынос в follow-up issue
происходит на уровне журнала находок, до того как гейт считает, есть ли
открытые блокирующие замечания.

### Куда попадают остатки при `PASS`

Перед тем как отчитаться о `PASS`, стадия проходит по журналу и выносит каждую
строку, не помеченную `fixed`, в `docs/planning/tech-debt.md` — по строке на
находку:

```
- `CR-002` (P2, 20260806-improve-codereview-convergence) — имя переменной `x` в `parse_line()` непонятно — state: `wont-fix`
```

Файл создаётся при первой надобности. Запись идемпотентна по паре
«идентификатор + issue»: повторный прогон той же issue не задваивает уже
вынесенную находку. Если непомеченных `fixed` строк нет, не пишется ничего, и
стадия об этом сообщает.

Это отдельный механизм от предыдущего, и путать их не следует: вынос в
follow-up issue — способ закрыть **конкретное** замечание средней важности на
гейте, а выгрузка в `tech-debt.md` — учёт **всего оставшегося** уже после того,
как гейт пройден.

## Новый блокирующий гейт в `/pf-execute`

Перед тем как передать работу в код-ревью, `/pf-execute` теперь выполняет четыре
механические проверки. Все четыре — жёсткие остановки, а не предупреждения.

1. **Все чекбоксы плана отмечены.** Незакрытый критерий приёмки блокирует
   передачу — **кроме** случая, когда все названные в нём тест-кейсы имеют тип
   `Manual`. Ручной кейс не может быть закрыт автоматическим прогоном; он
   закрывается позже, когда тестировщик реально его выполнит.
2. **У каждой задачи типа `code` есть тест.** Поле `**Mapped Test Cases:**`
   обязано называть хотя бы один кейс, и каждый названный кейс обязан
   существовать строкой в таблице состояния `test_plan.md`.
3. **Каждая задача типа `tests` привязана к кейсу.** Её критерии приёмки обязаны
   называть хотя бы один существующий кейс. Поле `Mapped Test Cases` у таких
   задач номеров кейсов не содержит по конвенции — оно машинно парсится, и номер
   в его прозе был бы прочитан как настоящее сопоставление.
4. **У каждого кейса есть задача.** Каждая строка таблицы состояния
   `test_plan.md` обязана быть названа хотя бы одной задачей плана.

Проверки 2 и 4 ловят разные дыры и друг друга не заменяют: первая — объявленное
и не построенное поведение, вторая — требование, которое никто не взялся
реализовать.

**Заодно `/pf-execute` теперь сам отмечает чекбоксы.** После подтверждения
каждой задачи он проставляет `[x]` у её критериев приёмки — раньше этого не
делал никто, и проверка 1 была бы невыполнима в принципе. Если задача
подтверждена частично или с отклонениями, чекбоксы остаются неотмеченными: это и
есть работа проверки 1.

### Что делать, если гейт заблокировал существующий план

Наиболее вероятные причины на планах, написанных до этого изменения:

- у задачи `code` пустое поле `Mapped Test Cases` — впишите кейсы, которые её
  проверяют;
- поле называет кейс, которого нет в таблице состояния `test_plan.md` —
  опечатка, переименование или выдуманный номер;
- кейс есть в таблице, но ни одна задача его не называет — либо добавьте
  сопоставление, либо уберите кейс из плана тестирования, если он не нужен;
- незакрытый критерий приёмки ссылается на автоматический кейс — прогоните
  тесты и отметьте, либо честно оставьте задачу незавершённой.

## Стадия, не сделавшая работу, больше не отчитывается об успехе

### Пустой предмет ревью

Если дифф пуст, `/pf-codereview` останавливается с явной ошибкой и не пишет
вердикт об успешном прохождении. То же правило действует в `/pf-check` вокруг
пути, вычисляющего дифф ветки.

Раньше пустой дифф выглядел как «отревьюено, замечаний нет».

### Документ вне ветки задачи

Планировочные документы часто пишутся до того, как создана ветка задачи. Раньше
`/pf-check` считал дифф против несуществующей ветки, получал пусто и трактовал
это как чистый результат.

Теперь отсутствие ветки обнаруживается, документ ревьюится по своему пути на
диске, и причина называется в отчёте.

### Признак пройденной проверки стал явным

`/pf-check` дописывает в `session-log.md` задачи одну из двух строк:

```
[pf-check PASSED] <документ> @ <время>
[pf-check OPEN] <документ> @ <время> — <причина>
```

`PASSED` пишется только когда блокирующих замечаний не осталось. Если вы выбрали
«исправлю сам» или «пропустить и продолжить» при открытых замечаниях, пишется
`OPEN` с причиной.

`/pf` читает **последнюю** такую строку для документа. Ранняя `PASSED` не
перекрывает более позднюю `OPEN`: журнал дописывается, и определяющей является
свежая запись. При `OPEN` следующая стадия не предлагается — задача считается
непроверенной.

Раньше «проверка пройдена» определялась циклически, через готовность следующего
документа, и `/pf` не видел уже выполненную проверку.

### `/pf-close` больше не обрывается молча

Каждая фаза закрытия теперь либо явно продолжается, либо явно останавливается с
сообщением. У остановок появились конкретные пути восстановления — нумерованные
шаги с командами вместо «разрешите конфликты вручную».

## Задание субагенту стало самодостаточным

Инструкции исполнителю больше не предписывают вызывать инструменты работы с
задачами, которых у него нет. Промпт диспетчеризации всегда несёт полное
содержание задачи — что делать, какие файлы, что считается выполненным, какие
кейсы проверяют, от чего зависит, — и никогда один голый номер задачи.

Это устраняет отказ, который наблюдался на практике: исполнитель, не сумев
получить задачу по идентификатору, взял её из плана по номеру, номера не
совпали, и он добросовестно сделал не ту работу.

## Migration notes

- **Отчёты ревью старого формата не мигрируются.** `code_review.md`,
  написанные секциями `### P0`/`### P1`/`### P2`, остаются как есть; журнал
  начинает вестись со следующего прогона `/pf-codereview`.
- **Гейт полноты может заблокировать план, который раньше проходил.** Это
  ожидаемо: он ловит ровно те несоответствия, которые прежде проходили молча.
  Что делать — см. раздел выше.
- **Файл `docs/planning/tech-debt.md` создаётся при первой надобности.** Заранее
  заводить его не нужно.
- **`review_rounds` добавлять в существующие `prompt.md` не обязательно** — без
  поля действует значение 3.
- **Обновлять `session-log.md` вручную не нужно.** Задачи без маркеров работают
  по прежнему правилу: `/pf` откатывается на старое определение, если ни одной
  строки маркера для документа нет.

## Принятые допущения

Документ написан без уточняющих вопросов, под непрерывной директивой доведения
issue до закрытия. Приняты два допущения, каждое из которых легко отменить:

1. **Пользователь фреймворка — разработчик, ведущий issue через пайплайн.**
   Поэтому команды (`/pf-check`, `/pf-codereview`, `/pf-execute`) и имена
   документов (`prompt.md`, `code_review.md`) употребляются прямо: для этой
   аудитории они интерфейс, а не внутренняя терминология.
2. **`README.md`, `CHANGELOG.md`, `PLANNING.md` и документы в
   `docs/planning/` этой правкой не изменяются.** Этот файл описывает, что в них
   следует внести, а не вносит. Если требуется прямая правка — это отдельное
   решение владельца.
