# Business Requirements Document: Матрица ролей write/review по стадиям issue

## Overview

Сегодня Planning Framework умеет делегировать Codex только ревью — и то, целиком
на документ, без разбивки по операциям. Кто именно пишет BRD, спецификацию,
тест-план, план реализации, код и документацию — всегда Claude, без
возможности выбора. Единственная существующая настройка, `reviewers:` в
`prompt.md`, описывает только «кто ревьюит какой документ» и не покрывает
авторство.

Эта функция вводит матрицу ролей на уровне issue: для каждой стадии
пайплайна отдельно записывается, кто пишет артефакт и кто (в каком режиме) его
ревьюит, поверх расширяемого реестра доступных агентов и набора именованных
профилей по умолчанию — чтобы не отвечать на длинный список вопросов при
каждом создании issue.

## Goals

- Для каждой стадии пайплайна (BRD, спецификация, тест-план, план
  реализации, код, автотесты, пользовательская документация, документация
  для разработчиков) отдельно задаётся, кто пишет артефакт и кто его
  ревьюит.
- Ревью можно вести в двух режимах: все ревьюеры проверяют один и тот же
  артефакт параллельно (сегодняшнее поведение), либо ревьюеры идут по
  цепочке — дешёвый триаж, затем более дорогой глубокий разбор, с
  автоматическим применением фиксов между шагами.
- Список доступных агентов (акторов) хранится в расширяемом реестре;
  добавление нового агента не требует переписывания существующих скиллов
  пайплайна.
- Пользователь выбирает один из именованных профилей распределения ролей при
  создании issue (единственный вопрос), с возможностью точечно
  переопределить отдельные стадии и сменить профиль позже, на любой
  ещё не пройденной стадии.
- Отдельные стадии (в первую очередь необязательная документация) можно
  явно объявить пропущенными, и пайплайн учитывает это, не спрашивая про них
  и не блокируя прохождение issue.
- Issue, открытые до появления этой функции и использующие старый формат
  `reviewers:`, продолжают работать — они автоматически переводятся на новый
  формат при первом обращении к ним.

## Non-Goals

- Человек (`human`) как актор, очередь задач, режимы `blocking`/
  `non-blocking` и переназначение задачи агенту — выносится в отдельную
  issue `20260806-improve-project-explorer-redesign`, поскольку вся
  поверхность взаимодействия с этим живёт в интерфейсе project explorer.
  Данная issue лишь не должна архитектурно закрывать дорогу для будущего
  добавления `human` в реестр акторов.
- Автоматическая проверка «ревьюер должен отличаться от автора» — по
  решению, принятому при подготовке этого документа, такая проверка не
  вводится. Любая комбинация write/review, включая полностью совпадающую
  (один и тот же актор пишет и ревьюит), разрешена и ничем не блокируется.
  Это отменяет соответствующий пункт исходного технического задания в
  `prompt.md` («Приёмка»), который требовал отклонять `{write: codex,
  review: [codex]}` — окончательное решение зафиксировано в этом BRD.
- Изменение самой инженерной логики стадий QA/тестирования, кроме проверки
  присутствия двух новых опциональных стадий документации — остальная логика
  `/pf-qa` не пересматривается.
- UI для управления ролями — распределение задаётся через конфигурационные
  файлы issue, а не через интерфейс project explorer (это тоже относится к
  зоне ответственности `20260806-improve-project-explorer-redesign`).

## User Stories

1. **Как пользователь framework**, хочу задавать, кто пишет и кто ревьюит
   каждый артефакт issue по отдельности, чтобы делегировать часть авторства
   более быстрому агенту (Codex) и ускорить прохождение issue, не теряя
   независимое ревью там, где я сам этого хочу.
2. **Как пользователь**, хочу управлять этим не только на уровне документа
   целиком, но и по видам операций (кто пишет, кто ревьюит, кто запускает
   тесты), чтобы, например, доверить Codex писать код и тесты, но оставить
   ревью за Claude.
3. **Как пользователь**, хочу выбирать режим ревью — либо все ревьюеры
   проверяют один и тот же артефакт параллельно, как сегодня, либо ревьюеры
   идут по цепочке (дешёвый триаж → дорогой глубокий разбор), с
   автоматическим применением фиксов первого ревьюера перед тем, как
   артефакт попадёт ко второму, — без дополнительного подтверждения с моей
   стороны на каждом шаге.
4. **Как пользователь**, хочу опираться на именованные профили распределения
   ролей (например «всё делает Claude» или «Claude пишет, Codex ревьюит»),
   чтобы не отвечать на длинный список вопросов при создании каждой issue —
   выбрать один профиль и точечно переопределить нужные стадии.
5. **Как пользователь**, хочу иметь возможность сменить профиль или
   отдельные роли посреди уже идущего пайплайна issue, и чтобы новое
   распределение применялось только к ещё не пройденным стадиям, не
   переделывая уже готовую работу.
6. **Как пользователь**, хочу иметь возможность явно пропустить
   необязательную стадию (в первую очередь — документацию для
   пользователей или для разработчиков), чтобы framework не спрашивал про
   эту стадию и не блокировал прохождение issue из-за её отсутствия.
7. **Как пользователь**, если я всё же пропускаю ревью кода, хочу получить
   явное подтверждение этого решения в момент, когда я его принимаю, и
   видеть его как отдельную строку риска в итоговом `qa_report.md`, чтобы
   риск был осознанным и видимым, а не тихим.
8. **Как пользователь**, работающий с issue, открытыми до появления этой
   функции (у них старый формат `reviewers:` без указания автора), хочу,
   чтобы framework сам перевёл их на новую схему при следующем обращении к
   issue, без ручной правки файлов с моей стороны.
9. **Как пользователь**, хочу, чтобы список доступных агентов был
   расширяемым реестром, а не зашитым в код списком, чтобы в будущем
   добавить нового агента одной записью, без переписывания существующих
   скиллов пайплайна.
10. **Как пользователь, задавший `roles.code.write: codex`**, хочу быть
    уверен, что реализацию действительно выполняет Codex, а ревью — Claude,
    чтобы распределение ролей в конфиге соответствовало наблюдаемому
    поведению, а не оставалось только записью на бумаге.

## Business Rules

### Матрица ролей на issue
- Для каждой применимой стадии (BRD, спецификация, тест-план, план
  реализации, код, автотесты, пользовательская документация, документация
  для разработчиков) задаётся: кто пишет артефакт (ровно один актор — у
  документа один автор), кто его ревьюит (один или несколько акторов), и,
  где это применимо (автотесты), кто их запускает.
- Стадию можно явно пометить как пропущенную. Пропуск стадии авторства кода
  невозможен — код всегда кем-то пишется. Пропуск ревью кода возможен, но
  требует явного подтверждения пользователем в момент, когда решение
  принимается, и фиксируется отдельной строкой риска в `qa_report.md`.
- Любая комбинация автора и ревьюеров допустима, включая полное совпадение
  (один и тот же актор пишет и ревьюит) — независимая проверка «ревьюер
  должен отличаться от автора» не вводится (см. Non-Goals).

### Режимы ревью
- **Параллельный режим** — все указанные ревьюеры проверяют один и тот же
  артефакт одновременно, находки объединяются с пометкой источника. Это
  сегодняшнее поведение при совместном ревью несколькими агентами.
- **Последовательный режим** — ревьюеры идут по цепочке: первый (обычно
  более дешёвый) находит проблемы, найденные фиксы применяются
  автоматически, без запроса подтверждения у пользователя, и только затем
  уже исправленный артефакт передаётся следующему (обычно более дорогому и
  глубокому) ревьюеру.

### Профили ролей
- При создании issue пользователю задаётся один вопрос о выборе профиля
  распределения ролей из именованного набора профилей по умолчанию
  (минимум: «всё делает Claude», «Claude пишет — Codex ревьюит», «Codex
  реализует»). Отдельные стадии внутри выбранного профиля можно
  переопределить точечно.
- Профиль (или отдельные роли) можно сменить в любой момент, пока issue ещё
  открыта — в том числе посреди уже идущего пайплайна. Смена применяется
  только к стадиям, которые ещё не пройдены; уже завершённые стадии не
  переделываются и не теряют свой результат.
- Для issue с tier `trivial`/`small` необязательные стадии документации
  (пользовательская и для разработчиков) по умолчанию считаются
  пропущенными.

### Обратная совместимость
- Issue, открытые до появления этой функции и использующие старый формат
  `reviewers:` (per-document, без указания автора), автоматически
  переводятся на новую схему при первом обращении к issue через `/pf` или
  `/pf-check` — без запроса подтверждения и без ручной правки файлов
  пользователем. Автор (`write`) для каждой ранее существовавшей записи при
  такой автоконверсии считается Claude, а список ревьюеров переносится из
  старой записи как есть.

### Реестр акторов и новые стадии
- Список доступных агентов — расширяемый реестр: добавление нового агента
  оформляется одной новой записью в реестре, без изменений в существующих
  скиллах пайплайна.
- Появляются две новые опциональные стадии — документация для пользователей
  и документация для разработчиков, — расположенные в пайплайне между
  стадией тестирования и стадией QA. QA-стадия проверяет их наличие, если
  они не объявлены пропущенными для данной issue.

## Acceptance Criteria

- [ ] Issue с ролью автора кода = Codex реализуется именно Codex, а ревью
      кода выполняет именно Claude — распределение ролей в конфиге issue
      соответствует тому, кто фактически выполняет операцию.
- [ ] Для каждой применимой стадии issue можно независимо задать автора
      (ровно один актор) и список ревьюеров (один или несколько акторов);
      никакая комбинация автора и ревьюеров не отклоняется автоматической
      проверкой на совпадение.
- [ ] Ревью можно вести в параллельном режиме (как сегодня, с объединением
      находок по источнику) и в последовательном режиме (по очереди, с
      автоматическим, не требующим подтверждения применением фиксов между
      ревьюерами).
- [ ] Существует набор именованных профилей распределения ролей по
      умолчанию (минимум три: «всё делает Claude», «Claude пишет — Codex
      ревьюит», «Codex реализует»); при создании issue задаётся ровно один
      вопрос о выборе профиля, с возможностью точечно переопределить
      отдельные стадии.
- [ ] Профиль или отдельные роли можно изменить в любой момент, пока issue
      открыта, включая середину уже идущего пайплайна; изменение
      затрагивает только ещё не пройденные стадии.
- [ ] Issue, использующие старый формат `reviewers:`, при первом обращении
      через `/pf` или `/pf-check` автоматически переводятся на новую схему
      без ручного вмешательства пользователя и без потери информации о
      существовавших ревьюерах.
- [ ] Любую применимую стадию, кроме авторства кода, можно явно пометить
      пропущенной; пайплайн и предусловия последующих стадий учитывают
      пропуск и не блокируют issue из-за отсутствующего артефакта пропущенной
      стадии. `/pf` отображает пропущенную стадию как таковую вместе с
      причиной пропуска.
- [ ] Пропуск ревью кода отдельно требует явного подтверждения пользователем
      в момент принятия решения и отражается отдельной строкой риска в
      `qa_report.md`.
- [ ] Появляются две новые опциональные стадии документации (для
      пользователей и для разработчиков) между стадией тестирования и
      QA-стадией; QA-стадия проверяет их наличие, если они не объявлены
      пропущенными; для issue с tier `trivial`/`small` они по умолчанию
      пропущены.
- [ ] Список доступных агентов оформлен как расширяемый реестр: добавление
      нового агента не требует изменений в существующих скиллах пайплайна.
- [ ] Человек как актор, очередь задач и режимы blocking/non-blocking не
      входят в объём этой issue.
