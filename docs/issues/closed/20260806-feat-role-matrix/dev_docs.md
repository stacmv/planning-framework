# Dev Docs: Матрица ролей write/review по стадиям issue

## Архитектура

### Резолвинг роли — единая точка, `skills/pf-roles/SKILL.md` §4

Любой скилл, которому нужно узнать write/review для стадии `<key>` (`brd`,
`specs`, `test_plan`, `implementation_plan`, `code`, `tests`, `user_docs`,
`dev_docs`, `notes`, `analysis`), резолвит роль через пятиуровневый
fallback, **вычисляемый заново при каждом обращении** (кэша нет —
`pf-roles` §8):

1. Явная точечная запись `roles.<key>` в `prompt.md`.
2. Точечная запись профиля (`role-profiles.yml`, `<profile>.<key>`).
3. Tier-дефолт `skip` для `user_docs`/`dev_docs` при `size_tier:
   trivial`/`small`.
4. `default` профиля (`role-profiles.yml`, `<profile>.default`).
5. Общий дефолт (`write: claude, review: [claude]`) — когда нет ни
   `roles:`, ни `profile:` вообще для конкретного ключа.

**Уровень 5 оценивается per-key, не как проверка наличия всего блока
`roles:`.** Это самый значительный баг, найденный `/pf-codereview` в этой
issue (round 1, P0): после частичной автомиграции у issue появляется
`roles:` с частью ключей — и если бы уровень 5 проверял «блока `roles:`
целиком нет», он был бы недостижим навсегда для любого ключа, включая те,
которых автомиграция никогда не переносит (`tests`, `user_docs`,
`dev_docs`). Исправлено: каждый ключ резолвится независимо.

### Реестр акторов и профилей

- `docs/planning/agents.yml` — `actors: {<name>: {kind, invoke, ...}}`.
  Скиллы резолвят имя актора через реестр, а не веткуются `if claude / elif
  codex` в коде — добавление нового актора (`gemini` уже задокументирован
  как заготовка, `kind: human` для `20260806-improve-project-explorer-redesign`
  добавится позже) не требует правки скиллов.
- `docs/planning/role-profiles.yml` — именованные наборы дефолтов
  (`solo-claude`, `claude-writes-codex-reviews`, `codex-implements`).
- Оба файла создаются автоматически с дефолтным содержимым при первом
  обращении, если отсутствуют — без вопроса пользователю (TC-006).

### Автомиграция `reviewers:` → `roles:`

`pf-roles/SKILL.md` §5. Конвертация: `write: claude` для каждого
перенесённого ключа (автор всегда был Claude до этой issue), `review` —
из старого значения (`both` → `[claude, codex]`). Запускается сама:
- `/pf` Step 2, до сканирования стадий, **только для выбранной issue**, не
  для всех открытых issue сразу (round 1 P1 fix — иначе редактировался бы
  `prompt.md` чужих issue без коммита-владельца).
- `/pf-check` (собственный необнумерованный раздел `## Automigration —
  this skill's own prerequisite`, до Phase 0) и `/pf-codereview` (Phase
  0.5, после Phase 0's input gate) — каждый как собственное предусловие,
  если вызваны напрямую в обход `/pf`.

**Расхождение с `specs.md`/`implementation_plan.md` — тихое, известное,
не исправленное на момент написания.** Оба документа всё ещё описывают
более раннюю версию решения — что автомиграция проходится по **всем**
открытым issue разом, а не только по выбранной. Это открытый cleanup-пункт
#11 из финального `code_review.md` (см. «Известные ограничения» ниже):
код и `pf-roles/SKILL.md` реализуют исправленную (per-issue) версию,
`specs.md`/`implementation_plan.md` — нет. Не полагайтесь на эти два
документа как на точное описание итогового scope автомиграции; полагайтесь
на `pf-roles/SKILL.md` §5 и сам код скиллов.

Тот же round-1-фикс заодно поправил смежный guard: legacy
reviewer-assignment guard в `pf-brd`/`pf`, который раньше не пропускался
даже когда `roles:` уже присутствовал (без `profile:`) — теперь пропуск
условие «`profile:` ИЛИ `roles:`».

Правка `prompt.md` не коммитится самой автомиграцией — она едет вместе с
коммитом той стадии, что первой запустилась после неё (`pf-git`'s
per-row qualifier во всех строках).

### Делегирование записи неClaude-актору

`pf-roles/SKILL.md` §6-§7. Асинхронная («с нуля») и синхронная («правка
существующего файла») формы вызова `codex-companion.mjs task ... --write`.
Для write (в отличие от review) **нет тихого отката на Claude при
недоступности Codex** — стадия останавливается с явной ошибкой, потому что
молчаливая подмена автора нарушила бы сконфигурированное авторство
(round 3 P1 fix).

### Режимы ревью

- `parallel` (дефолт) — сегодняшняя `both`-агрегация `pf-check`, без
  дедупликации, каждая находка помечена источником. Формально описана
  только для пары `[<agent-актор>, codex]` — 3+ актора или два
  `invoke: agent` актора одновременно в `both`-режиме не задокументированы
  (открытый P2 #18, см. ниже).
- `sequential` — первый ревьюер находит, актор `write` автоматически
  фиксит (без вопроса пользователю), второй ревьюит уже исправленную
  версию. Итоговый отчёт — блоки `[<actor>, pass N]`.
- `run` — третье поле схемы `roles:` (кто запускает тесты), уже
  присутствует в дефолтном `codex-implements`-профиле, но пока **reserved
  — не подключено ни к одному потребителю** (`pf-roles/SKILL.md` §1).

### Новые опциональные стадии: `pf-user-docs`/`pf-dev-docs`

Два новых скилла, `skills/pf-user-docs/SKILL.md` и
`skills/pf-dev-docs/SKILL.md` — тонкие обёртки вокруг того же паттерна
«резолвинг роли → написать самому или делегировать → ревью»: этот файл сам
по себе продукт `pf-dev-docs`. Маршрутизация пайплайна (`skills/pf/SKILL.md`
Step 5/Step 6) вставляет обе стадии строго между TESTING и QA:

```
... → /pf-codereview → TESTING → /pf-user-docs* → /pf-dev-docs* → /pf-qa → QA → ...
```

(`*` — резолвится в `skip` по tier-дефолту для `trivial`/`small`, либо
вручную через `roles.<key>: skip`.) `pf-qa`'s prerequisite-проверка
расширена: если стадия не `skip`, требует существующий непустой
`user_docs.md`/`dev_docs.md`, иначе останавливается тем же паттерном, что
и для `manual_test_checklist.md`. `pf-git`'s staging-таблица получила
строки для обеих новых команд.

### `Task Type` в `implementation_plan.md`

`pf-impl-plan`'s шаблон задачи получил поле `**Task Type:** code | tests`
(значение `docs` намеренно исключено из шаблона в round 4 — `pf-execute`
пока не умеет её диспетчеризовать). Поле переносится из Phase 1 в Phase 2
`pf-execute`, где по нему резолвится роль конкретной задачи (`code` или
`tests`, а не одна роль на всю issue); отсутствующее поле (старый/ручной
план) по дефолту трактуется как `code`.

## Ключевые решения (ADR-style)

**Инвариант независимости write/review не введён.** Оригинальный
`prompt.md` этой issue требовал отклонять `{write: codex, review:
[codex]}`. Решение пользователя в ходе BRD: убрать проверку полностью —
issue может быть выполнена целиком одним актором. Задокументировано в
`brd.md` Non-Goals как явное отклонение от исходного задания.

**Волны `pf-execute` для этой issue сериализованы 1:1**, а не сгруппированы
по зависимостям, как обычно — `pf-brd/SKILL.md` правится и Task 2, и
Task 3; `pf/SKILL.md` — и Task 2, и Task 7. Полная сериализация избежала
конфликта записи между параллельными суб-агентами без анализа на уровне
секций файла. Разовое решение для этой issue, не новое правило
`pf-execute`.

**`pf-codereview`'s skip-confirmation "no"-ветка** (round 4 P1, самый
значительный баг после уровня-5 fallback): вопрос подтверждения пропуска
ревью кода задавался, но при ответе «нет» ревью всё равно пропускалось —
hard gate был обходим. Исправлено: «нет» теперь реально запускает ревью
Claude-путём (in-memory override, без правки `prompt.md`) в этом же
прогоне.

## Известные ограничения (открыты на момент написания)

Из финального `code_review.md` — все 7 открытых P2, не блокируют, оставлены
на до-`/pf-close` уборку или на будущую issue:

- **#11** `specs.md`/`implementation_plan.md` (собственные планировочные
  документы этой issue, вне диффа) всё ещё описывают до-фиксовые детали
  дизайна — в частности, scope автомиграции (см. выше) и `Task Type: docs`
  как допустимое значение в шаблоне.
- **#18** `pf-check`'s параллельный `both`-режим формально описан только
  для пары `[<agent-актор>, codex]` — 3+ актора или два `invoke: agent`
  актора одновременно не задокументированы.
- **#19** `pf-roles/SKILL.md` §1's описание `code.review: skip` говорит,
  что `pf-codereview` «пишет тот же маркер» при запросе подтверждения — не
  отражает, что ветка «нет» ревью запускает, а не пишет `confirmed:`.
- **#20** `pf-impl-plan`'s строка про владение коммитом не упоминает
  делегированного (не-Claude) актора, в отличие от аналогичной строки
  `pf-check`.
- **[Codex]** `pf-execute`'s делегирование задачи веткуется по буквальному
  имени актора (`claude` vs. остальное), а не по `agents.yml`'s `invoke:`
  — `write: haiku` (валидный `invoke: agent` актор) ошибочно уйдёт по
  Codex-пути.
- **[Codex]** `pf-codereview`'s таблица выбора ревьюера всё ещё жёстко
  перечисляет `claude`/`codex`, не обобщена как аналогичная таблица
  `pf-check`.
- **[Codex]** `pf-qa`'s строка риска для `roles.code.review: skip` не
  проверяет маркер `confirmed:`/вердикт `SKIPPED` — может неверно показать
  риск для issue, где ревью на самом деле было проведено после отказа от
  пропуска.

## Runbook: расширение реестра акторов

Добавление нового LLM-актора — одна строка в `docs/planning/agents.yml`:

```yaml
actors:
  <name>: { kind: llm, invoke: agent, model: <model-id> }
```

Для `invoke: cli` — актор оборачивает произвольный CLI (`command:
"<template с {prompt}>"`). Резолвер сам подхватывает нового актора при
следующем обращении — правка скиллов не требуется.

## Deployment / rollout

Изменения — только в `skills/` и `docs/planning/` этого репозитория
(источник истины). Пропагируются в живую копию `~/.claude/skills/` через
`make update-skills` — на машине разработчика это влияет на **все**
параллельные Claude Code сессии, использующие эти скиллы, немедленно после
прогона. В рамках этой issue `make update-skills` запускался после каждой
волны `/pf-execute` и после каждого раунда фиксов `/pf-codereview`, чтобы
живая копия не оставалась подолгу в заведомо сломанном промежуточном
состоянии.
