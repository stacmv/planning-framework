# Technical Spec: Матрица ролей write/review по стадиям issue

## 0. Расширение охвата относительно BRD

По итогам уточняющих вопросов на этой стадии охват шире, чем в BRD:
`write:<actor>` для планировочных документов (`brd`/`specs`/`test_plan`/
`implementation_plan`) в этой issue **реализуется полностью**, а не только
декларируется как поле схемы. Реестр ключей `roles:` совпадает с
сегодняшними ключами `reviewers:` — `brd`, `specs`, `test_plan`,
`implementation_plan`, `code` (планировочный путь feat/improve/non-trivial
bug), плюс два ключа, которые сегодняшний `reviewers:` уже использует вне
этого пути (см. `skills/pf/SKILL.md`'s bug-workflow reviewer-assignment
guard и `skills/pf-brd/SKILL.md`'s trivial-tier reviewer-assignment guard):
`analysis` (стадия `analysis.md`, bug-type, не-trivial) и `notes` (стадия
`notes.md`, `size_tier: trivial`, любой тип issue). Оба резолвятся тем же
алгоритмом §1.4, что и остальные ключи (см. §6b) — новый короткий alias
`impl_plan` из черновика в `prompt.md` не используется.

## 1. Architecture overview

### 1.1 Где живут данные

```
docs/issues/open/<ISSUE-ID>/prompt.md   — roles: (per-issue, YAML frontmatter)
docs/planning/agents.yml                — реестр акторов (per-project)
docs/planning/role-profiles.yml         — именованные профили (per-project)
```

### 1.2 Кто резолвит роль и где

Каждый `pf-*` скилл, который сегодня читает `reviewers.<key>` (см.
`skills/pf-check/SKILL.md`, `skills/pf-codereview/SKILL.md`) и каждый
`pf-*` скилл, который сегодня безусловно пишет документ сам
(`pf-brd`, `pf-spec`, `pf-test-plan`, `pf-impl-plan`), получает общий шаг
**"Resolve role"**, вынесенный текстом в новый файл
`skills/pf-roles/SKILL.md` (reference-скилл, как `pf-git`/`pf-size-tiers` —
не вызывается напрямую, другие скиллы на него ссылаются).

```
                      prompt.md: roles.<key>
                              │
                    есть ли запись для <key>?
                    ┌─────────┴─────────┐
                   нет                  да
                    │                    │
        fallback на профиль        читать write / review
        (см. 1.4) → запись             из записи
        как если бы была
                    │                    │
                    └─────────┬──────────┘
                               │
                    write = ровно один актор
                    review = [актор, …] + mode: parallel|sequential
                               │
                   резолвинг актора → agents.yml
                   (kind, invoke, model/command)
```

### 1.3 Инвариант независимости

Не реализуется (см. BRD, Non-Goals). Резолвер не сравнивает `write` и
элементы `review` между собой; любая комбинация, включая полное совпадение,
принимается без предупреждений.

### 1.4 Профили по умолчанию и fallback

Резолвинг роли для стадии `<key>` — единственный алгоритм, применяемый
одинаково везде, кем бы он ни вызывался (см. §11). Порядок проверки —
строго сверху вниз, первое совпадение побеждает:

1. **Явная точечная запись** `roles.<key>` в `prompt.md` — если есть,
   используется как есть (`write`/`review`, либо `skip`). Высший приоритет.
2. **Точечная запись профиля** для `<key>` в `role-profiles.yml` — если у
   выбранного `profile:` есть запись именно для `<key>` (не `default`),
   используется она.
3. **Tier-дефолт `skip`** — только для `<key>` ∈ {`user_docs`, `dev_docs`}
   и только когда `size_tier` ∈ {`trivial`, `small`} — резолвится в `skip`
   (точная формулировка и мотивация — §8).
4. **`default`-запись профиля** — если у issue есть `profile:`, но ни один
   из уровней 1–3 не сработал, используется `default`-запись выбранного
   профиля.
5. **Общий дефолт** — если у issue нет ни `roles:`, ни `profile:` вовсе:
   `write: claude` для всех ключей, `review` резолвится из существующего
   `reviewers:` (см. §5, автомиграция), а если и его нет — `review:
   [claude]`. Это поведение как до этой issue.

**Почему уровень 3 идёт раньше уровня 4, а не после него.** `default`-запись
профиля существует у каждого профиля и матчит любой ключ без исключения —
если бы tier-дефолт `skip` проверялся после шага «резолвинг через профиль»
целиком (без разделения на «точечная запись профиля» и «`default`
профиля»), он никогда бы не срабатывал ни для одного из трёх дефолтных
профилей в §4: ни у `solo-claude`, ни у `claude-writes-codex-reviews`, ни у
`codex-implements` нет собственной точечной записи `skip` для
`user_docs`/`dev_docs`, только generic `default` — который для
`trivial`/`small` тем самым нарушал бы Acceptance Criteria из `brd.md`
(«для trivial/small tier они по умолчанию `skip`»), так как выбор профиля —
обязательный вопрос при создании issue (§4.1), и `default` матчит первым.
Поэтому только точечная запись профиля конкретно для `user_docs`/`dev_docs`
(уровень 2) может отменить tier-дефолт `skip`; общий `default` профиля —
не может.

### 1.5 Новая раскладка пайплайна

```
... /pf-test → /pf-user-docs* → /pf-dev-docs* → /pf-qa → /pf-close
              (* — опциональные, могут быть roles.<key>: skip)
```

## 2. `prompt.md` frontmatter: новый блок `roles:`

Заменяет `reviewers:` для issue, созданных после этой issue (см. §5 —
автомиграция для старых). Пример для issue типа `feat`/`improve`:

```yaml
profile: claude-writes-codex-reviews   # опционально — имя профиля из role-profiles.yml
roles:
  brd:              { write: claude, review: [codex] }
  specs:             { write: claude, review: { mode: sequential, by: [haiku, codex] } }
  test_plan:         { write: claude, review: [codex] }
  implementation_plan: { write: claude, review: [codex] }
  code:              { write: codex,  review: [claude] }
  tests:             { write: codex,  review: [claude], run: claude }
  user_docs:         { write: codex,  review: [claude] }
  dev_docs:          skip
```

Поля записи для стадии:
- `write` — ровно один актор (обязателен для всех стадий кроме `skip`-стадии
  документации; для `code` `skip` запрещён на уровне `write` в принципе —
  стадии без записи `code` не существует).
- `review` — короткая форма `[codex]` эквивалентна
  `{ mode: parallel, by: [codex] }`. `parallel` — сегодняшняя `both`-логика
  (объединение находок с тегами источника, без дедупликации/арбитража).
  `sequential` — по порядку списка `by`: первый ревьюер находит проблемы,
  актор `write` этой стадии применяет фиксы автоматически (без запроса
  подтверждения у пользователя), затем исправленный артефакт уходит
  следующему ревьюеру в списке.
- `run` — только для `tests`; кто фактически запускает тестовый прогон.
- `skip` — стадия целиком пропущена (только `user_docs`/`dev_docs`;
  `code.review: skip` — не пропуск всей стадии, а отдельно допустимое
  значение только для `review`, см. ниже). Попытка задать `code: skip`
  целиком (не `code.review: skip`) невалидна — пропуск авторства кода
  невозможен (см. §1, Business Rules в `brd.md`). Резолвер обязан явно
  останавливаться понятной ошибкой на таком значении, аналогично
  обработке `kind: human` в §3, например `"roles.code: skip is invalid —
  code authorship cannot be skipped; did you mean code.review: skip?"` —
  не падать необработанным исключением и не молча игнорировать значение.

Ключи `analysis` и `notes` (см. §0) не показаны в примере выше, потому что
они принадлежат не feat/improve-issue, а альтернативным путям: `analysis`
— стадия `analysis.md` для bug-type issue (не-trivial), `notes` — стадия
`notes.md`, которая заменяет `brd`/`specs`/`implementation_plan` (и, для
bug-type, `analysis`) целиком для `size_tier: trivial` issue любого типа
(см. §6b). Оба резолвятся тем же алгоритмом §1.4/§4, что и остальные ключи.

`code.review: skip` (пропуск только ревью кода, авторство остаётся
обязательным) — особый случай: разрешён, но:
1. в момент, когда пользователь задаёт эту роль (при создании issue или при
   ручной правке `prompt.md`, обнаруженной на следующем запуске `/pf`),
   `/pf` спрашивает подтверждение через `AskUserQuestion` ("Ревью кода для
   этой issue отключено — подтвердить?") и, получив "да", записывает рядом
   с `roles.code.review: skip` маркер `confirmed: <дата>` в frontmatter
   `prompt.md`. Если подтверждение ещё не записано к моменту, когда
   `/pf-codereview` доходит до этой роли (например, `skip` был вписан
   вручную в обход `/pf`), тот же вопрос задаёт и тот же маркер записывает
   сам `pf-codereview` (см. §7.3). Форма записи:
   ```yaml
   code: { write: claude, review: skip, confirmed: 2026-08-06 }
   ```
2. `qa_report.md` получает отдельную строку риска (см. §9).

## 3. `docs/planning/agents.yml` — реестр акторов

Per-project файл, создаётся этой issue с дефолтным содержимым при первом
использовании фичи (если файла ещё нет — любой `pf-*` скилл, которому
нужен резолвинг актора, создаёт его один раз со стандартным набором ниже,
без вопроса пользователю):

```yaml
actors:
  claude: { kind: llm, invoke: agent,  model: claude-sonnet-5 }
  haiku:  { kind: llm, invoke: agent,  model: claude-haiku-4-5-20251001 }
  codex:  { kind: llm, invoke: codex-companion }
  gemini: { kind: llm, invoke: cli,    command: "gemini -p {prompt}" }
```

`invoke` определяет, как скилл вызывает актора:
- `agent` — обычный субагент Claude (`Agent` tool), как сегодня для всех
  write-операций и для Claude-стороны ревью в `pf-check`/`pf-codereview`.
- `codex-companion` — тот же путь, что `skills/pf-check/SKILL.md`
  использует сегодня для ревью Codex (`codex-companion.mjs`), расширенный
  на write-операции:
  - для **ревью** — `node codex-companion.mjs review --wait --scope ...`
    (без изменений, см. §7);
  - для **write** — `node codex-companion.mjs task "<prompt>" --write`,
    тот же путь, которым `codex:codex-rescue` сегодня делегирует
    Codex запись в репозиторий (см.
    `codex-cli-runtime/SKILL.md`: `task ... --write`). Скилл-потребитель
    формирует `<prompt>` (см. §6.2) и передаёт его через тот же
    единственный `task`-вызов; не через `codex:codex-rescue` напрямую
    (тот субагент — чистый форвардер пользовательских rescue-запросов, не
    предназначен для программного вызова из другого скилла) — а тем же
    `codex-companion.mjs` скриптом, вызванным из Bash напрямую, аналогично
    тому, как `pf-check` уже вызывает его для `review`.
  - **Синхронный вызов рискует упереться в таймаут Bash-тула** (по
    умолчанию 2 минуты, до 10 минут при явном увеличении в этом
    окружении) для крупной генерации — полного BRD/specs/test-plan/
    impl-plan с нуля, либо нетривиальной implementation-задачи. Выбор
    между синхронным и асинхронным вызовом делается по ожидаемому объёму
    результата:
    - **Мелкая/точечная правка** (применение fix-findings к уже
      существующему файлу — см. §7.2; простая implementation-задача из
      одного-двух файлов) — синхронный вызов как описано выше (`task
      ... --write`, блокирующий).
    - **Генерация документа с нуля или нетривиальная
      implementation-задача** — асинхронный путь: `task ... --write
      --background`, затем опрос через уже существующий механизм
      `codex-companion.mjs status`/`result` (те же подкоманды, которые
      `codex-cli-runtime/SKILL.md` перечисляет как существующие для
      `codex-companion.mjs`, хотя и запрещённые к вызову изнутри
      `codex:codex-rescue`; здесь их вызывает сам скилл-потребитель
      напрямую, тем же Bash-путём, не через `codex:codex-rescue`) — не
      переизобретается заново. Ориентир, не жёсткий порог: если ожидаемый
      объём генерации — полный документ пайплайна с нуля или задача,
      создающая с нуля несколько файлов, — предпочесть асинхронный путь.
- `cli` — произвольная команда с плейсхолдером `{prompt}`, для будущих
  акторов вне Claude/Codex (в этой issue не реализуется ни для одного
  реального актора кроме заготовки `gemini` в дефолтном реестре — эта
  запись документирует форму, но не тестируется; см. §12 Out of scope).

Резолвер актора для `kind: human` не реализуется в этой issue (см. BRD,
Non-Goals), но формат реестра не должен требовать изменений, когда такая
запись появится (`human: { kind: human, inbox: project-explorer }`) —
резолвер обязан явно завершаться понятной ошибкой на `kind: human`
("actor '<name>' is kind: human — not supported until
20260806-improve-project-explorer-redesign"), а не падать необработанным
исключением.

## 4. `docs/planning/role-profiles.yml` — профили по умолчанию

```yaml
profiles:
  solo-claude:
    # backward-compat дефолт: всё делает Claude
    default: { write: claude, review: [claude] }
  claude-writes-codex-reviews:
    default: { write: claude, review: [codex] }
    code:    { write: claude, review: [codex] }
  codex-implements:
    default:  { write: claude, review: [codex] }
    code:     { write: codex, review: [claude] }
    tests:    { write: codex, review: [claude], run: claude }
    user_docs: { write: codex, review: [claude] }
```

`default` — роль, применяемая ко всем ключам стадий, для которых профиль не
задаёт точечное переопределение. Резолвер: для стадии `<key>` — если у
профиля есть запись `<key>`, использовать её; иначе — `default`. Это
правило описывает разрешение *внутри* одного профиля и является лишь одним
шагом (уровни 2 и 4) полного алгоритма резолвинга роли — см. §1.4 за полным
порядком: для `user_docs`/`dev_docs` на `trivial`/`small` tier-дефолт
`skip` проверяется **раньше**, чем `default` этого профиля, и может его
отменить, если у профиля нет собственной точечной записи для этих ключей.

Файл создаётся этой issue с этим содержимым как дефолт проекта, если его
ещё нет (тем же "создать при первом обращении" механизмом, что и
`agents.yml`).

### 4.1 Выбор профиля

- **Вопрос при создании issue** — `skills/pf/SKILL.md`, "Creating prompt.md":
  сразу после вопроса про `size_tier`, третий вопрос — "Какой профиль
  ролей использовать?" со списком имён профилей из
  `docs/planning/role-profiles.yml` (`solo-claude` рекомендован как
  сегодняшнее поведение). Ответ записывается как `profile:` в frontmatter,
  рядом с `size_tier`.
- Существующий отдельный **reviewer-assignment guard** (`pf`/`pf-brd`,
  вопрос "кто ревьюит каждый документ") **удаляется** для issue, у которых
  уже есть `profile:` — профиль покрывает и write, и review. Guard
  продолжает существовать только как автомиграционный путь для issue,
  созданных до этой фичи (см. §5).
- **Смена профиля/ролей посреди пайплайна** — ручная правка `roles:` /
  `profile:` в `prompt.md`; никакого отдельного скилла для этого не
  вводится (решение, зафиксированное в этой issue). `/pf` не кэширует
  резолвинг — каждый запуск любого `pf-*` скилла читает `prompt.md` заново,
  поэтому правка подхватывается со следующего запуска автоматически.
  Уже пройденные стадии не пересматриваются задним числом.

## 5. Обратная совместимость: автомиграция `reviewers:` → `roles:`

Место: общий шаг в `skills/pf/SKILL.md`, выполняется в начале — как часть
Step 2 (сканирование `docs/issues/open/`), сразу после составления списка
открытых issue и **до** Step 3 (вопрос «какую issue открыть», если найдено
несколько) и до Step 4. Автомиграция обходит **все** найденные открытые
issue, а не только ту, что в итоге выберет пользователь на Step 3, —
поэтому её место должно быть до точки, где путь расходится по конкретной
issue, а не после: иначе она применялась бы только к той issue, что была
выбрана, и оставляла бы остальные немигрированными до следующего запуска.
Условие срабатывания — для **каждой** открытой issue, у которой в
`prompt.md` есть `reviewers:`, но нет `roles:`.

Правило конверсии (детерминированное, без вопросов пользователю):

```
для каждого key: actor в старом reviewers:
  roles[key] = { write: claude, review: [actor] }
```

- Если у `reviewers.<key>` было значение `both` — `review: [claude, codex]`.
- Конверсия применяется к **каждому ключу, реально присутствующему** в
  старом блоке `reviewers:` этой issue — без ограничения фиксированным
  списком имён. Сегодняшние потребители `reviewers:` используют ключи
  `brd`, `specs`, `test_plan`, `implementation_plan`, `code`
  (планировочный путь), `analysis` (bug-type, `skills/pf/SKILL.md`'s
  reviewer-assignment guard) и `notes` (trivial-tier,
  `skills/pf-brd/SKILL.md`'s reviewer-assignment guard) — все семь
  переносятся как есть, теми же именами, что и в новой схеме `roles:`
  (см. §0). Этот список документирует известные на сегодня ключи для
  ясности реализации; правило конверсии само по себе не сверяет имя ключа
  со списком — оно мигрирует ровно то, что присутствует в `reviewers:`
  данной issue.
- После конверсии `roles:` записывается в `prompt.md`, старый блок
  `reviewers:` **удаляется** (не оставляется рядом — иначе резолвер должен
  бы решать, какой блок приоритетнее, а это новый источник рассинхрона).
- Конверсия — mutating-операция над `prompt.md`, поэтому по тем же
  правилам, что и любая другая правка issue-файла, коммитится как часть
  той же git-операции, что и следующий шаг пайплайна (не отдельным
  коммитом ради самой миграции) — то есть попадает в staged-паths того
  `pf-*` шага, который следующим пишет в эту issue. Это требует, чтобы у
  **каждой** строки таблицы Step 1 (staging) в `skills/pf-git/SKILL.md` —
  не только у строк `/pf-brd`/`/pf-test-plan`, которые сегодня несут
  условие «+ `prompt.md`, если `size_tier` изменился» — был эквивалентный
  квалификатор «+ `prompt.md`, если автомиграция сработала в этом же
  прогоне»: какая бы стадия ни оказалась первой после автомиграции для
  данной issue, именно она застейджит эту правку `prompt.md` вместе со
  своим артефактом (см. implementation_plan.md, задача, покрывающая
  `pf-git`).

## 6. Изменения в `skills/pf-brd/SKILL.md`, `pf-spec`, `pf-test-plan`, `pf-impl-plan`

Одинаковый паттерн для всех четырёх (BRD/specs/test-plan/impl-plan).

### 6.1 Когда write не claude

Каждый из этих скиллов сегодня безусловно пишет документ сам (в контексте
оркестрирующей сессии, без диспетчеризации субагента — см. текущий текст
`pf-brd`: "Write it directly — no sub-agent dispatch"). Новый шаг перед
записью файла:

1. Resolve role для `<key>` (см. §1.2/§1.4) → получить `write`.
2. Если `write == claude` — поведение не меняется (сегодняшний путь: сама
   сессия ведёт `AskUserQuestion`-цикл и пишет документ).
3. Если `write != claude` (в этой issue — только `codex`):
   - `AskUserQuestion`-цикл уточняющих вопросов **всё равно ведёт
     оркестрирующая сессия** (субагенты не умеют звать `AskUserQuestion` —
     см. `pf-autopilot/SKILL.md`). Сессия доводит уточнение требований до
     тех же ~95% уверенности, что и сегодня.
   - Вместо того чтобы писать документ самой, сессия формирует один текстовый
     промпт для actor'а (см. §6.2) и вызывает его инвокатор из `agents.yml`
     (для `codex` — `codex-companion.mjs task "<prompt>" --write`, см. §3).
   - Actor'у передаётся **путь целевого файла** (`docs/issues/open/<ID>/
     brd.md` и т.д.) — actor редактирует/создаёт файл сам (`--write`),
     скилл не парсит stdout как содержимое документа.
   - После возврата команды скилл читает получившийся файл с диска и
     продолжает свой сегодняшний post-processing без изменений (для
     `pf-brd` — tier reconfirmation; для `pf-spec` — split-at-1500-lines;
     и т.д.), как если бы файл появился обычным путём.

### 6.2 Форма промпта для write-делегирования

Единый шаблон (используется всеми четырьмя скиллами, с точечной заменой
"какой документ"):

```
Напиши <BRD|техническую спецификацию|тест-план|implementation plan>
для issue <ISSUE-ID> в файл <путь>.
Контекст: <содержимое prompt.md>
<содержимое предыдущих документов пайплайна, если есть — brd.md для specs,
 specs.md для test_plan, и т.д.>
Уточнённые в диалоге с пользователем требования: <сжатая выжимка ответов
 AskUserQuestion-цикла из этого прогона>
Язык документа: <doc_language>.
Структура и уровень детализации: <шаблон секций для этого документа и tier,
 как описано в текущем skills/<pf-brd|pf-spec|...>/SKILL.md и
 skills/pf-size-tiers/SKILL.md>.
```

### 6.3 Уточнение к `pf-spec`'s "1500-line split"

Split-логика (создание index-файла + 3 частей при превышении 1500 строк) не
меняется по сути, но при `write: codex` создание частей выполняет тот же
actor тем же вызовом (единый `task ... --write`, с инструкцией внутри
промпта разбить на части при превышении лимита) — не отдельным
пост-обработкой со стороны Claude.

### 6.4 `pf-impl-plan`: поле `Task Type` в шаблоне задачи

`pf-execute` (§6a) резолвит `roles.code.write` для задач кода и
`roles.tests.write` для задач, пишущих тесты — но сегодняшний шаблон
задачи в `skills/pf-impl-plan/SKILL.md` ("Step 2: Create Task Breakdown")
не помечает, к какому из двух типов относится конкретная задача, оставляя
это интерпретации модели, что тест-план (TC-012/TC-013) не может проверить
детерминированно. Шаблон получает новое поле, сразу после заголовка
задачи:

```markdown
#### Task N: [Name]
**Task Type:** code | tests | docs
**Mapped Test Cases:** TC-001, TC-002, TC-003
...
```

- `code` — задача пишет/меняет код продукта; `pf-execute` резолвит
  `roles.code` для неё.
- `tests` — задача пишет автотесты; `pf-execute` резолвит `roles.tests`.
- `docs` — задача пишет документацию как часть implementation plan (не
  через `pf-user-docs`/`pf-dev-docs`) — не используется для делегирования
  через §6a в этой issue, зарезервирована, чтобы не пришлось снова
  трогать шаблон при появлении такой задачи.

Сабагент, которому `pf-impl-plan` делегирует написание плана, обязан
проставлять это поле для каждой задачи.

## 6a. Изменения в `skills/pf-execute/SKILL.md`

Сегодня `pf-execute` для каждой задачи implementation plan безусловно
диспетчерит Claude-субагента (`Agent` tool). С матрицей ролей это
диспетчерство становится условным — тем же паттерном "resolve role", что
§6 описывает для планировочных документов, но на уровне отдельной задачи,
а не документа целиком.

Перед выполнением каждой задачи `pf-execute`:

1. Resolve role для `code` — а для задач, которые implementation plan
   помечает как задачи на написание тестов, для `tests` — тем же способом,
   что §1.2/§6.1 описывают для планировочных документов, → получить `write`
   для этой конкретной задачи.
2. Если `write == claude` — поведение не меняется: сегодняшний диспетч
   Claude-субагента через `Agent` tool на эту задачу.
3. Если `write != claude` (в этой issue — только `codex`) — `pf-execute`
   вызывает актора через его `invoke` из `agents.yml`, тем же путём, что
   §3/§6.1 описывают для write-делегирования: для `codex` —
   `codex-companion.mjs task "<prompt>" --write`. Промпт формируется из
   описания задачи, релевантного среза самого implementation plan (эта
   задача и её ближайший контекст) и контекста репозитория — нацелен на
   тот же файл/область, которую получил бы Claude-субагент для этой же
   задачи.

**Конкурентность внутри волны.** Сегодня Claude-сабагенты внутри одной
волны запускаются параллельно (`Agent` tool) и сами никогда не коммитят —
коммитит только оркестратор на границе волны, специально чтобы не было
гонки за рабочее дерево. Codex-делегированные (`--write`) задачи
используют другой, синхронный канал (`Bash` → `codex-companion.mjs task
... --write`) — безопасность одновременного исполнения этих двух разных
каналов (`Agent` tool vs `Bash`-подпроцесс) в этой issue не проверялась. Как
упрощение на время этой issue: Codex-делегированные задачи волны
выполняются **последовательно, после** того как все Claude-сабагенты этой
волны завершились, и **до** коммита оркестратора на границе волны — не
одновременно с Claude-сабагентами. Это осознанное временное упрощение, а
не постоянное архитектурное ограничение — параллельность между каналами
можно исследовать отдельно, когда матрица ролей будет в реальном
использовании.

Волновая/коммитная структура `pf-execute` (`git add -A` на границе волны,
см. `pf-git`) не меняется — коммитится то, что фактически записал актор,
тем же способом, независимо от того, кто им был.

## 7. Изменения в `skills/pf-check/SKILL.md`, `skills/pf-codereview/SKILL.md`

### 7.0 Автомиграция — собственное предусловие

Оба скилла не полагаются на то, что автомиграция (§5) уже была выполнена
запуском `/pf` перед ними. Каждый из них сам выполняет ту же
автомиграционную проверку из §5, как свой собственный первый шаг — до
резолвинга `roles.<key>` (§7.1) — на случай, когда `/pf-check` или
`/pf-codereview` вызываются напрямую на legacy issue в обход `/pf` (в том
числе из `/pf-autopilot`).

### 7.1 Источник роли — `roles.<key>.review`, не `reviewers.<key>`

Заменить резолвинг: было — `reviewers.<key>` (одно значение: `claude` /
`codex` / `both`); стало — `roles.<key>.review` (список + `mode`). Таблица
отображения старого поведения на новое:

| Старое `reviewers.<key>` | Новое `roles.<key>.review` |
|---|---|
| `claude` (или отсутствует) | `{ mode: parallel, by: [claude] }` |
| `codex` | `{ mode: parallel, by: [codex] }` |
| `both` | `{ mode: parallel, by: [claude, codex] }` |

`parallel`-режим с `by: [claude, codex]` — это сегодняшняя `both`-логика
(секция "`both`-mode aggregation" в `pf-check`) без изменений.

### 7.2 Новый `sequential`-режим

Ревьюеры из списка `by` идут по порядку. После каждого ревьюера, кроме
последнего:
1. Findings этого ревьюера передаются актору `write` этой стадии (см. §1.2)
   тем же путём, что и сегодняшний "Fix now" в `pf-check`/`pf-codereview`
   (диспетч на write-актора с P0/P1 findings, автоматическое применение,
   без промежуточного вопроса пользователю — решение, зафиксированное в
   BRD/эта issue).
2. Целевой документ перечитывается с диска.
3. Следующий ревьюер в `by` получает уже исправленную версию как TARGET.

**Форма промпта, когда write-актор не Claude.** Когда актор `write` этой
стадии — не Claude (например `codex`), диспетч из пункта 1 не может быть
обычным диспетчем Claude-сабагента — используется тот же write-инвокатор
из §3 (`task ... --write`), что и §6.2 для «написать документ с нуля», но
с другим содержанием промпта — не «напиши документ», а «примени эти
находки к уже существующему файлу»:

```
Примени следующие находки ревью к файлу <путь>:
<findings ревьюера, P0/P1, в формате как их сформировал ревьюер>
Не переписывай файл заново — вноси точечные правки, устраняющие
конкретно перечисленные находки. Сохраняй остальное содержимое файла и
стиль оформления без изменений.
```

Актору передаётся путь файла, он редактирует его сам (`--write`); скилл
после возврата перечитывает файл с диска, как и в §6.1. То же самое
относится к интерактивному «Fix now» в `pf-check`/`pf-codereview` (не
только к межпроходному шагу sequential-режима) — в обоих случаях
диспетчится резолвленный write-актор стадии, не всегда Claude.

Финальный отчёт (`code_review.md` / вывод `pf-check`) перечисляет находки
**каждого** ревьюера отдельным блоком с меткой `[<actor>, pass N]`, включая
находки, которые уже были исправлены до следующего прохода (помечаются
`(fixed before next reviewer)`), чтобы история прохода была видна, а не
только финальный срез.

### 7.3 `code.review: skip`

`pf-codereview` при `roles.code.review == skip` сначала проверяет наличие
маркера подтверждения `confirmed:` рядом с этой записью в frontmatter
`prompt.md` (см. §2) — того же маркера, который пишет `/pf`, когда сам
задаёт вопрос подтверждения в момент, когда пользователь устанавливает эту
роль:

- Если `confirmed:` уже есть — ревью не запускается, `pf-codereview` сразу
  переходит к записи вердикта.
- Если `confirmed:` ещё нет (например, `code.review: skip` попал в
  `prompt.md` ручной правкой, в обход `/pf`) — `pf-codereview` сам задаёт
  тот же вопрос через `AskUserQuestion` ("Ревью кода для этой issue
  отключено — подтвердить?"), который иначе задал бы `/pf` (см. §2), и при
  положительном ответе записывает `confirmed: <дата>` в frontmatter
  `prompt.md` рядом с `roles.code.review: skip`, прежде чем продолжить.

В обоих случаях `pf-codereview` не запускает ревью, записывает в
`code_review.md` `verdict: SKIPPED (roles.code.review: skip, confirmed
<дата подтверждения>)` и не блокирует переход к `/pf-test`.

**Предусловие `/pf-test`.** Сегодня `skills/pf-test/SKILL.md` перед
прогоном тестов требует, чтобы `code_review.md`'s `verdict:` было буквально
`PASS` — любое другое значение (включая `SKIPPED`) останавливает
`/pf-test` с сообщением о том, что нужен `PASS`. Эта issue меняет это
условие: `/pf-test`'s предусловие должно принимать `verdict: PASS` **или**
`verdict: SKIPPED` — иначе `code.review: skip`, описанный выше как не
блокирующий переход к `/pf-test`, на практике всё равно блокировал бы его
на следующем шаге. Формулировка сообщения об остановке для случая
`FAIL`/отсутствующего файла не меняется.

  запись профиля > общий дефолт `write: claude, review: [claude]` для
  issue без `profile:` вовсе.

- схемы `roles:`/`profile:` в `prompt.md` (§2),
- схемы `agents.yml`/`role-profiles.yml` (§3, §4),
- алгоритма резолвинга роли для стадии (§1.2, §1.4, включая полный
  пятиуровневый порядок fallback: явная точечная запись → точечная запись
  профиля → tier-дефолт `skip` для `user_docs`/`dev_docs` на
  `trivial`/`small` → `default`-запись профиля → общий дефолт `write:
  claude, review: [claude]`),
- автомиграции (§5),
- механики sequential-режима (§7.2).

Это устраняет риск, отмеченный в исходном `prompt.md` ("Учесть при
реализации"): единая точка вызова/резолвинга акторов — единая точка
починки при поломке любого из них, аналогично тому, как `pf-git`
централизовал commit&push процедуру.

## 12. Out of scope (подтверждено в BRD/уточняющих вопросах)

- `human` как актор, очередь задач, режимы `blocking`/`non-blocking` —
  `20260806-improve-project-explorer-redesign`.
- Инвариант независимости write/review — не реализуется вовсе.
- Отдельный интерактивный скилл для смены ролей/профиля посреди
  пайплайна — правка `prompt.md` вручную.
- Реальная работоспособность `kind: cli`/`invoke: cli` (`gemini`) —
  формат задокументирован в дефолтном `agents.yml`, но не тестируется и не
  вызывается ни одним профилем по умолчанию в этой issue.
- Изменение логики самого `.qa-workflow.md`/runnable-команд в `pf-qa` —
  только добавление prerequisite-проверки и risk-строки (§9).
