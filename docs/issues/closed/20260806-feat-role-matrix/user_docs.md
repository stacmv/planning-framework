# User Docs: Матрица ролей write/review по стадиям issue

## Что изменилось

До этой issue framework умел назначать только **ревьюера** для каждого
документа пайплайна (`reviewers:` в `prompt.md`, значения `claude` /
`codex` / `both`), а писал каждый документ всегда Claude. Теперь framework
умеет назначать отдельно **кто пишет** и **кто ревьюит** каждую стадию —
и автору можно назначить Codex, чтобы он реально писал документ или код, а
не только находил в нём проблемы.

Это может ускорить работу: Codex часто работает быстрее Claude, и теперь
можно поручить ему авторство кода/тестов/документации, оставив Claude
независимым ревьюером.

> ⚠️ Framework не проверяет, что автор и ревьюер разные акторы — комбинация
> вида «пишет Codex, ревьюит только Codex» технически допустима и не
> вызывает предупреждения. Осознанное решение — если важна независимость
> ревью, задавайте её сами через `roles.<key>.review`.

## Как этим пользоваться

### Профиль по умолчанию — один вопрос при создании issue

При создании новой issue через `/pf` framework задаёт один дополнительный
вопрос: «Какой профиль ролей использовать?». Доступные профили:

| Профиль | Что означает |
|---|---|
| `solo-claude` (по умолчанию) | Всё пишет и ревьюит Claude — сегодняшнее поведение без изменений. |
| `claude-writes-codex-reviews` | Claude пишет **все** стадии, Codex ревьюит **все** стадии (не только код) — рекомендованный режим для ускорения ревью. |
| `codex-implements` | Claude пишет документацию планирования (BRD/спецификацию/тест-план/план реализации/dev-доки) и их же ревьюит Codex; код, тесты и пользовательскую документацию пишет Codex, а ревьюит уже Claude. Максимальная скорость авторства там, где это безопаснее всего. |

Выбранный профиль записывается в `prompt.md` как `profile: <имя>` и
действует для всех стадий, у которых нет собственной точечной настройки.
Профили `claude-writes-codex-reviews` и `codex-implements` требуют
установленного и настроенного Codex CLI (плагин `openai-codex`) — без него
любая стадия, резолвящаяся в `codex`, останавливается с понятной ошибкой
вместо тихого отката на Claude.

Акторы (`claude`, `codex`, ...) и профили — не жёстко зашиты в framework, а
читаются из `docs/planning/agents.yml` и `docs/planning/role-profiles.yml`
соответственно; framework создаёт оба файла с дефолтным содержимым сам при
первом обращении, если их ещё нет. Добавить нового актора — одна строка в
`agents.yml`, без правки скиллов.

### Точечная настройка стадии

Любую стадию можно переопределить точечно, вручную отредактировав
`prompt.md`:

```yaml
roles:
  code: { write: codex, review: [claude] }
```

Изменение подхватывается со следующего запуска любой команды `/pf-*` —
ничего не нужно перезапускать или сбрасывать. Уже пройденные стадии не
переделываются задним числом — правка касается только того, что ещё не
выполнено.

Точно так же можно сменить и весь `profile:` целиком — просто заменить
значение в `prompt.md` вручную (`profile: solo-claude` →
`profile: codex-implements`, например). Отдельной команды для смены
профиля нет — правка frontmatter вручную и есть штатный способ, и он тоже
подхватывается со следующего запуска.

### Параллельное и последовательное ревью

Ревью одной стадии можно поручить нескольким акторам:

- `review: [claude, codex]` (или `{mode: parallel, by: [claude, codex]}`) —
  оба ревьюют одновременно, находки объединяются с пометкой источника.
- `review: {mode: sequential, by: [haiku, codex]}` — первый находит
  проблемы, автор стадии автоматически их исправляет, затем документ уходит
  второму ревьюеру уже исправленным.

### Пропуск ревью кода — с подтверждением

`roles.code.review: skip` отключает независимое ревью кода для issue.
Framework один раз запрашивает явное подтверждение и после этого
записывает в отчёт о финальной проверке качества предупреждение о том, что
независимого ревью не было. Пропустить можно только ревью — авторство кода
пропустить нельзя.

### Документация: новые опциональные стадии

Между тестированием и финальной проверкой качества появились две новые
опциональные стадии: `/pf-user-docs` (документация для пользователей — этот
самый документ) и `/pf-dev-docs` (документация для разработчиков —
архитектура, решения, инструкции по эксплуатации). Для маленьких задач
(`size_tier: trivial`/`small`) они по умолчанию пропущены; для более
крупных задач — включены по умолчанию, как и все остальные стадии. Пропуск
можно задать и вручную для issue любого размера — `roles.user_docs: skip`
(аналогично для `dev_docs`) в `prompt.md`.

## Миграция существующих issue

Issue со старым `reviewers:` блоком (и без `roles:`) автоматически
переводятся на новую схему при первом обращении к ним — либо через `/pf`,
либо напрямую через `/pf-check`/`/pf-codereview`. Автор каждой
переносимой стадии — всегда Claude (как и было раньше), ревьюер —
переносится из старого значения без изменений. Никакого вопроса
пользователю при этом не задаётся, старый блок `reviewers:` удаляется
целиком.
