# User Documentation — стадия идеи (idea/spike)

**Issue ID:** 20260902-feat-idea-stage
**Date:** 2026-09-04

Документ описывает, что изменилось **для пользователя фреймворка**, и какие
пользовательские документы репозитория нужно из-за этого поправить.

Несколько слов, которые дальше встречаются часто:

- **intake** — набор вопросов, который задаётся при создании задачи.
- **линзы** — способы разбора идеи (например «5 почему», SWOT, Lean Canvas).
  Какие именно применяются, зависит от вида идеи.
- **гейт** — точка, где нужно решение человека, и работа до него не идёт дальше.

---

## What changed for a user

### Два новых вида задач

К `feat`, `improve` и `bug` добавились `idea` и `spike`. Они хранятся там же
(`docs/issues/open/`), называются так же (`YYYYMMDD-idea-<slug>`,
`YYYYMMDD-spike-<slug>`) и управляются тем же `/pf` — но идут по собственным,
более коротким маршрутам, без BRD, спецификации, тест-плана, плана реализации
и QA. Существующие типы задач работают ровно как раньше: ни один их шаг не
изменился.

**`idea`** — разбор идеи до того, как решено, делать ли её вообще:

```
prompt.md → idea.md → research.md → critique.md → verdict.md → закрытие
```

- `idea.md` — боль и её подтверждение, аналоги, отличие, MVP, цена, риски.
  Набор линз зависит от вида идеи (`idea_tier`: `personal`, `infra`,
  `content`, `product`): личному инструменту не нужен SWOT, продукту нужен.
- `research.md` — факты со ссылками. Каждый факт помечен `проверено` или
  `не проверено`; непроверенное **не выдаётся за факт** и попадает в журнал
  открытых вопросов.
- `critique.md` — разбор с четырёх точек зрения: скептик-инвестор, целевой
  пользователь, техлид, безопасник (для некоторых видов идей добавляются
  ещё). Каждая точка зрения формирует возражения независимо от остальных; в
  конце сводная таблица «возражение → ответ / риск принят / идея меняется».
- `verdict.md` — вердикт из четырёх возможных.

**`spike`** — короткая техническая проверка гипотезы:

```
prompt.md → hypothesis.md → findings.md → закрытие
```

Закрытие спайка требует **реального прогона**: непустой раздел `## Conclusion`
невозможен без непустого `## Run Evidence`. Это проверяется и при записи
документа, и на входе в закрытие — на случай, если файл поправили руками.

Если проверка гипотезы потребовала кода, он остаётся на ветке
`issue/<spike-id>`: эта ветка **не мерджится и не удаляется**, в родительскую
ветку переносятся только документы задачи. Если код не понадобился, ветка не
создаётся вовсе.

### Четыре вердикта разбора идеи

| Вердикт | Что происходит при закрытии |
|---|---|
| `project` | Заводится первая `feat`-задача с `prompt.md`, предзаполненным из `idea.md` и ответов на intake |
| `spike-first` | Заводится `spike`-задача — сначала проверить гипотезу |
| `defer` | Идея закрывается без продолжения, с зафиксированным условием возврата |
| `archive` | Идея закрывается без продолжения |

Для `project` и `spike-first` пересказывать идею заново не нужно: `/pf-brd`
спросит только то, чего в `idea.md` нет.

Если разбор идеи начинался в пустой папке, при вердикте `project` или
`spike-first` перед созданием следующей задачи выполняется `git init` и
разворачивается каркас проекта — до этого момента ни того, ни другого нет.

### Старт с пустой папки

`mkdir proj && cd proj && claude`, затем `/pf` — и первым же действием
спрашивается, что делать: разбирать идею или сразу разворачивать проект.

- **«Сразу проект»** — выполняется `git init` (если это ещё не репозиторий) и
  разворачивается каркас, дальше обычный вопрос о виде задачи.
- **«Идея»** — на диске появляется только `prompt.md`. Ни `git init`, ни
  каркаса, ни лишних файлов.

Идею можно не набирать руками, а указать файл с её описанием: извлечённый текст
показывается для подтверждения, а если файл прочитать не удалось — попросят
ввести идею напрямую.

Разбор идеи, начатый в пустой папке, целиком проходит **без git**: стадии
завершаются нормально и сообщают, что результат не закоммичен, потому что
репозитория нет.

В существующем проекте без открытых задач `/pf` теперь предлагает четыре
варианта вместо прежнего свободного текста: новая возможность, ошибка, разбор
идеи, технический спайк.

### Автономный прогон

`/pf-autopilot` работает с обоими новыми видами задач. Он сам проходит стадии и
**останавливается перед единственным гейтом**: для идеи — перед сессией
решения, для спайка — перед закрытием. В отчёте показывает, какие ответы были
приняты по рекомендации и какие вопросы остались открытыми, чтобы решение
принималось со всей картиной. Финальное решение всегда за человеком; при
закрытии задачи расписание автопрогона снимается само.

Таким образом пользователю достаточно знать две команды: `/pf` и
`/pf-autopilot`. Остальные вызываются пайплайном.

### Меньше вопросов посреди работы

Для `idea` и `spike` вопросы собраны в два момента: один пакет на входе и одна
сессия решения в конце. В середине вопросов нет — недостающие ответы берутся по
рекомендации и записываются в `open_questions.md` с пометкой `[assumed]`, чтобы
в конце их можно было увидеть списком и при желании переопределить.

Для `feat`/`improve`/`bug` это поведение **опционально** и по умолчанию
выключено: включается полем `interaction: front-loaded` в `prompt.md` задачи.
Без этого поля всё работает как раньше.

Включать режим лучше при создании задачи — тогда intake соберёт все нужные
ответы сразу. Если добавить поле руками в уже существующий `prompt.md`, один
вопрос (о настройке ревью в Codex) может всё-таки быть задан по ходу работы,
потому что на intake его не задавали.

### Число скиллов: 21 → 28

Добавлены пять пишущих (`pf-idea`, `pf-idea-research`, `pf-idea-critique`,
`pf-idea-verdict`, `pf-idea-spike`) и два справочных (`pf-idea-lenses`,
`pf-interaction`). Справочные напрямую не вызываются.

Отдельно устанавливать их не нужно: установка и обновление копируют каталоги
скиллов по маске и подхватывают новые автоматически.

## Migration notes

**Ломающих изменений нет.**

- Открытые задачи `feat`/`improve`/`bug` продолжают работать без правок.
- Ни один существующий документ не требует нового поля.
- `interaction: front-loaded` — опциональное поле; его отсутствие означает
  сегодняшнее поведение.

**Обновление.** Из каталога фреймворка:

```
make converge TARGET=/path/to/your-project
```

Либо, если Makefile недоступен, из каталога проекта — запуском
`scripts/converge-to-v3.sh` фреймворка по полному пути. Голое `make converge`
без `TARGET` нацелено на текущий каталог, то есть на сам репозиторий
фреймворка. Исходники фреймворка при этом должны уже содержать новую версию.

**Важное уточнение про «без установки».** Новое здесь то, что для только что
созданной папки проекта отдельный шаг конвергенции больше не нужен — `/pf` сам
развернёт каркас. Первоначальная глобальная установка самого фреймворка
(`install.sh` / `converge` / `update-skills.sh`) по-прежнему обязательна: без
неё команды `/pf` в Claude Code просто не существует.

**Известное ограничение.** Фреймворк рассчитан на работу в Claude Code. Запуск
в других средах пока не поддерживается.

## What a user does not need to know

Внутренняя механика намеренно не выносится в пользовательские документы:
резолюция ролей и моделей, служебные маркеры в журнале задачи, устройство
реестра находок ревью, внутренние протоколы взаимодействия и структура тестовых
наборов.
