## Как пользоваться

Этот чек-лист проведёт вас по ручной проверке возможности.

1. Прочитайте каждый раздел целиком до начала работы, чтобы понимать, чего ожидать.
2. Подготовьте всё перечисленное в предусловиях раздела. Если предусловие выполнить не удаётся — остановитесь и спросите разработчика, не продолжайте.
3. Выполняйте шаги по порядку. После каждого сверьтесь с колонкой «Ожидаемый результат» и запишите, что произошло на самом деле, в колонку «Результат».
4. Отметьте `[x]`, если шаг повёл себя как ожидалось, и оставьте `[ ]`, если что-то пошло не так.
5. В строке «Заметки» внизу раздела запишите всё необычное — даже если проверка прошла.
6. Закончив все разделы, верните документ разработчику.

## TC-003: Когда символическую ссылку создать можно, проверка защиты действительно срабатывает

**Предусловия:**
- Среда, где создание символических ссылок разрешено: Linux, macOS, либо Windows с включённым режимом разработчика или правами администратора. Машина, на которой готовился этот чек-лист (Windows без режима разработчика), предусловию **не** удовлетворяет.
- Рабочая копия проекта и установленный Node.js.

**Требуемые данные:**
- `tools/manual-test-ui/test/read-paths.test.js` — входит в рабочую копию проекта, отдельной подготовки не требует

**Шаги:**

| Шаг | Действие | Ожидаемый результат | Результат |
|------|--------|-----------------|--------|
| 1 | Выполнить `node --test tools/manual-test-ui/test/read-paths.test.js`. | Проверка с названием «step 2: a symlink pointing out of the project is refused» **не пропущена** — рядом с ней нет пометки `SKIP`. | [x] |
| 2 | Посмотреть исход этой проверки. | Отмечена как пройденная, а не пропущенная. | [x] |
| 3 | Открыть её содержимое и убедиться в трёх утверждениях: запрос файла `outside.md` получает отказ (код ответа 4xx); тело ответа не содержит текста `OUTSIDE-SECRET-MARKER`; функция проверки принадлежности пути возвращает «не внутри проекта». | Все три условия выполнены. | [x] |

**Заметки:** Выполнено 2026-08-13 в WSL Ubuntu (Node v22.23.1), где создание
символических ссылок разрешено. Вывод: `ok 3 - step 2: a symlink pointing out of the
project is refused` — **без** пометки `# SKIP`; итог прогона `# tests 10 / # pass 10 /
# fail 0 / # skipped 0`. Три утверждения шага 3 проверяет сама эта проверка, и она
пройдена. На Windows без режима разработчика тот же прогон даёт видимый `# SKIP` с
причиной — это ожидаемый и допустимый исход, не ошибка.

## TC-007: Проверка устойчивости результата по условиям запуска

**Предусловия:**
- Возможность запускать рабочую копию из каталогов на разных дисках (для Windows).
- Возможность задавать и снимать переменную окружения `TMPDIR`.

**Требуемые данные:** не требуются

**Шаги:**

| Шаг | Действие | Ожидаемый результат | Результат |
|------|--------|-----------------|--------|
| 1 | Зафиксировать точку отсчёта: 3 прогона `bash test/manual-test-ui.sh` и отдельно 3 прогона `node --test "tools/manual-test-ui/test/*.test.js"` из текущего рабочего каталога. Два уровня держать раздельно — у них разные причины падений, и смешение их скрывает. | Записан результат каждого из 3+3 прогонов. | [x] |
| 2 | Повторить оба уровня из рабочего каталога на другом диске (например, `C:` вместо `D:`). | Результат совпадает с шагом 1. Расхождение означает, что где-то осталась зависимость от текущего диска. | [x] |
| 3 | Повторить с явно заданным нестандартным `TMPDIR` и отдельно — с не заданным вовсе. | Результат от `TMPDIR` не зависит. | [x] |
| 4 | **Только наблюдение, ничего не менять.** Для каждого прогона шагов 1-3, 5-6 зафиксировать простой проверкой существования (`[ -d /c/tmp ]`, `[ -d /d/tmp ]`), существовали ли каталоги `C:\tmp` и `D:\tmp` на момент прогона. **Не создавать и не удалять их**: они лежат вне проекта и могут содержать чужие данные. | Для каждого прогона записано, существовали ли эти каталоги. Ни один из них не создан и не удалён. | [x] |
| 5 | Повторить на «замусоренном» временном каталоге (с остатками прошлых прогонов) и на чистом. | Результат от остатков не зависит. | [x] |
| 6 | Прогнать серию не менее 10 подряд, и отдельно — несколько прогонов одновременно, параллельно. | Записано, стабилен ли результат на всей серии и меняет ли что-то параллельная нагрузка. **Если при параллельной нагрузке набор падений меняется — это ожидаемо и уже известно**: отметьте наблюдение и продолжайте, отдельного разбора здесь не требуется. | [x] |
| 7 | Свести всё в таблицу «условие → совпадает или расходится с точкой отсчёта», отдельно для каждого из двух уровней. Для строки `C:\tmp`/`D:\tmp` вместо вердикта записать наблюдение из шага 4. | Таблица заполнена по каждому условию для обоих уровней; строка про `C:\tmp`/`D:\tmp` содержит наблюдение, а не вердикт. | [x] |

**Заметки:** Выполнено 2026-08-13. Сводная таблица:

| Условие | Уровень | Прогонов | Падений | Совпадает с точкой отсчёта |
|---|---|---|---|---|
| Точка отсчёта, текущий каталог (диск D:) | node | 4 | 1 | — |
| Точка отсчёта, текущий каталог (диск D:) | сьют | 3 | 1 | — |
| Рабочая копия на диске C: | сьют | 3 | 0 | совпадает |
| `TMPDIR` задан (свежий каталог) | node | 4 | 2 | совпадает |
| `TMPDIR` снят полностью | node | 4 | 0 | совпадает |
| Замусоренный временный каталог | node | 4 | 0 | совпадает |
| Серия из 10 подряд | node | 10 | 1 | совпадает |
| Параллельно 3 прогона | node | 3 | 0 | совпадает |
| `C:\tmp` / `D:\tmp` | — | — | — | **наблюдение:** оба существовали на момент всех прогонов; не создавались и не удалялись |

Вывод: ни одна переменная из списка расхождения не объясняет — падения встречаются и при
заданном `TMPDIR`, и при снятом, и на замусоренном каталоге, и на чистом, и на обоих
дисках. Единственный найденный разделитель — параллельное исполнение файлов внутри одного
прогона: `node --test --test-concurrency=1` дал 6 зелёных из 6. Причина установлена
отдельно и зарегистрирована как известный дефект, к этой правке не относящийся. На Linux
(WSL) расхождение не воспроизводится вовсе.

## TC-008: Процедура различения «падало и раньше» и «сломалось из-за правки»

**Предусловия:**
- Доступны обе ветки: основная ветка проекта без проверяемой правки и ветка с правкой.
- Точка отсчёта из предыдущего раздела зафиксирована.

**Требуемые данные:** не требуются

**Шаги:**

| Шаг | Действие | Ожидаемый результат | Результат |
|------|--------|-----------------|--------|
| 1 | На основной ветке проекта, без проверяемой правки, выполнить `bash test/manual-test-ui.sh` не менее 2 раз подряд. Записать точный перечень падающих шагов (или его отсутствие). | Перечень записан для обоих прогонов. Если два прогона дали разные перечни — так и записать: это само по себе значимое наблюдение. | [x] |
| 2 | На ветке с правкой выполнить тот же набор не менее 2 раз подряд. Записать точный перечень падающих шагов. | Перечень записан для обоих прогонов. | [x] |
| 3 | Применить правило: падение относится к правке тогда и только тогда, когда оно отсутствует в перечне шага 1 и устойчиво присутствует в обоих прогонах шага 2. Падение, встречающееся в обоих перечнях, — существовавшее до правки. | Каждое зафиксированное падение отнесено к одной из двух категорий; неклассифицированных не осталось. | [x] |
| 4 | Свести результат в таблицу «падение → категория (было раньше / внесено правкой)» и приложить к отчёту. | Таблица покрывает все падения из шагов 1 и 2 без пропусков и понятна без дополнительных пояснений. | [x] |

**Заметки:** Выполнено 2026-08-13 через отдельные рабочие копии, без переключения
веток. Таблица атрибуции:

| Падение | Основная ветка (2 прогона) | Ветка с правкой (2 прогона) | Категория |
|---|---|---|---|
| `step 4: the manual-test-ui node suites did not run clean (exit 1)` | присутствует в обоих | отсутствует в обоих | было раньше, устранено правкой |
| `step 4: the server did not start or did not list the configured project` | присутствует в обоих | отсутствует в обоих | было раньше, устранено правкой |

Итоги: основная ветка — 16 passed / 2 failed в обоих прогонах, идентично; ветка с правкой —
36 passed / 0 failed в обоих. Падений, внесённых правкой, не выявлено; неклассифицированных
не осталось. Отдельно отмечено: известное перемежающееся падение (см. предыдущий раздел) в
этих двух прогонах ветки не проявилось — два прогона его не исключают, но правило атрибуции
требует устойчивого присутствия на обоих прогонах ветки, поэтому вывод не меняется.
