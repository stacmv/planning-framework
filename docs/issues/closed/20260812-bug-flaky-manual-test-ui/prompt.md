Набор тестов `tools/manual-test-ui` недетерминирован: на нетронутом `develop` два
прогона роняют разные тесты. Из-за этого `/pf-test` (Phase 4), останавливающий
пайплайн на любом `✗`, превращается из гейта в шум.

## Происхождение

Вынесено из issue `20260806-improve-codereview-convergence` решением владельца
2026-08-12. Там это был US-7. Три независимых источника указали, что это другая
подсистема, слабее связанная со сходимостью ревью: сам `prompt.md` исходной issue
(«Отдельный issue»), ревью её BRD и предварительная оценка объёма.

## Наблюдения

**Подтверждено измерением 2026-08-12** в ходе работы над
`20260806-feat-product-test-plan`:

- `bash test/manual-test-ui.sh` на ветке issue: `16 passed, 2 failed`;
- тот же сьют на **чистом** `develop` (отдельный worktree, коммит `9f171c3`):
  `16 passed, 2 failed` — идентично, то есть падения предсуществующие и к
  изменениям issue не относятся;
- падающие шаги: `step 4: the manual-test-ui node suites did not run clean
  (exit 1)` и `step 4: the server did not start or did not list the configured
  project`;
- дополнительно `read-paths.test.js` TC-011 падает с `EPERM` на `symlinkSync`
  под Windows — вероятно, среда, а не логика.

Исходное наблюдение из `20260806-improve-codereview-convergence` говорит о
**разных** падающих тестах между прогонами; измерение выше дало два одинаковых
прогона. Значит недетерминированность либо перемежающаяся, либо зависит от
окружения — это первое, что нужно установить в анализе, а не предполагать.

## Что нужно

1. Установить причину: настоящая недетерминированность (гонка, порядок, общий
   порт/файл) против средовой специфики Windows.
2. Отличать тест, падающий на нетронутой рабочей ветке, от теста, сломанного
   изменениями issue — с явной процедурой: сколько повторных прогонов,
   зафиксированный базовый результат, правило отнесения.
3. Сделать так, чтобы такое падение не блокировало пайплайн молча и не
   выдавалось за дефект issue.

## Приёмка

`/pf-test` на нетронутой рабочей ветке даёт стабильный результат от прогона к
прогону, а падение, не связанное с изменениями issue, отличимо от связанного и
не останавливает пайплайн как дефект issue.
