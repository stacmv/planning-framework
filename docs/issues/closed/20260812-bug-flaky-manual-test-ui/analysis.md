# Analysis: падения `tools/manual-test-ui` — недетерминированности нет

**Issue:** 20260812-bug-flaky-manual-test-ui
**Дата:** 2026-08-13
**Тип:** bug · **Tier:** small

---

## Краткий вывод

Исходная посылка issue — «на нетронутом `develop` два прогона роняют **разные**
тесты» — **не подтвердилась**. Измерение показало два стабильных падения, каждое
со своей детерминированной причиной. Ни одно не является гонкой, порядком
выполнения или конкуренцией за общий ресурс.

Одно из двух — настоящий дефект теста, воспроизводящийся всегда. Второе —
ограничение среды, но с усилением: оно отключает восемь посторонних проверок
вместе с одной затронутой.

|---|---|---|

**Вывод: недетерминированность не воспроизведена в измеренных условиях.**
Формулировка выбрана осторожно и это не смягчение ради вежливости: три
последовательных прогона в одном окружении доказывают стабильность **в этом
окружении**, и не более того. Эффект, зависящий от текущего диска, значения

прошлых прогонов, порядка запуска или параллельной нагрузки, такой серией
пропускается легко — тем более что причина №2 от рабочего каталога зависит
напрямую.

Исходное наблюдение при этом остаётся необъяснённым как наблюдение: наиболее
правдоподобно, что сравнивались прогоны в разных условиях. Что именно домерить,
чтобы закрыть вопрос, перечислено в открытых вопросах ниже.

## Причина №1 — `EPERM` на `symlinkSync`, и почему она стоит дороже, чем кажется

### Факт

`tools/manual-test-ui/test/read-paths.test.js`, TC-011. В `buildFixture()`,
строка 73:

```js
// A symlink that lives inside the project but points out of it: literal
// path comparison would accept it, realpath comparison must not.
fs.symlinkSync(path.join(parent, "secret-outside.md"), path.join(projectDir, "outside.md"));
```

Прогон падает с `EPERM: operation not permitted, symlink`. На Windows создание
символических ссылок требует включённого Developer Mode либо прав
администратора; ни того ни другого в этой среде нет.

### Что именно проверяет симлинк

Это не вспомогательная деталь фикстуры, а предмет проверки — шаг 2 TC-011
(`read-paths.test.js:148`) запрашивает `outside.md` и требует отказа.

Смысл — в комментарии самой фикстуры: путь `project/outside.md` **буквально**
лежит внутри проекта, поэтому текстовое сравнение путей такую ссылку пропустит.
Отличить её можно только разрешив ссылку через `realpath`. Тест существует, чтобы
поймать реализацию, сравнивающую пути как строки. Проверка с контролем:
`assertRefused` требует не просто отказа, а отсутствия маркера содержимого в
ответе — сервер не должен вернуть данные даже частично.

### Усиление — главное в этой причине

Симлинк создаётся в `buildFixture()`, то есть **до** всех подпроверок. `EPERM`
поэтому уносит не шаг 2, а **весь TC-011 целиком**. В нём девять подпроверок, и
симлинк нужен ровно одной:

| Подпроверка | Нужен симлинк |
|---|---|
| positive control: документ проекта читается | нет |
| step 1: обход наружу отвергается (`../`, `/etc/passwd`, percent-кодирование) | нет |
| **step 2: симлинк наружу отвергается** | **да** |
| step 3a: соседний каталог с общим префиксом (`project-x` против `project`) | нет |
| step 3b: сосед `public/` отвергается статическим маршрутом | нет |
| step 4: memory-префикс читается — единственное разрешённое расширение | нет |
| step 5: нормализация до сравнения префикса | нет |
| step 6: транскрипты сессии недоступны по имени и в листинге | нет |
| browser-модули отдаются по allowlist, не из всего `lib/` | нет |

То есть одно недоступное системное право отключает восемь проверок изоляции
чтения, которые к нему отношения не имеют. Среди них — классическая ошибка
сравнения префиксов (`project-x` проходит проверку «начинается с `project`») и
недоступность транскриптов сессии.

**Классификация:** ограничение среды, но с дефектом устройства теста —
неразделённость фикстуры и проверок.

## Причина №2 — POSIX-путь записан в JSON и разрешён нативным Windows-процессом

### Факт

`test/manual-test-ui.sh`, строки 348-350:

```sh
tc015_config="$tc015_root/projects.json"
printf '{"projects":[{"name":"%s","path":"%s","defaultBranch":"develop"}]}\n' \
  "$TC015_PROJECT" "$tc015_repo" >"$tc015_config"
```

`$tc015_repo` подставляется **как есть** — это POSIX-путь вида
`/tmp/pf-test-XXXXXXXX/pf-fixture-project`, полученный из `pf_mktemp_d`
(`test/lib.sh:130`, `mktemp -d "${TMPDIR:-/tmp}/pf-test-XXXXXXXX"`, при
`TMPDIR=/tmp`).

Диагностика сервера при провале:

```
WARNING: project "pf-fixture-project" path does not exist: D:\tmp\pf-test-IYCFPPdX\pf-fixture-project — skipping
No valid projects configured in projects.json. Nothing to serve.
```

### Механизм

Git Bash конвертирует POSIX-пути в нативные при передаче **аргументами**
запускаемым программам, но **содержимое файлов не переписывает** — а именно этим
каналом путь сюда и попадает. (Механизм конвертации MSYS шире и сложнее, чем один
только `argv`; для этой причины существенно лишь то, что на содержимое
`projects.json` он не распространяется.) Измерено:

```
bash /tmp resolves to (windows form):  C:\Users\Stac\AppData\Local\Temp
created (posix): /tmp/pf-probe-o6AB
windows form:    C:\Users\Stac\AppData\Local\Temp\pf-probe-o6AB

node, получивший тот же путь аргументом:
  argv:     C:/Users/Stac/AppData/Local/Temp/pf-probe-o6AB
  resolved: C:\Users\Stac\AppData\Local\Temp\pf-probe-o6AB
  exists:   true
```

Содержимое файлов не конвертируется ничем. Node читает `projects.json`, получает
буквальную строку `/tmp/...` и, будучи нативным Windows-процессом, разрешает
ведущий слэш **относительно текущего диска**. Рабочий каталог сьюта —
`D:\dev\planning-framework`, поэтому `/tmp/...` становится `D:\tmp\...`.

Каталог `D:\tmp` на этой машине существует (проверено), нужной подпапки в нём
нет — отсюда ровно то сообщение, которое печатает сервер.

**Сервер при этом не стартовал.** `tools/manual-test-ui/server.js`, `main()`
(строки 1078-1083): сначала `loadProjects()`, затем при `projects.size === 0`
печатается `No valid projects configured…` и вызывается `process.exit(1)` — **до**
`createServer()` и до прослушивания порта. Процесс дошёл до чтения конфига,
пропустил единственный проект в `loadProjects()` (строки 152-155) и завершился.

Более ранняя редакция этого документа утверждала, что сервер стартовал успешно, и
на этом основании называла сообщение шага 4 вводящим в заблуждение. Оба
утверждения неверны: здесь реализовалась именно ветка «не стартовал», и сообщение
обёртки её описывает точно. Ошибка исправлена по замечанию ревью; она стоит
упоминания, потому что тест-план, построенный на ней, проверял бы поведение,
которого не существует.

### Почему это дефект теста, а не среды

Тест записывает путь в формате, который потребитель этого файла заведомо
прочитает иначе. На Linux `/tmp/...` совпал бы с тем, что видит Node, и дефект не
проявился бы — он дожил до Windows именно потому, что там форма пути и её
интерпретация расходятся.

**Классификация:** дефект теста, воспроизводится всегда, от прав и таймингов не
зависит.

### Зависимость от рабочего каталога — вероятное объяснение исходного наблюдения

Разрешение `/tmp/...` идёт относительно **текущего диска**: прогон из каталога на
`C:` даёт `C:\tmp\...`, из каталога на `D:` — `D:\tmp\...`. Если в одном случае
такой каталог существовал, а в другом нет, исход отличался бы **при одном и том
же коде** — и выглядел бы как недетерминированность.

Гипотеза, не факт. Как её проверить — в списке замеров ниже.

## Влияние

- **`/pf-test` (Phase 4) останавливает пайплайн на любом `✗`.** Два стабильных
  падения превращают гейт в шум: красное становится «обычным», и своё падение
  перестаёт отличаться от чужого. Так и вышло в
  `20260806-improve-codereview-convergence`: `manual-test-ui.sh` был единственным
  красным во всех прогонах и каждый раз требовал отдельного доказательства, что
  падение предсуществующее.
- **Восемь проверок изоляции чтения не выполняются на Windows** — молча, как
  побочный эффект недоступного права. Это проверки безопасности: обход каталога,
  сравнение префиксов, доступ к транскриптам сессии.
- **`make test` возвращает 2**, поэтому любой автоматический гейт, завязанный на
  его код возврата, красный на нетронутом дереве.

## Что делать — направление, не реализация

Детали — стадии тест-плана и плана реализации. Здесь фиксируется только то, что
следует из причин.

1. **Разделить фикстуру и проверку симлинка.** Создание ссылки перенести из
   `buildFixture()` в шаг 2 либо обернуть проверкой доступности, и пропускать
   **только** шаг 2 — с явным сообщением о причине пропуска. Остальные восемь
   подпроверок обязаны выполняться. Решение владельца (2026-08-13): пропуск при
   недоступности симлинков — приемлемый исход, это не ошибка.
   **Пропуск обязан быть видимым**, а не молчаливым: пропущенная проверка
   безопасности, которую никто не заметил, хуже красной.
2. **Записывать в `projects.json` путь в форме, которую поймёт читающий
   процесс** — конвертировать перед записью (`cygpath -w` при наличии, либо
   эквивалент), а не подставлять POSIX-строку.

   Два ограничения, без которых это исправление само станет дефектом. **На Linux
   принудительной конвертации быть не должно** — там POSIX-путь и есть нативный,
   и `cygpath` отсутствует; конвертация должна применяться только там, где формы
   расходятся. И **JSON нельзя собирать `printf`-ом**: нативный путь Windows
   содержит обратные слэши, которые в JSON обязаны экранироваться, — нынешняя
   строка уже небезопасна для любого пути с кавычкой или слэшем. Генерировать
   сериализатором либо экранировать явно.
3. **Разделить сообщение шага 4 — как уточнение диагностики, не как исправление
   ошибки.** «Сервер не стартовал» и «сервер стартовал, но не перечислил проект»
   — разные отказы, и объединение их в одну строку заставляет читать лог, чтобы
   понять, какой из двух случился. Здесь реализовалась первая ветка, и сообщение
   было точным; разделение нужно для будущих случаев, а не потому, что оно
   солгало.
4. **Пункт 2 исходного `prompt.md` остаётся в силе** — отличать падение на
   нетронутой ветке от падения, внесённого issue, с явной процедурой. Но теперь
   он опирается не на предполагаемую флакующесть, а на факт: базовый результат
   **стабилен**, поэтому зафиксировать его и сравнивать с ним — выполнимо.

## Открытые вопросы

**Что домерить, чтобы закрыть вопрос о недетерминированности.** Три прогона в
одном окружении для вывода недостаточно (см. смягчённую формулировку выше).
Варьировать по одному:

- **рабочий каталог на другом диске** — прямая проверка гипотезы про разрешение
  ведущего слэша относительно текущего диска;
- **`TMPDIR`** — другое значение и отсутствующее;
- **наличие и отсутствие `C:\tmp` и `D:\tmp`** — если каталог существует и
  содержит постороннее, исход может отличаться от случая, когда его нет;
- **остаточные каталоги от прошлых прогонов** — прогон на «грязном» временном
  каталоге против чистого;
- **серия длиннее трёх** и **параллельная нагрузка** — то, что ловит
  перемежающиеся эффекты, которых короткая тихая серия не видит;
- **два уровня отдельно** — `node --test tools/manual-test-ui/test/*.test.js` и
  полный `bash test/manual-test-ui.sh`: у них разные причины падения, и смешивать
  их в одном замере значит терять различение.

## Закрыто измерением

Два вопроса, которые напрашивались, проверены здесь же, чтобы не уходить с ними в
тест-план как с догадками.

- **`symlinkSync` создаётся ровно в одном месте** — `read-paths.test.js:73`, в
  фикстуре TC-011. Единственное другое упоминание симлинков во всём наборе,
  `test/helpers/snapshot.js:63`, только **читает** цель ссылки для хеша
  (`symlink:${sha256(...)}`) и ничего не создаёт. Значит фикс причины №1 не имеет
  других адресатов.
- **POSIX-путь попадает в файл, читаемый нативным процессом, ровно в одном месте**
  — `test/manual-test-ui.sh:348-350`, запись `projects.json`. Других мест, где
  обёртка пишет shell-путь в конфиг для node, в сьюте нет. Значит фикс причины №2
  локален и не требует сплошного аудита.
