## How to use

Этот чеклист проводит вас по ручной проверке шести сценариев. Всё остальное уже проверено автоматически (726 проверок) — сюда попало только то, что невозможно проверить машиной: живой диалог с ассистентом и работа в настоящей пользовательской среде.

1. Прочитайте весь чеклист до начала работы, чтобы понимать, что вас ждёт.
2. Выполните общую подготовку (ниже) — без неё ни один тест не пройдёт.
3. Выполняйте шаги по порядку. После каждого сверьте фактическое поведение с колонкой «Expected Result» и запишите, что произошло на самом деле, в колонку «Result».
4. Ставьте `[x]`, если шаг отработал как ожидалось, и оставляйте `[ ]`, если что-то пошло не так.
5. В строке «Notes» внизу каждого теста записывайте всё необычное — даже если тест в целом прошёл.
6. Закончив, верните документ разработчику.

## TC-000: Подготовка окружения

**Что здесь проверяется, в двух словах.** Есть команда, которая приводит любой проект к актуальной версии рабочего процесса — неважно, начинали вы с пустого каталога, со старой версии или с наполовину обновлённой. И есть ассистент, который подсказывает следующий шаг работы над задачей. Раньше ассистент считал шаг выполненным просто потому, что нужный файл существует — даже если внутри файла была одна строчка-заглушка. Из-за этого он мог отправить вас писать код по плану, которого на самом деле нет. Вы проверяете, что это больше не случается.

**Prerequisites:**
- Терминал, открытый в каталоге проекта `planning-framework`
- Активна ветка этой работы (`issue/20260713-bug-v2-to-v3-migration-defects`)

**Steps:**

| Step | Action | Expected Result | Result |
|------|--------|-----------------|--------|
| 1 | **Резервная копия.** `cp -r ~/.claude/skills ~/.claude/skills.backup-$(date +%F)` и `cp ~/.claude/bin/pf ~/.claude/bin/pf.backup-$(date +%F)` | Копии созданы. **Не пропускайте:** тесты TC-049 и TC-050 работают с вашей настоящей папкой `~/.claude/`, а не с временной | [x] |
| 2 | **Свежие подсказки ассистента.** `bash scripts/update-skills.sh` | Скилы обновлены. Без этого ассистент работает по старым правилам и **все тесты покажут старое (неверное) поведение** | [x] |
| 3 | **Три тестовых проекта — по ОДНОМУ открытому issue в каждом.** См. блок команд под таблицей | Каталоги созданы | [x] |
| 4 | **Привести все три к актуальной версии:** `bash scripts/converge-to-v3.sh --target /tmp/proj-X --yes` для X = A, B, C | Все три завершились сообщением «Converge complete» | [x] |
| 5 | `ls /tmp/proj-A/docs/issues/open/` | Ровно **один** каталог: `20250102-bug-beta`. Внутри — `analysis.md`, `implementation_plan.md`, `prompt.md`; файла `test_plan.md` **нет**. Это исходные данные TC-045 | [x] |
| 6 | `cat /tmp/proj-B/docs/issues/open/20250101-feat-alpha/test_plan.md` | Ровно **один** открытый issue, и внутри его плана проверок — одна строчка `> TODO: Run /pf-test-plan to generate this file.` Это и есть заглушка, на которой ассистент раньше ошибался | [x] |

**Команды для шага 3:**

```bash
cd <каталог planning-framework>
rm -rf /tmp/proj-A /tmp/proj-B /tmp/proj-C

# A — bug-сценарий (TC-045): оставляем только bug-beta
cp -r test/fixtures/v2-project /tmp/proj-A
rm -rf /tmp/proj-A/planning/issues/open/20250101-feat-alpha

# B — заглушка, ответ medium (TC-046): оставляем только feat-alpha, у неё заглушка
cp -r test/fixtures/v2-with-stub /tmp/proj-B
rm -rf /tmp/proj-B/planning/issues/open/20250102-bug-beta

# C — заглушка, ответ trivial (TC-047): то же, что B
cp -r test/fixtures/v2-with-stub /tmp/proj-C
rm -rf /tmp/proj-C/planning/issues/open/20250102-bug-beta
```

**Notes:**

**Почему из каждого проекта убирается лишний issue.** Фикстуры содержат по два открытых issue. Ассистент при нескольких открытых issue останавливается и спрашивает «какой из них?» — и до проверки маршрутизации дело просто не доходит. Каждому тесту нужен ровно один открытый issue. *(Это ошибка первой редакции чеклиста, найденная тестировщиком.)*

**Проекты B и C — копии друг друга.** Различаются только тем, что вы ответите на вопрос о размере задачи: в B — `medium`, в C — `trivial`. Именно ответ `trivial` вскрывает самую опасную дыру, поэтому проект отдельный: после TC-046 файлы в B изменятся и для TC-047 уже не годятся.

**Если шаг 4 завершится текстом «Converge cancelled — stdin is closed»** — это **не** сбой: команда намеренно отказывается работать, когда её запускают без терминала и без явного согласия. Добавьте `--yes`, как в команде выше.

**Каждый тест портит свой проект.** Если понадобится перепройти тест — пересоздайте его проект командами из шага 3, иначе исходные данные уже не те.

## TC-048: Существующий файл не блокирует работу насмерть

**Prerequisites:**
- Любой из подготовленных проектов, где уже есть файл плана работ
- Открыта сессия Claude Code в нём

**Steps:**

| Step | Action | Expected Result | Result |
|------|--------|-----------------|--------|
| 1 | Введите `/pf-impl-plan` при уже существующем файле плана | Ассистент **не** останавливается с отказом, а предлагает выбор: перегенерировать / оставить / отменить | [x] |
| 2 | Выберите «оставить» | Файл не изменился, ошибки нет | [x] |
| 3 | Повторите и выберите «перегенерировать» | Файл перезаписан заново | [x] |
| 4 | Повторите и выберите «отменить» | Файл не изменился, показано сообщение об отмене | [x] |
| 5 | Проделайте то же для `/pf-test-plan`, `/pf-brd`, `/pf-spec` | Везде тот же выбор из трёх вариантов | [x] |
| 6 | Удалите план проверок и введите `/pf-impl-plan` | Здесь ассистент **обязан** отказаться: нельзя строить план работ без плана проверок | [ ] |
| 7 | Удалите план работ и введите `/pf-execute` | Тоже отказ | [ ] |

**Notes (заметка тестировщика):** AI не заметил, что test plan удален сразу. AI не заметил, что impl plan удален сразу.

> **Шаги 6 и 7 ПРОВАЛЕНЫ** — отмечены `[ ]`, хотя изначально были помечены пройденными. Заметка тестировщика описывает именно провал: гейты обязаны были отказать при удалённом документе и не отказали.
>
> **Диагноз.** Инструкция гейта была написана верно («документ обязан существовать… **stop**»), но это была **проза без единого обязательного вызова инструмента**. В живой сессии удалённый файл всё ещё лежал в контексте модели, и она отвечала по памяти, а не по диску. Показателен контраст с соседним oversized-guard в тех же скилах: он предписывает **механический счёт** (`wc -l`, подсчёт заголовков) — и работает именно поэтому.
>
> Это тот же провал, что чинит весь issue («стадия засчитана без проверки»), перенесённый с «файл-заглушка» на «файла больше нет».
>
> **Исправлено:** в общее определение «стадия завершена» (`pf-size-tiers`) добавлен раздел «Evaluating it is a MECHANICAL check, never a memory exercise» с обязательным `ls -1 docs/issues/open/<ID>/` перед любым суждением; оба входных гейта (`pf-impl-plan`, `pf-execute`) теперь предписывают этот вызов **первым действием**. Пять новых статических проверок в `test/skills-static.sh` не дают потерять принуждение при следующей правке.
>
> **Требуется перепрогон шагов 6-7** после `bash scripts/update-skills.sh` — статический тест доказывает, что принуждение записано, но что модель ему **подчиняется**, может подтвердить только живой прогон.
