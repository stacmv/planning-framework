# BRD: Глобальный чек-лист ручных тестов

**Issue:** 20260806-feat-product-test-plan
**Тип:** feat · **Tier:** medium
**Источник:** `prompt.md` + уточнение объёма владельцем (2026-08-11)

---

## Problem Statement

Ручные тест-кейсы живут только внутри issue. После закрытия папка уезжает в
`docs/issues/closed/`, и набор перестаёт существовать как знание о продукте:

- перед релизом нечего открыть и пройти — кейсы рассыпаны по десяткам закрытых
  папок, каждая со своей нумерацией `TC-NNN` с нуля;
- невыполненный ручной тест просто исчезает вместе с папкой. Наблюдалось
  трижды: `20260731-feat-pluggable-reviewers` (чек-лист пуст),
  `20260715-bug-gates-verification-and-tooling-fixes` (закрыт с невыполненными
  TC-002/TC-003), `20260703-improve-scale-doc-complexity` (20 кейсов, судьба
  неизвестна).

## Goals

Один файл, по которому можно прогнать релиз руками — в дополнение к автотестам,
которые гоняются `make test`. Ручные кейсы попадают в него из issue
автоматически, чтобы список не приходилось вести вручную.

## Non-Goals

Всё, что не нужно для чтения и прохождения чек-листа:

- блокирующие гейты закрытия issue по невыполненным тестам;
- фиксация того, кто именно выполнил кейс — человек или агент;
- автоматический отбор регрессии при планировании новой issue;
- дедупликация и схлопывание кейсов, перекрытых автотестами;
- перенос кейсов из ранее закрытых issue (см. Open Questions);
- изменения в Manual Test UI и в стадиях, предшествующих закрытию.

Ограничение объёма сознательное: сначала артефакт, который приносит пользу сам
по себе. Механика вокруг него — отдельными issue, если понадобится.

## User Stories

### US-1 — Прогнать релиз по одному списку

**Как** владелец, **я хочу** открыть один файл со всеми ручными кейсами
продукта, **чтобы** пройти их перед релизом, не разыскивая по закрытым issue.

**Acceptance Criteria:**
- AC-1.1 Существует `docs/planning/test-plan.md` со всеми ручными кейсами.
- AC-1.2 Кейс читается самостоятельно: понятно, что проверять, без открытия
  issue-источника.
- AC-1.3 У кейса виден приоритет — можно пройти только критичное, если времени
  мало.
- AC-1.4 Виден статус и дата последнего прогона.

### US-2 — Кейсы попадают в список сами

**Как** владелец, **я хочу**, чтобы ручные кейсы уезжали в общий список при
закрытии issue, **чтобы** не вести его руками и не терять кейсы.

**Acceptance Criteria:**
- AC-2.1 При закрытии issue её `Manual`-кейсы добавляются в общий список.
- AC-2.2 У каждого — глобальный номер `PTC-NNNN`, уникальный в пределах
  проекта.
- AC-2.3 Сохраняется ссылка на issue-источник.
- AC-2.4 Кейс, не выполненный в своей issue, приезжает со статусом «не
  выполнялся», а не теряется.

### US-3 — Отметить результат прогона

**Как** владелец, **я хочу** отмечать в списке результат прохождения,
**чтобы** при следующем релизе видеть, что уже проверено, а что нет.

**Acceptance Criteria:**
- AC-3.1 Статус правится вручную в файле.
- AC-3.2 Словарь статусов минимален и однозначен.
- AC-3.3 Кейс, потерявший смысл после изменения продукта, можно снять, не
  удаляя строку — чтобы номер не переиспользовался.

---

## Business Rules

| # | Правило |
|---|---|
| BR-1 | В общий список попадают только кейсы типа `Manual`. Автотесты гоняет `make test`. |
| BR-2 | `PTC-NNNN` уникален в пределах проекта и не переиспользуется. |
| BR-3 | Локальные `TC-NNN` внутри issue не переименовываются. |
| BR-4 | Файл правится руками; формат обязан это переживать. |

---

## Acceptance (issue level)

1. После закрытия issue с ручными кейсами они видны в
   `docs/planning/test-plan.md` с номерами, приоритетом и ссылкой на источник.
2. По этому файлу можно пройти релизную проверку, ничего больше не открывая.
3. Невыполненный ручной кейс не исчезает при закрытии issue.
