# Test Plan: 20260729-improve-manual-test-data-and-role-explorer

## Overview & Objectives

Issue состоит из двух равнозначных частей, и план покрывает обе сопоставимо.

**Часть A — подготовка тестового кейса.** Ручной тест-кейс должен приводиться
в готовое к прогону состояние одним действием: `/pf-test-plan` объявляет
требуемые данные в поле **Test Data**, `/pf-test` порождает
`docs/issues/<status>/<ID>/test-data/` (фикстуры под git + идемпотентный
`setup.mjs`), Manual Test UI даёт действие подготовки на issue целиком и на
отдельный кейс. Ключевое ограничение — подготовка не оставляет следов в
репозитории: рабочая копия разворачивается вне репозитория, чтобы `checkout`
в UI и `/pf-qa` не падали на проверке грязного дерева.

**Часть B — ролевой project explorer.** UI становится role-first: три вкладки
верхнего уровня (аналитик, разработчик, тестировщик), чек-лист — один из
экранов вкладки QA. Всё, кроме трёх явно перечисленных изменяющих действий,
строго read-only. Рендеринг markdown — свой, без npm-зависимостей, с
обязательной поддержкой таблиц.

**Цели плана:**

1. Доказать все критерии приёмки AC-01a…AC-06d из `brd.md`.
2. Отдельно закрыть требование US-03 — «после подготовки `git status
   --porcelain` пуст», потому что именно эта регрессия ломает закрытие issue.
3. Отдельно закрыть US-05 — перечень изменяющих действий исчерпывающий; это
   проверяется негативно, перебором остальных путей.
4. Подтвердить сохранность существующего поведения чек-листа (US-06) и
   отсутствие новых зависимостей.

Приоритет отдан автоматической проверке: ручными оставлены только три кейса,
где предметом является человеческое восприятие — вёрстка, читаемость и
удобство навигации.

## Prerequisites

- Рабочая копия `planning-framework` на ветке issue, дерево чистое
  (`git status --porcelain` пуст) — иначе часть кейсов про чистоту репозитория
  не отличит свой результат от постороннего шума.
- Node.js той же мажорной версии, что требуется для `make test-ui`; никаких
  `npm install` — их отсутствие само является предметом проверки (TC-018).
- Точки входа для автотестов:
  - `make test` — `test/*.sh` (включая `test/skills-static.sh`) +
    `node --test tools/onboarding-tui/test/*.test.js`;
  - `node --test tools/manual-test-ui/test/*.test.js` — тесты самого UI;
    **сегодня они не входят в `make test`** (см. Known Issues), поэтому
    запускаются отдельной командой.
- Для кейсов, поднимающих сервер: свободный порт (по умолчанию 4317, при
  занятости — `--port`), и собственный `PLANNING_TEST_UI_CONFIG`, указывающий
  на временный `projects.json` с фикстурными репозиториями. Реальный
  `tools/manual-test-ui/projects.json` в тестах не используется — он
  per-machine и gitignored.
- Фикстурные репозитории для тестов создаются во временном каталоге
  (`os.tmpdir()`) как настоящие git-репозитории (`git init`, коммит на
  `develop`, при необходимости ветка `issue/<ID>`) — только так проверяются
  ветки, `git ls-tree` и гард на грязное дерево.
- Для кейсов про память — подставной корень `~/.claude/projects/...`,
  задаваемый через переменную окружения или конфигурацию, а не реальный
  домашний каталог тестировщика.

### TC-001: Каждый ручной тест-кейс объявляет требуемые ему данные

**Description:** Проверяет AC-01a и AC-01d — связь «тест-кейс ↔ требуемые ему
данные» существует и доступна инструменту из чек-листа. Без объявленных данных
невозможно ни подготовить отдельный кейс, ни понять, где подготовка не нужна.
Проверяется и граница ответственности: прозаические предусловия (поднять
сервис, завести учётную запись) в требуемые данные не попадают.

**Preconditions:**
- `skills/pf-test-plan/SKILL.md` и `skills/pf-test/SKILL.md` в состоянии после
  реализации issue.
- Фикстура чек-листа с Manual-кейсами, среди которых есть кейс с данными и
  кейс без данных.

**Steps:**

| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Запустить `bash test/skills-static.sh`. | Exit 0. Проверка подтверждает, что `pf-test-plan/SKILL.md` предписывает заполнять **Test Data** для каждого Manual TC, а не оставлять поле пустым. |
| 2 | Запустить статическую проверку `pf-test/SKILL.md`: скил обязан переносить объявленные данные кейса в порождаемый чек-лист. | Совпадение найдено; инструкция про перенос присутствует. |
| 3 | Прогнать парсер `lib/checklist.js` на фикстуре чек-листа с объявленными данными. | Для кейса с данными парсер возвращает непустой перечень требуемых данных; для кейса без данных — явный признак «данные не требуются», а не `undefined`. |
| 4 | Прогнать парсер на кейсе, где в предусловиях только прозаический текст («поднять сервис X»). | Прозаический текст остаётся в предусловиях и НЕ попадает в перечень требуемых данных. |

**Test Data:**
- Фикстура `tools/manual-test-ui/test/fixtures/` — чек-лист с тремя Manual TC:
  (1) с объявленными файлами/фикстурами, (2) с явной пометкой «данные не
  требуются», (3) только с прозаическими предусловиями.
- Файлы скиллов `skills/pf-test-plan/SKILL.md`, `skills/pf-test/SKILL.md`.

**Expected Outcome:** Требуемые данные объявляются на этапе тест-плана,
доезжают до чек-листа и извлекаются оттуда инструментом; прозаические
предусловия предметом подготовки не становятся.

**Priority:** Critical

### TC-004: Идемпотентность повторной подготовки и изоляция кейсов

**Description:** Проверяет AC-02a, AC-02b, AC-02c. Кнопка «Подготовить» — это
же кнопка «Сбросить»: каждый запуск приводит кейс в заданное состояние с нуля,
независимо от того, что успело измениться в рабочей копии. Отдельного teardown
нет, ручной чистки от тестировщика не требуется. Сброс одного кейса не трогает
данные остальных.

**Preconditions:**
- Фикстурный issue минимум с двумя кейсами, у каждого свои данные.

**Steps:**

| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Подготовить TC-001, снять слепок дерева рабочей копии (пути + содержимое). | Слепок S1 получен. |
| 2 | Испортить рабочую копию: изменить файл, удалить файл, создать лишний файл. | Дерево отличается от S1. |
| 3 | Повторно подготовить TC-001. | Ошибки нет; операция завершается успешно. |
| 4 | Снять слепок повторно и сравнить с S1. | Слепки идентичны: изменённый файл восстановлен, удалённый создан заново, лишний файл удалён. |
| 5 | Подготовить TC-002, затем снова подготовить TC-001. | Рабочая копия TC-002 после повторной подготовки TC-001 не изменилась (слепок TC-002 совпадает с исходным). |
| 6 | Выполнить подготовку TC-001 трижды подряд без изменений между запусками. | Все три запуска успешны, итоговое дерево каждый раз равно S1. |
| 7 | Проверить, что тестировщику не потребовалось ни одной ручной операции чистки между шагами 2 и 4. | Восстановление полностью выполнено самим действием подготовки. |

**Test Data:**
- Фикстурный issue с данными TC-001 (несколько файлов во вложенных каталогах,
  включая пустой каталог и файл с не-ASCII содержимым) и данными TC-002.

**Expected Outcome:** Испорченный прогон возвращается в исходное состояние
одним действием, и это действие точечно — соседние кейсы не затрагиваются.

**Priority:** Critical

### TC-005: Подготовка не меняет состояние репозитория

**Description:** Проверяет AC-03a и AC-03b — самое дорогое требование issue.
Если подготовка оставляет файлы внутри репозитория, рабочее дерево становится
грязным: UI отказывает в `checkout`, а `/pf-qa` падает на своей обязательной
проверке `git status --porcelain`. Отсюда решение — рабочая копия
разворачивается во временном каталоге вне репозитория, а сами фикстуры и
скрипт коммитит та стадия пайплайна, которая их создала.

**Preconditions:**
- Фикстурный git-репозиторий с зафиксированным issue-каталогом; дерево чистое.

**Steps:**

| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Зафиксировать `git status --porcelain` до подготовки. | Вывод пуст. |
| 2 | Подготовить весь issue, затем отдельный кейс, затем повторно — суммарно не менее пяти запусков вперемежку. | Все запуски успешны. |
| 3 | Повторно выполнить `git status --porcelain`. | Вывод по-прежнему пуст: ни untracked, ни modified. |
| 4 | Проверить путь развёрнутой рабочей копии на принадлежность репозиторию. | Путь лежит вне корня репозитория (во временном каталоге системы); `path.relative(repoRoot, workdir)` начинается с `..`. |
| 5 | Испортить рабочую копию, перезапустить подготовку, снова проверить `git status --porcelain`. | Вывод пуст. |
| 6 | На чистом дереве выполнить сценарий UI: переключение на ветку issue (`checkout`) после серии подготовок. | Переключение проходит; отказа `dirty_working_tree` нет. |
| 7 | Проверить, что `test-data/` (фикстуры + `setup.mjs`) отслеживается git и зафиксирован. | `git ls-files` показывает файлы `test-data/`; после стадии, их создавшей, дерево чистое. |

**Test Data:**
- Фикстурный git-репозиторий: ветка `develop` с issue-каталогом, ветка
  `issue/<ID>` с чек-листом и `test-data/`.
- Никаких данных вне репозитория до старта кейса — временный каталог рабочей
  копии должен быть создан самим действием подготовки.

**Expected Outcome:** Сколько бы подготовок и прогонов ни было выполнено,
репозиторий с точки зрения git не меняется; переключение веток и проверка
качества не блокируются.

**Priority:** Critical

  `.qa-workflow.md`.
- Сервер поднят на фикстурной конфигурации.

**Steps:**

| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Запросить перечень ролей. | Ровно три роли: аналитик, разработчик, тестировщик. |
| 2 | Запросить наполнение роли «аналитик». | Присутствуют: исходная постановка, требования, разбор проблемы, рабочие заметки, конфигурация фреймворка, зафиксированные архитектурные решения. |

**Expected Outcome:** Каждый документ доступен из той роли, которой он нужен
по ходу работы; переключение ролей ничем не ограничено.

**Priority:** Critical

### TC-007: Состояния документа — неприменим, отсутствует со стадией, только на ветке

**Description:** Проверяет AC-04g и AC-04h. Документ, не порождаемый пайплайном
для данного типа и тира issue, помечается как **неприменимый**. Порождаемый,
но ещё не созданный — как **отсутствующий**, с указанием стадии, которая его
создаёт. Документ, существующий только на ветке issue, показывается только для
чтения, с предложением переключиться на ветку по явному подтверждению; действие
подготовки для такого issue доступно только после переключения.

**Preconditions:**
- Фикстурные issue: improve-issue (для него `specs.md` не порождается),
  feat-issue без `qa_report.md`, issue с документом только на ветке
  `issue/<ID>`.

**Steps:**

| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Открыть improve-issue, роль «разработчик», документ `specs.md`. | Помечен как **неприменимый**; сообщения «отсутствует» нет, пустого экрана нет. |
| 2 | Открыть feat-issue, роль «тестировщик», отчёт о качестве. | Помечен как **отсутствующий**, с указанием стадии, которая его создаёт (`/pf-qa`). |

### TC-019: Правило приоритета видимости действия подготовки

**Description:** Проверяет AC-06c — правило из трёх случаев, с явным
приоритетом. Если про кейс известно, что данные ему не нужны, действие не
предлагается. Если известно, что нужны, но не подготовлены — действие видно и
недоступно, с пояснением. Если неизвестно (issue создан до появления этой
возможности) — трактуется как второй случай. Третий случай важнее прочих:
легаси-issue не должны выглядеть сломанными.

**Preconditions:**
- Три фикстурных issue: с кейсом без потребности в данных; с кейсом, которому
  данные нужны и объявлены; легаси-issue без каталога `test-data/` и без
  объявленных данных в чек-листе.

**Steps:**

| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Открыть TC, про который известно, что данные не нужны. | Действие подготовки не предлагается вовсе; сообщения об ошибке нет. |
| 2 | Открыть TC с объявленными, но не подготовленными данными. | Действие видно и доступно к запуску (или недоступно с пояснением, если запуск невозможен) — но никогда не скрыто молча. |
| 3 | Открыть TC легаси-issue, где про данные ничего не известно. | Действие видно и недоступно, с пояснением причины — как во втором случае. |
| 4 | Убедиться, что легаси-issue открывается и его чек-лист полностью работоспособен. | Отметки и заметки работают; отсутствие `test-data/` ничего не ломает. |
| 5 | Проверить приоритет: кейс, у которого объявлено «данные не требуются», но каталог `test-data/` у issue есть. | Побеждает знание о кейсе: действие для этого TC не предлагается. |
| 6 | Проверить действие на уровне issue целиком для легаси-issue. | Видно и недоступно, с тем же пояснением; 500 и пустого экрана нет. |
| 7 | Проверить кейс с объявленными данными в issue, у которого `test-data/setup.mjs` отсутствует. | Действие видно и недоступно, пояснение указывает на отсутствие скрипта подготовки. |

**Test Data:**
- `fixture-nodata/` — чек-лист, где TC явно помечен как не требующий данных;
  каталог `test-data/` присутствует (для шага 5).

- `fixture-declared-noscript/` — объявленные данные без `setup.mjs`.

**Expected Outcome:** Правило приоритета соблюдается во всех четырёх
конфигурациях; ни одна из них не приводит к молчаливой пустоте или ошибке.

**Priority:** High

### TC-020: Закрытый issue, переносимость данных и второй настроенный проект

**Description:** Проверяет AC-03c, AC-04i и AC-06d — три краевых условия,

  `test-data/`.

| 6 | Выбрать посторонний проект и открытый issue в нём; пройти по трём ролям. | Наполнение ролей, состояния документов и рендеринг работают так же, как для основного проекта. |
| 7 | Выполнить подготовку кейса в постороннем проекте. | Отрабатывает; рабочая копия развёрнута вне обоих репозиториев; `git status --porcelain` пуст в обоих. |

| 9 | Проверить проект без единого issue и проект, не являющийся git-репозиторием. | Внятное сообщение вместо ошибки; инструмент остаётся работоспособным для остальных проектов. |

**Test Data:**
- Фикстурная конфигурация `projects.json` с тремя записями: основной проект,
  посторонний проект с открытым и закрытым issue (у обоих `test-data/`),
  каталог без git.
- Свежий клон фикстурного репозитория во временный каталог — для шага 5.
- Закрытый issue `docs/issues/closed/<ID>/` с полным `test-data/` под git.

**Expected Outcome:** Инструмент одинаково работает для любого настроенного
проекта и для закрытых issue; данные кейса переживают закрытие issue и смену
машины.

**Priority:** High
