# Test Plan: 20260729-improve-manual-test-data-and-role-explorer

## Overview & Objectives

Issue состоит из двух равнозначных частей, и план покрывает обе сопоставимо.

**Часть A — подготовка тестового кейса.** Ручной тест-кейс должен приводиться
в готовое к прогону состояние одним действием: `/pf-test-plan` объявляет
требуемые данные в поле **Test Data**, `/pf-test` порождает
`docs/issues/<status>/<ID>/test-data/` (фикстуры под git + идемпотентный
`setup.mjs`), Manual Test UI даёт действие подготовки на issue целиком и на
отдельный кейс. Ключевое ограничение — подготовка не оставляет следов в
репозитории: рабочая копия разворачивается вне репозитория, чтобы `checkout`
в UI и `/pf-qa` не падали на проверке грязного дерева.

**Часть B — ролевой project explorer.** UI становится role-first: три вкладки
верхнего уровня (аналитик, разработчик, тестировщик), чек-лист — один из
экранов вкладки QA. Всё, кроме трёх явно перечисленных изменяющих действий,
строго read-only. Рендеринг markdown — свой, без npm-зависимостей, с
обязательной поддержкой таблиц.

**Цели плана:**

1. Доказать все критерии приёмки AC-01a…AC-06d из `brd.md`.
2. Отдельно закрыть требование US-03 — «после подготовки `git status
   --porcelain` пуст», потому что именно эта регрессия ломает закрытие issue.
3. Отдельно закрыть US-05 — перечень изменяющих действий исчерпывающий; это
   проверяется негативно, перебором остальных путей.
4. Подтвердить сохранность существующего поведения чек-листа (US-06) и
   отсутствие новых зависимостей.
5. Обеспечить, что автоматические кейсы этого issue вообще могут получить
   вердикт: сегодня `make test` не запускает node-тесты Manual Test UI, и
   расширение цели `test` входит в объём issue (TC-016).

Приоритет отдан автоматической проверке. Ручных кейсов два, и они разные по
природе: TC-019 — восприятие (вёрстка, читаемость, отсутствие полей правки),
TC-020 — сквозной функциональный сценарий, который остаётся ручным потому,
что проходит через браузер и файловый менеджер, а браузерную инфраструктуру
тестирования issue не заводит.

## Prerequisites

- Рабочая копия `planning-framework` на ветке issue, дерево чистое
  (`git status --porcelain` пуст) — иначе часть кейсов про чистоту репозитория
  не отличит свой результат от постороннего шума.
- Node.js той же мажорной версии, что требуется для `make test-ui`; никаких
  `npm install` — их отсутствие само является предметом проверки (TC-015).
- **Единственная точка входа для автоматических проверок — `make test`.**
  Сегодня цель `test` гоняет `test/*.sh` и `node --test` только по
  `tools/onboarding-tui/test/*.test.js`. Расширение цели на
  `tools/manual-test-ui/test/*.test.js` — требование этого issue (TC-016): без
  него ни один Auto-кейс не попадёт в вывод `/pf-test`, Status Tracker
  останется незаполненным и гейт `.qa-workflow.md` не пропустит issue к
  закрытию.
- **Где живут новые проверки.** Всё новое автоматическое размещается только в
  новом bash-сьюте `test/manual-test-ui.sh` и в
  `tools/manual-test-ui/test/*.test.js`. `test/lib.sh` и `test/converge-*.sh`
  этим issue **не изменяются**: они уже содержат литералы `TC-001…TC-020` в
  собственных значениях, а `/pf-test` (Phase 3.2) сканирует любой изменённый
  тестовый файл на такие литералы и построил бы ложное соответствие.
- **Архитектурные требования, делающие кейсы проверяемыми без браузера**
  (браузерную инфраструктуру issue не заводит — AC-06b):
  - соответствие «роль → документы» отдаёт **сервер через API**; клиент только
    отображает ответ и собственного перечня документов не содержит;
  - markdown-рендерер и модуль ролевого соответствия оформлены как модули,
    загружаемые и из Node (`node --test`), и из браузера; при загрузке они не
    обращаются к `document`/`window`.
- Конфигурация для кейсов, поднимающих сервер: свободный порт (по умолчанию
  4317, при занятости — `--port`) и собственный `PLANNING_TEST_UI_CONFIG`,
  указывающий на временный `projects.json` с фикстурными репозиториями.
  Реальный `tools/manual-test-ui/projects.json` в автотестах не используется —
  он per-machine и gitignored; для ручных кейсов он создаётся из
  `projects.json.example` (без него `make test-ui` отказывает).
- Фикстурные репозитории создаются во временном каталоге (`os.tmpdir()`) как
  настоящие git-репозитории (`git init`, коммит на `develop`, при
  необходимости ветка `issue/<ID>`). Ограничения фикстур:
  - ID issue обязаны соответствовать `^[0-9]{8}-(feat|improve|bug)-[a-z0-9-]+$`
    (валидатор `server.js:22`), иначе сервер отвергнет их до всякой проверки;
  - git не хранит пустых каталогов: где нужен «пустой» каталог, фикстура
    содержит `.gitkeep`; issue, документы которого лежат только на ветке,
    обязан иметь на `develop` хотя бы один зафиксированный файл (`prompt.md`),
    иначе его каталог не появится в `git ls-tree` и issue не будет перечислен.
- Корень памяти подставляется переменной окружения. Фикстура повторяет
  фактическую раскладку машины: `<memRoot>/projects/<slug>/memory/*.md`
  (включая `MEMORY.md`, если он лежит там), а рядом с `memory/` — транскрипты
  `*.jsonl` и `sessions-index.json`. Отдельного `MEMORY.md` уровнем выше на
  машине разработки нет, и ни один шаг на нём не строится.

### TC-004: Подготовка не меняет состояние репозитория; данные переносимы

**Description:** Проверяет AC-03a, AC-03b, AC-03c — самое дорогое требование
issue. Если подготовка оставляет файлы внутри репозитория, рабочее дерево
становится грязным: UI отказывает в `checkout`, а `/pf-qa` падает на своей
обязательной проверке `git status --porcelain`. Отсюда решение — рабочая копия
разворачивается вне репозитория, а исходные фикстуры и скрипт лежат под git и
поэтому сопровождают issue после закрытия и на другой машине.

**Preconditions:**
- Раннер — `node --test tools/manual-test-ui/test/prepare-repo-state.test.js`.
- Фикстурный git-репозиторий с зафиксированным issue-каталогом; дерево чистое.

**Steps:**

| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Зафиксировать `git status --porcelain` до подготовки. | Вывод пуст. |
| 2 | Выполнить не менее пяти запусков вперемежку: issue целиком, отдельный кейс, повтор того же кейса. | Все запуски успешны. |
| 3 | Повторно выполнить `git status --porcelain`. | Вывод по-прежнему пуст: ни untracked, ни modified. |
| 4 | Проверить путь развёрнутой рабочей копии на принадлежность репозиторию. | `path.relative(repoRoot, workdir)` начинается с `..`; путь лежит внутри `os.tmpdir()`. |
| 5 | Испортить рабочую копию, перезапустить подготовку, снова снять `git status --porcelain`. | Вывод пуст. |
| 6 | Выполнить `git ls-files docs/issues/open/<ID>/test-data/`. | Перечислены `setup.mjs` и все файлы фикстур — они под git, а не порождаются на лету. |
| 7 | Перенести issue-каталог в `docs/issues/closed/<ID>/` отдельным коммитом, сделать свежий клон репозитория во временный каталог и выполнить в клоне `node docs/issues/closed/<ID>/test-data/setup.mjs`. | Exit 0, данные развёрнуты без дополнительных шагов: они пережили и закрытие issue, и перенос на «другую машину». |

**Test Data:**
- Фикстурный git-репозиторий: ветка `develop` с закоммиченным
  `docs/issues/open/20260107-feat-fixture-twocases/` целиком (включая
  `test-data/`).
- Второй каталог назначения для `git clone --local` — пустой временный
  каталог, создаётся кейсом.
- Никаких данных вне репозитория до старта кейса: временный каталог рабочей
  копии обязан быть создан самим действием подготовки.

**Expected Outcome:** Сколько бы подготовок ни было выполнено, репозиторий с
точки зрения git не меняется, а исходные данные кейса сопровождают issue после
закрытия и переносятся вместе с клоном.

**Priority:** Critical

### TC-005: Отчёт о результате подготовки — успех, неуспех, таймаут

**Description:** Проверяет AC-01e с обеих сторон. При успехе сообщается, что
подготовлено, где это находится и чем закончилось. При неуспехе сообщается
причина, и кейс не остаётся в наполовину подготовленном виде — иначе
тестировщик начнёт прогон на битых данных и спишет провал на продукт.
Проверяется и таймаут: зависший скрипт не должен подвешивать инструмент.

**Preconditions:**
- Раннер — `node --test tools/manual-test-ui/test/prepare-report.test.js`.
- Сервер поднят на фикстурной конфигурации; таймаут подготовки в тестовой
  конфигурации укорочен (2 с), чтобы кейс не занимал минуты.

**Steps:**

| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Выполнить успешную подготовку. | В ответе: перечень подготовленного, путь рабочей копии, stdout, stderr, код возврата 0. |
| 2 | Выполнить подготовку скриптом, падающим на середине. | Ответ помечен как неуспех и содержит причину: текст из stderr и ненулевой код возврата. |

### TC-019: Внешний вид разделов по ролям, навигация и читаемость документов

**Description:** Проверяет вёрстку, читаемость и ощущение навигации — то, что
автоматическая проверка подтвердить не может. Разделы по ролям должны
читаться как верхний уровень приложения, а не как второй список внутри окна.
Отдельно проверяется, что широкие таблицы в отформатированном виде остаются
читаемыми и что нигде, кроме страницы проверки вручную, нет полей ввода.

  запуска отказывает.
- Никаких команд установки пакетов перед запуском не выполнялось.
- В браузере открыт адрес, который инструмент печатает при старте; размер окна

### TC-020: Подготовка данных одним действием и прогон проверки с первого шага

**Description:** Проверяет главную цель issue глазами адресата: владелец
проекта в роли тестировщика берёт проверку, нажимает подготовку и начинает
прогон, не обращаясь к разработчику. Автоматические кейсы подтверждают каждый
механизм по отдельности; этот кейс подтверждает, что из них складывается
работающий сценарий, — он проходит через браузер и файловый менеджер, поэтому
остаётся ручным.

**Preconditions:**
- Инструмент запущен, в нём выбраны проект и задача, у которой есть страница
  проверки вручную и каталог с исходными данными для проверок.
- Рабочая копия проекта уже приведена в состояние, в котором эта страница
  доступна для правки (иначе инструмент предложит перевести её и попросит
  подтверждение).
- Данные проверок заранее не разворачивались: каталога, путь к которому
  печатает действие подготовки, ещё не существует.

**Steps:**

| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Открыть раздел тестировщика и выбрать проверку, для которой перечислены нужные ей файлы. | Действие подготовки видно и доступно. |
| 2 | Нажать подготовку для одной проверки. | Сначала запрашивается подтверждение; без него ничего не выполняется. |
| 3 | Подтвердить и дождаться завершения. | Показаны итог, путь к развёрнутым данным, вывод скрипта и код возврата; понятно без чтения исходников, чем всё закончилось. |
| 4 | Открыть указанный путь в файловом менеджере или терминале. | Все перечисленные для этой проверки файлы на месте, содержимое непустое. |
| 5 | Выполнить первый шаг выбранной проверки по её описанию. | Шаг выполним сразу; обращаться к разработчику за подготовкой среды не потребовалось. |
| 6 | Удалить один из подготовленных файлов и нажать подготовку повторно. | Данные вернулись в исходное состояние; ручной чистки не потребовалось. |
| 7 | Отметить шаг как пройденный, написать заметку и перезагрузить страницу. | Отметка и заметка на месте; страница проверки открывается внутри раздела тестировщика. |
| 8 | Нажать подготовку для задачи целиком. | Подготовлены данные всех проверок задачи; отметки и заметки при этом не изменились. |

**Test Data:**
- Задача `20260729-improve-manual-test-data-and-role-explorer` этого проекта:
  каталог `test-data/` с `setup.mjs` и исходными файлами двух ручных
  проверок — TC-019 и TC-020, не меньше двух файлов на проверку (для TC-019 —
  копия конфигурации из двух записей и документ с широкой таблицей; для
  TC-020 — два текстовых файла по 2–3 строки).
- `manual_test_checklist.md` этой задачи: две проверки, у каждой заполнен блок
  предусловий с путём к развёрнутым данным.
- Файловый менеджер или терминал для шага 4.

**Expected Outcome:** Прогон начинается с первого шага одним действием и
переигрывается тем же действием, без обращения к разработчику.

**Priority:** High
