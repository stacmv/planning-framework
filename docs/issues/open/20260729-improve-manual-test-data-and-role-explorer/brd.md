# BRD: Подготовка тестового кейса и ролевой project explorer в Manual Test UI

**Version:** 1.1
**Date:** 2026-07-29
**Status:** Draft

## Interview Notes

Интервью с владельцем проекта (он же единственный разработчик, аналитик и QA) 29.07.2026. Обе потребности пришли из плана недели 31 и были объединены в один issue, потому что затрагивают один и тот же инструмент — Manual Test UI.

Ключевые высказывания и вскрытые ограничения:

- Про подготовку данных: ручной прогон упирается в предусловия ещё до первого шага. Сегодня чек-лист говорит тестировщику «если не можешь выполнить предусловие — остановись и спроси разработчика», то есть штатный сценарий ручного теста — это остановка.
- Граница ответственности осознанно узкая: «файлы и фикстуры». Подъём сервисов, БД и аккаунтов остаётся текстом в предусловиях — автоматизировать их не просили.
- Про роли (возникло в ходе интервью, не было в исходной формулировке): «нужно всё разделить на группы по условным ролям пользователя: аналитик, разработчик, тестировщик (QA) и показывать на каждой вкладке релевантные для роли экраны. Пользователь может переключаться между вкладками ролей по желанию».
- Роль «тестировщик» — это владелец проекта в роли QA, а не внешний человек. Прятать от него внутреннюю терминологию не нужно.
- Ограничение, названное явно: инструмент не должен обзаводиться дополнительными зависимостями.
- Обе части признаны равнозначными: issue считается выполненным только при обеих.

Контекст интервью, объясняющий требование G3: сегодня изменённое рабочее дерево блокирует переключение на ветку issue и роняет проверку качества перед закрытием. Отсюда требование к результату — подготовка не должна менять состояние репозитория (US-03). Каким способом это достигается, BRD не предписывает.

## Executive Summary

Manual Test UI сегодня умеет ровно один экран — чек-лист ручного теста. Всё, что нужно вокруг него (контекст задачи, требования, спецификация) читается в стороннем редакторе, а данные для теста тестировщик готовит руками по прозаическому описанию. Issue закрывает обе дыры: ручной кейс приводится в готовое состояние одним действием, а сам инструмент становится рабочим местом с тремя ролевыми вкладками, где каждый экран лежит там, где он нужен по ходу работы.

## Problem Statement

Ручное тестирование в фреймворке доведено до чек-листа и на нём остановлено.

1. **Подготовка кейса не автоматизирована вообще.** Предусловия — свободный текст. Тестировщик, который по замыслу «ничего не знает о внутреннем устройстве проекта», должен сам создать нужные файлы и состояние. Инструкция честно предлагает ему в этом месте остановиться и спросить разработчика — то есть цена каждого ручного прогона включает прерывание разработчика.
2. **Контекст теста недоступен из инструмента.** Чтобы понять, что вообще проверяет тест-кейс, нужно открыть требования и спецификацию в редакторе, найти issue, сопоставить с тем, что на экране. Инструмент, созданный для прохождения тестов, не показывает ничего, кроме самих тестов.

## Goals

| # | Goal |
|---|---|
| G1 | Ручной тест-кейс приводится в готовое к прогону состояние одним действием, без обращения к разработчику |
| G2 | Подготовка повторяема: повторный запуск возвращает кейс в то же исходное состояние, испорченный прогон не требует ручной чистки |
| G3 | Подготовка не меняет состояние репозитория и не мешает переключению веток и проверке качества |
| G4 | Документы, нужные по ходу работы, доступны из самого инструмента и разложены по ролям, а не свалены в один список |
| G5 | Инструмент по-прежнему не требует установки дополнительных зависимостей: запустил и работаешь |

## Non-Goals

- Автоматизация подъёма сервисов, БД, аккаунтов и внешних систем. Такие предусловия остаются прозаическим текстом в кейсе и предметом подготовки не являются (см. AC-01a).
- Редактирование требований, спецификаций и прочих документов пайплайна из инструмента: правка в обход этапов пайплайна обесценивает их проверку.
- Показ полной истории (транскриптов) рабочих сессий агента.
- Замена автоматических тестов ручными или наоборот.
- Отдельная роль для внешнего тестировщика: адресат ролевых вкладок — владелец проекта в роли QA.
- Массовое дооснащение уже закрытых issue подготовкой данных задним числом.

## Users

| User | Context |
|---|---|
| Primary — владелец проекта в роли QA | Проходит ручные тест-кейсы по чек-листу. Нужна готовая к прогону среда и возможность быстро свериться с тем, что кейс проверяет |
| Primary — он же в роли разработчика | Возвращается к issue, которое вёл раньше или на другой машине. Нужен контекст: спецификация, планы, действующие инструкции проекта, накопленная память |
| Primary — он же в роли аналитика | Проверяет, что реализованное соответствует заявленному: требования, исходная постановка, принятые решения |
| Secondary — внешний тестировщик | Получает чек-лист как файл, вне инструмента. Ему адресован сам чек-лист, но не ролевые вкладки |

## User Stories

### US-01: Как QA, я хочу привести тест-кейс в готовое состояние одним действием, чтобы начать прогон без обращения к разработчику.

**Acceptance Criteria:**
- AC-01a: Предметом подготовки являются только файлы и фикстуры, явно объявленные для тест-кейса как требуемые им данные. Прозаические предусловия (поднять сервис, завести учётную запись, подготовить внешнюю систему) предметом подготовки не являются и остаются на тестировщике — см. Non-Goals.
- AC-01b: Для тест-кейса, которому объявлены требуемые данные, в инструменте доступно действие подготовки; после его выполнения все объявленные для кейса данные существуют и кейс можно начать с первого шага.
- AC-01c: Подготовить можно как весь issue целиком, так и один конкретный тест-кейс.
- AC-01d: Связь «тест-кейс ↔ требуемые ему данные» доступна инструменту из того же документа, который он читает для ручного теста (чек-листа). Без этого невозможно ни подготовить отдельный кейс, ни определить, где действие подготовки не нужно.
- AC-01e: Результат действия сообщается тестировщику: что подготовлено, где это находится, чем закончилось. При неуспехе сообщается причина неудачи, и кейс не остаётся в наполовину подготовленном виде.
- AC-01f: Расположение подготовленных данных доводится до тестировщика в самом чек-листе, в предусловиях кейса, — чтобы чек-лист оставался самодостаточным при чтении файлом, вне инструмента.
- AC-01g: Подготовку можно выполнить как из инструмента, так и без него — одной командой, на всех платформах, где запускается сам инструмент.

### US-02: Как QA, я хочу вернуть испорченный кейс в исходное состояние, чтобы перепройти тест, не разбираясь, что я сломал.

**Acceptance Criteria:**
- AC-02a: Повторная подготовка приводит развёрнутую рабочую копию кейса к тому же состоянию, что и первая, независимо от того, что успело измениться в этой копии между запусками.
- AC-02b: Возврат кейса в исходное состояние не требует от тестировщика ручной чистки и разбирательства в том, что именно было изменено прогоном.
- AC-02c: Сброс одного тест-кейса не трогает данные остальных.

### US-03: Как разработчик, я хочу, чтобы подготовка не меняла состояние репозитория, чтобы не терять переключение веток и прохождение проверки качества.

**Acceptance Criteria:**
- AC-03a: После любого числа подготовок и прогонов состояние репозитория с точки зрения системы контроля версий не меняется: ни переключение на ветку issue, ни проверка качества перед закрытием не блокируются следами подготовки.
- AC-03b: Артефакты подготовки, создаваемые самим пайплайном, не оставляют рабочее дерево в изменённом состоянии — они фиксируются той же стадией пайплайна, которая их создала.
- AC-03c: Исходные данные тест-кейса сопровождают issue: они остаются доступны на другой машине и после закрытия issue.

### US-04: Как участник в любой из трёх ролей, я хочу видеть в инструменте документы, относящиеся к моей текущей роли, чтобы не искать их в редакторе.

**Acceptance Criteria:**
- AC-04a: В инструменте есть три роли — аналитик, разработчик, тестировщик; переключение между ними свободное и в любой момент.
- AC-04b: Роль аналитика даёт исходную постановку, требования, разбор проблемы, рабочие заметки, зафиксированные архитектурные решения, конфигурацию фреймворка для проекта, а для issue тривиального тира — заменяющий их сводный документ.
- AC-04c: Роль разработчика даёт спецификацию, план реализации issue, глобальную дорожную карту проекта (отдельный от плана реализации документ), журнал сессий проекта, действующие инструкции проекта и накопленную по проекту память.
- AC-04d: Роль тестировщика даёт тест-план, чек-лист ручного теста, отчёт о качестве и правила проверки качества, а также действие подготовки кейса из US-01.
- AC-04e: В качестве инструкций проекта показываются те, что реально на него действуют, включая унаследованные от родительских каталогов. Файлы инструкций, являющиеся тестовыми данными или шаблонами, либо не показываются, либо явно помечаются как недействующие.
- AC-04f: Если накопленной памяти по проекту нет, роль разработчика сообщает об этом явно, а не показывает пустоту. Полные транскрипты рабочих сессий предметом показа не являются.
- AC-04g: Документ, не порождаемый пайплайном для данного типа и тира issue, обозначается как **неприменимый**. Документ, порождаемый, но ещё не созданный, обозначается как **отсутствующий**, с указанием стадии, которая его создаёт. Ролевые вкладки не пустуют и не сообщают об отсутствии там, где документа и не должно быть.
- AC-04h: Для документа, существующего только на ветке issue, показывается его содержимое только для чтения и предлагается переключение на эту ветку — по явному подтверждению. Действие подготовки кейса для такого issue доступно только после переключения.
- AC-04i: Для закрытого issue документы доступны для чтения, а действие подготовки кейса не предлагается.
- AC-04j: Документы читаются в отформатированном виде, включая таблицы.

### US-05: Как разработчик, я хочу быть уверен, что инструмент не позволяет править документы пайплайна, чтобы его нельзя было использовать в обход пайплайна и его проверок.

**Acceptance Criteria:**
- AC-05a: Документы пайплайна — исходная постановка, требования, спецификации, планы, разбор проблемы, отчёты, инструкции проекта и память — доступны из инструмента только для чтения; изменить их через инструмент нельзя.
- AC-05b: Перечень изменяющих действий инструмента исчерпывающий и состоит из трёх: (1) отметки и заметки в чек-листе ручного теста, (2) переключение на ветку issue по явному подтверждению, (3) подготовка тестового кейса. Ничего другого инструмент не изменяет.
- AC-05c: Инструмент читает документы проекта и накопленную по нему память — и ничего за этими пределами; история (транскрипты) рабочих сессий в доступ не входит.

### US-06: Как владелец проекта, я хочу, чтобы нововведения не сломали то, что уже работает, и не потребовали установки дополнительных зависимостей.

**Acceptance Criteria:**
- AC-06a: Функциональное ядро существующей работы с чек-листом сохраняется: отметки и заметки сохраняются; запись точечная — правка одного пункта не затрагивает остальной документ; переключение на ветку issue работает как прежде, вместе со своей защитой; три состояния чек-листа (доступен на диске, доступен только на ветке, отсутствует) по-прежнему различаются. Навигация к чек-листу при этом меняется намеренно — он становится одним из экранов ролевой вкладки.
- AC-06b: Инструмент по-прежнему запускается одной командой и не требует установки дополнительных зависимостей.
- AC-06c: Видимость действия подготовки определяется по правилу приоритета: если про кейс известно, что данные ему не нужны, — действие не предлагается; если известно, что нужны, но не подготовлены, — действие видно и недоступно, с пояснением; если неизвестно (issue создан до появления этой возможности) — трактуется как второй случай: видно и недоступно, с пояснением.
- AC-06d: Всё описанное работает для любого настроенного в инструменте проекта, а не только для того, из которого инструмент запущен.

## Success Metrics

| # | Метрика | Как считаем | Цель |
|---|---|---|---|
| M1 | Ручные тест-кейсы с объявленными требуемыми данными, начатые без обращения к разработчику | Доля таких кейсов от всех кейсов с объявленными требуемыми данными | 100% |
| M2 | Ручные прогоны, потребовавшие ручной чистки перед повторным проходом | Число таких прогонов за issue | 0 |
| M3 | Проверки качества перед закрытием issue, упавшие из-за следов подготовки данных | Число падений за issue | 0 |
| M4 | Открытия стороннего редактора ради контекста во время ручного прогона | Число открытий за прогон, среди документов, перечисленных в AC-04b–AC-04d | 0 |
| M5 | Дополнительные зависимости, которые нужно установить для запуска инструмента на чистой машине | Число зависимостей сверх текущего состояния | 0 |
