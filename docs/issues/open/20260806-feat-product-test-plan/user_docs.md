# User Docs: глобальный чек-лист ручных тестов

**Issue:** 20260806-feat-product-test-plan

Изменения, которые нужно внести в пользовательскую документацию (`README`,
`CHANGELOG`, руководство), и что именно поменялось для того, кто пользуется
фреймворком.

---

## Что изменилось

Появился один файл на весь проект — `docs/planning/test-plan.md`. В нём
накапливаются ручные тест-кейсы, и он пополняется сам при закрытии issue.

До этого ручные кейсы жили только внутри issue. После закрытия папка уезжала в
`docs/issues/closed/`, и набор перестал существовать как знание о продукте:
перед релизом было нечего открыть и пройти, а невыполненный ручной тест просто
исчезал вместе с папкой.

Теперь при закрытии issue её ручные кейсы переносятся в общий список. Кейс,
который в своей issue выполнить не успели, приезжает со статусом `pending` — то
есть остаётся видимым, а не теряется.

## Как этим пользоваться

**Перед релизом** откройте `docs/planning/test-plan.md` и пройдите строки со
статусом `pending`, начиная с приоритета `Critical`. Автотесты при этом гоняет
`make test` — общий список их не дублирует, в него попадают только ручные кейсы.

**Результат прогона** отмечается прямо в файле, руками. Словарь статусов
короткий:

| Статус | Когда ставить |
|---|---|
| `pending` | не выполнялся или пора перепроверить |
| `✓` | пройден при последнем прогоне |
| `✗` | провален при последнем прогоне |
| `retired` | потерял смысл после изменения продукта |

Кейс, потерявший смысл, помечайте `retired`, а не удаляйте — так видно, что
проверка существовала и была снята осознанно, а не потерялась. Если строку всё же
удалили, номер сам по себе не переиспользуется: его помнит строка-счётчик над
таблицей. Единственный способ всё-таки получить повтор — удалить руками и строку
с наибольшим номером, и сам счётчик; тогда восстанавливать максимум будет уже
неоткуда.

**Файл рассчитан на ручную правку.** Формат это переживает: значения `Prio` и
`Status` берутся из закрытых словарей, символ `|` внутри ячейки записывается как
`\|`, каждая ячейка — одна строка.

**Автоматической проверки формата в вашем проекте нет.** Валидатор, который
отличает испорченную строку (значение вне словаря, номер не из четырёх цифр,
дубликат номера, потерянная строка-счётчик), живёт в тестах самого репозитория
`planning-framework` и в проекты не копируется: обновление приносит только
шаблоны и скиллы. Так что за формой следите глазами, а если файл станет заметной
частью работы — имеет смысл завести такую проверку у себя.

## Две ситуации, о которых стоит знать заранее

**Закрытие прервалось посреди переноса.** Само по себе оно не возобновится:
к этому моменту закрытие уже переключилось на родительскую ветку, поэтому
повторный запуск остановится с требованием перейти на ветку issue. Порядок
восстановления такой — отбросить недописанный `docs/planning/test-plan.md`
(вернуть его из последнего коммита, а если файл только что создан и ещё не
отслеживается — удалить), перейти на ветку issue, запустить закрытие снова.
Терять при этом нечего: строки выводятся заново из тест-плана issue, а строки
прежних issue лежат в закоммиченной версии файла. Дублей повторный запуск не
создаёт.

**Две issue закрыли параллельно.** Уникальность номеров между ветками не
защищена, и это принято сознательно: две ветки, стартовав с одного значения
счётчика, выдадут один и тот же номер, а git смерджит это молча — для него это
совпадающее изменение, а не конфликт. Поэтому после параллельного закрытия
загляните в таблицу: если один номер встречается дважды, перенумеруйте строку,
приехавшую второй, и поднимите счётчик до нового максимума. Автоматически в вашем
проекте это не обнаружится (см. выше про отсутствие валидатора).

## Откуда берутся строки

Каждая строка ссылается на issue-источник в колонке `Origin` (в виде
`ISSUE-ID#TC-NNN`), но читать её можно без перехода по ссылке: название кейса при
переносе дополняется до самостоятельной фразы. Полные шаги остаются в issue.

Локальные номера `TC-NNN` внутри issue не переименовываются — глобальный номер
`PTC-NNNN` живёт отдельно.

## Что делать существующим проектам

Ничего вручную. Файл создаётся из шаблона при обновлении проекта до текущей
версии фреймворка (`make converge`), а если его на момент закрытия issue всё ещё
нет — он будет создан при закрытии.

Уже закрытые issue автоматически в список **не** переносятся: он начинает
наполняться со следующего закрытия. Перенос накопленного — отдельная задача, если
это понадобится.

## Чего эта версия не делает

Сознательно, чтобы артефакт приносил пользу сам по себе:

- не блокирует закрытие issue из-за невыполненных ручных тестов;
- не фиксирует, кто именно выполнил кейс;
- не предлагает существующие кейсы как регрессию при планировании новой issue;
- не схлопывает кейсы, перекрытые автотестами;
- не отображается в Manual Test UI — он этот список не читает и никак с ним не
  связан;
- не меняет ничего в стадиях до закрытия: локальные тест-планы issue и работа с
  ними остаются как были.
