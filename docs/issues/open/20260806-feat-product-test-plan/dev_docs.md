# Dev Docs: глобальный чек-лист ручных тестов

**Issue:** 20260806-feat-product-test-plan

Архитектурные решения, runbook и заметки о доставке. Пользовательская часть — в
`user_docs.md`, здесь её нет.

---

## Architecture

Один артефакт и одна новая фаза. Никаких новых компонентов, процессов и
зависимостей.

```
docs/issues/open/<ID>/test_plan.md        docs/planning/test-plan.md
  Status Tracker                            (один на проект)
  ┌──────────────────────┐                ┌────────────────────────────────┐
  │ TC-001 … Manual … ✓  │──Phase 4.5──▶  │ PTC-0001 … Critical … pf-close │
  │ TC-002 … Auto   … ✓  │  (Manual only) │ PTC-0002 … High     … scripts  │
  └──────────────────────┘                └────────────────────────────────┘
            │                                        ▲
        Phase 4 (merge)                        Phase 8 (git add)
            └──────── Phase 5 (archive) ───────────┘
```

**Затронутые файлы.** `skills/pf-close/SKILL.md` (новая Phase 4.5 + путь в
`git add` на Phase 8), `docs/planning/templates/global/test-plan.md` (новый
шаблон), `scripts/converge-to-v3.sh` (`t5_global_docs()` знает про новый файл),
`test/pf-product-test-plan.sh` (новый сьют, 82 ассерта).

**Phase 4.5 — не код, а проза, исполняемая моделью.** Это определяет всё
устройство тестов ниже: сьют не может её запустить, поэтому проверяет либо
транскрибированные хелперы, либо текст скилла grep'ом, либо реальные git-топологии
пробниками.

---

## ADR-1. Перенос на `/pf-close`, между мерджем и архивацией

**Решение.** Phase 4.5 стоит после Phase 4 (merge) и до Phase 5 (archive).

**Почему.** `/pf-close` определяет активную issue сканированием
`docs/issues/open/` и останавливается, если там пусто. Поставь перенос после
архивации — упавшая фаза оставит issue уже закрытой, повторный запуск скажет «No
active issue found», и ручные кейсы потеряны без возможности восстановления. До
архивации сбой оставляет папку на месте, и issue остаётся находимой.

**Альтернативы отклонены.** Отдельная стадия конвейера — issue закрывалась бы
раньше неё и теряла бы кейсы так же. Перенос на `/pf-qa` — до мерджа нет
merge-коммита, из которого выводится `Area`.

## ADR-2. Реестра долга не заводить

**Решение.** «Невыполненный ручной тест» — это не отдельная сущность, а строка
общего списка со статусом `pending`.

**Почему.** Два артефакта об одном и том же неизбежно расходятся. Один список
служит и чек-листом релиза, и перечнем долга — расходиться не с чем.

## ADR-3. Номер = max(счётчик, максимум таблицы) + 1

**Решение.** Следующий номер берётся как максимум двух величин плюс один, и
записывается как `PTC-` плюс ровно четыре цифры с ведущими нулями.

**Почему два источника.** Каждый по отдельности дырявый: только таблица —
`retired`-строку удалят руками, максимум упадёт, номер переиспользуется; только
счётчик — прогон успел записать строки и упал до обновления счётчика, следующий
выдаст те же номера поверх существующих. Максимум из обоих самовосстанавливается
после частичной записи.

**Почему форма записи задана отдельно.** Первая редакция описывала только
арифметику. Реальное закрытие на свежем списке записало `| 1 | …` и
`Last allocated: 1` — арифметически верно и отвергнуто валидатором формата. Ни
один из 59 автотестов этого не поймал: все они звали хелпер, **транскрибирующий**
правильное форматирование, то есть сьют соглашался сам с собой, пока текст скилла
оставлял форму неопределённой. См. «Testing notes» ниже.

## ADR-4. Уникальность номеров обнаруживается, а не предотвращается

**Решение.** Коллизия между параллельно закрываемыми ветками допускается и чинится
руками.

**Почему.** Первая редакция спеки утверждала, что меняющийся счётчик даёт
git-конфликт. Это неверно: две ветки, стартовав с `PTC-0003`, обе запишут
`PTC-0004` — для git это совпадающее изменение, а не конфликт, merge пройдёт
молча. Гарантировать уникальность можно было бы внешним счётчиком или ID,
производным от `Origin` (уникален по построению) — оба дороже проблемы: проект
односоставный, две issue редко закрываются параллельно, цена ошибки — одна ручная
перенумерация.

**Важное следствие для доставки.** Детектор (`pf_validate_test_plan_file`) живёт
в `test/pf-product-test-plan.sh` и в проекты **не копируется** — ни `converge`
(зеркалит только `docs/planning/templates`), ни `update-skills` (копирует только
`skills/` в `~/.claude/skills/`) его не доставляют. В стороннем проекте коллизия
обнаруживается только глазами. Это зафиксировано в `user_docs.md` как
предупреждение.

## ADR-5. `Area` выводится из первого мерджа issue, не из `HEAD`

**Решение.** `MERGE=$(git log --merges --format=%H --grep "merge: close ISSUE-ID"
PARENT-BRANCH | tail -1)`, затем `git diff --name-only "$MERGE^1" "$MERGE^2"`.

**Почему не трёхточечный диапазон.** После `--no-ff` мерджа merge-base двух ветвей
становится вершиной issue-ветки, поэтому `git diff PARENT...issue/<ID>` всегда даёт
пустой список. Измерено на реальном закрытии: 0 файлов против 15 у формы через
родителей мерджа.

**Почему не `HEAD^1 HEAD^2`.** Повторный запуск может создать **второй** мердж —
достижимо двумя путями: сохранённая частичная запись при восстановлении и правило
stop-and-surface, велящее закоммитить починку тест-плана на issue-ветке. Тогда
родители `HEAD` описывают одну бухгалтерскую правку, которая исключается, и `Area`
вырождается в `general`. Привязка к первому мерджу инвариантна к обоим путям, не
требует состояния и не требует сбрасывать родительскую ветку. На чистом прогоне
первый мердж и есть `HEAD` — поведение не меняется.

**Что исключается из списка файлов.** `docs/issues/` целиком и **ровно четыре**
бухгалтерских файла поимённо: `docs/planning/session-log.md`, `decisions.md`,
`implementation-plan.md`, `test-plan.md`. Именно список, а не glob и не каталог:
`docs/planning/*.md` захватил бы настоящую документацию того же уровня
(`FRAMEWORK.md`, `QUICKSTART.md`, `MIGRATION-GUIDE-V3.md`,
`v2.0-design-analysis.md`), а исключение каталога — `docs/planning/templates/` с
продуктовыми артефактами.

## ADR-6. Колонки определяются по имени заголовка, не по позиции

**Решение.** `Type`, `Test Case`, `Priority`, `Status` ищутся по имени в строке
заголовка.

**Почему.** В репозитории сосуществуют два реальных порядка колонок:
`docs/planning/templates/issue/test_plan.md` даёт `TC | Type | Test Case | …`, а
скилл `pf-test-plan` генерирует `TC | Test Case | Type | …`. Позиционный парсер на
одной из двух раскладок примет название кейса за тип и не отберёт ни одной
`Manual`-строки. Расхождение самого фреймворка — не в объёме этой issue.

## ADR-7. При восстановлении частичная запись выбрасывается

**Решение.** Порядок восстановления после сбоя внутри Phase 4.5: отбросить
недописанный файл (вернуть из коммита; удалить, если он ещё не отслеживается),
затем `git checkout issue/<ID>`, затем перезапустить.

**Почему именно выбрасывать.** Сохранение ломает восстановление двумя способами,
оба измерены. Первый: если issue-ветка отрезана до появления
`docs/planning/test-plan.md` на родительской ветке, `git checkout` отказывается
переключаться — файла на ветке нет, а он изменён (`error: Your local changes …
would be overwritten … Aborting`, exit 1). Восстановление оказалось бы неисполнимым
для всех ветвей старше файла. Второй: Phase 2 закоммитит недописанную (возможно,
оборванную) строку на issue-ветку и даст ветке коммит, для которого она не делала
работы.

**Что осталось не решено сознательно.** Phase 0 всё равно требует ручного
`git checkout issue/<ID>` — привести её и семантику уборки Phase 2 к бесшовному
возобновлению значило бы менять существующее поведение `/pf-close` вне объёма этой
issue.

## ADR-8. Нераспознанный вход — останов, а не пропуск

**Решение.** Останов с сообщением, если `Type` вне `{Manual, Auto}`, если таблица
Status Tracker не найдена вовсе, или если у отобранной `Manual`-строки пустая
ячейка `Test Case`. Отсутствующая строка `Last allocated:` — исключение: её
восстанавливают, а не падают.

**Почему.** Все три первых случая неотличимы от легитимного «переносить нечего»,
если их просто проскочить, и каждый молча теряет ручной кейс — ровно та потеря,
против которой заведена вся фаза. `Critical`-кейс не должен исчезать из-за
опечатки в регистре. Счётчик, в отличие от них, восстановим из максимума таблицы,
поэтому там останов был бы вредным.

## Testing notes

**Вакуумность через транскрипцию — главный риск этого сьюта.** Phase 4.5
исполняется моделью, поэтому большинство кейсов работают на bash-хелперах,
транскрибирующих правило. Такой тест проходит и при неверном тексте скилла: он
сверяет копию требований с собой. Отсюда два обязательных приёма.

1. **Drift-guard в каждом таком кейсе** — grep по тексту `skills/pf-close/SKILL.md`,
   подтверждающий, что правило там действительно записано. Guard пишется только на
   текст, который существует: проверка на отсутствующую формулировку вечно красная
   и бесполезна (два guard'а из брифа реализации сознательно не написаны именно
   поэтому).
2. **Проверка формы, а не наличия, там где дефект в форме.** Трижды проверка «текст
   присутствует» прошла бы и на сломанной версии: у порядка шагов Phase 4.5 дефект
   был исключительно в порядке (лечится сравнением номеров строк); у сужения
   исключения `Area` проверка «верхний уровень исключён» одинаково довольна и
   сужённым, и слишком широким правилом (лечится утверждением трёх взаимно
   ограничивающих условий); у устаревшего обоснования grep закреплял именно ту
   формулировку, которую надо было менять — тест **пинил противоречие** вместо того
   чтобы его ловить.

**Где грепа недостаточно — реальные пробники.** Три места проверяются исполнением, а
не чтением: `git add` с отсутствующим путём (exit 128, пустой индекс — это и делает
находку блокирующей); топология повторного мерджа (наивная форма против формы
первого мерджа); отказ `git checkout` на неотслеживаемом файле и успех после
`rm`.

**Безопасность сьюта.** Правило S-1 (`test/lib.sh`): имя скрипта конвергенции
встречается под `test/` ровно в одном файле, потому что скрипт перезаписывает
`~/.claude/`. Кто читает этот скрипт из теста — собирает имя из соседних литералов,
как это делает `test/safety-audit.sh`.

**Известный пробел страховочной сетки.** `assert_repo_untouched` аудирует только
внутри репозитория, поэтому запись **за** его пределы остаётся зелёной. Не
гипотетически: в ходе этой issue хелпер вернул пустой путь, он дошёл до `git -C`,
и файлы-пробники были созданы в корне Git Bash при зелёном сьюте. Действующее
правило — конвенция, не автоматика: любой хелпер, возвращающий путь, проверяется
вызывающей стороной на непустоту **до** использования в пишущей команде (образец —
`pf_ptp_area_setup` и его вызов).

## Runbook

**Закрытие упало внутри Phase 4.5.** Issue не потеряна — папка осталась в
`docs/issues/open/`. Порядок: отбросить недописанный `docs/planning/test-plan.md`
(`git checkout -- docs/planning/test-plan.md`, а если файл только что создан и не
отслеживается — `rm`), `git checkout issue/<ID>`, перезапустить закрытие. Дублей не
будет: идентичность строки — пара (`ISSUE-ID`, `TC-NNN`), номер — максимум из
счётчика и таблицы.

**Закрытие остановилось с жалобой на строку тест-плана.** Починить строку нужно на
issue-ветке и закоммитить, иначе повторный запуск встанет на том же месте. Порядок
тот же, что выше, плюс правка `docs/issues/open/<ID>/test_plan.md` перед
перезапуском.

**Один номер `PTC` встречается дважды.** Следствие параллельного закрытия
(ADR-4). Перенумеровать строку, приехавшую второй, и поднять `Last allocated:` до
нового максимума. В этом репозитории поймает `make test`; в проектах — только
глазами.

**Строка `Last allocated:` исчезла.** Фаза восстановит её сама из максимума
таблицы. Ручного действия не требуется.

## Deployment notes

Развёртывать нечего: фича состоит из текста скилла, шаблона и одной строки в
скрипте конвергенции.

- `skills/pf-close/SKILL.md` попадает в проекты через `make update-skills` /
  `/pf-update` (копирует `skills/` в `~/.claude/skills/`) — **вне объёма этой
  issue**, но без этого шага реальные закрытия продолжат исполнять старую версию
  без Phase 4.5.
- `docs/planning/templates/global/test-plan.md` и создание
  `docs/planning/test-plan.md` приходят с `make converge`.
- `Makefile` не менялся: цикл `test:` подхватывает новый сьют сам.
- Обратная совместимость: проект без глобального файла получает его при
  конвергенции либо при первом же закрытии — Phase 4.5 создаёт файл безусловно, до
  отбора строк, потому что `git add` на Phase 8 называет путь безусловно.
