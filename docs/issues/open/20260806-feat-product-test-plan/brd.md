# BRD: Продуктовый тест-план и сохранение ручного долга

**Issue:** 20260806-feat-product-test-plan
**Тип:** feat · **Tier:** medium
**Источник:** `prompt.md`

---

## Problem Statement

Тест-кейсы живут только внутри issue. `TC-NNN` нумеруется с нуля в каждой, а
после закрытия весь набор уезжает в `docs/issues/closed/` и перестаёт быть
знанием о продукте. Следствия:

1. **Нельзя сослаться на тест глобально** — `TC-001` означает разное в разных
   issue.
2. **Нет регрессионного набора** — ручные кейсы issue N не переигрываются,
   когда issue N+5 трогает ту же область.
3. **Невыполненному ручному тесту негде жить** — он исчезает вместе с папкой.

Третье наблюдалось трижды подряд и зафиксировано документально:
`20260731-feat-pluggable-reviewers` (коммит `1783864`, чек-лист пуст),
`20260715-bug-gates-verification-and-tooling-fixes` (закрыт с невыполненными
TC-002/TC-003, чек-лист не сгенерирован), `20260703-improve-scale-doc-complexity`
(20 ручных кейсов, судьба неизвестна).

Закрывать issue с невыполненными ручными тестами часто **полезно** — это
разблокирует мердж. Проблема не в закрытии, а в потере.

---

## Goals

- Ручной тест переживает закрытие issue, породившей его.
- На тест можно сослаться глобально и однозначно.
- Невыполненный критичный ручной тест **физически не даёт** закрыть issue.
- Новая issue видит уже существующие ручные кейсы в затронутых областях и
  переиспользует их вместо сочинения почти таких же заново.

## Non-Goals

- Отдельный реестр долга. Ключевое решение issue: **ручной долг = Manual TC в
  продуктовом плане со статусом `pending`**. Два артефакта неизбежно разойдутся.
- Изменение пайплайна внутри issue. Локальные `TC-NNN` остаются как есть,
  стадии до закрытия не трогаются.
- Разбиение плана на файлы по областям. Делается позже, когда файл перестанет
  читаться, — не заранее.
- Промоушен `Auto`-кейсов (см. решение D-3 ниже).

---

## Stakeholders

| Роль | Интерес |
|---|---|
| Владелец репозитория | Не терять ручной долг; сохранять возможность закрыть issue, не выполнив некритичные тесты |
| Агент, ведущий issue | Однозначный ответ, можно ли закрывать; готовый список кандидатов на регрессию |
| Потребитель Project Explorer | Очередь ручных тестов (issue `20260806-improve-project-explorer-redesign`) читает именно этот артефакт |

## User Stories

### US-1 — Ручной долг переживает закрытие

**Как** владелец репозитория, **я хочу**, чтобы невыполненный ручной тест
оставался видимым после закрытия issue, **чтобы** не терять знание о
непроверенном поведении.

**Acceptance Criteria:**
- AC-1.1 При закрытии issue каждый её Manual TC попадает в продуктовый план под
  глобальным идентификатором `PTC-NNNN`.
- AC-1.2 Строка плана хранит обратную ссылку на породившую issue.
- AC-1.3 Невыполненный тест получает статус `pending` и остаётся в плане
  бессрочно, пока не будет выполнен или явно снят.
- AC-1.4 Закрытие issue невозможно, если промоушен не состоялся: закрыть с
  долгом можно, потерять долг — нельзя.

### US-2 — Критичный ручной тест блокирует закрытие

**Как** владелец, **я хочу**, чтобы невыполненный критичный ручной тест не
позволял закрыть issue, **чтобы** гейт оставался гейтом.

**Acceptance Criteria:**
- AC-2.1 Невыполненный Manual TC приоритета `Critical` → QA-вердикт `FAIL`.
- AC-2.2 Обхода нет: владелец **не может** продавить закрытие поверх этого
  вердикта. Единственный законный путь — явно понизить приоритет кейса правкой
  тест-плана, что остаётся видимым решением в истории.
- AC-2.3 Невыполненные некритичные кейсы закрытию не мешают: вердикт остаётся
  `PASS`, но отчёт несёт отдельную строку о числе отложенных.

### US-3 — Кто выполнил тест, видно

**Как** владелец, **я хочу** отличать тест, выполненный человеком, от
выполненного агентом, **чтобы** агентское подтверждение не читалось как внешняя
приёмка.

**Acceptance Criteria:**
- AC-3.1 Выполнение агентом **засчитывается**: статус закрывается, гейт US-2
  пропускает.
- AC-3.2 Строка плана хранит, кто выполнил — агент или человек.
- AC-3.3 Признак виден без открытия других документов.

> Прецедент: в issue `20260806-bug-test-plan-tc-untracked` единственный
> Critical Manual TC подтверждён агентом. Без AC-3.1 эта issue по новым
> правилам не закрылась бы; без AC-3.2 подтверждение читалось бы как приёмка
> человеком.

### US-4 — Новая issue переиспользует существующие кейсы

**Как** агент, планирующий тесты новой issue, **я хочу** видеть уже
существующие ручные кейсы в затронутых областях, **чтобы** предлагать их как
регрессию вместо сочинения дубликатов.

**Acceptance Criteria:**
- AC-4.1 Стадия планирования тестов читает продуктовый план до написания новых
  кейсов.
- AC-4.2 Существующие кейсы в затронутых областях предлагаются кандидатами на
  регрессию.
- AC-4.3 Новый кейс, дублирующий существующий, линкуется к нему, а не
  создаётся заново.
- AC-4.4 Ручной кейс, для которого появилось автоматическое покрытие,
  помечается покрытым и перестаёт быть ручным долгом.

### US-5 — Долг из старых issue поднимается по одному разу

**Как** владелец, **я хочу** решать по каждой ранее закрытой issue, забирать
ли её тесты в план, **чтобы** не терять исторический долг и не отвечать на один
и тот же вопрос дважды.

**Acceptance Criteria:**
- AC-5.1 Тесты из ранее закрытых issue **не** переносятся автоматически.
- AC-5.2 По каждой ранее закрытой issue задаётся вопрос: забирать её ручные
  кейсы в план или нет.
- AC-5.3 Ответ запоминается. Повторно по той же issue вопрос не задаётся —
  независимо от ответа, включая отказ.
- AC-5.4 Механика работает **для каждого проекта**, использующего фреймворк, а
  не только для этого репозитория: у каждого проекта свой план и своя отметка
  об уже обработанных issue.

### US-6 — Состояние долга видно сразу

**Как** владелец, **я хочу** видеть объём ручного долга в статусе проекта,
**чтобы** он не накапливался незаметно.

**Acceptance Criteria:**
- AC-6.1 Обзор состояния показывает число ручных кейсов в статусе `pending`.
- AC-6.2 Показатель виден без открытия самого плана.

## Business Rules

| # | Правило |
|---|---|
| BR-1 | Ручной долг и продуктовый план — **один** артефакт. Отдельного реестра долга не существует. |
| BR-2 | Идентификатор `PTC-NNNN` глобален в пределах проекта и не переиспользуется даже после снятия кейса. |
| BR-3 | Локальные `TC-NNN` внутри issue остаются как есть; промоушен их не переименовывает. |
| BR-4 | В продуктовый план попадают **только** кейсы типа `Manual` (см. D-3). |
| BR-5 | Статус `pending` — единственный законный способ отложить ручной тест. |
| BR-6 | Выполнение агентом засчитывается, но актор фиксируется всегда. |
| BR-7 | Ранее закрытые issue обрабатываются по явному решению владельца, по одному разу на issue. |

---

## Decisions

Решения, принятые владельцем в ходе BRD. Записаны потому, что три из четырёх
расходятся с буквой `prompt.md` или закрывают оставленную им неоднозначность.

**D-1. Агентское выполнение засчитывается, актор фиксируется.**
`prompt.md` не оговаривал актора вовсе. Без этого решения гейт US-2 сделал бы
незакрываемой любую issue, чьи Critical-кейсы прогонял агент.

**D-2. Бэкфилл — интерактивный, с отметкой.**
`prompt.md` перечислял три пострадавшие issue, но не говорил, что с ними
делать. Решено: не переносить автоматически и не игнорировать, а спрашивать по
каждой и запоминать ответ. Требование расширено с этого репозитория на **любой
проект** на фреймворке.

**D-3. Промоутятся только `Manual`-кейсы.**
Расходится с примером таблицы в `prompt.md`, где строка `PTC-0042` помечена
`Auto`. Владелец выбрал Manual-only осознанно: план остаётся артефактом про
ручной долг и не разрастается автотестами, которые и так исполняются на каждом
прогоне.

*Следствие, которое надо принять вместе с решением:* регрессионный отбор (US-4)
работает только по ручным кейсам. Пункт `prompt.md` про «схлопывание Auto-кейсов
через `covered-by`» меняет смысл: это не про промоушен автотестов, а про
**ручной** кейс, для которого появилось автоматическое покрытие — он помечается
покрытым и выбывает из долга (AC-4.4).

**D-4. Обхода hard FAIL нет.**
Владелец отклонил вариант «продавить с записью причины». Обоснование: гейт с
обходом перестаёт быть гейтом — ровно это уже произошло с тремя issue,
перечисленными в постановке. Законный путь остаётся один и он видимый —
понизить приоритет кейса правкой плана.

---

## Acceptance (issue level)

Issue считается выполненной, когда:

1. Issue, закрытая с невыполненным **не**критичным ручным тестом, оставляет его
   видимым в продуктовом плане со статусом `pending`.
2. Issue с невыполненным **критичным** ручным тестом не закрывается вовсе.
3. Ранее закрытая issue обрабатывается по решению владельца ровно один раз.
4. Планирование тестов новой issue опирается на существующий продуктовый план.

## Open Questions

- **OQ-1.** Словарь статусов ручного кейса. Точно нужны `pending` и «выполнен».
  Нужны ли отдельно «заблокирован» и «снят» — решается на стадии spec.
- **OQ-2.** Момент задавания вопроса из US-5: при первом обращении к проекту,
  отдельной командой или при первом же закрытии issue. На бизнес-приёмку не
  влияет, влияет на удобство.
