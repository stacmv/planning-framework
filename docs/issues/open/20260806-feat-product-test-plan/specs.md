# Spec: Продуктовый тест-план и сохранение ручного долга

**Issue:** 20260806-feat-product-test-plan
**Тип:** feat · **Tier:** medium
**Источник:** `brd.md`

---

## Overview

Вводится один новый артефакт — `docs/planning/test-plan.md` — и правки в четыре
существующие стадии плюс одна новая команда. Ручной кейс, родившийся в issue,
при закрытии получает глобальный `PTC-NNNN` и переезжает в продуктовый план;
там же он живёт со статусом, пока не будет выполнен, покрыт автотестом или
снят. Никакого второго реестра не заводится (BR-1).

```
issue N                              docs/planning/test-plan.md
┌──────────────────┐                 ┌─────────────────────────────┐
│ test_plan.md     │   /pf-close     │ PTC-0042 … pending          │
│  TC-001 Manual   │ ──promotion──▶  │ PTC-0043 … ✓ (human)        │
│  TC-002 Auto     │  (Manual only)  │ PTC-0044 … covered          │
└──────────────────┘                 └──────────┬──────────────────┘
        ▲                                       │
        │            /pf-test-plan              │
        └───── кандидаты на регрессию ──────────┘
                   (issue N+5)
```

Стадии до закрытия не меняются: локальные `TC-NNN` остаются как есть (BR-3).

## Data model: `docs/planning/test-plan.md`

Файл — markdown с одной таблицей и одной служебной секцией. Читается и правится
руками; всё машиночитаемое извлекается грепом по строке таблицы.

### Строка кейса

| Колонка | Значения | Назначение |
|---|---|---|
| `PTC` | `PTC-NNNN` | глобальный ID, 4 цифры с ведущими нулями |
| `Area` | свободный текст | подсистема (`pf-close`, `explorer-ui`, …) |
| `Test case` | свободный текст | название кейса |
| `Manual reason` | `human-judgment` \| `agent-infeasible` \| `env-dependent` | почему ручной |
| `Prio` | `Critical` \| `High` \| `Med` \| `Low` | приоритет |
| `Origin issue` | ISSUE-ID | обратная ссылка (AC-1.2) |
| `Last run` | `YYYY-MM-DD` \| `—` | когда выполнялся последний раз |
| `Run by` | `human` \| `agent` \| `—` | кто выполнил (AC-3.2) |
| `Status` | см. ниже | текущее состояние |
| `Covered by` | путь к тесту \| `—` | автопокрытие (AC-4.4) |

Колонка `Type` из примера в `prompt.md` **не заводится**: по решению D-3
промоутятся только `Manual`-кейсы, поэтому колонка была бы константой.

### Словарь статусов

| Статус | Смысл | Считается долгом | Блокирует закрытие при `Critical` |
|---|---|---|---|
| `pending` | не выполнялся | да | **да** |
| `✓` | выполнен успешно | нет | нет |
| `✗` | выполнен, провален | да | **да** |
| `blocked` | не может быть выполнен по внешней причине | да | **да** |
| `covered` | появилось автопокрытие, из долга выбыл | нет | нет |
| `retired` | потерял смысл после изменения продукта | нет | нет |

**`blocked` блокирует закрытие наравне с `pending`.** Это прямое следствие
решения D-4 («обхода hard FAIL нет»): если бы `blocked` пропускал закрытие,
он и стал бы обходом — достаточно объявить критичный тест заблокированным.
Внешняя причина не отменяет того, что критичное поведение не проверено.

`retired` и `covered` — единственные способы убрать кейс из долга, не выполняя
его, и оба требуют содержательного основания в колонке `Covered by` либо в
отдельной строке-примечании под таблицей.

### Секция обработанных issue

Отметка из AC-5.3 живёт в этом же файле — отдельным списком под таблицей:

```markdown
## Backfill log

Ранее закрытые issue, по которым решение принято. Повторно не спрашиваются.

- `20260731-feat-pluggable-reviewers` — 2026-08-12 — imported (3 кейса)
- `20260703-improve-scale-doc-complexity` — 2026-08-12 — declined
```

Оба исхода (`imported` / `declined`) записываются одинаково: AC-5.3 требует не
спрашивать повторно **независимо от ответа**, поэтому отказ обязан оставлять
след. Хранение внутри `test-plan.md` соблюдает BR-1 — отметка не может
разойтись с планом, потому что это один файл и один дифф.

### Выделение `PTC-NNNN`

Следующий номер = максимальный существующий `PTC-NNNN` в файле + 1. Отдельного
счётчика нет — он был бы вторым источником правды. Номера не переиспользуются
даже после `retired` (BR-2): удалённая строка не освобождает номер, потому что
строка не удаляется, а переводится в `retired`.

Коллизия при параллельной работе двух веток разрешается на мердже как обычный
конфликт markdown-таблицы; правило разрешения — перенумеровать строки той
ветки, что мерджится второй.

## Stage: `/pf-close` — промоушен и гейт

### Phase 0.5 — гейт промоушена (новая, до всех текущих проверок)

Выполняется после проверки `qa_report.md`, до мерджа.

1. Прочитать `test_plan.md` закрываемой issue, отобрать строки `Type: Manual`.
2. Если таких строк нет — гейт пройден, ничего не делается.
3. Если есть, но в `docs/planning/test-plan.md` нет ни одной строки с
   `Origin issue` = этой issue — **остановиться**: «Промоушен ручных кейсов не
   состоялся. Закрыть issue с долгом можно, потерять долг — нельзя.»

Гейт реализует AC-1.4 и намеренно проверяет **результат** промоушена, а не факт
его запуска: единственный надёжный признак — строки в целевом файле.

### Phase 5.5 — промоушен (новая, после архивации папки issue)

Для каждой строки `Type: Manual` из `test_plan.md`:

| Поле issue | → | Поле продуктового плана |
|---|---|---|
| название кейса | → | `Test case` |
| `Priority` | → | `Prio` |
| `Status` (`✓`/`✗`/`[ ]`) | → | `Status` (`✓`/`✗`/`pending`) |
| ISSUE-ID | → | `Origin issue` |
| — | → | `PTC` (выделяется по правилу выше) |
| — | → | `Area` (выводится из issue; при неоднозначности спрашивается) |
| — | → | `Run by` (`agent`/`human`/`—`, см. ниже) |

**Источник `Run by`.** `manual_test_checklist.md` фиксирует, кто выполнял
прогон. Если пометки нет, поле заполняется `—`, а статус не может быть `✓`:
кейс без известного актора считается невыполненным. Это делает AC-3.2
непропускаемым.

Промоушен — **последняя** запись в issue: он идёт после `mv` папки в `closed/`,
чтобы `Origin issue` ссылался на уже финальный путь.

## Stage: `/pf-qa` — Phase 3.5, учёт ручного долга

Выполняется после Phase 3 (ручные пункты), до Phase 4 (запись отчёта).

```
прочитать manual_test_checklist.md
        │
        ├─ есть невыполненный Manual TC с Prio=Critical?
        │        └─ да ──▶ вердикт FAIL, блокер «Critical manual test not run»
        │                  (обхода нет — D-4)
        │
        └─ есть невыполненные не-Critical?
                 └─ да ──▶ AskUserQuestion: выполнить сейчас / отложить
                            └─ отложить ──▶ вердикт PASS
                                            + строка «Deferred manual tests: N»
```

Отложить можно **только** переводом кейса в `pending` при промоушене (BR-5) —
отдельного механизма отсрочки нет. Строка `Deferred manual tests: N` пишется в
`qa_report.md` рядом с вердиктом и читается грепом.

Определение «невыполненный» здесь то же, что в словаре статусов: `pending`,
`✗` и `blocked`.

## Stage: `/pf-test-plan` — Step 0, регрессия и дедупликация

Выполняется до написания новых кейсов.

1. **Чтение.** Если `docs/planning/test-plan.md` отсутствует — Step 0
   пропускается целиком (проект ещё не на новой схеме), стадия работает как
   сегодня.
2. **Отбор областей.** Из `brd.md`/`specs.md`/`analysis.md` извлекаются
   затронутые области; сопоставляются с колонкой `Area`.
3. **Кандидаты на регрессию.** Кейсы в этих областях со статусом `pending`,
   `✗`, `blocked` или `✓` предлагаются пользователем через
   `AskUserQuestion`: включить в тест-план issue или нет. Кейсы `covered` и
   `retired` не предлагаются.
4. **Дедупликация.** Если новый кейс дублирует существующий `PTC`, вместо
   создания пишется ссылка на него (AC-4.3).
5. **Схлопывание.** Если для существующего `PTC` в этой issue появляется
   автотест, `PTC` переводится в `covered` с заполненным `Covered by`
   (AC-4.4).

Пункты 4 и 5 меняют `docs/planning/test-plan.md` **до** закрытия issue — это
единственный случай, когда план правится не на `/pf-close`.

## Stage: `/pf` — индикатор долга

В статус-блок добавляется строка, только если долг ненулевой:

```
Planning Framework v3.0.0
Active issue: 20260806-feat-product-test-plan  (type: feat, tier: medium)
Completed stages: CREATE, BRD
⚠ 7 pending manual TC
Next step: /pf-spec
```

Считаются строки со статусом `pending`, `✗` и `blocked` — то есть всё, что
словарь относит к долгу. Отсутствие файла плана трактуется как ноль, без
предупреждения.

## New skill: `/pf-backfill`

Разовый интерактивный разбор ранее закрытых issue (US-5). Отдельная команда, а
не часть `/pf-close` — по решению владельца.

1. Перечислить папки `docs/issues/closed/*`, отбросив те, что уже есть в
   секции `Backfill log`.
2. Для каждой оставшейся: показать её `Manual`-кейсы и спросить через
   `AskUserQuestion` — импортировать или отказаться.
3. Импорт: строки промоутятся тем же правилом, что в Phase 5.5, со статусом
   `pending` и `Last run: —`.
4. Любой исход дописывается в `Backfill log` (AC-5.3).
5. Прерывание безопасно: обработанные issue уже записаны, при повторном запуске
   не переспрашиваются.

Скилл работает **в любом проекте** на фреймворке (AC-5.4): он не содержит
знания об этом репозитории и опирается только на `docs/issues/closed/` и
`docs/planning/test-plan.md`.

## Rollout для существующих проектов

`converge` кладёт `docs/planning/test-plan.md` из шаблона, если файла нет.
Существующий файл **не перезаписывается** — он пользовательский документ, а не
артефакт фреймворка.

Проект без файла плана продолжает работать: Step 0 в `/pf-test-plan`
пропускается, индикатор в `/pf` не показывается, а гейт Phase 0.5 в
`/pf-close` пропускает issue, у которой нет `Manual`-кейсов. Первая issue с
ручными кейсами создаст файл при промоушене.

## Risks

- **R-1.** Промоушен на `/pf-close` — последний шаг длинной стадии. Если он
  упадёт после мерджа, issue окажется закрытой без долга. Смягчение: Phase 0.5
  проверяет результат до мерджа, Phase 5.5 выполняется после архивации, и обе
  фазы идемпотентны — повторный запуск не создаёт дублей (проверка по паре
  `Origin issue` + название кейса).
- **R-2.** `Area` — свободный текст, поэтому отбор регрессии зависит от того,
  насколько единообразно её заполняют. Смягчение: при промоушене предлагаются
  уже встречавшиеся значения.
- **R-3.** Ручная правка таблицы ломает греп-контракт гейтов. Смягчение:
  `test/pf-product-test-plan.sh` проверяет форму строк, а не только их наличие.
