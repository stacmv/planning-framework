## Overview

Вводится один новый артефакт — `docs/planning/test-plan.md` — и правки в
пять существующих стадий (`/pf-close`, `/pf-qa`, `/pf-test`, `/pf-test-plan`,
`/pf`), Manual Test UI и `converge`, плюс одна новая команда (`/pf-backfill`).
Ручной кейс, родившийся в issue,
при закрытии получает глобальный `PTC-NNNN` и переезжает в продуктовый план;
там же он живёт со статусом, пока не будет выполнен, покрыт автотестом или
снят. Никакого второго реестра не заводится (BR-1).

```
issue N                              docs/planning/test-plan.md
┌──────────────────┐                 ┌─────────────────────────────┐
│ test_plan.md     │   /pf-close     │ PTC-0042 … pending          │
│  TC-001 Manual   │ ──promotion──▶  │ PTC-0043 … ✓ (human)        │
│  TC-002 Auto     │  (Manual only)  │ PTC-0044 … covered          │
└──────────────────┘                 └──────────┬──────────────────┘
        ▲                                       │
        │            /pf-test-plan              │
        └───── кандидаты на регрессию ──────────┘
                   (issue N+5)
```

BR-3 держит: локальные `TC-NNN` не переименовываются и не перенумеровываются
промоушеном. Но `brd.md`'s Non-Goals идёт шире («стадии до закрытия не
трогаются») — эта issue такую границу не удерживает буквально, см. Open
Questions ниже.

## Data model: `docs/planning/test-plan.md`

Файл — markdown с одной таблицей и одной служебной секцией. Читается и правится
руками; всё машиночитаемое извлекается грепом по строке таблицы.

### Строка кейса

| Колонка | Значения | Назначение |
|---|---|---|
| `PTC` | `PTC-NNNN` | глобальный ID, 4 цифры с ведущими нулями |
| `Area` | свободный текст, экранированный (см. ниже) | подсистема (`pf-close`, `explorer-ui`, …) |
| `Test case` | свободный текст, экранированный (см. ниже) | название кейса |
| `Manual reason` | `human-judgment` \| `agent-infeasible` \| `env-dependent` | почему ручной |
| `Prio` | `Critical` \| `High` \| `Med` \| `Low` | приоритет |
| `Origin issue` | ISSUE-ID | обратная ссылка (AC-1.2) |
| `Origin TC` | `TC-NNN` | локальный ID внутри `Origin issue` — см. «Идемпотентность» ниже |
| `Last run` | `YYYY-MM-DD` \| `—` | когда выполнялся последний раз |
| `Run by` | `human` \| `agent` \| `—` | кто выполнил (AC-3.2) |
| `Status` | см. ниже | текущее состояние |
| `Covered by` | `ISSUE-ID#TC-NNN` \| `—` | какой Auto-кейс закрыл ручной долг (AC-4.4) |

Колонка `Type` из примера в `prompt.md` **не заводится**: по решению D-3
промоутятся только `Manual`-кейсы, поэтому колонка была бы константой.

**Идемпотентность промоушена — пара, не название.** Ключ — (`Origin issue`,
`Origin TC`), а не (`Origin issue` + название кейса), как было в первой версии
спеки. Название не годится в ключ: два Manual TC в одной issue могут называться
одинаково при разных шагах, и тогда «дубль по названию» тихо не переносит
второй. `TC-NNN` внутри одной issue уникален по построению (`/pf-test-plan`
нумерует их), поэтому пара с ним — надёжный ключ. `Covered by` при этом ссылается
не на файл теста, а на `ISSUE-ID#TC-NNN` того Auto-кейса, что перекрыл долг —
путь к файлу нестабилен (тест может переехать), а issue+TC-NNN — нет, и оттуда
всегда можно дойти до реального теста через `/pf-test`'s TC-ID mapping.

**`Covered by` не заполняется в момент промоушена.** Строка приходит в план
Manual-кейсом со статусом из чеклиста (см. ниже); `covered` и `Covered by`
проставляются позже, отдельным механизмом (Stage `/pf-close`, шаги 8–11) —
только когда Auto-тест, который перекрывает её, реально прогнан и подтверждён.

### `manual_test_checklist.md`: поле `**Result:**` — откуда берётся `Run by`

Реальный шаблон `docs/planning/templates/issue/manual_test_checklist.md` не
хранит, кто выполнил кейс — только общее свободное поле `**Tester:**` на весь
документ и построчные чекбоксы, из которых «провалено» не отличимо от «ещё не
делалось» (см. Stage `/pf-qa` ниже). Без этого AC-3.2 нечем удовлетворить.

Фикс — по каждому TC-блоку, вместо расширения общего `**Tester:**`, отдельное
поле на уровне блока (`docs/planning/templates/issue/manual_test_checklist.md`,
сразу после `**Notes:**`; генерирует `/pf-test`'s Phase 5.3):

```markdown
**Result:** —
```

Значения — фиксированный словарь, читается грепом:

| Значение | Смысл |
|---|---|
| `—` | кейс ещё не выполнялся |
| `✓ human` | выполнен человеком, успешно |
| `✓ agent` | выполнен агентом, успешно (D-1: засчитывается) |
| `✗ human` | выполнен человеком, провален |
| `✗ agent` | выполнен агентом, провален |

Тестер (человек или агент) переводит `—` в одно из четырёх значений после
прохождения кейса — вручную в файле, либо через `/pf-manual-test`'s UI
(`tools/manual-test-ui`), который получает для этого элемент управления и
патч-функцию `patchResult()` в `tools/manual-test-ui/lib/checklist.js`, по
образцу уже существующих `patchNotes`/`patchStepResult` в том же файле —
включая то же правило «перечитать файл заново перед точечной правкой строки»,
которое те уже соблюдают, чтобы не затирать параллельную правку из другой
вкладки. Построчный чекбокс шагов при этом не трогается и не читается машинно
(см. Stage `/pf-qa`, «Per-step чекбокс не трогается») — `**Result:**` это
единственная машинно-читаемая запись исхода всего кейса.

`Priority` и `Type` в чеклист не переносятся: они уже есть в `test_plan.md`'s
Status Tracker, и тестеру они для выполнения шагов не нужны — дублирование
здесь стало бы вторым источником правды, тому же самому, от чего уже
предостерегает BR-1 для продуктового плана в целом.

**Регенерация не стирает `**Result:**`.** `/pf-test`'s Phase 5.3 может
перезаписать `manual_test_checklist.md` повторно (например, после фикса и
повторного `/pf-test`). Без явного правила это стёрло бы уже записанные
исходы и авторство — ровно тот класс потери, который сформулирован в
пользовательских инструкциях этого проекта для файлов с ручными правками:
перечитать и мерджить точечно, не генерировать поверх. При регенерации
Phase 5.3 сопоставляет новые TC-блоки со старыми по `TC-NNN` и переносит
`**Result:**` старого блока в новый как есть; блок без прежнего
`**Result:**` (кейс генерируется впервые, либо старый чеклист ещё не знал об
этом поле) получает `—`. Отсутствие строки `**Result:**` в чеклисте,
записанном до этой issue, тоже читается как `—`, не как ошибка формата —
тот же принцип, что уже применён к `dataStatus: "unknown"` для `Test Data` в
`tools/manual-test-ui/lib/checklist.js`.

### Экранирование и нормализация (грep-контракт)

Файл читается инструментами построчно (grep/awk), поэтому формат строки
таблицы обязан быть однозначным:

- **Ячейка — одна физическая строка**, без переносов и без `<br>`.
- **Буквальный `|` внутри `Area`/`Test case` экранируется как `\|`** — то же
  правило, что уже применяет `tools/manual-test-ui/lib/checklist.js`
  (`splitCells`/patch-функции) для ячеек `manual_test_checklist.md`. Разбор
  строки таблицы обязан делать то же самое: разбивать по `\|`, не предшествуемому
  обратным слешем (regex `(?<!\\)\|`), обрезать пробелы, затем разэкранировать
  `\|` обратно в `|` внутри уже отделённой ячейки. `Covered by` этому риску не
  подвержен — его значение это либо `—`, либо `ISSUE-ID#TC-NNN`, символ `|` там
  структурно невозможен.
- **`✓`/`✗` — канонические символы** (U+2713, U+2717) — то же написание, что уже
  использует `qa_report.md` и `test_plan.md`'s Status Tracker (`skills/pf-test/
  SKILL.md` Phase 3.4). Любой инструмент, читающий колонку `Status`, принимает на
  вход также `[x]`/`x`/`X`/`PASS` (регистронезависимо) как `✓` и нормализует их к
  каноническому виду при следующей же машинной правке этой строки — вручную
  вписанный нестандартный вариант не ломает чтение, но и не остаётся навсегда:
  следующий автоматический проход переписывает его в канон.
- `test/pf-product-test-plan.sh` проверяет форму строк механически: число ячеек
  после разбора совпадает с числом колонок заголовка, и в колонке `Status`
  встречаются только значения из словаря ниже.

### Словарь статусов

| Статус | Смысл | Считается долгом | Блокирует закрытие при `Critical` |
|---|---|---|---|
| `pending` | не выполнялся | да | **да** |
| `✓` | выполнен успешно | нет | нет |
| `✗` | выполнен, провален | да | **да** |
| `blocked` | не может быть выполнен по внешней причине | да | **да** |
| `covered` | появилось автопокрытие, из долга выбыл | нет | нет |
| `retired` | потерял смысл после изменения продукта | нет | нет |

**`blocked` блокирует закрытие наравне с `pending`.** Это прямое следствие
решения D-4 («обхода hard FAIL нет»): если бы `blocked` пропускал закрытие,
он и стал бы обходом — достаточно объявить критичный тест заблокированным.
Внешняя причина не отменяет того, что критичное поведение не проверено.

`retired` и `covered` — единственные способы убрать кейс из долга, не выполняя
его, и оба требуют содержательного основания в колонке `Covered by` либо в
отдельной строке-примечании под таблицей.

### Секция обработанных issue

Отметка из AC-5.3 живёт в этом же файле — отдельным списком под таблицей:

```markdown
## Backfill log

Ранее закрытые issue, по которым решение принято. Повторно не спрашиваются.

- `20260731-feat-pluggable-reviewers` — 2026-08-12 — imported (3 кейса)
- `20260703-improve-scale-doc-complexity` — 2026-08-12 — declined
```

Оба исхода (`imported` / `declined`) записываются одинаково: AC-5.3 требует не
спрашивать повторно **независимо от ответа**, поэтому отказ обязан оставлять
след. Хранение внутри `test-plan.md` соблюдает BR-1 — отметка не может
разойтись с планом, потому что это один файл и один дифф.

### Выделение `PTC-NNNN`

Файл несёт одну служебную мутируемую строку, в отдельной секции:

```markdown
## Sequence

Last allocated: PTC-0057 (20260731-feat-pluggable-reviewers)
```

Следующий номер = число из этой строки + 1. Отдельного счётчика вне файла нет —
он был бы вторым источником правды (BR-1). Выделение номера переписывает **обе**
части строки — и число, и ID issue в скобках — на новый номер и на issue,
которая его сейчас забирает.

Это не декорация, а сама защита от коллизии. Прежняя версия спеки полагалась
на то, что параллельный мердж разрешится «обычным конфликтом markdown-таблицы»
— неверно: если две ветки независимо друг от друга вставляют по одной новой
строке в *разные* места таблицы, git молча сливает обе вставки без единого
текстового пересечения, и обе строки могут получить один и тот же `PTC-NNNN`.
Одна мутируемая строка убирает эту дыру: две issue, промоутающие параллельно от
одного и того же родительского состояния, каждая переписывают эту же самую
строку — либо на разный номер, либо на тот же номер, но с разным ID issue в
скобках. Текст обеих правок при этом не может совпасть, а значит git не может
слить их молча: это настоящий конфликт, и Phase 4 `/pf-close` уже останавливает
мердж на конфликте и просит разрешить его руками. Защита не зависит от того,
повезёт ли вставке новой строки таблицы не пересечься по позиции — она
гарантирована самим фактом, что обе стороны трогают одну и ту же строку.

**Разрешение конфликта — руками, по одному правилу.** Тот, кто мерджит
вторую из двух веток, перенумеровывает **свои** только что добавленные строки
(`PTC` в таблице и `Origin issue`/`Origin TC` не трогаются — это чужие данные,
трогается только номер), взяв за основу `Last allocated` из уже смерженной
(победившей) версии секции `Sequence`, и переписывает саму строку `Sequence`
на новый максимум с собственным ISSUE-ID. Это ровно то же правило выделения
номера, что и в обычном, неконфликтном случае (шаг 5 промоушена) — конфликт
лишь заставляет применить его руками один раз, вместо того чтобы дать git
применить его молча и неверно.

**Непереиспользование (BR-2).** Строка только растёт. Перевод кейса в `retired`
и даже ручное удаление строки из таблицы не двигают её назад: следующее
выделение читает эту строку, а не таблицу, поэтому повторно выдать уже
выданный номер можно только осознанной ручной правкой этой строки назад — не
случайной правкой таблицы.

`test/pf-product-test-plan.sh` дополнительно проверяет отсутствие повторов
`PTC-NNNN` в таблице — страховка на случай, если эту строку всё же испортили
руками.

## Stage: `/pf-close` — промоушен и гейт

Прежняя версия спеки ставила гейт (Phase 0.5) раньше самого промоушена
(Phase 5.5, после архивации) — на первой же обычной issue с Manual TC гейт
видел, что строк ещё нет, и останавливал закрытие навсегда: промоушен, который
мог бы его удовлетворить, происходил только позже, за той же самой остановкой.
Отдельно, порядок «мердж → архивация → промоушен» не восстанавливается: реальный
`skills/pf-close/SKILL.md:7` определяет активную issue только по
`docs/issues/open/`, а Phase 5 к этому моменту уже переносит папку в `closed/`
— сбой между архивацией и записью в план необратимо теряет долг, и повторный
`/pf-close` эту issue уже не находит.

Обе проблемы чинятся одним и тем же порядком: **промоушен выполняется первым,
до подтверждения у пользователя, до мерджа, до архивации** — пока issue ещё
физически лежит в `open/` и ветка `issue/ISSUE-ID` ещё активна. Гейт
разворачивается не в отдельную фазу, а во вторую половину той же фазы: сначала
пишем, затем перечитываем с диска и проверяем, что написанное действительно
там.

### Phase 0.5 — промоушен и гейт (новая, заменяет прежние 0.5+5.5)

Выполняется сразу после Phase 0 (все её проверки уже прошли, включая «на
правильной ветке»), до Phase 1 (подтверждение у пользователя).

1. Прочитать `docs/issues/open/ISSUE-ID/test_plan.md`'s Status Tracker,
   отобрать строки `Type: Manual`.
2. Если таких строк нет — перейти к шагу 8 (обработка `covered`, см. ниже):
   переносить нечего, но покрытие проверяется независимо от наличия Manual TC.
3. Если `docs/planning/test-plan.md` не существует (первый промоушен в этом
   проекте) — создать его из `docs/planning/templates/global/test-plan.md`.
   Если и локального шаблона нет (проект не сходился через `converge` после
   этой issue) — создать файл по минимальной структуре, эквивалентной
   шаблону: шапка таблицы, пустая секция `## Sequence`, пустая секция
   `## Backfill log`. Отсутствие шаблон-файла никогда не блокирует промоушен.
4. **Проверка идемпотентности.** Для каждой Manual-строки искать в
   `docs/planning/test-plan.md` строку с той же парой (`Origin issue`,
   `Origin TC`). Если найдена — эта строка уже промоутирована (предыдущая
   попытка `/pf-close` дошла до этого места раньше и упала позже) — пропустить
   её, не создавать вторую.
5. Для каждой оставшейся Manual-строки выделить `PTC-NNNN` (правило — см.
   «Выделение `PTC-NNNN`» выше) и добавить строку в `docs/planning/test-plan.md`:

   | Поле issue | → | Поле продуктового плана |
   |---|---|---|
   | название кейса | → | `Test case` |
   | `Priority` | → | `Prio` |
   | ISSUE-ID | → | `Origin issue` |
   | `TC-NNN` | → | `Origin TC` |
   | — | → | `PTC` (выделяется по правилу выше) |
   | — | → | `Area` (см. Stage `/pf-test-plan`, «Отбор областей»; при пустом результате — спросить) |
   | `**Result:**` из `manual_test_checklist.md` (см. ниже) | → | `Status` + `Run by` |

   **Источник `Status`/`Run by` — маппинг `**Result:**` → строка плана:**

   | `**Result:**` в чеклисте | `Status` | `Run by` |
   |---|---|---|
   | `—` (не выполнялся) | `pending` | `—` |
   | `✓ human` | `✓` | `human` |
   | `✓ agent` | `✓` | `agent` |
   | `✗ human` | `✗` | `human` |
   | `✗ agent` | `✗` | `agent` |

   Это механическое соответствие, не эвристика: кейс без известного актора не
   может стать `✓` (`Run by: —` возможен только вместе со `Status: pending`),
   что делает AC-3.2 непропускаемым. Откуда берётся сам `**Result:**` — см.
   Stage `/pf-qa`, «Синхронизация чеклиста».
6. Если шаг 5 добавил хотя бы одну строку — закоммитить это изменение отдельно
   от всего остального: `git add docs/planning/test-plan.md && git commit -m
   "chore: promote N manual TC to product test-plan [ISSUE-ID]"`. Коммит
   остаётся на ветке `issue/ISSUE-ID`; отдельный push здесь не нужен — Phase 4
   унесёт его в PARENT-BRANCH тем же `--no-ff`-мерджем, что и любой другой
   коммит ветки, а запушит Phase 8.5, как обычно.
7. **Гейт — проверка по факту, не по памяти.** Перечитать
   `docs/planning/test-plan.md` заново с диска (не полагаться на то, что было
   записано на шаге 5 в этой же сессии — тот же принцип, что и в
   `~/.claude/skills/pf-size-tiers/SKILL.md`, «Evaluating it is a MECHANICAL
   check»). Для каждой Manual-строки из шага 1 убедиться, что строка с её
   парой (`Origin issue`, `Origin TC`) теперь существует. Если хотя бы одной
   не хватает — **остановиться**, перечислив все недостающие: «Промоушен
   ручных кейсов не состоялся для TC-NNN[, TC-MMM, ...]. Закрыть issue с
   долгом можно, потерять долг — нельзя.» Не переходить к Phase 1.
8. **Обработка `covered` (не гейт, best-effort).** Если
   `docs/planning/test-plan.md` не существует (и шаг 3 не создавал его, потому
   что на шаге 2 Manual-строк не было) — шаги 8–11 пропускаются целиком:
   нечего связывать со строкой, которой ещё нет, и заводить файл только ради
   `covered`-пометки не нужно. Иначе: прочитать `test_plan.md`'s Status
   Tracker ещё раз, отобрать строки `Type: Auto`, `Status: ✓`, чей блок
   `### TC-NNN:` содержит `**Supersedes:** PTC-NNNN` (поле пишет
   `/pf-test-plan`, см. Stage `/pf-test-plan`).
9. Для каждой найденной пары: если `PTC-NNNN` существует в
   `docs/planning/test-plan.md` и его `Status` не `covered`/`retired` —
   выставить `Status: covered`, `Covered by: ISSUE-ID#TC-NNN` (свой же
   Auto-кейс).
10. Отсутствие `PTC` или `Supersedes` ничего не ломает и не останавливает
    закрытие — единственный жёсткий гейт этой фазы — шаг 7.
11. Если шаг 9 что-то изменил, зафиксировать это тем же коммитом, что шаг 6
    (если он ещё не сделан) либо отдельным коммитом с тем же сообщением-шаблоном.

Промоушен откладывается до момента, когда Auto-тест реально прогнан и
подтверждён (`Status: ✓` в Status Tracker), а не в момент, когда он только
запланирован в `/pf-test-plan` — иначе ручной долг мог бы исчезнуть раньше,
чем появился реальный тест, который его закрывает.

#### Что делает повторный запуск после сбоя на каждом шаге

- **Сбой до коммита шага 6** (например, до записи строк или во время неё):
  рабочее дерево либо чистое, либо содержит незакоммиченную правку
  `docs/planning/test-plan.md`. `git status --porcelain` это покажет; issue
  всё ещё в `open/`, ветка всё ещё `issue/ISSUE-ID` — повторный `/pf-close`
  просто начинается заново с Phase 0. Если висит частичная незакоммиченная
  правка — отменить её (`git checkout -- docs/planning/test-plan.md`) перед
  повтором: шаг 4 проверяет закоммиченную историю, а не грязное дерево.
- **Сбой после коммита шага 6, до подтверждения на шаге 7** (в том числе
  случай, когда шаг 7 сам находит недостающую строку): коммит промоушена уже
  есть на `issue/ISSUE-ID`. Повторный `/pf-close` заново входит в Phase 0.5;
  шаг 4 находит уже промоутированные строки и пропускает их — добавляются
  только реально недостающие. Phase 5 (архивация) не наступит, пока шаг 7 не
  пройдёт.
- **Сбой где угодно после прохождения Phase 0.5** (конфликт мерджа, обрыв
  архивации, сбой usage-report/session-log): промоушен уже закоммичен и уже
  подтверждён — он въезжает в PARENT-BRANCH вместе с остальной историей ветки
  на `--no-ff`-мердже Phase 4, как любой другой коммит. Потерять ручной долг с
  этой точки уже невозможно; остальные сбои Phase 4-8 — это те же случаи,
  что `/pf-close` уже обрабатывал до этой issue, и они `test-plan.md` не
  касаются.

## Stage: `/pf-qa` — Phase 3.6, учёт ручного долга

Реальный `skills/pf-qa/SKILL.md` уже занимает номер Phase 3.5 (риск
пропущенного код-ревью) — прежняя спека этого не учла и указывала на
несуществующую точку встраивания. Новая фаза — **Phase 3.6**, сразу за
существующей 3.5, всё ещё до Phase 4 (запись `qa_report.md`).

Реальный `manual_test_checklist.md` не хранит ни `Priority`, ни `Type`, ни
однозначного «выполнен/провален» на уровне кейса — там только чекбоксы на
уровне отдельных шагов, и чекбокс `[ ]` по инструкции самого чеклиста
означает и «не сделано», и «сделано, но не так, как ожидалось» одновременно.
Приоритет и тип кейса живут только в `test_plan.md`'s Status Tracker. Поэтому
Phase 3.6 использует оба файла, каждый для того, что в нём реально есть, а не
угадывает по одному:

```
test_plan.md (issue) — Type=Manual, Priority   ←── источник приоритета/типа
        │
        ▼
manual_test_checklist.md — **Result:** для каждого TC   ←── источник факта прогона
        │
        ▼
синхронизировать: **Result:** → Status Tracker'а Status-колонка
        │
        ├─ остался Manual+Critical с Status ∈ {[ ], ✗}?
        │        └─ да ──▶ вердикт FAIL, блокер «Critical manual test not run/failed»
        │                  (обхода нет — D-4)
        │
        └─ остались некритичные Manual с Status ∈ {[ ], ✗}?
                 └─ да ──▶ AskUserQuestion: выполнить сейчас / отложить
                            └─ отложить ──▶ вердикт PASS
                                            + строка «Deferred manual tests: N»
```

### Синхронизация чеклиста

1. Прочитать `test_plan.md`'s Status Tracker, отобрать строки `Type: Manual`
   — по каждой знаем `TC-NNN` и `Priority`.
2. Прочитать `manual_test_checklist.md`; для каждого `TC-NNN` из шага 1 найти
   его `**Result:**` (поле, которое пишет `/pf-test` при генерации чеклиста и
   правит тестер/агент вручную либо через `/pf-manual-test`'s UI — см.
   «Result: откуда берётся `Run by`» ниже). Значения: `—` (не выполнялся),
   `✓ human`, `✓ agent`, `✗ human`, `✗ agent`.
3. Переписать в `test_plan.md`'s Status Tracker Status-колонку для этой
   строки: `—` → оставить `[ ]`; `✓ *` → `✓`; `✗ *` → `✗`. Сохранить
   `test_plan.md`. Это тот же принцип, что уже применяет `/pf-test`'s Phase
   3.4 к Auto-кейсам (там — по выводу тест-раннера, здесь — по чеклисту):
   Status Tracker остаётся единственным местом, откуда что-либо читает
   дальше по конвейеру, включая промоушен на `/pf-close`.

   Эта правка нуждается в владельце коммита: реальная таблица стадий в
   `~/.claude/skills/pf-git/SKILL.md` (Step 1) до этой issue отводила
   `/pf-qa` только `qa_report.md`, и правка `test_plan.md` осталась бы
   висеть неучтённой — ровно то, что этот же файл называет источником
   «дальней» дырки в `git status`, всплывающей у другой стадии. Правка этой
   issue: строка `/pf-qa` в этой таблице получает второй путь,
   `test_plan.md`, наравне с `qa_report.md` (см. Files to Create/Modify).
4. **Гейт.** Строка с `Type: Manual`, `Priority: Critical` и Status ∈
   `{[ ], ✗}` после синхронизации — жёсткий `FAIL`, без обхода (D-4): и
   невыполненный, и выполненный-но-проваленный критичный ручной тест
   одинаково означают, что критичное поведение не подтверждено.
5. Некритичные Manual со Status ∈ `{[ ], ✗}` предлагаются пользователю через
   `AskUserQuestion`: выполнить сейчас или отложить. Отложить не меняет их
   `Status` в `test_plan.md` (кейс мог быть реально `✗`, это не стирается) —
   отсрочка означает только «вердикт остаётся `PASS`», а долг всё равно
   попадёт в продуктовый план таким, каким получен по факту (BR-5: `pending`
   — законный способ отложить *невыполненный* кейс; уже выполненный и
   провалённый некритичный кейс отсрочки не требует, он просто не блокирует).
   Строка `Deferred manual tests: N` пишется в `qa_report.md` рядом с
   вердиктом и читается грепом.

### Per-step чекбокс не трогается

Построчный чекбокс `| ... | [ ] |` в таблице шагов каждого TC остаётся как
есть и **не читается машинно** ни этой фазой, ни промоушеном — это
человеко-читаемый дневник прохождения шагов для тестера, отдельный от
итогового `**Result:**` на уровне всего TC. Смешивать их обратно — именно тот
источник неоднозначности, который эта фаза устраняет.

## Stage: `/pf-test-plan` — Step 0, регрессия и дедупликация

Выполняется до написания новых кейсов. **Ничего в этой стадии не пишет в
`docs/planning/test-plan.md`** — план целиком читается, никогда не правится
здесь; единственные места, где он меняется, это `/pf-close` (Phase 0.5) и
`/pf-backfill`. Это инвариант, а не случайность: `/pf-test-plan` работает на
этапе планирования, когда ни один автотест этой issue ещё не написан и не
прогнан, — записывать в продуктовый план что-либо раньше, чем есть факт
(прогон или реальный код автотеста), значило бы промоутить домысел.

1. **Чтение.** Если `docs/planning/test-plan.md` отсутствует — Step 0
   пропускается целиком (проект ещё не на новой схеме), стадия работает как
   сегодня.
2. **Отбор областей.** Механически, не по интуиции модели:
   - Словарь областей — значения, уже встречающиеся в колонке `Area`
     `docs/planning/test-plan.md` (пустой словарь на первом прогоне — тогда
     этот пункт не находит кандидатов, см. ниже).
   - Из путей файлов, упомянутых в `brd.md`/`specs.md`/`analysis.md`, берётся
     второй сегмент пути под известным корнем (`skills/`, `tools/`,
     `scripts/`) как токен: `skills/pf-close/SKILL.md` → `pf-close`,
     `tools/manual-test-ui/...` → `manual-test-ui`. Несколько разных токенов
     — issue считается многообластной, каждый токен участвует в отборе
     кандидатов по отдельности (совпадение с любым токеном включает кейс в
     кандидаты).
   - Токен, отсутствующий в словаре, всё равно предлагается как «новая
     область» на шаге 3, а не отбрасывается — словарь используется для
     сопоставления с уже существующими `PTC`, а не как белый список
     допустимых значений.
   - Если из документов issue не удалось извлечь ни одного токена (пути не
     упоминаются вовсе) — Step 0 пропускает отбор регрессии с пометкой «не
     удалось определить область» и переходит сразу к шагу 4; кейсы для
     регрессии не подбираются наугад.
3. **Кандидаты на регрессию.** Кейсы в отобранных областях со статусом
   `pending`, `✗`, `blocked` или `✓` предлагаются пользователем через
   `AskUserQuestion`: включить в тест-план issue или нет. Кейсы `covered` и
   `retired` не предлагаются.
4. **Дедупликация.** Если новый кейс дублирует существующий `PTC`, вместо
   создания локального `TC-NNN` в `test_plan.md` пишется ссылка на
   существующий `PTC` (AC-4.3). Это правка **локального** `test_plan.md`
   issue, не продуктового плана — сам `PTC` не трогается.
5. **Ссылка на покрытие, не схлопывание.** Если новый Auto-кейс issue
   покрывает существующий ручной `PTC` (пользователь подтвердил это в рамках
   пункта 3/4), в блок нового `TC-NNN` в **локальном** `test_plan.md`
   дописывается `**Supersedes:** PTC-NNNN`. Статус самого `PTC` не меняется
   здесь: на этой стадии автотест ещё не написан и не прогнан, откладывать
   долг раньше факта нельзя (это и была P1-находка ревью против прежней
   версии). Фактическое `covered` происходит на `/pf-close` (Phase 0.5, шаги
   8–11) — только когда этот же `TC-NNN` в Status Tracker реально получил
   `✓` после `/pf-execute`/`/pf-test`.

## Stage: `/pf` — индикатор долга

В статус-блок добавляется строка, только если общий долг (`pending` + `✗` +
`blocked`) ненулевой:

```
Planning Framework v3.0.0
Active issue: 20260806-feat-product-test-plan  (type: feat, tier: medium)
Completed stages: CREATE, BRD
⚠ 1 pending manual TC, 6 failed/blocked
Next step: /pf-spec
```

**Число перед «pending manual TC» — строго количество строк со статусом
`pending`**, ровно как требует AC-6.1 буквально; предыдущая версия спеки
считала туда же `✗` и `blocked`, из-за чего строка называлась «pending», а
показывала совсем другую цифру. `✗`/`blocked` не исчезают из вида — они
дописываются вторым сегментом `, M failed/blocked`, только если их
количество не ноль (в примере выше: 1 pending, 6 failed/blocked). Если
`pending = 0`, но `failed/blocked > 0`, строка всё равно печатается —
`⚠ 0 pending manual TC, 6 failed/blocked` — потому что долг в целом не ноль,
а прятать `✗`/`blocked` за отсутствием строки было бы ровно той же ошибкой,
только в другую сторону.

Отсутствие файла плана трактуется как ноль, без предупреждения.

## New skill: `/pf-backfill`

Разовый интерактивный разбор ранее закрытых issue (US-5). Отдельная команда, а
не часть `/pf-close` — по решению владельца.

1. Перечислить папки `docs/issues/closed/*`, отбросив те, что уже есть в
   секции `Backfill log`.
2. Для каждой оставшейся: показать её `Manual`-кейсы и спросить через
   `AskUserQuestion` — импортировать или отказаться.
3. **Импорт.** Строки промоутятся тем же правилом, что в `/pf-close` Phase
   0.5 (шаг 5) — включая пару (`Origin issue`, `Origin TC`) в качестве ключа
   идемпотентности — со статусом `pending`, `Run by: —` и `Last run: —`:
   бэкфилл не подтверждает исполнение, он лишь спасает от потери сам факт
   существования кейса.
4. **Атомарность записи.** Импортированные строки (если исход — `imported`)
   и запись в `Backfill log` пишутся на диск за один проход и коммитятся
   **одним и тем же коммитом**: `git add docs/planning/test-plan.md && git
   commit -m "chore: backfill ISSUE-ID (imported N|declined) [pf-backfill]"`.
   Один коммит на одну обработанную issue, не один коммит на весь прогон —
   так прерывание после issue №3 из 10 не откатывает уже решённые 1–3, и не
   оставляет ни одной issue в промежуточном состоянии «строки есть, лога
   нет» или наоборот дольше одной итерации цикла.
5. **Что делает повторный запуск.** Если процесс упал **до** этого коммита
   (например, между записью строк на диск и `git commit`), рабочее дерево
   останется грязным по `docs/planning/test-plan.md` — `git status
   --porcelain` покажет незакоммиченную правку. `/pf-backfill` при следующем
   запуске проверяет это первым делом: если правка похожа на незавершённый
   импорт (строки и/или запись в лог есть, коммита нет) — закоммитить её
   перед тем, как делать что-либо ещё; иначе (правка не своя, либо дерево
   чисто, но лога об этой issue нет) issue считается ещё не решённой и
   спрашивается заново — это безопасно, потому что AC-5.3 обязывает не
   переспрашивать только про уже **записанные** (закоммиченные) решения, а
   незакоммиченная попытка решением не является.
6. После обработки всех папок — commit & push по обычной процедуре
   (`~/.claude/skills/pf-git/SKILL.md`), как последнее действие скилла;
   локальные коммиты по шагу 4 уже страхуют прогресс независимо от push.

Скилл работает **в любом проекте** на фреймворке (AC-5.4): он не содержит
знания об этом репозитории и опирается только на `docs/issues/closed/` и
`docs/planning/test-plan.md`.

## Rollout для существующих проектов

`docs/planning/test-plan.md` доставляется тем же механизмом, что уже
используют `session-log.md`/`decisions.md`/`implementation-plan.md` —
`t5_global_docs()` в `scripts/converge-to-v3.sh:926-939`: файл создаётся из
шаблона **только если его ещё нет** в проекте, существующий файл не
перезаписывается (он пользовательский документ, а не артефакт фреймворка).
Правка: добавить `test-plan.md` в перечень `for f in session-log.md
decisions.md implementation-plan.md`, а сам шаблон положить в
`docs/planning/templates/global/test-plan.md` — рядом с шаблонами тех же трёх
файлов. Это разъясняет прежнюю формулировку, которая называла несуществующий
путь `docs/planning/templates/test-plan.md` и не указывала, каким именно
циклом converge файл будет создан — `t6_mirror_templates()` (тот же
`converge-to-v3.sh`, строки 945-976) заодно зеркалит и сам шаблон в
`docs/planning/templates/global/` целевого проекта — это ожидаемо и не
требует отдельной правки: `t6` уже зеркалит всю директорию `templates/`
целиком.

Если проект **не сходился** через `converge` после появления этой issue,
локального шаблона может не быть вовсе — `/pf-close`'s Phase 0.5 (шаг 3) на
этот случай создаёт `docs/planning/test-plan.md` по минимальной инлайн-схеме,
эквивалентной шаблону, а не падает из-за отсутствующего файла шаблона.

Проект без файла плана продолжает работать: Step 0 в `/pf-test-plan`
пропускается, индикатор в `/pf` не показывается, а Phase 0.5 в `/pf-close`
пропускает шаги 3–7, если у закрываемой issue нет `Manual`-кейсов (шаг 2).
Первая issue с ручными кейсами создаст файл при промоушене.

## Risks

- **R-1.** Промоушен на `/pf-close` теперь выполняется первым шагом стадии
  (Phase 0.5), а не последним — если он упадёт, issue остаётся в `open/` на
  своей ветке, и повторный запуск находит её и продолжает (см. «Что делает
  повторный запуск» под Phase 0.5). Идемпотентность — по паре (`Origin
  issue`, `Origin TC`), не по названию кейса.
- **R-2.** `Area` — свободный текст, поэтому отбор регрессии зависит от того,
  насколько единообразно её заполняют. Смягчение: словарь уже встречавшихся
  значений плюс механическое извлечение токена из пути (`/pf-test-plan` Step
  0, пункт 2); пустой результат честно пропускает отбор, а не гадает.
- **R-3.** Ручная правка таблицы ломает греп-контракт гейтов. Смягчение:
  `test/pf-product-test-plan.sh` проверяет форму строк (число ячеек,
  допустимые значения `Status`, отсутствие повторов `PTC-NNNN`), а не только
  их наличие.
- **R-4.** Единственный правдоподобный источник конкурентной записи в
  `docs/planning/test-plan.md` — две issue, промоутающие параллельно на
  разных ветках. Смягчение — «Sequence»-строка (см. Data model): любая
  конкурентная попытка выделить номер правит одну и ту же строку по-разному,
  что git не может слить молча, а разрешает как обычный конфликт мерджа —
  ранее эта коллизия не была бы замечена вовсе.
- **R-5.** `manual_test_checklist.md`'s новое поле `**Result:**` вводит
  зависимость от `tools/manual-test-ui` (парсинг/патч, см. Files to
  Create/Modify) — тестер, работающий только через UI, а не руками в файле,
  не сможет проставить исход, пока UI не получит соответствующий контрол.
  Смягчение: поле остаётся обычным markdown-текстом, редактируемым и без UI —
  UI необязателен для корректности данных, только для удобства.

## Open Questions

- **OQ-1 (тензия с Non-Goal `brd.md`).** `brd.md`'s Non-Goals заявляет:
  «Изменение пайплайна внутри issue... стадии до закрытия не трогаются».
  Эта спека это обязательство буквально не удерживает. P0-3 (найдено ревью:
  `manual_test_checklist.md` физически не несёт `Priority`/`Type`/однозначного
  исхода) не оставляет способа выполнить AC-2.1/AC-2.2/AC-3.2, не трогая
  до-закрытие стадии: `/pf-test` (Phase 5.3 — новое поле `**Result:**`
  генерируется прямо в чеклист), `/pf-qa` (новая Phase 3.6 читает **и
  переписывает** `test_plan.md`'s Status Tracker — это правка существующей
  механики стадии, не только добавление нового шага рядом с ней),
  `/pf-test-plan` (Step 0 читает план и пишет ссылки `**Supersedes:**`/дедуп-
  ссылки в локальный `test_plan.md`). BR-3 (`TC-NNN` не переименовываются и не
  перенумеровываются) остаётся верным отдельно от этого — оно у́же, чем текст
  Non-Goal, и ни одно из трёх изменений его не задевает. Но сам текст
  Non-Goal сформулирован шире, чем BR-3, и это расхождение открытое: решение
  владельца — либо принять его как есть, либо сузить формулировку Non-Goal в
  `brd.md` до того, что фактически гарантирует BR-3.
