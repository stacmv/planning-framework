## Overview

Один новый артефакт — `docs/planning/test-plan.md` — и одна правка в одну
стадию: `/pf-close` переносит в него `Manual`-кейсы закрываемой issue.

```
issue N                            docs/planning/test-plan.md
┌──────────────────┐               ┌──────────────────────────────┐
│ test_plan.md     │  /pf-close    │ PTC-0001 … Critical … ✓      │
│  TC-001 Manual   │ ──перенос──▶  │ PTC-0002 … High     … pending│
│  TC-002 Auto     │ (Manual only) │ PTC-0003 … Med      … retired│
└──────────────────┘               └──────────────────────────────┘
                                            │
                                    прогон перед релизом
```

Стадии до закрытия не трогаются. Manual Test UI не трогается. Гейтов,
блокирующих закрытие issue, не вводится.

## Data model: `docs/planning/test-plan.md`

Файл — markdown с заголовком, строкой-счётчиком и одной таблицей. Правится
руками (BR-4), поэтому формат выбран так, чтобы ручная правка его не ломала.

```markdown
# Manual Test Plan

Ручные тест-кейсы продукта. Автотесты — `make test`.
Прогон перед релизом: пройти строки со статусом `pending`, начиная с `Critical`.

Last allocated: PTC-0003

| PTC | Area | Test case | Prio | Origin | Last run | Status |
| --- | --- | --- | --- | --- | --- | --- |
| PTC-0001 | pf-close | Родительская ветка определяется при self-tracking upstream | Critical | 20260729-bug-pf-close-parent-branch#TC-004 | 2026-08-06 | ✓ |
| PTC-0002 | explorer-ui | Тема сохраняется между перезагрузками страницы | High | 20260729-improve-manual-test-data#TC-020 | — | pending |
```

### Колонки

| Колонка | Значения | Назначение |
|---|---|---|
| `PTC` | `PTC-NNNN` | глобальный номер, 4 цифры с ведущими нулями (AC-2.2) |
| `Area` | короткий идентификатор подсистемы | чтобы группировать при прогоне |
| `Test case` | одна фраза | что проверяем (AC-1.2) |
| `Prio` | `Critical` \| `High` \| `Med` \| `Low` | AC-1.3 |
| `Origin` | `ISSUE-ID#TC-NNN` | ссылка на источник (AC-2.3) |
| `Last run` | `YYYY-MM-DD` \| `—` | AC-1.4 |
| `Status` | `pending` \| `✓` \| `✗` \| `retired` | AC-1.4, AC-3.2 |

### Словарь статусов

| Статус | Смысл |
|---|---|
| `pending` | не выполнялся или требует повторного прогона |
| `✓` | пройден успешно при последнем прогоне |
| `✗` | провален при последнем прогоне |
| `retired` | потерял смысл после изменения продукта; строка остаётся ради номера (BR-2, AC-3.3) |

Четырёх значений достаточно: `pending` покрывает и «никогда не гоняли», и «пора
перепроверить». Отдельный `blocked` не заводится — он не меняет действий
читателя перед релизом, а различать причины можно словами в `Test case`.

### Самодостаточность кейса (AC-1.2)

В `Test case` переносится название кейса из `test_plan.md` issue. Если название
не читается в отрыве от контекста issue (`Проверить шаг 3`), при переносе оно
дополняется до самостоятельной фразы. Полные шаги остаются в issue и доступны
по ссылке `Origin`.

### Выделение номера

Следующий номер = **максимум из двух величин, плюс единица**: значения в строке
`Last allocated: PTC-NNNN` над таблицей и наибольшего `PTC` в самой таблице.
После переноса строка обновляется до выданного номера.

**Форма записи задаётся отдельно от арифметики.** Номер пишется как `PTC-` плюс
ровно четыре цифры с ведущими нулями — и в ячейке, и в строке-счётчике; `none`
(стартовое значение шаблона) считается нулём, поэтому первый выданный номер всегда
`PTC-0001`. Это не дублирование правила «максимум плюс один»: реальное закрытие на
свежем списке, выполненное по редакции, где была задана только арифметика, записало
строку `| 1 | …` и счётчик `Last allocated: 1` — арифметически верно и отвергнуто
собственным валидатором формата, требующим четыре цифры.

**Если строки `Last allocated:` нет вовсе — её восстанавливают, а не падают.** BR-4
разрешает ручную правку файла, значит строку могли удалить. Она восстановима:
отсутствующий счётчик считается `none` (нулём), эффективным максимумом остаётся
наибольший `PTC` таблицы, и строка дописывается обратно над таблицей. Молчаливый
пропуск здесь опаснее ошибки: подстановка по образцу на файле без такой строки
завершается успешно и не меняет ничего, поэтому строка исчезла бы, а кейс всё равно
записался (P1 code review).

Два источника, а не один, потому что каждый по отдельности дырявый:

- **только таблица** — `retired`-строку могут удалить руками, максимум упадёт,
  номер переиспользуется, нарушая BR-2. Счётчик помнит удалённое;
- **только счётчик** — если перенос успел записать строки, но упал до
  обновления счётчика, следующий запуск выдаст те же номера поверх уже
  существующих. Таблица помнит записанное.

Максимум из обоих самовосстанавливается после частичной записи: расхождение
счётчика и таблицы никогда не приводит к повторной выдаче.

**Параллельные ветки этим не защищены, и это принято сознательно.** Первая
версия спеки утверждала, что меняющийся счётчик даёт git-конфликт. Это неверно:
две ветки, стартовав с `PTC-0003` и перенеся по одному кейсу, обе запишут
`PTC-0004` — для git это не конфликт, а совпадающее изменение, merge пройдёт
молча и оставит два разных кейса под одним номером.

Поэтому уникальность не предотвращается, а **обнаруживается**:
`test/pf-product-test-plan.sh` падает при дубликате `PTC`, то есть на первом же
`make test` после мерджа. Разрешение — перенумеровать строки, приехавшие
вторыми, и поднять счётчик до нового максимума. Гарантировать уникальность на
уровне файла можно было бы только внешним счётчиком или ID, производным от
источника (`Origin` уникален по построению) — оба варианта дороже проблемы:
проект односоставный, две issue редко закрываются параллельно, а цена ошибки —
одна ручная перенумерация, пойманная автотестом.

### Устойчивость к ручной правке (BR-4)

- Символ `|` внутри `Area`, `Test case` и `Origin` экранируется как `\|`.
  Перенос заменяет `|` на `\|` при записи.
- Значения `Prio` и `Status` — из закрытых словарей выше, в нижнем регистре для
  `pending`/`retired` и символами `✓`/`✗` для прогонов. Иных написаний не
  предусмотрено: `test/pf-product-test-plan.sh` проверяет, что каждая строка
  таблицы соответствует форме, и падает на самодельных значениях, не давая им
  расползтись.
- Ячейка — одна строка. Многострочный текст в таблицу не переносится.

## Stage: `/pf-close` — Phase 4.5, перенос

Выполняется **после мерджа (Phase 4), до архивации (Phase 5)** — то есть пока
папка issue ещё лежит в `docs/issues/open/`.

Это единственное безопасное место, и вот почему. `/pf-close` определяет
активную issue сканированием `docs/issues/open/` и останавливается, если там
пусто (`skills/pf-close/SKILL.md:7`). Если перенос поставить после архивации и
он упадёт, повторный `/pf-close` завершится с «No active issue found» — issue
уже закрыта, а ручные кейсы потеряны без возможности восстановления. С
переносом до архивации сбой оставляет папку на месте, и повторный запуск
находит issue и доводит дело до конца.

Привязки к пути папки у переноса нет: `Origin` — это `ISSUE-ID#TC-NNN`, а не
путь на диске, поэтому перенос до архивации ничего не ломает.

1. **Убедиться, что `docs/planning/test-plan.md` существует — это делается ПЕРВЫМ
   шагом, до любого отбора.** Нет файла — создать из шаблона; нет и шаблона
   (старый проект без конвергенции) — записать содержимое инлайн.

   Порядок именно такой, а не «создать, если понадобилось», потому что Phase 8
   кладёт путь в `git add` безусловно, а `git add` с одним несуществующим
   pathspec завершается кодом 128 и **не стажирует ничего** — даже остальные
   валидные пути той же команды. Создание файла только при наличии
   `Manual`-строк ломало бы архивный коммит любой issue с `Auto`-only
   тест-планом: папка issue уже перемещена на диске, а коммита нет (P0 code
   review, измерено).

2. Прочитать `test_plan.md` закрываемой issue, отобрать строки Status Tracker
   с `Type: Manual`. Если таблица есть, но `Manual`-строк в ней нет — фазе больше
   нечего делать (файл из шага 1 остаётся, с пустой таблицей). **Колонки
   таблицы определяются по заголовку** (`Type`, `Test Case`, `Priority`,
   `Status`), а не по фиксированной позиции: в репозитории сосуществуют два
   реальных порядка колонок — `TC | Type | Test Case | Priority | Status |
   Remarks` (`docs/planning/templates/issue/test_plan.md`) и `TC | Test Case
   | Type | Priority | Status | Remarks` (`~/.claude/skills/pf-test-plan/
   SKILL.md`, Step 4 — тот же порядок, что и в `test_plan.md` этой самой
   issue). Позиционный парсинг на одной из двух раскладок прочитает название
   кейса как `Type` и не отберёт ни одной `Manual`-строки.
   **Нераспознанный вход — останов с сообщением, а не молчаливый пропуск.** Три
   случая неотличимы от легитимного «переносить нечего», если их просто
   проскочить, и каждый молча теряет ручной кейс — ровно та потеря, против
   которой заведена вся фаза (P1 code review). Останов, а не пропуск, если:
   `Type` не `Manual` и не `Auto` (пустая ячейка, регистр `manual`,
   декорированное `Manual (blocked)`) — по умолчанию считать такую строку `Auto`
   нельзя, `Critical`-кейс не должен исчезать из-за опечатки; таблица Status
   Tracker не найдена вовсе (секция отсутствует, переименована, заголовок без
   нужных колонок) — это НЕ то же, что таблица без `Manual`-строк; у отобранной
   `Manual`-строки пустая ячейка `Test Case`.

   При остановке сообщение обязано называть конкретный дефект и путь исправления:
   к этому моменту Phase 4 уже смерджила и переключилась на родительскую ветку,
   поэтому нужный `test_plan.md` не перед оператором. Он должен выбросить
   частичную запись, перейти на issue-ветку, **починить строку и закоммитить**, и
   только затем перезапускать — иначе повторный прогон встанет на том же месте.

3. Для каждого отобранного кейса, которого ещё нет в списке (ключ — пара
   `ISSUE-ID` + `TC-NNN` в колонке `Origin`), добавить строку:

   | Поле issue | → | Поле списка |
   |---|---|---|
   | название кейса | → | `Test case` (дополняется до самостоятельного, см. выше) |
   | `Priority` | → | `Prio` (с нормализацией, см. ниже) |
   | `Status` `✓`/`✗`/`[ ]` | → | `✓` / `✗` / `pending` |
   | ISSUE-ID + TC-NNN | → | `Origin` |
   | дата закрытия, если статус не `pending` | → | `Last run` |
   | — | → | `PTC` (см. «Выделение номера») |
   | — | → | `Area` (см. ниже) |

4. Обновить строку `Last allocated:` до наибольшего выданного номера.
5. Оставить файл в рабочем дереве: он попадёт в коммит закрытия на Phase 8,
   чья команда `git add` дополняется путём `docs/planning/test-plan.md`
   (`skills/pf-close/SKILL.md:147`). Правка именно там, а **не** в таблице
   стейджинга `pf-git`: строки `/pf-close` в ней нет вовсе — эта стадия
   коммитит сама, своим `git add docs/issues/ docs/planning/session-log.md`.

**Нормализация `Priority` → `Prio`.** Шаблон issue использует
`Critical / High / Medium / Low` (`docs/planning/templates/issue/test_plan.md:24`),
а словарь списка — `Critical / High / Med / Low`. Отображение однозначное:
`Critical`→`Critical`, `High`→`High`, `Medium`→**`Med`**, `Low`→`Low`. Значение
вне этих четырёх переносится как `Med` с примечанием в `Test case`, чтобы
закрытый словарь не порождал падение автопроверки на чужом написании.

**`Area`.** Определяется по списку файлов, изменённых issue. Phase 4.5 идёт
**после** Phase 4 (`git merge --no-ff issue/ISSUE-ID`), поэтому диапазон
нельзя брать как трёхточечный `<parent>...<issue-branch>`: после `--no-ff`
мерджа merge-base(`<parent>`, `issue/ISSUE-ID`) — это уже сама вершина
issue-ветки, и такой diff всегда пуст. Измерено на реальном закрытии
`20260806-bug-test-plan-tc-untracked`: `git diff --name-only
develop...issue/20260806-bug-test-plan-tc-untracked` → 0 файлов, тогда как
`git diff --name-only <merge-коммит>^1 <merge-коммит>^2` → 15 файлов. Вместо
трёхточечного диапазона команда берёт оба родителя мерджа: на Phase 4.5 этот
merge-коммит — ещё свежий `HEAD` родительской ветки (архивный коммит Phase 8
случится позже), поэтому команда — `git diff --name-only HEAD^1 HEAD^2`:
`HEAD^1` — состояние родительской ветки до мерджа, `HEAD^2` — вершина
`issue/ISSUE-ID`; разница между ними — ровно набор файлов issue.

**Берутся родители ПЕРВОГО мерджа этой issue, а не текущего `HEAD`** (P2 code
review, проход 3): `git log --merges --format=%H --grep "merge: close ISSUE-ID"
<родитель> | tail -1`, затем `git diff --name-only <merge>^1 <merge>^2`. На чистом
прогоне этот мердж и есть `HEAD`, поэтому поведение не меняется. Но правило
stop-and-surface велит оператору починить строку и **закоммитить её на
issue-ветке**, из-за чего повторный `git merge` создаёт второй merge-коммит, и
родители `HEAD` описывают уже не набор файлов issue, а одну правку под
`docs/issues/`, которая исключается — `Area` вырождается в `general`. Привязка к
первому мерджу не требует состояния и не требует сбрасывать родительскую ветку. Из
результата исключаются `docs/issues/` (документы самой issue не говорят о
подсистеме) **и ровно четыре бухгалтерских файла, поимённо**:
`docs/planning/session-log.md`, `decisions.md`, `implementation-plan.md` и сам
`test-plan.md`; иначе мердж, отличающийся только ими, дал бы бессмысленное
`Area: docs`.

Именно список, а не glob и не каталог — оба обобщения неверны (P2 code review,
проходы 2 и 3). `docs/planning/*.md` захватил бы настоящую документацию того же
уровня (`FRAMEWORK.md`, `QUICKSTART.md`, `MIGRATION-GUIDE-V3.md`,
`v2.0-design-analysis.md`), и issue про правку `FRAMEWORK.md` получила бы
`general` — ровно то бессмысленное значение, от которого исключение защищает.
Исключение каталога целиком дополнительно захватило бы
`docs/planning/templates/` с продуктовыми артефактами фреймворка (эта же issue
добавила туда `global/test-plan.md`). Подкаталоги `docs/planning/` не
исключаются никогда. Из
оставшихся путей берётся второй сегмент для `skills/` и
`tools/` (`skills/pf-close/…` → `pf-close`, `tools/manual-test-ui/…` →
`manual-test-ui`), первый — для остальных (`scripts/…` → `scripts`).
Побеждает подсистема с наибольшим числом файлов; при пустом остатке —
`general`. Значение правится руками при прогоне, поэтому точность здесь не
критична — но команда задана, чтобы реализация не изобретала свою.

**Идемпотентность.** Ключ — пара (`ISSUE-ID`, `TC-NNN`), а не название кейса:
два `Manual`-кейса в одной issue могут называться одинаково при разных шагах.
Повторный запуск фазы не создаёт дублей. Номера при повторе тоже не съезжают:
следующий номер считается как максимум из счётчика и таблицы (см. «Выделение
номера»), поэтому частично записанный перенос самовосстанавливается.

**Если фаза упала.** Папка issue ещё в `docs/issues/open/`, ветка issue цела,
issue не потеряна. Сама фаза идемпотентна: идентичность строки — пара
(`ISSUE-ID`, `TC-NNN`), а номер считается как максимум из счётчика и таблицы,
поэтому повторный проход не создаёт дублей.

**Окружающие фазы сами не возобновляются** — исходная редакция этого раздела
утверждала обратное, и это было неверно (P1 code review). Фаза 4 к моменту сбоя уже
переключилась на родительскую ветку, поэтому Phase 0 требует находиться на
`issue/ISSUE-ID` и остановится с «Switch to the issue branch first» — нужен ручной
`git checkout issue/ISSUE-ID`.

**Частичную запись при восстановлении нужно выбросить, а не сохранять.** Порядок:
восстановить файл из коммита (`git checkout -- docs/planning/test-plan.md`; если он
был создан в этом же прогоне и ещё не отслеживается — удалить), затем переключиться
на issue-ветку, затем перезапустить. Сохранение частичной записи ломает
восстановление двумя независимыми способами, оба измерены (Codex pass 2):

- **Переключение вообще не проходит**, если issue-ветка отрезана до появления
  `docs/planning/test-plan.md` на родительской ветке — на такой ветке файла нет, а он
  изменён, поэтому git отказывается: «Your local changes … would be overwritten by
  checkout … Aborting», exit 1. Документированное восстановление оказалось бы
  неисполнимым для всех ветвей старше файла.
- **`Area` вычисляется неверно** там, где переключение всё же прошло: Phase 2
  закоммитит недописанный файл как `chore: pre-close cleanup` на issue-ветку, из-за
  нового коммита повторный `git merge` создаст **второй** merge-коммит, и
  `git diff HEAD^1 HEAD^2` опишет этот второй мердж (одну бухгалтерию) вместо
  реального набора файлов issue.

При выбрасывании частичной записи оба эффекта исчезают: дерево чистое, Phase 2 нечего
подметать, повторный `git merge` действительно отрабатывает как no-op (`Already up to
date`, `HEAD` остаётся исходным merge-коммитом), и `Area` считается из исходного
диффа issue так же, как на первом прогоне.

Приводить Phase 0 и Phase 2 к бесшовному возобновлению без ручного шага означало бы
менять существующее поведение `/pf-close` вне объёма этой issue — этот остаток
ограничения зафиксирован в самой Phase 4.5, а не обойдён.

---

## Rollout

`converge` доставляет шаблон в проект по правилу «создать, если файла нет»
(механизм `t5_global_docs()`), рядом с прочими глобальными документами
`docs/planning/`. Существующий файл не перезаписывается — он пользовательский.

Проект без файла работает как раньше: первая же закрытая issue с ручными
кейсами создаст его.

## Risks

- **R-1.** `Area` определяется эвристикой по диффу и будет иногда мазать.
  Принято сознательно: поле правится руками, а ошибка в нём не мешает пройти
  кейс.
- **R-2.** Список растёт без ограничения. Разбивать на файлы по областям — не
  сейчас, а когда перестанет читаться.
