## Findings

### P0 (Blocker)

**1. `[Claude]` `[Codex]` `git add` на Phase 8 ломает закрытие issue без Manual-кейсов.**
`skills/pf-close/SKILL.md:186` передаёт `docs/planning/test-plan.md` в `git add`
безусловно. Но `skills/pf-close/SKILL.md:80` говорит: при отсутствии `Manual`-строк
Phase 4.5 «does nothing; proceed to Phase 5» — файл не создаётся.

Найдено обоими ревьюерами независимо. Codex пометил находку `[P2]`, при том что его
же summary называет её блокирующей («This is a blocking correctness issue for that
workflow»); приоритет поднят до P0 по результату измерения, а не по метке.

Проверено эмпирически на живом репозитории:

```
$ git add docs/issues/ docs/planning/session-log.md docs/planning/test-plan.md
fatal: pathspec 'docs/planning/test-plan.md' did not match any files
$ echo $?
128
$ git diff --cached --name-only
(пусто)
```

`git add` с одним несуществующим pathspec завершается кодом 128 и **не стажирует
ничего** — ни `docs/issues/`, ни `session-log.md`.

**Сценарий отказа.** Закрывается обычный багфикс, у которого в Status Tracker только
`Type: Auto` кейсы, в проекте глобального файла ещё нет. Phase 4.5 корректно ничего
не делает. Phase 5 уже переместила папку issue в `docs/issues/closed/`. Phase 8
падает, коммита `close: archive ISSUE-ID` нет: на диске issue закрыта, в истории —
нет.

**Этот репозиторий в зоне поражения:** `git cat-file -e develop:docs/planning/test-plan.md`
→ `does not exist`. Текущая issue уцелела случайно — у неё есть ручные кейсы.

**Почему сьют не поймал.** TC-013 шаг 2 (`test/pf-product-test-plan.sh:478-495`) только
грепает секцию Phase 8 на литералы, команду не выполняет. Оба ручных прогона
TC-014/TC-016 использовали фикстуры с Manual-кейсами, поэтому файл к Phase 8 всегда
существовал — эта ветка ни разу не проходилась вживую.

### P1 (Important)

**2. `[Claude]` Восстановление после сбоя внутри Phase 4.5 работает не так, как
заявлено в трёх местах диффа; TC-016 этот сценарий не проверял.**

Сбой *внутри* Phase 4.5 означает, что Phase 4 уже выполнилась: `git checkout
PARENT-BRANCH` и `git merge --no-ff` прошли, текущая ветка — PARENT-BRANCH, в дереве
незакоммиченный `docs/planning/test-plan.md`. Цепочка при перезапуске:

1. Phase 0 проверка 3 (`skills/pf-close/SKILL.md:19`) видит PARENT-BRANCH вместо
   `issue/ISSUE-ID` и останавливается «Switch to the issue branch first». Это уже
   опровергает формулировку `skills/pf-close/SKILL.md:78` «a re-run picks the issue
   back up and finishes the phase idempotently» — прямого подхвата нет, нужен ручной
   шаг, о котором текст фазы не говорит.
2. После `git checkout issue/ISSUE-ID` грязный файл переезжает вместе. Phase 2 видит
   непустой `git status` и коммитит его как `chore: pre-close cleanup` **на
   issue-ветку** — недописанный кусок глобального файла попадает в историю
   issue-ветки, а не в архивный коммит Phase 8, как задумано в `specs.md`.
3. Phase 4 выполняется второй раз. Поскольку на issue-ветке появился новый коммит,
   это **не** no-op — вопреки `specs.md:224` («повторный `git merge` на Phase 4
   отработает как no-op»): создаётся второй самостоятельный merge-коммит.
4. Phase 4.5 шаг 5 считает `Area` как `git diff --name-only HEAD^1 HEAD^2`. На
   повторном прогоне это разница между первым merge-коммитом и `chore: pre-close
   cleanup` — то есть **только** `docs/planning/test-plan.md`. Путь не под
   `docs/issues/`, фильтр его не исключает, первый сегмент — `docs`. **`Area`
   становится `docs`** вместо реальной подсистемы.

Одна цепочка событий опровергает три отдельных утверждения диффа.

**Почему TC-016 это не поймал (важно для честности вердикта).** Фикстура
материализует частичное состояние на ветке `issue/<fixture-ID>` **без**
предшествующего merge-коммита, поэтому живой прогон делает **первый** merge, а не
повторный, и не проходит ни через Phase 0 проверку 3, ни через повторный merge, ни
через подметание Phase 2. Зафиксированный `PASS` относится к более слабому сценарию
(«одна строка уже записана»), чем тот сбой посреди фазы, который кейс декларирует.

**3. `[Claude]` Phase 4.5 не описывает вход, не укладывающийся в перечисленные ветки;
транскрибированные хелперы доопределяют поведение молча, из-за чего сьют соглашается
сам с собой.** Один класс дефекта, четыре проявления:

- **`Type` не `Manual` и не `Auto`.** `SKILL.md:80` перечисляет два значения как
  исчерпывающие. `pf_ptp_select_manual` (`test/pf-product-test-plan.sh:110-113`) делает
  `awk '$3 == "Manual"'` — опечатка `manual`, пустое значение или `Manual (blocked)`
  тихо отбрасываются наравне с `Auto`. `Critical` ручной кейс теряется при закрытии
  без единого сообщения.
- **Секция `## Status Tracker` отсутствует или переименована.** `pf_ptp_parse_rows`
  не находит строк; результат неотличим от легитимного «нет Manual-строк». Тот же
  тихий полный проигрыш ручных кейсов.
- **Строка `Last allocated:` удалена руками.** BR-4 прямо разрешает ручную правку, но
  для переноса этот случай не описан. `pf_ptp_promote_row`
  (`test/pf-product-test-plan.sh:246-254`) делает
  `sed -i "s/^Last allocated:.*/…/"`; проверено эмпирически — на файле без этой строки
  `sed -i` завершается кодом 0 и молча ничего не меняет, функция всё равно печатает
  присвоенный `PTC`, счётчик исчезает из файла. Фикстура `no-counter` используется
  только для валидатора (TC-008 шаг 5), никогда для промоушена — комбинация не покрыта.
- **Пустой заголовок кейса.** `pf_ptp_expand_title` на пустой строке возвращает её же
  (regex «шаг N» не матчится → считается самодостаточной), а
  `pf_validate_test_plan_file` непустоту `Test case` не проверяет — пустая ячейка
  проходит валидацию и попадает в человеко-читаемый список.

**4. `[Claude]` TC-014 шаг 3 в тест-плане остался дефектным.**

## Проходы 2-5

Гейт `/pf-codereview` — циклический: после каждого исправления дифф пересчитывается и
оба ревьюера запускаются заново. Здесь это оправдалось трижды — каждый следующий P1
был дефектом **в исправлении предыдущего**, а не новым слоем проблем.

| Проход | Codex | Claude | Итог |
|---|---|---|---|
| 1 | P0 (помечен `[P2]`) | P0 + 3 P1 + 2 P2 | FAIL |
| 2 | 2 находки (обе помечены `[P2]`, одна — неисполнимость восстановления) | новый P1 + 3 P2 | FAIL |
| 3 | 1 P2 (`Area` на повторе) | тот же P1 независимо + 3 P2 | FAIL |
| 4 | чисто | 1 P1 (устаревшее обоснование, закреплённое тестом) | FAIL |
| 5 | 1 P2 (валидатор принимает файл без таблицы) | P0/P1 нет, 2 редакторских P2 | **PASS** |

**Что нашли проходы 2-5, сверх отчёта выше.**

- **Восстановление после сбоя было неисполнимо** (Codex, проход 2). Если issue-ветка
  отрезана до появления `docs/planning/test-plan.md`, `git checkout issue/ID` падает с
  exit 1: на ветке файла нет, а он изменён. Три остальные открытые issue репозитория
  как раз такие. Исправлено выбрасыванием частичной записи вместо сохранения — это
  же сняло и вторую находку про неверную `Area`.
- **`Area` вырождалась в `general` на повторном мердже** (оба ревьюера, проход 3) —
  причём триггером было моё же правило stop-and-surface, велящее закоммитить починку
  на issue-ветке. Исправлено привязкой к **первому** мерджу issue вместо `HEAD`; на
  чистом прогоне это тот же коммит, поэтому поведение не меняется.
- **`specs.md` воспроизводила исправленный P0 в прозе** (Claude, проход 2) —
  синхронизирована.
- **Исключение `docs/planning/` было слишком широким** (Claude, проход 3): захватывало
  `docs/planning/templates/` с продуктовыми артефактами и настоящую документацию
  (`FRAMEWORK.md` и др.). Сужено до четырёх бухгалтерских файлов поимённо.
- **Тест закреплял противоречие** (Claude, проход 4): `TC-021 step 7` грепал
  утверждение про неверную `Area`, ставшее ложным после фикса прохода 3 — привести
  прозу в порядок значило уронить тест. Guard переписан на действующее утверждение,
  корректность `Area` проверяется git-пробником, а не grep'ом по прозе.
- **Валидатор принимал файл без таблицы** (Codex, проход 5): счётчик на месте, таблица
  снесена руками — цикл разбора не выходил из поиска заголовка и возвращал успех.
  Исправлено, покрыто двумя фикстурами.

**Форма тестов оказалась отдельным источником дефектов.** Трижды проверка на
существование текста прошла бы и на сломанной версии: у порядка шагов Phase 4.5
дефект был исключительно в порядке; у сужения исключения `Area` — проверка «верхний
уровень исключён» одинаково довольна и сужённым, и слишком широким правилом; у
устаревшего обоснования grep закреплял именно ту формулировку, которую надо было
менять. Поэтому такие места проверяются сравнением номеров строк, утверждением
нескольких взаимно ограничивающих условий и реальными git-пробниками.

**Инциденты процесса.** Ревьюер прохода 2, которому предписано только читать, оставил
рабочее дерево на `develop` — следующая задача видела не те файлы. Обнаружено и
исправлено; `develop` остался на `9f171c3`, совпадает с `origin/develop`, на него
