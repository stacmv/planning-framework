# Test Plan: Глобальный чек-лист ручных тестов

**Date:** 2026-08-11

## Overview

Фича не имеет нового UI. Три источника поведения:

- `docs/planning/templates/global/test-plan.md` — новый шаблон, статический файл;
- `skills/pf-close/SKILL.md` — новая Phase 4.5, текст, интерпретируемый
  LLM-агентом во время реального `/pf-close`;
- `scripts/converge-to-v3.sh` (`t5_global_docs()`) и `test/pf-product-test-plan.sh` —
  обычные bash-скрипты, детерминированные и исполняемые напрямую.

Отсюда два рода Auto-проверок (подробности — в Prerequisites, группы A/B):

- **Группа A** — поведение описано прозой в Phase 4.5 и исполняется LLM-агентом,
  а не скриптом. Транскрибировать его в bash-хелпер и прогнать на фикстуре можно
  (как `test/pf-close.sh` делает для Phase 3/Phase 6), но хелпер сам по себе
  проверяет копию требований, а не продукт. Поэтому КАЖДЫЙ такой кейс обязан
  нести собственный drift-guard-шаг — grep по тексту `skills/pf-close/SKILL.md`,
  подтверждающий, что проверяемое правило реально там задокументировано. Без
  этого шага тест остаётся зелёным, даже если Phase 4.5 в SKILL.md так и не
  появится — это и есть P0-1 из ревью, устранённый ниже.
- **Группа B** — поведение исполняет сам `converge-to-v3.sh`/`pf-product-test-plan.sh`
  напрямую; кейс запускает реальный скрипт на фикстуре.

**Manual** — где утверждение проверяемо только реальным прогоном `/pf-close`
живой Claude Code сессией: факт переноса и попадание файла в коммит закрытия,
восстановление после сбоя посреди фазы. Оба таких кейса (TC-014, TC-016)
запускаются НЕ в рабочем дереве проекта, а в изолированной одноразовой копии
репозитория — см. Prerequisites.

Цель прогона — подтвердить приёмку из `brd.md`: невыполненный ручной кейс не
исчезает при закрытии issue, а виден в `docs/planning/test-plan.md` с
номером, приоритетом и ссылкой на источник (AC-1.1–AC-3.3, BR-1–BR-4).

## Prerequisites

План написан test-first: на момент написания ничего из перечисленного ниже
ещё не существует в репозитории. Чтобы красный результат до реализации был
диагностичным, а не «упало на сетапе», кейсы разведены по двум группам, а
Required Data ниже — это то, что реализация ДОЛЖНА создать, а не готовое
условие входа.

**Группа A — красный сегодня означает «фичи нет» (ожидаемый, диагностичный
сигнал).** TC-001–TC-006, TC-009, TC-010, TC-013, TC-015, TC-017 читают текст
`skills/pf-close/SKILL.md` через grep (drift-guard). Сегодня в файле нет
Phase 4.5 вообще — эти grep-проверки падают именно поэтому. Как только
Phase 4.5 появится с описанными в ней правилами, кейсы позеленеют без
создания какой-либо дополнительной тестовой инфраструктуры. Там, где кейс
группы A также требует транскрибированный helper на фикстуре (TC-001–006,
009, 010, 015), drift-guard — отдельный шаг внутри ТОГО ЖЕ TC, а не отдельный
TC: так фикстура и SKILL.md проверяются одним прогоном, и совпадение
хелпера со спекой не маскирует отсутствие правила в самом SKILL.md.

**Группа B — красный сегодня означает «тестовая инфраструктура ещё не
создана», а не то, что проверяемое правило неверно.** TC-007, TC-008, TC-011,
TC-012, TC-018, TC-019 запускают `test/pf-product-test-plan.sh` и/или реальный
`scripts/converge-to-v3.sh`. `test/pf-product-test-plan.sh` — часть той же
issue (specs.md, «Files to Create/Modify») и сегодня не существует;
`t5_global_docs()` в `converge-to-v3.sh` сегодня ничего не знает о
`test-plan.md`. Каждый такой TC ниже первым шагом делает explicit-проверку
существования/правила с ОТДЕЛЬНЫМ диагностическим сообщением («скрипт/правило
ещё не создан(о)» — сетап или отсутствующая фича), и только после неё
переходит к шагам, проверяющим конкретную логику («дубликат PTC не пойман» и
т.п.) со своим отдельным сообщением. Так первая причина падения не
маскирует вторую.

**Фикстуры.** Все пути под `test/fixtures/pf-product-test-plan/` в
«Требуемые данные» ниже — это ФИКСТУРЫ, КОТОРЫЕ ЕЩЁ НЕ СУЩЕСТВУЮТ. Их
создание — задача реализации, наравне с `test/pf-product-test-plan.sh` и
`docs/planning/templates/global/test-plan.md`, а не готовое условие входа.
`implementation_plan.md` должен явно заводить шаг «создать фикстуры
`test/fixtures/pf-product-test-plan/*`» до соответствующих Auto-задач.

**Харнесс.** `test/lib.sh` (`pf_setup_case`, `pf_repo_copy`, `pf_pass`/`pf_fail`,
`assert_repo_untouched`, `TMP_HOME`) уже существует и используется БЕЗ
изменений — гарантии S-1..S-5 уже даны им, отдельно их обеспечивать не нужно.

**Manual-кейсы (TC-014, TC-016).** Ни один из них не касается рабочего дерева
`<repo-root>` напрямую. Оба следуют одной и той же
последовательности: (1) снять копию репозитория в отдельную временную
директорию вне репозитория — тем же приёмом, что `pf_repo_copy` использует
для Auto-кейсов; (2) в этой копии `git remote remove origin`, затем
`git remote -v` и убедиться, что вывод пуст, — ПЕРВЫМ действием, а не
сноской, чтобы Phase 8.5 (`/pf-close`, «safe auto-push») физически не могла
никуда запушить; (3) удалить из копии реальные issue под `docs/issues/`,
оставив только фикстур-issue; (4) выполнить `/pf-close` внутри копии; (5)
последним шагом — подтвердить, что реальное рабочее дерево не тронуто.
Детали — в Preconditions/Steps каждого из двух кейсов.

## Test Cases

### TC-001: Только Manual-кейсы переносятся в глобальный список (BR-1) — группа A

**Description:** Проверяет, что промоушен Phase 4.5 отбирает из Status Tracker закрываемой issue только строки с `Type: Manual` и полностью игнорирует строки с `Type: Auto` — ни сама строка, ни любые её поля не попадают в `docs/planning/test-plan.md`. Красный сегодня по двум независимым причинам: drift-guard (шаг 3) падает первым и сразу, потому что `skills/pf-close/SKILL.md` вообще не содержит Phase 4.5; отдельно, фикстура и транскрибированный helper ещё не созданы (задача реализации). Именно drift-guard, а не совпадение хелпера со спекой, доказывает, что тест проверяет продукт, а не копию требований — тем же приёмом, что `test/pf-close.sh` TC-005 использует для Phase 3/6.

**Preconditions:**
- Собрана bash-функция, транскрибирующая алгоритм отбора из `specs.md` («Stage: /pf-close — Phase 4.5», шаг 1), тем же приёмом, что `test/pf-close.sh` использует для Phase 3/Phase 6 (helper ещё не создан — задача реализации).
- Фикстура issue, чей Status Tracker содержит минимум одну строку `Type: Auto` и минимум две строки `Type: Manual` (фикстура ещё не создана — задача реализации).

**Steps:**

| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Запустить транскрибированный отбор на фикстуре | В выборке присутствуют обе строки `Type: Manual`, строка `Type: Auto` отсутствует |
| 2 | Сравнить число отобранных строк с числом строк `Type: Manual` в фикстуре | Числа совпадают |
| 3 | Drift-guard: в секции Phase 4.5 файла `skills/pf-close/SKILL.md` (от заголовка `## Phase 4.5` до следующего заголовка `## Phase`) найти явное указание, что переносятся только строки `Type: Manual` (допустима любая формулировка, содержащая литерал `Type: Manual` или эквивалент) | Указание присутствует; если Phase 4.5 отсутствует или не документирует отбор по `Type: Manual` — тест падает с сообщением «Phase 4.5 не документирует отбор по Type: Manual», отдельным от провала шагов 1-2 |

**Требуемые данные:**
- `test/fixtures/pf-product-test-plan/issue-mixed-types/docs/issues/open/20990101-feat-fixture-mixed/test_plan.md` _(фикстура создаётся в рамках реализации этой issue)_

**Expected Outcome:** В выборке для промоушена присутствуют только строки `Type: Manual`; ни один Auto-TC не порождает строку в глобальном файле; правило задокументировано в самом SKILL.md, а не только в этом тесте.

**Priority:** Critical
