# Test Plan: `make tui` — интерактивный мастер установки/обновления

## Обзор и цели

Данный тест-план проверяет новую make-цель `make tui` — интерактивный терминальный мастер (Node.js, `node:readline`, без npm-зависимостей), который определяет текущее состояние целевого проекта (`none` / `v2-or-older` / `v3` / `unknown`), показывает соответствующее меню действий, предлагает новым пользователям обучающий туториал по концепциям фреймворка и делегирует фактическую работу существующим скриптам (`setup-planning-v3.sh`, `migrate-v2-to-v3.sh`, `update-skills.sh`) через `child_process.spawn` с унаследованным stdio.

Цели тестирования:
- Убедиться, что `lib/detect.js` корректно классифицирует все четыре состояния проекта на основе маркерных файлов.
- Убедиться, что меню показывает правильный набор пунктов для каждого состояния и что состояние `unknown` никогда не выбирает действие автоматически.
- Убедиться, что туториал поддерживает навигацию вперёд/назад/выход и не блокирует переход к установке.
- Убедиться, что выбор пункта меню корректно делегируется существующим скриптам через `spawn` с унаследованным stdio, без дублирования их логики.
- Убедиться, что существующие `make`-цели (`setup-v3`, `update-skills`, `migrate-v1-to-v2`, `migrate-v2-to-v3`, `setup-v2`, `issue-status`) продолжают работать без изменений (AC-4).

## Предварительные условия

- Репозиторий `planning-framework` склонирован локально, ветка с изменениями для `tools/onboarding-tui/` актуальна.
- Установлен Node.js (без дополнительных npm-зависимостей — `tools/onboarding-tui` не должен требовать `npm install`).
- Для сценариев с целевым проектом подготовлены временные фикстур-директории, имитирующие каждое из состояний:
  - `none`: пустая директория без `docs/issues/`, `PLANNING.md`, `CLAUDE.md`.
  - `v3`: директория с `PLANNING.md`, содержащим строку `Framework Version: 3.x`.
  - `v2-or-older`: директория с `CLAUDE.md`, но без `PLANNING.md`.
  - `unknown`: директория с `docs/issues/`, но без `PLANNING.md` и `CLAUDE.md`.
- Доступ к терминалу для ручного запуска `make tui` и наблюдения за интерактивным вводом/выводом.
- Существующие скрипты `scripts/setup-planning-v3.sh`, `scripts/migrate-v2-to-v3.sh`, `scripts/update-skills.sh` присутствуют и исполняемы.
- Важно (изоляция окружения): `scripts/update-skills.sh` всегда пишет в реальный `$HOME/.claude/skills` — у него нет понятия "целевой проект", и флаг `TARGET`/`SOURCE` на это не влияет. Перед любым тест-кейсом, вызывающим `update-skills.sh` (напрямую или через TUI), необходимо сделать резервную копию `~/.claude/skills` (например, `cp -r ~/.claude/skills ~/.claude/skills.bak.$$`) либо запускать команду с переопределённой переменной окружения `HOME`, указывающей на scratch-директорию; после теста — восстановить исходное содержимое (или удалить scratch-`HOME`).
- `make setup-v3` запускает `scripts/setup-planning-v3.sh` без аргументов — скрипт интерактивно запрашивает целевую директорию (`read -rp`, по умолчанию `$(pwd)`). У цели `setup-v3` нет переменной `TARGET` в Makefile.
- `make migrate-v2-to-v3` запускает `scripts/migrate-v2-to-v3.sh` без аргументов — Makefile не прокидывает позиционный аргумент, хотя сам скрипт поддерживает `$1` (`TARGET_DIR="${1:-.}"`); поэтому `make migrate-v2-to-v3` всегда работает с `.` (директорией, из которой вызван `make`).
- Единственная make-цель, реально поддерживающая `TARGET=<путь>`, — это `tui` (`node tools/onboarding-tui/cli.js $(if $(TARGET),--target $(TARGET),)`). Использование `TARGET=` с `setup-v3` или `migrate-v2-to-v3` не имеет эффекта и не должно фигурировать в шагах тест-кейсов ниже.
- Вне рамок данного тест-плана: прочие нестандартные/некорректные комбинации фикстур (например, повреждённый `docs/issues/` без прав на чтение, симлинки, частично записанные файлы маркеров и т.п.) явно не тестируются — только четыре состояния из таблицы specs.md плюс перечисленные ниже граничные случаи.

### TC-002: Определение состояния `v3` (включая совместное наличие `CLAUDE.md`)

**Description:** Проверяет, что `detect.js` возвращает `v3`, когда `PLANNING.md` содержит строку `Framework Version: 3.x` — как в чистом виде, так и когда в той же директории одновременно присутствует `CLAUDE.md` (реальная структура репозитория `planning-framework`), чтобы убедиться, что `v3` имеет приоритет над `v2-or-older` согласно таблице определения состояния в specs.md.

**Preconditions:**
- Фикстур-директория A: файл `PLANNING.md`, содержащий текст `Framework Version: 3.0.0`, без `CLAUDE.md`.
- Фикстур-директория B: файл `PLANNING.md`, содержащий текст `Framework Version: 3.0.0`, и одновременно файл `CLAUDE.md` в той же директории.

**Steps:**

| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Вызвать функцию определения версии, передав путь к фикстур-директории A | Функция выполняется без ошибок |
| 2 | Проверить возвращаемое значение для директории A | Возвращается состояние `v3` |
| 3 | Вызвать функцию определения версии, передав путь к фикстур-директории B (`PLANNING.md` 3.x + `CLAUDE.md` одновременно) | Функция выполняется без ошибок |
| 4 | Проверить возвращаемое значение для директории B | Возвращается состояние `v3` (не `v2-or-older`) — `PLANNING.md` с версией 3.x имеет приоритет в таблице определения состояния |

**Test Data:**
- A: `PLANNING.md` с содержимым, включающим `Framework Version: 3.0.0`
- B: то же `PLANNING.md`, плюс `CLAUDE.md` в той же директории

**Expected Outcome:** Наличие `PLANNING.md` с версией 3.x корректно распознаётся как `v3` независимо от того, присутствует ли также устаревший `CLAUDE.md`.

**Priority:** Critical

### TC-004: Определение состояния `unknown`

**Description:** Проверяет, что `detect.js` возвращает `unknown` для нестандартных случаев: (a) есть `docs/issues/`, но нет ни `PLANNING.md`, ни `CLAUDE.md`; (b) `PLANNING.md` присутствует, но не содержит маркер `Framework Version: 3.x` (отсутствует, повреждён или указывает на будущую версию, например 4.0) и `CLAUDE.md` отсутствует — такой файл не подходит ни под одно из известных состояний таблицы specs.md.

**Preconditions:**
- Фикстур-директория A: поддиректория `docs/issues/`, без `PLANNING.md` и `CLAUDE.md`.
- Фикстур-директория C: файл `PLANNING.md` без строки `Framework Version: 3.x` (например, содержит `Framework Version: 4.0.0` или вообще не содержит строку `Framework Version:`), `CLAUDE.md` отсутствует.

**Steps:**

| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Вызвать функцию определения версии, передав путь к фикстур-директории A | Функция выполняется без ошибок |
| 2 | Проверить возвращаемое значение для директории A | Возвращается состояние `unknown` |
| 3 | Вызвать функцию определения версии, передав путь к фикстур-директории C (`PLANNING.md` без маркера 3.x, без `CLAUDE.md`) | Функция выполняется без ошибок |
| 4 | Проверить возвращаемое значение для директории C | Возвращается состояние `unknown` (не `v3` и не `v2-or-older`) |

**Test Data:**
- A: `docs/issues/` присутствует; `PLANNING.md` и `CLAUDE.md` отсутствуют
- C: `PLANNING.md` без валидного маркера версии 3.x; `CLAUDE.md` отсутствует

**Expected Outcome:** Нестандартная структура и файл `PLANNING.md` без распознаваемого маркера версии 3.x корректно помечаются как `unknown`, а не ошибочно как одно из известных состояний.

**Priority:** High

### Integration — делегирование существующим скриптам

### TC-007: Делегирование установки в `setup-planning-v3.sh` через spawn

**Description:** Проверяет, что выбор "Install v3.0 into this project" в состоянии `none` запускает `scripts/setup-planning-v3.sh` как дочерний процесс с унаследованным stdio (пользователь видит и может отвечать на промпты скрипта так же, как при прямом запуске `make setup-v3`), и что TUI не перехватывает и не переинтерпретирует его вывод.

**Preconditions:**
- Фикстур-директория `none` подготовлена.
- TUI запущен командой `make tui TARGET=<путь к фикстуре none>` (единственная make-цель, реально поддерживающая `TARGET=`), показано меню состояния `none`.

**Steps:**

| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Выбрать пункт [2] "Install v3.0 into this project" | Запускается `scripts/setup-planning-v3.sh` как дочерний процесс |
| 2 | Наблюдать вывод в терминале | Вывод скрипта отображается напрямую (унаследованный stdio), без изменений/фильтрации со стороны TUI |
| 3 | Ответить на интерактивные промпты скрипта (например, на запрос целевой директории — подтвердить/ввести путь к фикстуре `none`) | Ввод пользователя корректно передаётся дочернему процессу |
| 4 | Дождаться завершения скрипта | TUI получает код завершения дочернего процесса и корректно возвращает управление (например, показывает результат или завершает работу) |
| 5 | Проверить фикстур-директорию после завершения | Файлы фреймворка v3.0 установлены — результат эквивалентен прямому запуску `scripts/setup-planning-v3.sh` с той же целевой директорией (сравнение с `make setup-v3` невозможно один-в-один, так как эта цель не принимает `TARGET=` и всегда работает интерактивно/с `$(pwd)`) |
| 6 | В отдельном прогоне: во время выполнения дочернего процесса (шаг 1-3) нажать `Ctrl+C` / `q`, чтобы прервать TUI до завершения делегированного скрипта | TUI завершается; проверить список процессов (например, `ps aux \| grep setup-planning-v3`) — осиротевший дочерний процесс `setup-planning-v3.sh` не остаётся запущенным в фоне |

**Test Data:**
- TARGET: фикстур-директория `none`

**Expected Outcome:** Установка через TUI даёт тот же результат, что и прямой запуск `scripts/setup-planning-v3.sh`, при этом бизнес-логика скрипта не дублируется и не изменяется TUI, а прерывание TUI не оставляет висящих дочерних процессов.

**Note (open question against specs.md):** specs.md не определяет ожидаемое поведение TUI, если делегированный скрипт завершается с ненулевым кодом выхода или недоступен (например, файл скрипта отсутствует/не исполняем). Данный тест-план не проверяет это поведение как определённое требование — фиксируем как открытый вопрос к спецификации, а не как непроверенное требование.

**Priority:** Critical

### TC-008: Делегирование миграции и обновления скиллов (`migrate-v2-to-v3.sh`, `update-skills.sh`)

**Description:** Проверяет, что состояния `v2-or-older` и `v3` корректно делегируют выбранное действие соответствующим скриптам (`migrate-v2-to-v3.sh` и `update-skills.sh`) через spawn с унаследованным stdio.

**Preconditions:**
- Фикстур-директории `v2-or-older` и `v3` подготовлены.
- Важно: шаг 3-4 запускает `scripts/update-skills.sh`, который всегда пишет в реальный `$HOME/.claude/skills` (фикстура `v3` влияет только на то, какое меню/детекцию покажет TUI, но не на то, куда `update-skills.sh` фактически устанавливает скиллы). Перед шагом 3 сделать резервную копию `~/.claude/skills` (`cp -r ~/.claude/skills ~/.claude/skills.bak.$$`) или запустить TUI с переопределённым `HOME`, указывающим на scratch-директорию; после шага 4 — восстановить исходное содержимое `~/.claude/skills` (или удалить scratch-`HOME`).

**Steps:**

| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Запустить `make tui TARGET=<фикстура v2-or-older>` и выбрать [1] "Migrate this project to v3.0" | Запускается `scripts/migrate-v2-to-v3.sh`, вывод отображается напрямую |
| 2 | Дождаться завершения | Фикстура мигрирована на v3.0 (появляется `PLANNING.md`), результат эквивалентен прямому запуску `bash scripts/migrate-v2-to-v3.sh <фикстура v2-or-older>` (сравнение с `make migrate-v2-to-v3` невозможно, так как эта цель не прокидывает аргумент и всегда работает с `.`) |
| 3 | Сделать резервную копию `~/.claude/skills` (см. Preconditions), затем запустить `make tui TARGET=<фикстура v3>` и выбрать [1] "Update skills to latest version" | Запускается `scripts/update-skills.sh`, вывод отображается напрямую |
| 4 | Дождаться завершения, затем восстановить `~/.claude/skills` из резервной копии | Скиллы в `~/.claude/skills` обновлены (до восстановления), результат эквивалентен прямому запуску `make update-skills` (эта цель фикстуру/проект не различает — работает с реальным `$HOME` в обоих случаях) |
