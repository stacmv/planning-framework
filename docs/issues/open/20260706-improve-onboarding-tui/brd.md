# BRD: Улучшение UX установки/обновления через make + TUI-мастер

## Проблема

Сегодня установка и обновление Planning Framework в проект-потребитель выполняются через отдельные `make`-цели (`setup-v3`, `update-skills`, `migrate-v2-to-v3` и т.д.), каждая из которых требует, чтобы пользователь заранее знал, какая команда ему подходит и в каком состоянии находится его проект. Для человека, впервые столкнувшегося с фреймворком, это высокий порог входа: нужно прочитать README/PLANNING.md, понять концепции (issue, BRD, spec, workflow, QA) и только потом решиться на первый запуск. Для существующих пользователей, обновляющих версию, тоже нет единой точки, которая бы сама разобралась, что у них установлено, и предложила правильное действие (обновление скиллов vs миграция v2→v3).

## Целевая аудитория

Одинаково важны обе группы:
- Новые пользователи, впервые устанавливающие Planning Framework в проект.
- Существующие пользователи, обновляющие версию/скиллы.

## Пользовательские истории

**US-1.** Как новый пользователь, никогда не видевший Planning Framework, я хочу запустить одну команду и получить интерактивный мастер, который объяснит мне основные концепции фреймворка и проведёт через установку, чтобы я мог создать свой первый issue без чтения документации целиком.

**US-2.** Как существующий пользователь, я хочу запустить ту же команду в проекте с уже установленным фреймворком и получить автоматически определённую версию (v2.0 или более старую) с предложением подходящего действия (обновить скиллы до последней версии или мигрировать v2→v3), чтобы не выбирать вручную нужный скрипт.

**US-3.** Как пользователь любого уровня, я хочу, чтобы существующие команды (`make setup-v3`, `make update-skills`, `make migrate-v2-to-v3` и т.д.) продолжали работать без изменений, чтобы не сломать существующие скрипты/CI, которые их вызывают.

**US-4.** Как пользователь любого проекта на моей машине, я хочу запускать мастер одной короткой командой из любой директории (не только находясь внутри папки planning-framework), чтобы её можно было спокойно предложить кому-то в одну строку, без `make -C <путь> tui TARGET=$(pwd)`.

**US-5.** Как совершенно новый пользователь, который никогда не клонировал репозиторий фреймворка, я хочу скопировать одну команду из README на GitHub (одну для Linux/macOS, одну для Windows) и получить полностью установленный фреймворк — без ручного `git clone`, без чтения инструкций по установке зависимостей вручную.

**US-6.** Как пользователь, уже установивший фреймворк через однокомандный установщик, я хочу иметь возможность запустить ту же самую команду повторно, чтобы обновить фреймворк до последней версии, не помня отдельную команду обновления.

## Функциональные требования

- Добавить новую make-цель (например, `make tui`) как единственную новую точку входа для TUI-мастера. Существующие цели (`setup-v3`, `update-skills`, `migrate-v1-to-v2`, `migrate-v2-to-v3`, `setup-v2`, `issue-status`) не изменяются и не удаляются.
- TUI при запуске определяет текущее состояние целевого проекта (нет фреймворка / v2.0 / v3.0) и предлагает соответствующее действие:
  - Нет фреймворка → интерактивная установка (эквивалент `setup-v3`), предварённая коротким обучающим экраном для новичков.
  - Обнаружена v2.0 или более старая версия → предложение миграции на v3.0 (эквивалент `migrate-v2-to-v3`).
  - Обнаружена v3.0 → предложение обновить скиллы (эквивалент `update-skills`) либо посмотреть статус issue.
- Для новых пользователей TUI включает подробный интерактивный туториал по основным концепциям фреймворка (issue, жизненный цикл CREATE → BRD/ANALYSIS → SPEC → TEST_PLAN → IMPL_PLAN → EXECUTE → TEST → QA → CLOSE, назначение `/pf`-команд) — пошагово, прямо внутри TUI, без необходимости открывать другие файлы.
- TUI должен работать в терминале (без внешних GUI-зависимостей) и не требовать сетевого доступа сверх того, что уже требуется существующим скриптам.
- Установка (`setup-planning-v3.sh`) и обновление скиллов (`update-skills.sh`) дополнительно устанавливают глобальный исполняемый шим с именем `pf` в директорию на `PATH` (по аналогии с тем, как скиллы уже устанавливаются в `~/.claude/skills`), запускающий TUI с `TARGET`, равным текущей директории вызова. Установка шима не ломает и не заменяет существующие `make`-цели.
- Добавить однокомандный кросс-платформенный установщик самого фреймворка (не проекта-потребителя): один вариант команды для Linux/macOS (bash-скрипт, запускаемый через `curl | sh` или аналог) и один для Windows (PowerShell-скрипт, запускаемый через `irm | iex` или аналог), публикуемые в README на GitHub.
  - Клонирует/обновляет репозиторий фреймворка в `~/.claude/planning-framework` (git pull, если уже существует).
  - Проверяет наличие `git` и `node` перед началом работы; при отсутствии — понятное сообщение об ошибке с указанием, что установить, без попытки автоматически поставить зависимости через системный пакетный менеджер.
  - Устанавливает глобальный шим `pf` и скиллы (эквивалент `setup-planning-v3.sh`/`update-skills.sh`, применяемых к самому фреймворку, а не к проекту-потребителю).
  - Идемпотентен: повторный запуск той же команды обновляет существующую установку, не спрашивая пользователя, устанавливать заново или нет.

## Критерии приёмки

- **AC-1 (Понимание без документации):** Новый пользователь, никогда не видевший Planning Framework, запускает `make tui` и доходит до создания своего первого issue, не открывая PLANNING.md/README вручную.
- **AC-2 (Минимум шагов):** Установка и обновление фреймворка выполняются одной командой (`make tui`) с интерактивным выбором действия внутри, вместо запоминания нескольких разных make-целей.
- **AC-3 (Автоопределение состояния):** При запуске `make tui` в проекте с уже установленным фреймворком (любой версии) TUI корректно определяет версию и предлагает релевантное действие (обновление скиллов или миграцию), без необходимости пользователю самому решать, какой скрипт запускать.
- **AC-4 (Обратная совместимость):** Все существующие `make`-цели (`setup-v3`, `update-skills`, `migrate-v1-to-v2`, `migrate-v2-to-v3`, `setup-v2`, `issue-status`) продолжают работать так же, как до этого изменения.
- **AC-5 (Встроенное обучение):** Новый пользователь может пройти интерактивный туториал по концепциям фреймворка прямо внутри TUI, без перехода к внешним документам.
- **AC-6 (Глобальный доступ):** После установки/обновления фреймворка (через `setup-planning-v3.sh` или `update-skills.sh`) команда `pf`, запущенная из любой директории, открывает TUI-мастер для текущей директории — без `make -C` и без указания пути к фреймворку вручную.
- **AC-7 (Установка одной командой):** Пользователь, у которого фреймворк не установлен вовсе, копирует одну команду из README (свою для Linux/macOS, свою для Windows) и получает установленный фреймворк, глобальный шим `pf` и скиллы — без ручного `git clone` и без чтения инструкций по установке зависимостей.
- **AC-8 (Идемпотентное обновление):** Повторный запуск той же однокомандной установочной команды на машине, где фреймворк уже установлен, обновляет его (`git pull` + переустановка шима/скиллов) без ошибок и без запроса подтверждения переустановки.

## Вне рамок

- Изменение бизнес-логики самих скриптов установки/миграции/обновления (setup-planning-v3.sh, migrate-v2-to-v3.sh и т.д.) — TUI оборачивает их, но не переписывает их поведение.
- Веб- или графический интерфейс — только текстовый интерфейс терминала (TUI).
- Изменение состава или логики самих skills (`/pf`, `/pf-brd` и т.д.).
- Автоматическая установка отсутствующих системных зависимостей (git, node) через пакетные менеджеры (apt/brew/choco и т.д.) — установщик только проверяет их наличие и сообщает об ошибке.
