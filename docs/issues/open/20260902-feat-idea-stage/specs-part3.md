### 8.1a Поведенческие/fixture-based тесты (новые, finding #27)

Статические grep-проверки §8.1 — drift guards, не доказательство
корректности исполняемого поведения (то, что находка #27 явно требует
отличать). Для каждого из перечисленных ниже опасных сценариев — отдельный
TC в **том же** `test/pf-idea-stage-static.sh` (или отдельном файле, если
он вырастет за бюджет §8's "трёх новых файлов" — решение реализации), по
образцу `test/pf-close.sh`/`test/converge-fresh.sh`: throwaway-репозиторий
через `pf_setup_case <fixture> --git` (новые fixture-каталоги под
`test/fixtures/`, по образцу существующих `pf-close-basic`/`no-pf-bare`),
затем bash-транскрипция проверяемой логики, затем assert на реальный
результат в файловой системе/git-истории — не только текст скилла:

1. **Bare-folder idea создаёт только папку issue.** Fixture — пустая
   директория (`test/fixtures/no-pf-bare`, уже существует, переиспользуется).
   Транскрипция §3.1.1's ветки "Идея": создать
   `docs/issues/open/<id>-idea-x/prompt.md` и ничего больше. Assert: после
   выполнения `find . -mindepth 1` даёт ровно ожидаемый набор путей — ни
   `PLANNING.md`, ни `docs/planning/`, ни `.git` не появились (AC-01b).
2. **`project`-вердикт — bootstrap + git init + follow-up, в правильном
   порядке.** Fixture — bare-folder idea-issue с `verdict.md`'s "## Decision"
   = `project` уже на месте. Транскрипция Phase 4.6 (§7.3.4 part2):
   `git init`, копирование каркаса, initial scaffold commit, создание
   follow-up `feat`-папки, **затем** Phase 5's `mv` идеи в `closed/`.
   Assert, в этом порядке: репозиторий существует после Phase 4.6 и до
   Phase 5; initial scaffold commit существует и **не** содержит
   `docs/issues/`-путей (scoped `git add`, finding #3); follow-up
   `feat`-папка существует под `open/` **до** архивации idea (finding #4
   — не после); после полного прогона `git status --porcelain` пуст
   (finding #3's QA-breaking untracked files не воспроизводятся).
3. **Spike close оставляет ветку нетронутой.** Fixture — `pf-close-basic`-
   подобный git-репозиторий с веткой `issue/<spike-id>`, код и
   `findings.md` на ней. Транскрипция Phase 3.5 (§7.3.2 part2). Assert:
   `issue/<spike-id>` всё ещё существует после закрытия (`git branch

   и `docs/issues/closed/<spike-id>/` содержит скопированные документы на
   PARENT-BRANCH.
4. **`pf-check` никогда не спрашивает `size_tier` для idea/spike.** Fixture
   — открытый `idea`-issue с `idea_tier` в `prompt.md`, без `size_tier`.

   определяется первым, `size_tier`-ветка не достигается для этого TYPE.
   Assert (static, на уровне транскрипции — этот TC не запускает реальную
   AI-сессию): условие "TYPE is idea or spike → skip" синтаксически
   предшествует условию "no size_tier → ask" в собственной bash-модели
   теста, тем же способом, что TC-005 `pf-close.sh` держит транскрипцию в
   синхроне со skill-текстом через drift-guard §8.1 п.4 выше.
5. **Spike close отказывает при пустом Run Evidence (AC-09c, finding #6).**
   Fixture — git-репозиторий с завершённым `hypothesis.md`, но

### 8.2 `test/pf-idea-front-loaded-static.sh` (новый)

Проверяет каждую строку таблицы §7.13 part2 механически: для каждого
(скилл, секция) — извлечь текст файла между этим заголовком/якорем и
следующим заголовком того же или более высокого уровня, и убедиться, что
внутри этого диапазона присутствует ссылка на `pf-interaction` (канонический
hook-текст или его смысловой эквивалент — минимально: подстрока
`pf-interaction` **и** подстрока `front-loaded` в одном и том же диапазоне
строк). Для строк, помеченных **"исключение"** (`code.review: skip`
confirmation, безусловно) — обратная проверка: диапазон **не должен**
содержать hook. Для codex-install-подсказок (`pf-check`'s "Codex
invocation chain" шаг 1/2a/3, finding #12) — assert **условный**: диапазон
может не содержать hook (обе формы валидны — issue, включивший
front-loaded на CREATE, резолвит это на intake, не здесь; issue,
включивший вручную, оставляет это безусловным), тест здесь не требует
ни присутствия, ни отсутствия hook-ссылки, а только что раздел
по-прежнему упоминает оба пути текстом ("intake" и "unconditional"). Для
`pf-close`'s Phase 1 (finding #10 — больше не чистое "исключение") — assert
**положительный**: диапазон должен содержать И упоминание `front-loaded`
(hook применяется — расширенный гейт, §7.13.1), И текст, подтверждающий,
что для issue **без** `front-loaded` поведение Phase 1 не меняется. Для
`pf-test` (finding #11) — assert **обновлён**: файл по-прежнему не
содержит ни одного литерального вызова `AskUserQuestion` (это по-прежнему
верно), но Phase 1's plain-text вопрос ("No test runner detected…")
**обязан** быть покрыт hook-ссылкой в этой новой таблице — тест ищет
`pf-interaction`/`front-loaded` в диапазоне вокруг этого текста, не
довольствуется отсутствием `AskUserQuestion` как доказательством
отсутствия остановки (это и была сама ошибка finding #11).

## 9. Codex compatibility notes

Инструкция для ревью (issue-специфичная, prompt.md/decision 14): каждая
Claude-специфичная конструкция, на которую опираются семь новых скиллов
(и правки существующих), перечислена ниже с реалистичной оценкой и либо
переносимой альтернативой/фолбэком, либо явной пометкой "принято как
ограничение" — не "не ново для этого issue, поэтому не разбирается"
(находки #20-25 этого ревью били именно по случаям, где более ранняя
редакция уходила от оценки таким способом). Список — то, что должно быть
передано codex-ревьюеру как дополнительное измерение "совместимость с
Codex" при отправке этого issue на ревью (AC-13a/b) — сама эта секция и
есть механизм, которым AC-13a/b удовлетворяются: она не описывает новую
функциональность, поставляемую пользователям, а фиксирует, что именно
проверяется, когда документы/скиллы **этого** issue отправляются на
ревью (см. §10, AC-13a/b трактуются как процессные, не поведенческие).

Но `Agent` **как оркестрирующий примитив** — вызов, которым сама сессия (Claude или Codex) порождает и координирует независимые дочерние под-агенты одним вызовом — не имеет эквивалента в Codex-как-оркестраторе (finding #21): Codex-сессия использует свой собственный sub-agent API (`spawn_agent`/аналог, не `Agent` tool, не Claude tier-имена как `model:`), и одновременный запуск нескольких независимых персон **в этой же форме** там не специфицирован. Отдельно: даже для Claude-оркестратора одновременный запуск всех 4-6 персон `pf-idea-critique` для `product`-tier потенциально превышает типичный лимит параллельных дочерних слотов (обычно три) — сам этот спек не решает, как это разруливается для Claude-стороны (последовательные волны? уменьшенный параллелизм?), и то же самое верно и подавно для Codex. **Принято как ограничение** с названным fallback: под Codex-оркестрацией — последовательный запуск персон один за другим внутри одной codex-сессии (`codex exec`-подобные под-процессы или последовательные вызовы `codex-companion.mjs`), не параллельно и без общей сессионной изоляции саб-агента — функционально возможно, не реализовано и не идентично по гарантиям на данном этапе |

Тот же паттерн, что и весь существующий фреймворк (ни один из 21 текущих скиллов не абстрагирует путь) — этот issue не делает ситуацию хуже, но и не может честно назвать это "не ново, не разбираем" применительно к самому Codex-запуску. **Правильная формулировка:** параметризация корня skills-каталога (переменная/резолвер вместо литерального `~/.claude/skills/...`) необходима для запуска в Codex вообще, но остаётся вне скоупа этого issue (BRD Non-Goals: "Работа фреймворка в Codex прямо сейчас… не требуется") — **принято как явное ограничение issue**, зафиксированное здесь, чтобы будущий Codex-runtime-issue не открывал его заново с нуля |
| `WebSearch`/`WebFetch` | `pf-idea-research`, когда `write == claude` | Когда `write` резолвится в `codex`, факт-чек выполняет сам делегированный актор своими средствами (сеть доступна `codex-companion.mjs`'s песочнице, если разрешено конфигурацией) — промпт делегирования (§3.3 part1) не называет конкретный инструмент, только задачу "найти и процитировать источник", так что здесь **нет** блокирующей несовместимости, только замечание для ревью: сформулировать явно в implementation plan, что промпт делегированному Codex-актору не должен предполагать вызов Claude-инструментов по имени |
| `CronCreate`/`CronList`/`CronDelete` | `pf-autopilot` (переиспользуется без изменений для idea/spike-issue; финальное закрытие теперь тоже проверяет/удаляет schedule — §7.3.6 part2) | **Не отклонено — зафиксировано как принятое ограничение, затрагивающее конкретно `pf-autopilot` (AC-13b, finding #22).** Доступный сегодня Codex runtime не имеет периодического scheduler'а, эквивалентного `CronCreate`/`CronList`/`CronDelete` — `/pf-autopilot` целиком неисполним под Codex-оркестрацией до появления эквивалента (не только "старое ограничение, не в объёме этого ревью" — оно должно быть явно названо ревьюеру как затрагивающее именно эту команду, поскольку этот issue расширяет `pf-autopilot` на два новых типа issue). Переносимая альтернатива не специфицируется этим issue (вне скоупа per BRD Non-Goals) — но статус фиксируется как **принято как ограничение**, не молчаливо унаследованное |
| `Skill` tool / способ вызова `/pf-*` (finding #23) | Весь routing, "Next step" и `pf-autopilot`'s work loop выражены как Claude slash-команды (`/pf-idea`, `/pf-check`, …) | Более ранняя редакция ошибочно считала это уже переносимым, потому что ни один новый скилл не вызывает другой через `Skill`-инструмент **программно** — но это не то же самое утверждение, что "все текстовые упоминания `/pf-*` одинаково переносимы". `/pf-*`-команды — механизм вызова, специфичный Claude Code slash-command'ам; Codex активирует skills иначе (по упоминанию/discovery, не слэш-командой с тем же именем). Каждая строка "Next step: `/pf-idea-critique`" и весь `pf-autopilot`'s Step 2 work loop, буквально перечисляющий slash-имена, не является provider-neutral инструкцией как есть. **Принято как ограничение** с названным направлением фикса (вне скоупа этого issue): provider-neutral идентификаторы стадий (например, просто имя скилла, `pf-idea-critique`, без слэша) плюс adapter, отображающий его в Claude slash-command **или** Codex skill-invocation в зависимости от runtime — этот issue продолжает использовать слэш-форму, унаследованную от всего существующего фреймворка, не вводит новую несовместимость сверх уже существующей, но и не решает её |
| Session-log/usage-атрибуция (finding #25) | `pf-close` Phase 7 (`[Claude Code]`-префикс в `session-log.md`), Phase 6 (usage/cost из `~/.claude/projects/*.jsonl`) — не новое для этого issue, но новые маркеры `[pf-check]`/`[assumed]`/`[availability]` добавляют к тому же файлу | Сами новые маркеры — обычный текст, переносим (любой provider читает и пишет их одинаково). Но **окружающий** механизм — нет: Phase 7's литеральный `[Claude Code]`-префикс атрибутировал бы Codex-прогон неверно, а Phase 6's usage-источник (`~/.claude/projects/...`) специфичен формату Claude Code транскриптов и не находит ничего под Codex-runtime. Не блокирует функциональность этого issue (idea/spike-пайплайн работает независимо от того, откуда взят usage-отчёт), но требует **provider-neutral actor-tag** вместо литерального `[Claude Code]` и честного "usage source unavailable under this provider" пути вместо молчаливо пустого отчёта — вне скоупа реализации этого issue (существующий механизм, не новый), но названо здесь явно, а не пропущено как "не ново, не разбираем" |
