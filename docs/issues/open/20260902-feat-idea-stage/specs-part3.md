## 8. Tests

Стиль — тот же, что `test/skills-static.sh`/`test/skills-role-matrix-
static.sh`: read-only, grep-based структурные проверки скиллов/скриптов/

### 8.2 `test/pf-idea-front-loaded-static.sh` (новый)

Проверяет каждую строку таблицы §7.13 part2 механически: для каждого
(скилл, секция) — извлечь текст файла между этим заголовком/якорем и
следующим заголовком того же или более высокого уровня, и убедиться, что
внутри этого диапазона присутствует ссылка на `pf-interaction` (канонический
hook-текст или его смысловой эквивалент — минимально: подстрока
`pf-interaction` **и** подстрока `front-loaded` в одном и том же диапазоне
строк). Для строк, помеченных **"исключение"** (codex-install-подсказки,
`code.review: skip` confirmation, `pf-close`'s Phase 1) — обратная
проверка: диапазон **не должен** содержать hook (эти вопросы остаются
безусловными). Для `pf-test` — assert, что в файле по-прежнему нет ни
одного вызова `AskUserQuestion` (документирует, что hook туда не нужен, и
ловит будущий дрейф, если в `pf-test` когда-нибудь появится интерактивный
вопрос без соответствующего hook'а).

### 8.4 Правки существующих тестов

**`test/docs-refs.sh` (TC-040) — изменений в коде файла не требуется.**
`N_SKILLS` вычисляется динамически (`find skills -mindepth 1 -maxdepth 1
-type d`) — после появления семи новых директорий `N_SKILLS` автоматически
становится 28, и `assert_lists_every_skill`/счётчик-проверки начинают
падать **до тех пор**, пока не выполнены правки §7.6/§7.8/§7.10 (CLAUDE.md,
README.md, FRAMEWORK.md, QUICKSTART.md, `pf-update/SKILL.md`,
`tutorial.js`) — это ровно то самозащитное свойство, ради которого
`docs-refs.sh` был написан ("adding a skill fails this suite until the
lists are updated"), и данный issue обязан пройти эту проверку тем, что
все перечисленные файлы правятся, а не тем, что тест меняется.

**`test/skills-static.sh`** — если его циклы по `skills/*/` не хардкодят
список имён (проверено при чтении: `for planning in "$REPO_ROOT/PLANNING.md"
"$REPO_ROOT/docs/planning/templates/config/PLANNING.md"` на строке 546 —
единственное вхождение `skills/pf-update` там жёстко названо по имени
файла, не итерируется как часть общего цикла) — новые директории
автоматически проходят через любые общие структурные assert'ы этого
файла (шапка YAML, обязательные поля) без правок кода теста. Точечных
правок не требуется.

**`test/skills-role-matrix-static.sh`** — не хардкодит список ключей ролей
(проверено — ни `Known stage keys`, ни перечисление `analysis`/`notes` в
виде закрытого списка не найдено при грепе этого файла); новые ключи
`idea`/`research`/`critique`/`verdict`/`hypothesis`/`findings` не требуют
правок этого теста.

**`test/converge-fresh.sh`, `test/converge-migrate.sh`,
`test/converge-normalize.sh`, `test/lib.sh`** — их T6-зеркало-проверки
(`docs/planning/templates`) не меняются (§1.1.C — `docs/planning/templates`
остаётся тем же деревом, что и сегодня, не переименовывается и не
перемещается). Новая проверка зеркала `skills/pf/templates/project` — это
**отдельный, новый** файл (§8.3), не правка этих четырёх.

**`Makefile`'s `test:`-цель** — не требует правок: она уже итерирует
`for t in test/*.sh` с исключением только `lib.sh` и
`converge-migrate.sh` по имени; три новых файла (`pf-idea-stage-static.sh`,
`pf-idea-front-loaded-static.sh`, `pf-idea-templates-mirror.sh`)
подхватываются автоматически при следующем `make test`.

## 9. Codex compatibility notes

Инструкция для ревью (issue-специфичная, prompt.md/decision 14): каждая
Claude-специфичная конструкция, на которую опираются семь новых скиллов,
перечислена ниже с переносимой альтернативой либо явной пометкой "принято
как ограничение". Список — то, что должно быть передано codex-ревьюеру
как дополнительное измерение "совместимость с Codex" при отправке этого
issue на ревью (AC-13a/b) — сама эта секция и есть механизм, которым
AC-13a/b удовлетворяются: она не описывает новую функциональность,
поставляемую пользователям, а фиксирует, что именно проверяется, когда
документы/скиллы **этого** issue отправляются на ревью (см. §10, AC-13a/b
трактуются как процессные, не поведенческие).

| Конструкция | Где используется | Переносимая альтернатива / статус |
|---|---|---|
| `AskUserQuestion` | Intake-батч (`/pf`'s "Creating prompt.md — idea/spike"), decision session (`pf-idea-verdict` режим 2), output-гейты всех пяти пишущих скиллов | Codex сегодня не имеет прямого эквивалента интерактивного batched-вопроса внутри самого движка задач; front-loaded-дизайн этого issue минимизирует поверхность, требующую этого инструмента, до ровно двух точек (§3.8/§4.2 part1) — **принято как ограничение**: под Codex-оркестрацией эти две точки требуют либо человека в текстовом REPL codex, либо остаются нереализованными до появления эквивалента |
| `Agent` tool с `model:` | Диспетчеризация персон критики (`pf-idea-critique`, §3.4 part1), диспетчеризация саб-агента при нестандартном tier в `pf-idea`/`pf-idea-research`/`pf-idea-verdict` | Когда резолвнутый актор — `codex`, диспетчеризация уже идёт не через `Agent`, а через `pf-roles` §7's write-invocator (`codex-companion.mjs task ... --json`/`--write`) — то есть путь для Codex-как-исполнителя уже переносим и специфицирован (§3.4 part1, п.2). Специфично Claude — только сам механизм параллельного запуска **нескольких независимых персон одним вызовом Agent tool**, когда write-актор — `claude`: аналог для `codex` (несколько параллельных `codex-companion.mjs` вызовов без общей сессионной изоляции саб-агента) функционально возможен, но не реализован и не идентичен по гарантиям — **принято как ограничение** на данном этапе |
| `~/.claude/skills/...` — абсолютные пути | Каждая ссылка одного скилла на другой (все 7 новых + все правки в существующих) | Тот же паттерн, что и весь существующий фреймворк (ни один из 21 текущих скиллов не абстрагирует путь) — **принято как ограничение**, не новое для этого issue; параметризация пути к каталогу скиллов — отдельная задача вне скоупа (BRD Non-Goals: "Работа фреймворка в Codex прямо сейчас… не требуется") |
| `WebSearch`/`WebFetch` | `pf-idea-research`, когда `write == claude` | Когда `write` резолвится в `codex`, факт-чек выполняет сам делегированный актор своими средствами (сеть доступна `codex-companion.mjs`'s песочнице, если разрешено конфигурацией) — промпт делегирования (§3.3 part1) не называет конкретный инструмент, только задачу "найти и процитировать источник", так что здесь **нет** блокирующей несовместимости, только замечание для ревью: сформулировать явно в implementation plan, что промпт делегированному Codex-актору не должен предполагать вызов Claude-инструментов по имени |
| `CronCreate`/`CronList`/`CronDelete` | `pf-autopilot` (не новое — переиспользуется без изменений для idea/spike-issue) | Существующее ограничение фреймворка, не введённое этим issue — не включается в объём ревью заново |
| `Skill` tool (`skill: "pf-idea-lenses"` и т.п. — косвенно, через файловые ссылки `~/.claude/skills/pf-idea-lenses/SKILL.md`, не прямой вызов) | Ни один новый скилл не вызывает другой через `Skill`-инструмент напрямую — все ссылки текстовые ("см. `~/.claude/skills/X/SKILL.md`"), тем же способом, что и весь существующий фреймворк | Не Claude-специфично сверх уже принятого — текстовые ссылки читаются моделью любого провайдера одинаково |
