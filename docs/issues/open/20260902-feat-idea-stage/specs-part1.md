## 1. Обзор архитектурных решений

Этот issue добавляет во фреймворк два новых типа issue — `idea` и `spike` —
как ветки поверх существующей машинерии `docs/issues/{open,closed}/`,
`/pf`, `/pf-check`, `/pf-close`, `/pf-autopilot`, `pf-roles`, `pf-git`,
`session-log.md`. Пайплайны `feat`/`improve`/`bug` содержательно не
меняются: ни одна их стадия, ни один их гейт, ни один их документ не
переопределяются — правки в общих скиллах (`/pf`, `pf-check`, `pf-close`,
`pf-git`, `pf-autopilot`, `pf-roles`, `pf-help`) везде оформлены как
**дополнительные ветки, включаемые по типу issue или по новому
опциональному полю**, никогда не как замена существующей ветки (G7,
AC-12a).

Семь новых скиллов:

- **Пишущие** (создают ровно один документ за вызов, по образцу
  `pf-brd`/`pf-spec`): `pf-idea` (`idea.md`), `pf-idea-research`
  (`research.md`), `pf-idea-critique` (`critique.md`), `pf-idea-verdict`
  (`verdict.md`, и, вторым режимом того же скилла, сессия решения),
  `pf-idea-spike` (`hypothesis.md`, и, вторым режимом, `findings.md`).
- **Справочные** (не вызываются пользователем напрямую, читаются другими
  скиллами — по образцу `pf-size-tiers`/`pf-roles`/`pf-git`):
  `pf-idea-lenses` (определения `idea_tier`, наборы линз, наборы персон
  критики, бюджеты документов, таблицы стадий обоих новых пайплайнов,
  словарь вердиктов) и `pf-interaction` (правило front-loaded
  взаимодействия, применяемое и к idea/spike, и, опционально, к
  feat/improve/bug).

Итого 21 + 7 = **28 скиллов** (5 пишущих + 2 справочных новых). См. §7 для
точного списка мест, где счётчик "21" и списки скиллов должны стать "28".

### 1.1 Три несущих архитектурных решения

**(A) Таблицы стадий новых типов живут в `pf-idea-lenses`, не в `/pf`.**
`/pf` уже ~38 КБ (ограничение G12b/decision 12). Как `/pf-check`'s Codex-цепочка
или `pf-roles`'s alorithm — единый источник, на который остальные
*ссылаются*. `/pf` Step 6 получает один короткий абзац
("для `idea`/`spike` смотри таблицу стадий в `pf-idea-lenses` и веди себя
по тому же правилу первой незавершённой стадии") вместо ещё одной полной
таблицы маршрутизации.

**(B) `idea`/`spike`-issue используют `idea_tier`, никогда `size_tier`.**
Bсе существующие "legacy-tier guard"'ы (`/pf` перед Step 5, `pf-brd`,
`pf-spec`, `pf-check`, `pf-execute`, `pf-impl-plan`, `pf-test-plan`) задают
вопрос про `size_tier` безусловно для issue без этого поля. Каждый такой
guard получает одну и ту же дополнительную оговорку: *"Пропустить этот
guard целиком, если TYPE issue — `idea` или `spike`"* — эти типы `size_tier`
не используют вообще; `pf-brd`/`pf-spec`/`pf-test-plan`/`pf-impl-plan`/
`pf-execute` для `idea`/`spike`-issue не вызываются в принципе (у этих
типов нет BRD/spec/test-plan/impl-plan/кода — US-01 Non-Goals), так что их
guard'ы физически не достигаются; изменения нужны только в `/pf`
(единственном месте, где guard мог бы сработать на `idea`/`spike`-issue,
поскольку `/pf` — единственный скилл, который видит issue любого типа на
каждом шаге).

**(C) Единственный источник каркаса проекта — `skills/pf/templates/project/`,
зеркало `docs/planning/templates/`.** У конечного пользователя framework-репозиторий
недоступен — установлен только `~/.claude/skills/*` (decision 7). Сценарий
"пустая папка → `/pf` → сразу проект" должен уметь развернуть каркас,
используя только то, что скопировано вместе со скиллом `pf`. Решение:
`docs/planning/templates/` остаётся единственным **вручную редактируемым**
источником (как сегодня — на него ссылаются `CONTRIBUTING.md`,
`converge-to-v3.sh`, десяток тестов; трогать это дерево значило бы менять
`TEMPLATES_SRC` и вслед за ним половину тестового набора конвергенции —
несоразмерная переделка ради самого issue). `skills/pf/templates/project/`
— новая директория, **побайтовое зеркало** `docs/planning/templates/`,
проверяемое статическим тестом (§8) по тому же принципу, что уже
использует `test/lib.sh` для T6-зеркала конвергенции (`diff -r … …`).
Обновляется вручную вместе с `docs/planning/templates/` — правило внесено
в `CONTRIBUTING.md`'s существующий чек-лист синхронизации (§7). Копируется
в `~/.claude/skills/pf/templates/project/` тем же самым механизмом, что уже
копирует `skills/pf-test/templates/` — `install.sh`/`update-skills.sh`/
`converge-to-v3.sh`'s T7 копируют `skills/<name>/.` целиком, без списка
файлов; правки этих трёх скриптов не требуются.

### 1.2 Что не меняется

`pf-execute`, `pf-codereview`, `pf-test`, `pf-qa`, `pf-qa-setup`,
`pf-manual-test`, `pf-user-docs`, `pf-dev-docs` не читаются и не
вызываются ни в `idea`-, ни в `spike`-пайплайне (BRD Non-Goals: без
BRD/спецификации/кода/ревью кода для обоих новых типов) и в этом issue не
редактируются вообще. `role-profiles.yml` не редактируется: три поставляемых
профиля покрывают новые ключи (`idea`/`research`/`critique`/`verdict`/
`hypothesis`/`findings`) через свой `default:` — см. §7.11.

## 3. Component Specs

### 3.1 `/pf` — пустая папка и три несущих правки

#### 3.1.1 Пустая папка: вопрос "идея или сразу проект" (AC-01a/b/c/d)

**Где именно.** Сегодня `/pf` Step 2 листит `docs/issues/open/` "если она
существует" и, если нет issue вообще, Step 3 печатает `No open issues
found` и просит описать задачу свободным текстом. Новая логика вклинивается
**перед** этим — как **Step 0: обнаружение состояния папки**, выполняемый
до Step 1 (чтение версии) не обязательно, но до Step 2 (git-синк) —
обязательно, поскольку git-синк в пустой не-git-папке некорректен
(см. §3.1.2).

```
Step 0 — Есть ли у CWD признаки PF-проекта?
  has_pf := существует PLANNING.md ИЛИ существует docs/issues/ ИЛИ существует .pf-version
  has_git := `git rev-parse --is-inside-work-tree` завершился успешно (0)

  ┌─────────────┬─────────┬──────────────────────────────────────────┐
  │ has_pf      │ has_git │ Ветка                                     │
  ├─────────────┼─────────┼──────────────────────────────────────────┤
  │ true        │ любое   │ Обычный путь — переходим к Step 1 как сегодня │
  │ false       │ любое   │ НОВОЕ: задать вопрос "идея или сразу проект" │
  └─────────────┴─────────┴──────────────────────────────────────────┘
```

`has_git` не влияет на то, *задаётся ли* вопрос — он влияет только на то,
что происходит **после** ответа "сразу проект" (git-инициализация нужна
только тогда; ответ "идея" никогда не трогает git — AC-01b).

**Вопрос** (`AskUserQuestion`, ровно один вызов, до подтверждения не более
95%-уверенности не требуется — это не Q&A-цикл, а развилка):

> **"Над чем работаем: над идеей (которая может и не стать проектом) или
> сразу создаём проект?"**
> - **Идея** — сначала проработать: боль, аналоги, риски, вердикт. Может
>   закончиться проектом, спайком или архивом.
> - **Сразу проект** — знаю, что строю; разворачиваем каркас фреймворка и
>   начинаем как обычно.

**Ветка "Идея" (AC-01b).** Создаётся **только**
`docs/issues/open/YYYYMMDD-idea-<slug>/` с `prompt.md`, заполненным через
intake-батч (§3.1.3). Ничего больше не создаётся: ни `PLANNING.md`, ни
`docs/planning/*`, ни `.pf-version`, ни `git init`. `<slug>` — как для
feat/improve/bug: короткий kebab-case из темы идеи, определяется в момент
записи `prompt.md`. После записи — переход к §3.1.4 ("нет git — стадии
завершаются без коммита").

**Ветка "Сразу проект" (AC-01c).** Выполняется то же самое, что сегодня
делает `make converge`/`converge-to-v3.sh` (T1-T8) **и**, если `has_git`
ложно, `git init` — но **изнутри `/pf` как установленного скилла**, не
вызовом `converge-to-v3.sh` (тот скрипт недоступен конечному пользователю,
decision 7). Источник каркаса — `~/.claude/skills/pf/templates/project/`
(§1.1.C), не `docs/planning/templates/`. Конкретные шаги, зеркалирующие
T1-T8 из `converge-to-v3.sh` в объёме, нужном для по-настоящему пустой
папки (T5's "не переписывать существующее" здесь тривиально верно —
писать не по чему):
  1. `git init` — только если `has_git` ложно (иначе не трогать текущий
     репозиторий).
  2. Создать `docs/issues/{open,closed}/`, `docs/planning/` (T1).
  3. Записать `.pf-version` = значению `version:` из **шапки самого
     `~/.claude/skills/pf/SKILL.md`**, только что прочитанному в Step 1 —
     не `PF_VERSION` из `converge-to-v3.sh` (тот файл недоступен). См. §5.2
     про то, почему это два независимых поля и как они держатся в
     синхроне.
  4. Скопировать `~/.claude/skills/pf/templates/project/config/PLANNING.md`
     → `./PLANNING.md`, подставив `[Project Name]` → имя текущей
     директории (тот же приём, что `render_template` в
     `converge-to-v3.sh` — sed-замена одного плейсхолдера).
  5. Создать/дополнить `CLAUDE.md`: тот же маркерный блок
     `<!-- pf:begin -->…<!-- pf:end -->`, тело —
     `~/.claude/skills/pf/templates/project/config/CLAUDE.md`,
     рендер тем же способом. В по-настоящему пустой папке `CLAUDE.md` не
     существует — просто создаётся с этим блоком.
  6. Скопировать `~/.claude/skills/pf/templates/project/global/*.md` →
     `docs/planning/*.md`, если целевой файл ещё не существует (T5 —
     never overwrite user docs; в пустой папке всегда "ещё не существует").
  7. Зеркалировать `~/.claude/skills/pf/templates/project/` →
     `docs/planning/templates/` (T6-аналог: та же семантика "зеркало, не
     оверлей" — здесь снова тривиально, целевой директории ещё нет).
  8. Пропустить T7/T8 (skills/shim) — `/pf` **уже** является установленным
     скиллом; переустанавливать себя не нужно, и переустановка `pf`-шима
     не имеет отношения к содержимому одной консьюмерской папки.
  9. Продолжить как сегодняшний "tell me what you want to build or fix"
     (Step 3, "No issue folders found" — но теперь с трёхвариантным
     вопросом, см. §3.1.5, поскольку `docs/issues/open/` только что
     создана и пуста).

**Ошибки при развороте каркаса** (например, `~/.claude/skills/pf/templates/
project/` отсутствует — версия `pf`, установленная до этого issue)
останавливают `/pf` с понятным сообщением: "Каркас проекта не найден в
установленном скилле `pf` (`~/.claude/skills/pf/templates/project/` не
существует). Обновите скиллы: `/pf-update`." — не безмолвный переход к
частично развёрнутому проекту.

#### 3.1.2 Not-a-repo guard перед git-синком (новый — не было в BRD явно,
    но обязателен для AC-01a: "не падает")

Сегодняшний Step 2 запускает `git remote`/`git fetch origin`/
`git branch --show-current`/`git rev-list` безусловно. Вне git-репозитория
(`has_git` ложно — то же вычисление, что в §3.1.1) `git remote` завершается
кодом 128 и печатает на stderr `fatal: not a git repository…`; последующие
три команды падают так же. Не будучи явно перехваченным, это выглядит как
каскад ошибок перед тем, как пользователь вообще увидел вопрос
"идея или проект" — прямое нарушение AC-01a ("не падает").

**Правка:** Step 2 получает предваряющую строку: *"Если `has_git` ложно
(вычислено в Step 0), пропустить весь git-синк (пп. 1-4 этого Step)
целиком и перейти сразу к листингу `docs/issues/open/`"* — которая тоже
пуста/не существует, так что Step 3 срабатывает как обычно (или, после
этого issue, как трёхвариантный вопрос §3.1.5, если Step 0 уже определил
`has_pf: true`, но репозиторий по какой-то причине не инициализирован —
редкий, но не невозможный случай: проект с `PLANNING.md`, но без `git
init`, например экспортированный архивом). Это относится к **каждому**
вызову `/pf`, не только к "первому в пустой папке" — `has_git` пересчитывается
каждый раз (правило "механическая проверка, не память" уже действует
везде в этом фреймворке, см. `pf-size-tiers`, "Evaluating it is a MECHANICAL
check").

#### 3.1.3 Intake-батч — где именно он выполняется

**Intake выполняет `/pf` сам**, в новой ветке "Creating prompt.md — idea"
(соответственно "— spike"), не `pf-idea`/`pf-idea-spike`. Причина: пайплайн
диаграмма BRD/prompt.md явно показывает CREATE-стадию **как уже несущую**
intake-батч ("CREATE (`prompt.md` с intake-батчем) → IDEA"), а сегодняшняя
CREATE-стадия для feat/improve/bug — это тоже `/pf`'s "Creating prompt.md"
(doc_language/size_tier/roles/on_unavailable), не отдельный скилл. Это
сохраняет инвариант "ноль вопросов в середине пайплайна" буквально: к
моменту, когда `pf-idea` первый раз читает `prompt.md`, там уже есть всё,
что нужно, и `pf-idea` физически не имеет собственного `AskUserQuestion`
для содержательных вопросов (только для output-гейта "regenerate/keep/
cancel", как у любого пишущего скилла — не про контент).

Полный текст полей и группировка вопросов — §6.1 (idea) / §6.8 (spike).
Здесь фиксируется только **где** это происходит и **как** это связано с
существующим "Creating prompt.md":

```
/pf: Creating prompt.md
  │
  ├─ путь "feat/improve/bug" — БЕЗ ИЗМЕНЕНИЙ (doc_language → size_tier →
  │  role assignment → on_unavailable), см. pf/SKILL.md сегодняшний текст
  │
  ├─ путь "idea" (НОВОЕ) — doc_language передаётся тем же вопросом что и
  │  сегодня (переиспользуется, не дублируется), затем два AskUserQuestion-
  │  вызова по ≤4 вопроса (§6.1); дальше — развилка по тому же признаку,
  │  что и carve-out §7.12.1 part2:
  │    • голая папка без каркаса PF (сценарий AC-01b) — role assignment и
  │      on_unavailable-вопрос НЕ задаются вовсе; `roles:`/`profile:`/
  │      `on_unavailable:` не пишутся в `prompt.md`; резолв для этого
  │      issue навсегда падает на уровень 5 (`write: claude, review:
  │      [claude]`), пока пользователь не впишет `roles:` вручную позже
  │      (единственный существующий путь изменить роли посреди пайплайна,
  │      pf-roles §3) — иначе задавание этих вопросов потребовало бы
  │      прочитать `role-profiles.yml` (список имён профилей для кнопок,
  │      §10 pf-roles шаг 4), а его в голой папке ещё нет
  │    • существующий проект (сценарий US-02, каркас уже есть) — role
  │      assignment (та же процедура §10 pf-roles, но kind-набор —
  │      `idea`/`research`/`critique`/`verdict`, без `code`/`tests`/
  │      `user_docs`/`dev_docs`), затем on_unavailable (тот же
  │      единственный вопрос, что и сегодня) — без изменений от общего
  │      случая
  │
  └─ путь "spike" (НОВОЕ) — та же развилка, вопросы §6.8, роли для
     `hypothesis`/`findings`
```

**Идея-текст, введённая вручную или извлечённая из файла (US-03a).**
Один из вопросов первого intake-батча — сама формулировка идеи. Если
пользователь называет файл вместо того, чтобы написать текст, `/pf` читает
файл и **само** решает, как извлечь из него нужную идею (BRD Non-Goals —
это явно не регламентируется скиллом: "как именно извлекать идею из файла
— не регламентируется скиллом, ИИ решает сам"). После извлечения `/pf`
показывает извлечённый текст пользователю на подтверждение тем же
`AskUserQuestion`-вызовом (варианты: "Да, это то" / "Нет, дай
переформулировать" — свободный текст через встроенный "Other"). Только
подтверждённый текст попадает в `prompt.md`. Это единственное место всего
issue, где чтение внешнего файла (в т.ч. потенциально из vault
пользователя) вообще происходит — и оно происходит **не** как хук на
что-то специфичное (никакого знания о vault/Obsidian/инкубаторе нигде в
коде, BRD Non-Goals), а как обычное чтение файла по пути, который назвал
пользователь.

#### 3.1.4 "Нет git — стадии завершаются без коммита" (AC-01d)

Это расширение `pf-git`, не `/pf` — см. §7.4. Здесь фиксируется только, что
`/pf` **само** ничего не коммитит (как и сегодня — единственная запись `/pf`
делает в `prompt.md` при intake, коммит которой лежит на следующей
запущенной стадии, тем же образом, что и automigration правки `roles:`,
см. `pf-git` Step 1's таблица). "Не закоммичено: нет репозитория" —
формулировка, которую **каждая** стадия idea/spike-пайплайна печатает
вместо обычной git-строки `pf-git`'s Step 4, когда `has_git` ложно в
момент завершения стадии — единая точка определения в `pf-git` (§7.4), не
семь копий в семи новых скиллах.

#### 3.1.5 Существующий проект без открытых issue: четыре варианта (US-02a)

Step 3's "No issue folders found" (`has_pf: true`, `docs/issues/open/`
существует и пуста) заменяется с сегодняшнего свободного текста ("Tell me
what you want to build or fix") на явный `AskUserQuestion`:

> **"Что делаем?"**
> - **Build a feature** — новая функциональность (`feat`)
> - **Fix a bug** — что-то сломано (`bug`)
> - **Describe an idea** — идея, которая может не стать проектом (`idea`)
> - **Run a technical spike** — ответить на технический вопрос экспериментом (`spike`)

Свободный текст через встроенный `AskUserQuestion`'s "Other" остаётся
доступен для случая, когда ни одна из четырёх кнопок не подходит буквально
(например, "improve" — сегодня `/pf` определяет `improve` по содержанию
свободного текста, не по отдельной кнопке; это не меняется — "Other" с
улучшением текста маршрутизируется в `improve` тем же эвристическим
чтением, что и сегодня). **Spike напрямую — четвёртая кнопка (AC-09b).**
Кнопка **Run a technical spike** ведёт в spike-intake (§3.6.2) и создаёт
`YYYYMMDD-spike-<slug>/`; это прямой путь создания `spike` через `/pf`,
помимо автосоздания из вердикта `spike-first` (§3.6.4). Пользователю не
нужно знать слово "spike" заранее — описание кнопки объясняет его. Если
свободный текст ("Other") описывает технический эксперимент ("проверить
сначала технически", "PoC", "экспериментально выяснить..."), `/pf` не
создаёт issue молча под другим типом: оно подтверждает одним дополнительным
`AskUserQuestion` ("Похоже на технический спайк — создать `spike`-issue
вместо фичи?", варианты **Да, spike** / **Нет, это фича**) и затем создаёт
issue выбранного типа.

Выбор "Build a feature"/"Fix a bug" (или свободный текст, классифицированный
как таковой) продолжает **сегодняшним, неизменным** путём "Creating
prompt.md" (doc_language/size_tier/…) — никакой дополнительной развилки
внутри этого пути нет; развилка — только на уровне "какой путь взять",
не внутри уже существующего.

#### 3.1.6 Step 4 — определение типа

Добавляются два варианта к существующим трём:
- Папка начинается с `YYYYMMDD-idea-` → тип **idea**
- Папка начинается с `YYYYMMDD-spike-` → тип **spike**

Step 2's паттерн-фильтр (`YYYYMMDD-TYPE-SLUG`, TYPE ∈ {feat, improve, bug})
расширяется до TYPE ∈ {feat, improve, bug, idea, spike}.

#### 3.1.7 Step 5 — завершённые стадии

Таблица получает шесть новых строк (плюс явное исключение
`open_questions.md`, см. §5.6):

| Документ | Стадия завершена |
|---|---|
| `idea.md` | IDEA |
| `research.md` | RESEARCH |
| `critique.md` | CRITIQUE |
| `verdict.md` | VERDICT (документ написан; **не** то же самое, что "вердикт подтверждён человеком" — см. §3.5.3 про отдельный маркер подтверждения) |
| `hypothesis.md` | HYPOTHESIS |
| `findings.md` | FINDINGS |

Критерий "стадия завершена" — тот же самый разделяемый критерий из
`pf-size-tiers` ("Stage completion", три конъюнкта), без изменений в самом
критерии. Третий конъюнкт ("каждая предыдущая стадия своего пайплайна тоже
завершена") требует, чтобы у `idea`/`spike` был определён порядок стадий —
это добавляется в `pf-size-tiers`'s "Pipelines" таблицу, а не в `/pf` (§7.11.1),
сохраняя решение (A) из §1.1: `/pf` сам не растёт, ссылается на общий
источник, который для этой узкой цели (порядок стадий, используемый
критерием completeness) уже и так является `pf-size-tiers`, а не
`pf-idea-lenses` (`pf-idea-lenses`'s собственная копия той же таблицы,
§3.7, используется для читаемого вывода "что дальше" в Step 6 — два
представления одного порядка стадий, не два источника истины: см. §5.7
про то, как они держатся в согласии).

`open_questions.md` **не появляется в этой таблице** ни в каком виде — это
не стадия пайплайна, а сквозной журнал (§3.1.9, §5.6): его наличие/отсутствие
никогда не входит в критерий завершённости никакой стадии.

#### 3.1.8 Step 6 — маршрутизация для idea/spike

Новый короткий абзац перед существующими таблицами (сохраняя решение (A)):

> **idea/spike-пайплайн.** Если TYPE — `idea` или `spike`, применяется
> **только** таблица стадий из `~/.claude/skills/pf-idea-lenses/SKILL.md`
> ("Stage tables") для этого типа, по тому же правилу первой незавершённой
> стадии и той же семантике маркеров `[pf-check PASSED]`/`[pf-check OPEN]`,
> что и остальные workflow-таблицы этого файла — не восстанавливается
> здесь заново. Feat/improve/bug/trivial-таблицы этого файла для `idea`/
> `spike` не применяются вообще. **Одно исключение из "маршрутизация
> только по существованию/заглушке/маркерам чек-предшественников"** (то,
> чем обычно ограничивается routing везде в этом файле): различение строк
> `VERDICT (документ написан, check ещё не пройден)` и `VERDICT + check
> passed, "## Decision" отсутствует` требует прочитать **содержимое**
> `verdict.md` — присутствует ли в нём секция `## Decision` — не только
> факт существования файла и последний `[pf-check ...]`-маркер в
> `session-log.md`. Это единственное место всего `/pf`, где routing
> заглядывает в тело документа, а не только в его существование/заглушку/
> маркеры — реализация должна это явно предусмотреть, а не считать
> достаточным переиспользование обычной "stage complete" механики.

#### 3.1.9 Step 7 — вывод

Статус-блок не меняется по форме. "Roles for next stage" резолвится тем же
`pf-roles` §4 с TARGET→key маппингом, расширенным в `pf-check`'s таблице
(§7.2) — та же таблица переиспользуется и здесь по имени, без дублирования
(`/pf`'s текст уже сегодня ссылается на "ту же TARGET-to-key mapping,
которую использует таблица `pf-check`'s 'Reviewer selection'").

Для `verdict.md`, ожидающего сессии решения (документ написан, check
пройден, но человек ещё не подтвердил) — `Next step` показывает не
`/pf-idea-verdict`, а явно **`/pf-idea-verdict (decision session)`**, чтобы
пользователь не путал этот шаг с обычной генерацией документа.

### 3.2 `pf-idea` — пишущий скилл, `idea.md`

Структура один-в-один с `pf-brd`'s small/medium/large-веткой (output-гейт
regenerate/keep/cancel по общему критерию `pf-size-tiers`, resolve role
для ключа `idea` через `pf-roles` §4, `write == claude` → пишет сама
сессия без диспетчеризации саб-агента при tier по умолчанию / диспетчирует
саб-агент через `Agent` при нестандартном tier / делегирует через `pf-roles`
§7 при `write != claude`), но **без `AskUserQuestion`-цикла по содержанию**
— это ключевое отличие от `pf-brd`: весь контент уже есть в `prompt.md`
(front-loaded, §3.8).

**Вход:** `prompt.md` целиком (идея, свидетельства боли, ограничения,
вне рамок, критерий "что убедит сказать project"), `idea_tier`.

**Действие:**
1. Прочитать `idea_tier` из `prompt.md`'s фронтматтера.
2. Прочитать из `pf-idea-lenses` (§3.7.2) обязательный набор линз для этого
   `idea_tier` и бюджет строк документа (§6.2.2).
3. Составить `idea.md` по секциям §6.2.1, применяя каждую обязательную
   линзу к материалу из `prompt.md`. Там, где применение линзы требует
   факта, которого в `prompt.md` нет и который нельзя вывести логически
   (например, оценка размера рынка для TAM/SAM/SOM у `product`-идеи) —
   **не выдумывать и не спрашивать**: написать `[assumed]`-строку в
   `open_questions.md` (формат §6.9) с лучшим предположением и обоснованием,
   использовать это предположение в тексте секции с явной пометкой
   "(допущение, см. `open_questions.md` #N)".
4. Секция "Применённые линзы" перечисляет ровно тот список, что вернул
   `pf-idea-lenses` для этого `idea_tier` — не даёт `idea.md` право
   переопределять состав (AC-04c: "`idea.md` не переопределяет их").
5. Проверить объём документа механически (`wc -l`) против бюджета §6.2.2 —
   тот же паттерн "механическая проверка", что и oversized-guard у
   `pf-execute`/`pf-check`; при превышении — не останавливать запись, а
   пометить это как P1-подобное наблюдение в собственном отчёте скилла
   ("`idea.md` превышает бюджет tier `<tier>`: N vs budget"), поскольку
   единственный настоящий гейт по объёму — последующий `/pf-check` (§7.2).

**Выход и закрытие стадии:** commit & push по `pf-git` (§7.4), с
guard'ом "нет репозитория" (§3.1.4). Следующий шаг, печатаемый в отчёте —
`/pf-check`.

### 3.3 `pf-idea-research` — пишущий скилл, `research.md`

**Вход:** `prompt.md`, `idea.md` (предшествующий документ). Веб-поиск
разрешён (BRD decision 15) — при наличии `WebSearch`/`WebFetch`
(инструменты уже доступны сессии `/pf`, отдельного включения не требует).

**Действие:**
1. Извлечь из `idea.md` каждое утверждение, которое можно фактчекнуть:
   аналоги (существуют ли, что делают, какая у них цена/лицензия),
   ограничения платформы, наличие API, юридические/лицензионные
   ограничения — список не закрыт, это минимум из BRD AC-05a.
2. Для каждого утверждения — попытаться найти источник (веб-поиск, чтение
   документации, чтение файла, который назвал пользователь на intake).
   **Найден источник → строка помечается `проверено`, с URL или путём к
   файлу.** Источник не найден, поиск дал противоречивые результаты, или
   утверждение в принципе непроверяемо (мнение, прогноз, "как правило...")
   → строка помечается `не проверено`, **без исключения из документа** —
   непроверенный факт не превращается в вопрос пользователю (US-03d), он
   остаётся видимым и помеченным.
3. **AC-05b — жёсткое правило записи, не только конвенция.** Строка со
   Status = `проверено` без непустого Source — невалидная строка; скилл
   не пишет такую комбинацию никогда (это утверждение о том, как скилл
   формирует таблицу, а не runtime-валидация — сравнимо с тем, как
   `pf-test-plan` не производит строку `Manual` без `Manual reason:`
   префикса).
4. Каждая `не проверено`-строка дополнительно копируется (по одной записи
   на факт, не пересказом) в `open_questions.md` как unverified-fact
   запись (Status = `unverified-fact`, не `assumed` — см. §6.9) — это то,
   что AC-03d требует буквально: "непроверенный факт... попадает в
   `open_questions.md`".
5. Секция "Methodology" фиксирует, что и как искалось — не для
   декоративности: следующий ревьюер (`/pf-check`, если вызван вручную на
   `research.md`, хотя маршрутная таблица его сюда не ставит по умолчанию,
   §3.7.4) и сессия решения должны понимать охват поиска.

**Не задаёт вопросов пользователю ни при каких обстоятельствах** — это
единственный из шести новых пишущих скиллов, у которого даже output-гейт
"regenerate/keep/cancel" по-прежнему присутствует (общий для всех
пишущих скиллов), но контентных вопросов не было и в `pf-brd`-подобных
скиллах этой ветки — здесь их тем более нет, потому что даже сам факт
"это не проверено" не требует уточнения у человека, это констатация.

### 3.4 `pf-idea-critique` — пишущий скилл, `critique.md`

**Вход:** `idea.md`, `research.md`, `idea_tier`.

**Действие:**
1. Прочитать из `pf-idea-lenses` (§3.7.3) набор персон для этого
   `idea_tier`: базовые четыре (скептик-инвестор, целевой пользователь,
   техлид, безопасник) плюс tier-специфичное расширение.
2. **Диспетчеризовать каждую персону независимо, параллельно, как
   саб-агента** (US-06b: "каждая роль формирует возражения независимо от
   других ролей") — `Agent` tool, по одному вызову на персону, все вызовы
   одного сообщения (см. системную инструкцию про параллельные вызовы).
   Актор/tier для диспетчеризации — **не персона**, персона это точка
   зрения промпта; актор/tier резолвится **один раз** для всего документа
   через ключ `critique`, `pf-roles` §4 (AC-06d: "тот же матрице ролей, без
   отдельного механизма") — все четыре-шесть персон запускаются под одним
   и тем же резолвнутым `(actor, tier, model)`, различается только промпт
   ("ты — скептик-инвестор, читай `idea.md`/`research.md`, сформулируй
   возражения с точки зрения..."). Если `write == claude` — каждая персона
   это независимый `Agent`-вызов с `model: <resolved tier>`; если
   `write != claude` — каждая персона диспетчеризуется **не** через
   `pf-roles` §7 (та форма — всегда `--write`, с жёстким стопом при
   недоступности актора; персона не пишет файл, значит это не запись
   документа) — а через тот же document-form, что уже канонически
   определён в `pf-check`'s "Codex invocation chain"
   (`codex-companion.mjs task "<brief>" --json`, без `--write`), с той же
   семантикой graceful fallback на Claude при недоступности Codex (chain
   шаг 5), применённой к **каждой персоне независимо** — недоступность
   Codex для одной персоны не блокирует остальные и не останавливает
   `pf-idea-critique` целиком (подробное обоснование этого выбора формы —
   §7.12.2 part2, найдено и зафиксировано отдельным пунктом ревью этого
   спека). Итоговую сборку в `critique.md` выполняет сама сессия
   `pf-idea-critique`, как и `pf-check`'s Claude review path не поручает
   сборку итогового отчёта саб-агенту.
3. Каждая персона получает промпт по образцу `pf-check`'s Claude review
   path ("read X, do not edit anything, return only your findings as your
   final message") — персона **не пишет в файл**, возвращает список
   возражений своей персоны; `pf-idea-critique` сама собирает секции по
   персонам плюс сводную таблицу.
4. Секция per-персона — сырые возражения этой персоны (US-06a/b).
5. Сводная таблица "возражение → ответ / риск принят / идея меняется"
   (AC-06c): для каждого возражения `pf-idea-critique` (эта сессия, не
   персона) формулирует диспозицию — **Отвечено** (почему возражение не
   меняет идею — с обоснованием), **Риск принят** (осознанно оставлен,
   без изменения идеи), или **Идея меняется** (какая секция `idea.md`
   должна быть скорректирована — но `pf-idea-critique` **не редактирует**
   `idea.md`: коррекция откладывается либо на решение пользователя в
   сессии решения [override, §3.5.4], либо остаётся зафиксированной как
   входные данные для `verdict.md`'s обоснования). Каждая строка сводной
   таблицы обязана быть отражена либо в `verdict.md`, либо в
   `open_questions.md` (AC-06c, второе предложение) — `pf-idea-verdict`
   при чтении `critique.md` проходит по каждой строке таблицы и либо
   ссылается на неё в своём обосновании, либо, если сама
   `pf-idea-critique` не смогла определить диспозицию однозначно (пример:
   возражение техлида про архитектуру, для которого нет очевидного
   "отвечено/риск принят/меняется" ответа без дополнительной информации),
   записывает `[assumed]` в `open_questions.md` с рекомендованной
   диспозицией.

### 3.5 `pf-idea-verdict` — пишущий скилл (два режима) + сессия решения

**Режим 1 — запись `verdict.md`** (когда `verdict.md` отсутствует, или
существует, но не завершён по общему критерию `pf-size-tiers`, или
существует и завершён, но `/pf-check` для него ещё не выдал `PASSED`,
последним маркером в `session-log.md`, тем же правилом "последний маркер
по позиции в файле", что уже определяет `/pf`'s Step 6 для остальных
типов):

**Вход:** `idea.md`, `research.md`, `critique.md`, `open_questions.md`
(если существует).

**Действие:**
1. Оценить материал по словарю вердиктов (§3.7.5): `project` /
   `spike-first` / `defer` / `archive`. Критерий выбора — не жёстко
   формализован BRD (это суждение), но пять сигналов, которые
   `pf-idea-verdict` обязана явно проверить и назвать в "## Reasoning":
   подтверждена ли боль (research.md), остались ли открытые критичные
   технические вопросы без ответа (→ `spike-first`, если ответ на них
   дешевле получить экспериментом, чем полным проектом), перевешивают ли
   нерешённые возражения критики пользу идеи прямо сейчас (→ `defer`, с
   текстовыми условиями возврата) или принципиально (→ `archive`), и
   соответствует ли идея собственному критерию пользователя "что убедит
   сказать project" из intake.
2. Секция "Return Conditions" пишется **только** для `defer` — свободный
   текст, без дат (BRD Non-Goals — PF дат не отслеживает, AC-07a).
3. Секция "Assumptions Summary" — построчный пересказ каждой `[assumed]`-
   записи `open_questions.md` (не просто ссылка — сессия решения должна
   видеть содержание одним экраном, не переключаться на другой файл).
4. Секция "Unverified Facts Summary" — то же для `unverified-fact`-записей.
5. Секция "## Decision" **не пишется в этом режиме** — остаётся
   отсутствующей до подтверждения (см. §3.5.3): её отсутствие — то, чем
   Режим 1 отличим от "уже подтверждено" при следующем вызове.
6. Commit & push, следующий шаг в отчёте — `/pf-check`.

**Режим 2 — сессия решения** (когда `verdict.md` существует, завершён, и
последний `/pf-check`-маркер для `verdict.md` — `PASSED`, но секция
"## Decision" ещё отсутствует):

#### 3.5.1 Одним батчем

`AskUserQuestion` (один вызов, при необходимости несколько вопросов внутри
него, но не более 4 — тот же лимит, что и у intake, §3.1.3):

> **"Вердикт по идее: `<recommended-verdict>`. Подтверждаете?"**
> Показывается: рекомендованный вердикт + обоснование (сокращённо, полный
> текст в `verdict.md`), полный список `[assumed]`-допущений, полный
> список открытых вопросов, полный список непроверенных фактов.
> - **Подтвердить `<recommended-verdict>`** — закрыть issue с этим вердиктом.
> - **Выбрать другой вердикт** — открывает второй `AskUserQuestion` с
>   оставшимися тремя вариантами словаря.
> - **Переопределить допущение** — открывает третий `AskUserQuestion`,
>   список `[assumed]`-записей для выбора (по одной за раз — множественный
>   выбор не поддерживается за один проход, но цикл §3.5.4 позволяет
>   переопределить несколько последовательно).

#### 3.5.2 Переопределение (AC-07d)

1. Пользователь выбирает конкретную `[assumed]`-запись и даёт новый ответ
   (свободный текст).
2. `pf-idea-verdict` читает у этой записи поле "Used in" (§6.9 — какие
   документ+секция её использовали).
3. Регенерирует **только** названные секции — то есть переписывает именно
   эти `## `-заголовки в названных файлах, оставляя всё остальное
   содержимое файла нетронутым (текстовая операция уровня "заменить блок
   между этим заголовком и следующим", не переписывание документа целиком
   — та же дисциплина, что `pf-execute`'s "never rewrite the whole
   document in a single pass" для чекбоксов, применённая здесь к секциям
   документов). Если переопределённое допущение использовалось в
   нескольких документах (например, допущение из `idea.md`'s "MVP",
   процитированное в `verdict.md`'s "Reasoning") — регенерируются секции
   во **всех** названных документах, не только в одном (AC-07d: "секций
   документов", множественное число).
4. Помечает исходную запись в `open_questions.md` как `[overridden]`,
   рядом — новый ответ пользователя (аудируемость: видно и что было
   допущено, и чем заменено).
5. Пересчитывает рекомендуемый вердикт **заново**, целиком по правилу
   п.1 Режима 1, на обновлённом материале (переопределение могло изменить
   вывод).
6. Возвращается к §3.5.1 — сессия решения показывается заново, теперь с
   обновлённым вердиктом/списками.

Цикл повторяется, пока пользователь не подтвердит один из четырёх
вердиктов словаря.

#### 3.5.3 Подтверждение

По подтверждению — дописывается секция "## Decision" в конце `verdict.md`:
подтверждённый вердикт (может отличаться от изначально рекомендованного,
если пользователь выбрал "другой вердикт"), дата, ISO-timestamp,
пользователь-инициатор (сессия). Именно наличие этой секции — единственный
машиночитаемый признак "вердикт подтверждён" (AC-07e: "без подтверждения
человека issue не закрывается"; `/pf-close`'s prerequisite guard для
`idea`-типа проверяет присутствие именно этой секции — см. §7.3.1).
Commit & push. Отчёт: следующий шаг — `/pf-close`.

#### 3.5.4 Автопилот и front-loaded (US-10b)

`/pf-autopilot` **обязано остановиться перед Режимом 2** и ждать человека
— не применяет правило "3 попытки, затем дефолт" к сессии решения (US-10b,
явно). Механизм: Режим 2 не диспетчеризуется автопилотом вообще — рабочий
цикл автопилота (§7.5) для `idea`-issue доходит до состояния "verdict.md
готов и check пройден, следующий шаг — сессия решения" и **останавливается
там**, печатая финальный отчёт с полным списком `[assumed]`/открытых
вопросов, вместо того чтобы запускать `pf-idea-verdict` ещё раз. Это то же
самое разделение, что уже действует для обычного `/pf-check`'s
interactive-gate против `autopilot`-gate — только здесь автопилот не
подменяет интерактив автоматическим ответом вообще, а прекращает работу.

### 3.6 `pf-idea-spike` — пишущий скилл (два режима)

**Режим 1 — запись `hypothesis.md`** (когда файл отсутствует или не
завершён): переносит вопрос/критерий успеха/time-box/метод **из
`prompt.md`** (уже собраны на intake, §3.1.3/§6.8) в структуру §6.6, без
дополнительных вопросов — это форматирующий шаг, не исследовательский.
Commit & push, следующий шаг — (опционально `/pf-check`, не входит в
маршрутную таблицу по умолчанию — §3.7.4) `/pf-idea-spike` (Режим 2).

**Режим 2 — запись `findings.md`** (когда `hypothesis.md` завершён,
`findings.md` отсутствует или не завершён):

1. **Нужен ли код/эксперимент, требующий изменений в репозитории?**
   Определяется по `hypothesis.md`'s "## Method": если метод описывает
   код/конфигурацию/скрипт — да; если метод — "прочитать документацию X и
   сравнить с Y" — нет.
2. **Если да** — создать/checkout ветку `issue/<spike-id>` **тем же
   механизмом, что `pf-execute`'s Phase 0** (ссылка по имени, не
   копирование текста: "тот же Branch Setup, что `pf-execute` Phase 0"),
   выполнить эксперимент на этой ветке, зафиксировать код туда обычным
   `git add -A && git commit` (без пуша до конца эксперимента — пуш
   происходит стандартным `pf-git`'s Step 3 в конце стадии, на **этой**
   ветке — эксперимент пушится, это не финальный merge). `findings.md`
   пишется **тоже на этой ветке** (это то, что при закрытии копируется
   обратно на родительскую, см. §7.3.2) — не отдельным коммитом на
   родительской.
3. **Если нет** — эксперимент выполняется прямо в текущей сессии
   (например, чтение реальной документации/API вживую через `WebFetch`),
   без создания ветки; `findings.md` пишется на той же ветке, где уже
   находится сессия (обычно родительская, если ветка вообще не создавалась
   этим issue).
4. **AC-09c — гейт "findings подтверждены реальным прогоном".** Секция
   "## Run Evidence" обязана содержать конкретное свидетельство: команда
   и её вывод (полный или показательный фрагмент), путь к артефакту
   (лог-файл, скриншот), или прямая цитата из реально прочитанного
   источника с URL/путём — не пересказ "я думаю, это сработает бы". Это
   verify-before-claim, применённое механически: `pf-idea-spike` не пишет
   "## Conclusion" без непустой "## Run Evidence", тем же правилом, что
   `research.md` не пишет `проверено` без Source (§3.3, п.3).
5. Секция "## Result vs. Success Criterion" — met / not met / partial,
   сверяясь с критерием из `hypothesis.md`.
6. Commit & push (на той ветке, где сессия сейчас находится — п.2/п.3).
   Следующий шаг — `/pf-close`.

### 3.7 `pf-idea-lenses` — справочный скилл

Структура по образцу `pf-size-tiers`: если вызван напрямую — просто
печатает содержимое ниже. Полные таблицы — §6.2.2 (бюджеты идеи), §6.10
(общая сводная таблица бюджетов); здесь — состав и обоснование.

#### 3.7.1 `idea_tier` — закрытый словарь

| `idea_tier` | Когда выбирать |
|---|---|
| `personal` | Личный инструмент/скрипт для себя, без внешних пользователей и без рыночного контекста |
| `infra` | Внутренний инструмент/автоматизация для существующих проектов — не продукт, но нужна операционная надёжность |
| `content` | Контентный проект (блог, курс, рассылка) — успех определяется аудиторией/дистрибуцией, не рынком в классическом смысле |
| `product` | Продукт с внешними пользователями/рынком — полный набор бизнес-линз |

#### 3.7.2 Наборы линз

| Линза | personal | infra | content | product |
|---|:---:|:---:|:---:|:---:|
| 5 почему (по боли) | ✓ | ✓ | ✓ | ✓ |
| SWOT (лёгкий) | — | ✓ | ✓ | ✓ |
| Build vs. Buy | — | ✓ | — | — |
| Audience/Distribution Fit | — | — | ✓ | — |
| Lean Canvas | — | — | — | ✓ |
| JTBD | — | — | — | ✓ |
| Pre-mortem | — | — | — | ✓ |
| TAM/SAM/SOM | — | — | — | ✓ |

"5 почему" обязательна для всех (AC-04b, дословно). `personal` не получает
ни SWOT, ни рыночных оценок (AC-04b, дословно). Остальное — дизайн-решение
этого спека, обоснование в §1 преамбулы каждой строки таблицы выше.

#### 3.7.3 Наборы персон критики

| Персона | personal | infra | content | product |
|---|:---:|:---:|:---:|:---:|
| Скептик-инвестор | ✓ | ✓ | ✓ | ✓ |
| Целевой пользователь | ✓ | ✓ | ✓ | ✓ |
| Техлид | ✓ | ✓ | ✓ | ✓ |
| Безопасник | ✓ | ✓ | ✓ | ✓ |
| Эксплуатация/надёжность | — | ✓ | — | — |
| Рыночный аналитик/конкурент | — | — | — | ✓ |
| Аудитория/дистрибуция | — | — | ✓ | — |

Базовые четыре — минимум US-06a (дословно). Расширение — дизайн-решение
этого спека (BRD делегирует состав расширения `pf-idea-lenses`, US-06a:
"набор ролей может расширяться по `idea_tier`").

#### 3.7.4 Таблицы стадий

```
idea:  CREATE(prompt.md) → /pf-idea(idea.md) → /pf-check
       → /pf-idea-research(research.md) → /pf-idea-critique(critique.md)
       → /pf-idea-verdict[режим 1](verdict.md) → /pf-check
       → /pf-idea-verdict[режим 2, сессия решения] → /pf-close

spike: CREATE(prompt.md) → /pf-idea-spike[режим 1](hypothesis.md)
       → /pf-idea-spike[режим 2](findings.md) → /pf-close
```

| Позиция (первая незавершённая стадия) | Next step |
|---|---|
| CREATE only | `/pf-idea` (`/pf-idea-spike` для spike) |
| IDEA | `/pf-check` |
| IDEA + check passed | `/pf-idea-research` |
| RESEARCH | `/pf-idea-critique` |
| CRITIQUE | `/pf-idea-verdict` |
| VERDICT (документ написан, check ещё не пройден) | `/pf-check` |
| VERDICT + check passed, "## Decision" отсутствует | `/pf-idea-verdict (decision session)` |
| VERDICT + "## Decision" присутствует | `/pf-close` |

| Позиция (spike) | Next step |
|---|---|
| CREATE only | `/pf-idea-spike` |
| HYPOTHESIS | `/pf-idea-spike` |
| FINDINGS | `/pf-close` |

**Почему `/pf-check` только после `idea.md` и после `verdict.md`
(decision 3).** Четыре довода, каждый — самостоятельная причина не
вставлять check после `research.md`/`critique.md`:
1. **Короткий прогон — явная цель фреймворка** (G6/prompt.md constraint 3:
   "человек только в начале и в конце"; automated-check gates добавляют
   раунды `Fix now`, которые в автопилоте не бесплатны по времени, даже
   будучи неинтерактивными).
2. **`idea.md`** — единственная точка, где ошибка **дёшево исправить
   рано**: если позиционирование идеи в принципе кривое, это должно
   всплыть до того, как `research`/`critique` потратят усилия на
   исследование и критику неверно сформулированной идеи.
3. **`research.md`'s собственная дисциплина уже есть встроенный гейт** —
   AC-05b делает "проверено без источника" структурно невозможной записью
   самим скиллом (§3.3, п.3), а не чем-то, что нужно поймать отдельным
   ревью после факта.
4. **`critique.md`'s весь смысл — уже и есть adversarial-проверка** —
   ещё один общий P0/P1-ревью поверх документа, чья единственная функция
   — противоречить идее с разных точек зрения, структурно избыточен.
5. **`verdict.md`** — последний документ перед тем, как решение увидит
   человек: ошибка здесь (неверно посчитанные допущения, пропущенное
   возражение из сводной таблицы критики) — это ровно то, что должно быть
   поймано **до**, а не во время сессии решения, где переделка стоит
   дороже (нужно заново показывать батч).

**Почему у `spike` нет обязательного `/pf-check` вообще.** Настоящий
гейт качества спайка — не текстовое ревью, а AC-09c ("findings
подтверждены реальным прогоном"), встроенный в саму `pf-idea-spike`
(§3.6, п.4) тем же способом, что и `research.md`'s встроенная дисциплина
источников. `/pf-check` остаётся доступным **по требованию** — US-11d
требует, чтобы гейт для документов idea/spike **работал**, не чтобы он
**был обязателен в маршруте**; TARGET↔key отображение (§7.2) делает его
пригодным для ручного/автопилотного вызова на `hypothesis.md`/`findings.md`,
просто маршрутная таблица его туда не вставляет по умолчанию.

#### 3.7.5 Словарь вердиктов

`project` / `spike-first` / `defer` / `archive` — закрытый список (BRD
decision, AC-07a). `defer` несёт свободнотекстовые условия возврата, без
дат (§3.5, п.2). Это **отличается** от формулировки в `prompt.md`
("`incubate-until:<дата>`") — расхождение сознательное и разрешено в
пользу связанного (`decisions already made` п.5, AC-07a): PF не хранит
дат и не знает про инкубатор (BRD Non-Goals, prompt.md constraint 4).

### 3.8 `pf-interaction` — справочный скилл

Единая точка определения front-loaded режима — читается и `idea`/`spike`-
пайплайном (где это единственный режим, не переключаемый), и
feat/improve/bug (где это опциональный `interaction: front-loaded` в
`prompt.md`, дефолт — сегодняшнее интерактивное поведение). Полное
содержание — §7.13 (список hook-сайтов) и §6.9 (формат `open_questions.md`,
общий для обоих применений). Здесь — определение самого правила,
переиспользуемое по имени во всех hook-сайтах:

> **Front-loaded rule.** Для стадии, вызванной внутри issue с
> `interaction: front-loaded` (явно в `prompt.md`, или неявно для
> `idea`/`spike` — эти типы front-loaded всегда, поле не читается как
> переключатель для них, см. §6.1): при вопросе, который в интерактивном
> режиме задаётся через `AskUserQuestion`, стадия **не вызывает
> `AskUserQuestion`**. Вместо этого:
> 1. Взять рекомендованный вариант ответа тем же способом, каким сегодня
>    вычисляется рекомендация для интерактивного вопроса (та же
>    Recommendation-процедура, если она есть у конкретного вопроса —
>    `pf-roles` §10 для ролевых вопросов; иначе — собственное суждение
>    стадии с обоснованием, как оно уже формулируется в
>    "add your recommendation (with reason why) below the options"
>    практически везде в текущих скиллах).
> 2. Записать строку в `open_questions.md`:
>    `[assumed] <вопрос> → <взятый ответ> — <почему>` (точный формат §6.9).
> 3. Продолжить стадию с этим ответом, не останавливаясь.
>
> **Исключения — вопросы, которые задаются всегда, даже в front-loaded
> режиме** (§7.13.1 — исчерпывающий список: `/pf-close`'s Phase 1
> подтверждение закрытия; `code.review: skip` confirmation guard;
> предложение установить codex-плагин; `/pf-idea-verdict`'s сессия
> решения). Это разные вопросы по разной причине — деструктивное/
> внешнее действие (установка ПО, закрытие issue, отключение ревью) не
> становится допущением молча; финальное решение по вердикту — это и
> есть единственная точка человека "в конце", а не то, что можно
> заменить рекомендацией.

## 5. Edge Cases & Constraints

### 5.1 `type:` во фронтматтере избыточен с именем папки — конфликт есть ошибка

`prompt.md` idea/spike несёт `type: idea|spike` (§6.1) **несмотря на то**,
что тип уже читается из имени папки (как и для feat/improve/bug сегодня).
Причина избыточности — hand-edit-риск (папку переименовали, фронтматтер
не тронули, или наоборот) и то, что этот тип используется как ключ
резолва ролей (`pf-roles` §4 читает тип, чтобы понять, какой набор ключей
применим). **Правило:** каждая стадия, читающая `prompt.md`, сверяет
`type:` с именем папки; расхождение — это не тихий приоритет одного над
другим, а явная ошибка остановки: *"`prompt.md`'s `type: <X>` не совпадает
с именем папки (`<Y>`) — почини вручную, какое из двух верно"*.

### 5.2 `.pf-version`, записанный `/pf`, и `PF_VERSION` в `converge-to-v3.sh` — два источника, требующие ручной синхронизации

`/pf`'s "сразу проект" путь (§3.1.1, п.3) пишет `.pf-version` из
`~/.claude/skills/pf/SKILL.md`'s `version:`, а не из `PF_VERSION`
(`scripts/converge-to-v3.sh`), поскольку у установленного скилла нет
доступа ко второму. Оба значения сегодня равны `3.0.0`, но это два
независимых литерала в двух файлах: расхождение возможно, если один
бампнут, а другой — нет. Это не новая проблема этого issue (CONTRIBUTING.md
уже перечисляет несколько мест синхронизации версии), но список мест
должен вырасти на одно — `skills/pf/SKILL.md`'s `version:` — см. §7.10.
**Последствие для `pf-update`:** его Step 3 сравнивает `.pf-version`
проекта с `PF_VERSION` из репозитория фреймворка (доступного тому, кто
запускает `pf-update` — тот, у кого framework-репозиторий есть локально).
Проект, чей `.pf-version` был записан `/pf`'s собственным сканфолдом,
пройдёт эту проверку ровно тогда, когда оба литерала синхронны — то есть
поведение `pf-update` не меняется, но становится зависимым от той же
дисциплины синхронизации, что уже требуется для major/minor-бампов.

### 5.3 Пустая папка без `node`/`git` на PATH

`/pf` — это не `install.sh`, у него нет собственной проверки зависимостей.
Если `git` отсутствует на PATH вообще (не просто "не инициализирован") —
`git rev-parse` из §3.1.1 завершится ошибкой "command not found", а не
кодом not-a-repo; "сразу проект"-путь не может выполнить `git init`.
**Правило:** различить эти два случая по тексту ошибки/коду выхода; при
отсутствии самой команды `git` — остановиться с понятным сообщением
("`git` не найден — установите его, затем повторите `/pf`"), не пытаться
продолжить каркас без git. Путь "идея" не требует `git` вообще (AC-01b) и
не задет этим краевым случаем.

### 5.4 Idea/spike-issue в проекте, где размерные tier'ы уже используются

`idea_tier` и `size_tier` — независимые поля разных типов issue; ничего в
`prompt.md` одного issue не влияет на другой. `/pf`'s Step 5/6 читают
`size_tier` только для feat/improve/bug/trivial-веток, `idea_tier` — только
внутри idea/spike-ветки (§3.1.8); один и тот же проект свободно держит
issue обоих семейств одновременно, каждый маршрутизируется по своей
таблице.

### 5.5 Автопилот на нескольких открытых idea/spike-issue одновременно

Не новое ограничение — существующее правило `pf-autopilot` ("один
schedule на проект") действует без изменений: `/pf-autopilot <idea-id>`
пиннит конкретный idea-issue на весь прогон, как и для feat/improve/bug
(§3.5.4/§7.5 описывают только точку остановки перед сессией решения, не
меняют пиннинг/schedule-механику).

### 5.6 `open_questions.md` — не стадия, может не существовать вовсе

Файл создаётся **первой стадией, которой есть что в него записать**
(любой из шести пишущих скиллов, или сама `/pf` при intake, если
допущение потребовалось уже там) — не создаётся заранее пустым при
CREATE. Его отсутствие **не** означает "стадия не завершена" ни для
одной стадии: критерий completeness (`pf-size-tiers`) и таблицы стадий
(`pf-idea-lenses`, §3.7.4) никогда не упоминают этот файл. Пустая идея,
где не потребовалось ни одного допущения и ни одного непроверенного
факта — валидный, полностью завершаемый case; сессия решения (§3.5.1)
в этом случае показывает пустые списки допущений/вопросов, не ошибку.

### 5.7 Два представления одного порядка стадий (`pf-size-tiers` и `pf-idea-lenses`) не должны разойтись

`pf-size-tiers`'s "Pipelines" таблица (§7.11.1) существует только для
конъюнкта 3 критерия completeness (список стадий по порядку, без
привязки к конкретной следующей команде). `pf-idea-lenses`'s таблица
стадий (§3.7.4) — тот же порядок, плюс конкретная команда на каждом шаге,
плюс check-гейты. Оба представления **обязаны перечислять документы в
одном и том же порядке** — расхождение сделало бы критерий completeness
и маршрутизацию противоречащими друг другу для одного и того же issue.
Это не проверяется программно нигде в фреймворке и для существующих
типов (одна и та же двойная развёртка уже есть для feat/improve/bug/
trivial между `pf-size-tiers` и `/pf`'s собственными таблицами) — та же
degree of risk, принятая осознанно, покрывается статическим тестом §8.1
(сверка списка документов в обоих файлах).

### 5.8 Найденный файл идеи может быть недоступен / бинарным / без текста

Если пользователь на intake называет файл, который `/pf` не может
прочитать как текст (бинарный, повреждённый, отсутствует) — это не
регламентировано отдельно BRD (Non-Goals: извлечение — на суждение
ассистента), но `/pf` обязано **не падать молча**: сообщить об ошибке
чтения и попросить ввести идею текстом напрямую вместо файла, в рамках
того же intake-вызова (не отдельная стадия, не сбой всего intake-батча —
только этот один вопрос переспрашивается).

### 5.9 `defer`/`archive` не пишут ничего, кроме закрытия

Вердикты `defer`/`archive` (§4.4, правая ветка) не создают Phase 5.5
последующего issue — `/pf-close` для них выполняет **только** обычные
Phase 0-9 (адаптированные под idea-тип, §7.3.1), без дополнительного
шага. Условия возврата `defer` живут исключительно текстом внутри уже
заархивированного `verdict.md` — PF не хранит их нигде ещё и не создаёт
никакого будущего напоминания (BRD Non-Goals, decision 4/5).
