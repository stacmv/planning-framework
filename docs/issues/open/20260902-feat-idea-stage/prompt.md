Добавить в Planning Framework стадию **идеи**: сценарий создания нового проекта
с нуля или из описания идеи, до первого `feat`-issue. Сценарий пользователя:
`mkdir proj`, `cd proj`, `claude`, `/pf`. В пустой папке `/pf` сам доводит
проект до состояния v3 (эквивалент `make converge`, без отдельного шага
пользователя) и предлагает начать с идеи.

## Ограничения (заданы пользователем)

1. **Не ломать основной воркфлоу.** Идея реализуется как новые типы issue
   поверх существующей машинерии (`docs/issues/open/YYYYMMDD-idea-<slug>/`,
   `YYYYMMDD-spike-<slug>/`), а не как параллельный механизм. Пайплайны
   feat/improve/bug остаются как есть; новые ветки только добавляются.
2. **Пользователь знает только `/pf` и `/pf-autopilot`.** Все остальные
   скиллы (`pf-idea`, линзы, research, критика) внутренние; каждый шаг сам
   печатает, что делать дальше. `/pf` без открытых issue предлагает третий
   вариант: «опиши идею». `/pf-autopilot` гонит idea-issue до вердикта.
3. **Human-in-the-middle только в начале и в конце.** Режим front-loaded:
   один intake-батч вопросов при создании `prompt.md` (язык, `idea_tier`,
   свидетельства боли, ограничения, что вне рамок, критерий «что убедит
   сказать project», права ИИ на самостоятельные решения); ноль вопросов в
   середине — недостающие ответы берутся по рекомендации и пишутся в
   `open_questions.md` с пометкой `[assumed]`; одна сессия решения в конце
   (вердикт + список допущений + открытые вопросы одним батчем,
   переопределение = точечная перегенерация затронутых секций).
   Сначала обкатать на `idea`/`spike`, затем тем же флагом
   `interaction: front-loaded` в `prompt.md` распространить на
   feat/improve/bug с дефолтом «как сегодня».
4. **PF ничего не знает про инкубатор и про vault** — это внешние сущности,
   у других пользователей их нет. Никаких хуков на заметки Obsidian.

## Состав (один large issue)

- **Тип `idea`:** `prompt.md` (intake) → `idea.md` (боль и её подтверждение,
  аналоги, отличие/УТП, MVP, цена, риски — по линзам `idea_tier`) →
  `research.md` (факты с ссылками и пометкой «проверено / не проверено»,
  непроверенное не выдаётся за факт) → `critique.md` (красная команда через
  `pf-roles`: скептик-инвестор, целевой пользователь, техлид, безопасник;
  сводка «возражение → ответ / риск принят / идея меняется») →
  `verdict.md` → `/pf-close`. Без BRD/spec/кода.
- **Линзы** в reference-скилле (`pf-idea-lenses`, по образцу
  `pf-size-tiers`): `idea_tier` = personal / infra / product / content
  выбирает набор (личному инструменту SWOT не нужен, продукту — Lean Canvas,
  JTBD, SWOT, pre-mortem, TAM/SAM/SOM; всем — «5 почему» по боли).
- **Вердикт** из закрытого словаря: `project` / `spike-first` /
  `incubate-until:<дата>` с обязательным условием выхода / `archive`.
  Закрытие issue = вердикт зафиксирован. `project` → `/pf` следующим шагом
  заводит первый `feat`-issue с `prompt.md`, предзаполненным из `idea.md`
  и intake; `pf-brd` при ссылке на `idea.md` спрашивает только по пробелам.
  `git init` и первый коммит, если папка ещё не репозиторий, через `pf-git`.
- **Тип `spike`:** `prompt.md` → `hypothesis.md` (вопрос, критерий успеха,
  time-box, метод) → `findings.md` → `/pf-close`; гейт закрытия: findings
  подтверждены реальным прогоном (verify-before-claim).
- Таблицы стадий новых типов держать в reference-скилле, не раздувать
  `/pf` SKILL.md (уже ~38 КБ). `pf-check` получает TARGET-ы
  `idea`/`research`/`critique`/`verdict`/`hypothesis`/`findings`.
  `pf-help` дополняется.

## Инструкция для ревью (задана пользователем)

При отправке документов и кода на ревью в codex дополнительно запрашивать
проверку скиллов на совместимость с Codex: в будущем фреймворк должен
работать и в Claude Code, и в Codex.

## Контекст

Мозговой штурм 02.09.2026 в сессии Claude Code: до этого разбор идей делался
вручную (аналоги, боль, MVP, цена, вердикт «инкубатор до даты»/проект/архив),
три раза за лето; повторяющиеся вердикты «сначала технический спайк» и
случаи, когда ИИ выдал непроверенный факт за проверенный, легли в основу
требований к `research.md` и типу `spike`.
