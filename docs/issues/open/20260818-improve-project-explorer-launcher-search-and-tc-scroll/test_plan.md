# Test Plan: 20260818-improve-project-explorer-launcher-search-and-tc-scroll

**Date:** 2026-09-09

## Overview

Issue закрывает два независимых долга Project Explorer (`tools/manual-test-ui`),
отложенных при закрытии `20260806-feat-project-explorer-redesign`: поиск на
сетке карточек проектов (AC-01…AC-06) и прокрутку/подсветку нужного
тест-кейса при переходе из инбокса (AC-07, AC-08).

Обе части устроены по одному и тому же принципу, уже принятому в этом
инструменте для ролевого фильтра (`filterInboxItemsByRoles` в
`public/inbox.js`, `.role-switch`): чистая функция фильтрации/поиска
отдельно от DOM, что делает почти всё поведение проверяемым в
`node --test` под fake DOM без браузера. План отдаёт приоритет Auto:
подстрочный поиск, скрытие разделов, пустое сообщение, отсутствие
персистентности, неизменность выпадающего списка в шапке, a11y-атрибуты,
проброс `tcId` через URL и нахождение нужного `[data-tc-id]` — всё это
факты о данных/DOM, а не о восприятии, и укладывается в существующие
сьюты (`project-picker.test.js`, `launcher.test.js`, `inbox.test.js`,
`workspace.test.js`, `a11y.test.js`). Ручным остаётся только то, что fake
DOM не может дать в принципе — действительно ли подсветка и скролл
воспринимаются человеком в настоящем браузере (AC-07).

**Цели плана:**

1. Доказать все критерии приёмки AC-01…AC-08 из `brd.md`.
2. Отдельно закрыть BR-1 (поиск не переживает перезагрузку, в отличие от
   ролевого фильтра), BR-2 (поиск и переход к тест-кейсу остаются read-only
   относительно документов проекта — ни один из этих двух сценариев не
   пишет в файлы проекта) и BR-3 (нет связи → тихая деградация до перехода
   на вкладку, никогда — подсветка не того кейса).
3. Подтвердить, что AC-05 не регрессирует: рендер шапки других экранов
   (`renderProjectSelector()`, `public/project-picker.js`) не приобретает
   поле поиска — оно только на главном экране
   (`renderLauncherProjectSections()`, `public/launcher.js`). Проверяется по
   наблюдаемому сигналу в DOM (присутствию/отсутствию элемента поля
   поиска), а не по сигнатуре `renderProjectSections()` — до реализации
   issue не фиксируется, принимает ли эта функция параметр поиска вообще
   или фильтрация происходит целиком на уровне вызывающей стороны.

## Prerequisites

- Рабочая копия `planning-framework` на ветке issue.
- Node.js той же версии, что требуется для `make test-ui`; `node --test`
  запускается по `tools/manual-test-ui/test/*.test.js` — то же, что
  `make test` уже гоняет для этого инструмента.
- Реализация вводит новую чистую функцию поиска/фильтрации по подстроке
  (по аналогии с `filterInboxItemsByRoles`), вызываемую из
  `renderLauncherProjectSections()` в `public/launcher.js` перед передачей
  данных в `renderProjectSections()` (`public/project-picker.js`) — тесты
  ниже адресуются к этому месту по поведению, а не по гипотетическому
  имени функции, поскольку до реализации issue точное имя не фиксировано.
- Для части про прокрутку: `ptcId` (формат `PTC-NNNN`, из
  `docs/planning/test-plan.md`, `collectManualTests()` в `lib/inbox.js`) и
  issue-локальный `tcId` (формат `TC-NNN`, из `manual_test_checklist.md`
  issue, `parseChecklist()` в `lib/checklist.js`) — разные номера одного и
  того же кейса. Сегодня связь между ними теряется дважды:
  1. `ORIGIN_RE` в `lib/inbox.js` разбирает `Origin` (`ISSUE-ID#TC-NNN`) и
     захватывает `TC-NNN`-половину (`match[2]`), но `collectManualTests()`
     отдаёт в каждом элементе `manualTests[]` только `issueId` (`match[1]`)
     — сам `TC-NNN` нигде не сохраняется. Это новый контракт, который
     реализация issue должна ввести: `collectManualTests()` обязана начать
     возвращать issue-локальный `tcId`.
  2. Даже до этой доработки данные, которые сегодня реально доходят до
     `maybeScrollToPtcId()` (`public/workspace.js`, ищет
     `[data-tc-id="..."]`), — это продуктовый `ptcId` (`row.ptc`, формат
     `PTC-NNNN`): `manualTestItemView()` кладёт его в `where.ptcId`,
     `inboxTargetHash()` пробрасывает его как есть в query, `parseRoute()`
     возвращает как `initialPtcId`, и `workspace.js` ищет по нему
     `[data-tc-id="PTC-NNNN"]` — которого в чек-листе никогда нет (там
     `data-tc-id="TC-NNN"`). Это и есть баг AC-07/AC-08, который данная
     issue закрывает: реализация должна пронести именно issue-локальный
     `TC-NNN` (не продуктовый `ptcId`) по всей цепочке
     `collectManualTests()` → `manualTestItemView()` →
     `inboxTargetHash()`/`parseRoute()` → `maybeScrollToPtcId()`. Имя
     query-параметра/опции, которым это будет обозначено (`tcId=` вместо
     переиспользованного `ptcId=`, или иначе), архитектурой не
     зафиксировано — тесты ниже проверяют, что issue-локальный номер
     доходит до места назначения, а не конкретное имя поля/параметра.
- Реальный путь клика по пункту инбокса (важно для TC-005/TC-008): на
  глобальном экране `#/inbox` (`public/inbox.js`, `mount()`) нет
  кликабельных пунктов конкретных тест-кейсов — там только сводная таблица
  проектов/issue со счётчиками (`renderProjectSummary`). Клик по строке
  issue в этой таблице ведёт на `#/p/<project>/inbox?issue=<id>`
  (`project-inbox.js`'s `mountInbox()`), где issue раскрывается в две
  секции («Ручные тесты» / «Человеческие задачи», `renderIssueGroup`) —
  вот там и рендерятся кликабельные `.inbox-item` конкретных тест-кейсов
  (`renderManualTestsSection`/`renderItem`, оба в `public/inbox.js`).
- Фикстуры для этой части — issue с продуктовым тест-планом, где хотя бы
  одна pending-строка имеет `Origin`, разбираемый `ORIGIN_RE`, и
  соответствующий `manual_test_checklist.md` с тем же `TC-NNN`.

### TC-001: Поиск по подстроке — совпадение по названию проекта или ID issue, регистронезависимо

**Description:** Проверяет AC-01. Ввод подстроки оставляет только те
проекты, у которых совпало название **или** идентификатор хотя бы одного
открытого issue; сравнение регистронезависимое.

**Preconditions:**
- Раннер — `node --test tools/manual-test-ui/test/launcher.test.js` (или
  `project-picker.test.js`, в зависимости от того, куда реализация
  поместит функцию поиска).
- Фикстурные данные лаунчера: несколько проектов; у части — несколько
  открытых issue с разными ID (`status: "open"`), у части — issue со
  `status: "closed"`. Хотя бы один ID/название содержит regex-метасимвол
  (например `.`, `(`, `-`) в позиции, где буквальное совпадение и
  regex-совпадение дали бы разный результат.

**Steps:**

| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Вызвать функцию поиска с подстрокой, совпадающей с частью названия одного проекта. | Возвращён/отрендерен только этот проект. |
| 2 | Вызвать с подстрокой, совпадающей с частью ID открытого issue другого проекта (не с его названием). | Возвращён именно этот проект — совпадение по ID issue тоже работает. |
| 3 | Повторить шаг 1 и шаг 2 той же подстрокой в другом регистре (верхний/смешанный). | Результат идентичен — сравнение регистронезависимое. |
| 4 | Вызвать с подстрокой, не совпадающей ни с одним названием и ни с одним ID. | Ни один проект не проходит фильтр (пустой результат на этом уровне — сообщение проверяется в TC-003). |
| 5 | Вызвать с подстрокой, совпадающей одновременно с названием одного проекта и ID issue другого. | Оба проекта проходят фильтр. |
| 6 | Вызвать с подстрокой, совпадающей только с ID **закрытого** (`status: "closed"`) issue проекта, не совпадающей ни с названием проекта, ни с ID ни одного его **открытого** issue. | Проект НЕ проходит фильтр — AC-01 требует совпадения по названию или ID хотя бы одного **открытого** issue, закрытый issue в счёт не идёт. |
| 7 | Проект с несколькими открытыми issue; вызвать с подстрокой, совпадающей с ID только одного из них — не первого в списке проекта. | Проект проходит фильтр — совпадение работает по «хотя бы один из всех», а не только по первому issue проекта. |
| 8 | Вызвать с подстрокой, содержащей regex-метасимвол (например `.` или `(`), которая: (а) как литеральная подстрока совпадает с частью названия/ID одного проекта; (б) как regex совпала бы дополнительно с чем-то ещё (например `.` совпал бы с любым символом любого названия). | Совпадает только проект из (а); поиск не интерпретирует ввод как regex и не выбрасывает исключение на «неправильном» regex-синтаксисе (например непарной скобке). |

**Expected Outcome:** Поиск находит проект и по названию, и по ID
открытого issue, независимо от регистра ввода, сравнивает подстроку
буквально (без regex-семантики) и учитывает только открытые issue.

**Priority:** Critical

### TC-004: `collectManualTests()` возвращает issue-локальный tcId; деградация без ошибки, когда прокрутка невозможна

**Description:** Проверяет AC-08 и BR-3, на двух уровнях. Во-первых, сам
контракт данных: `collectManualTests()` (`lib/inbox.js`) должна начать
возвращать issue-локальный `tcId` (сегодня `ORIGIN_RE` разбирает его из
`Origin` как `match[2]`, но функция отдаёт наружу только `issueId` —
`match[1]`). Во-вторых, реально достижимые случаи деградации: строка с
неразбираемым `Origin` СЕГОДНЯ не деградирует на экране — она вообще не
попадает в `manualTests[]` (штатное поведение `collectManualTests()`,
никакая реализация issue не обязана и не должна это менять), так что
«клик по пункту со сломанным Origin» непроверяем — такого пункта не
существует. Реально достижимая деградация — рассинхронизация номеров:
`tcId` из `Origin` распознан корректно, но чек-лист issue не содержит
тест-кейса с таким id (например, тест-кейс в чек-листе переномерован, или
строка продуктового тест-плана заполнена вручную и ссылается на
несуществующий/ещё не написанный `TC-NNN`, BR-3). В этом случае поведение
остаётся сегодняшним: переход на правильную вкладку без прокрутки, без
ошибки и без сообщения о сбое — и без ложной подсветки другого кейса.

**Preconditions:**
- Раннер — `node --test tools/manual-test-ui/test/inbox.test.js` (для
  контракта `collectManualTests()`) и
  `tools/manual-test-ui/test/workspace.test.js` (для деградации
  `maybeScrollToPtcId`/аналога).
- Фикстурный `docs/planning/test-plan.md` с pending-строкой, у которой
  `Origin` — валидный `20260101-feat-fixture#TC-007`, и отдельно
  pending-строкой со сломанным `Origin` (для шага 2).
- Фикстурный `manual_test_checklist.md`, не содержащий тест-кейса
  `TC-007` (для шага 3) — рассинхронизация продуктового тест-плана и
  чек-листа issue.

**Steps:**

| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Вызвать `collectManualTests()` на фикстуре с валидным `Origin: 20260101-feat-fixture#TC-007`. | Возвращённый элемент несёт issue-локальный `tcId: "TC-007"` — не только `issueId`/продуктовый `ptcId`, как сегодня. |
| 2 | Вызвать `collectManualTests()` на фикстуре со сломанным (не разбираемым `ORIGIN_RE`) `Origin`. | Строка полностью исключена из `manualTests[]` (текущее поведение, не меняется этой issue), в лог уходит `console.warn` с путём файла и номером строки — это не UI-деградация, пункт не появляется в инбоксе вовсе. |
| 3 | Смонтировать workspace с `initialTab` на чек-лист и `tcId: "TC-007"`, при этом чек-лист (фикстура) не содержит `[data-tc-id="TC-007"]` ни на одной панели. | Открывается правильная вкладка чек-листа; `scrollIntoView` не вызывается ни для одного элемента; исключение не выбрасывается. |
| 4 | Проверить DOM после шага 3 на отсутствие класса/атрибута подсветки у любого `[data-tc-id]`. | Ни один тест-кейс не помечен как подсвеченный. |
| 5 | Проверить отсутствие вызова функций отображения ошибки/уведомления после шага 3. | Ни один notice/error-рендер не вызван. |

**Expected Outcome:** `tcId` — часть публичного контракта
`collectManualTests()`; нераспознанная или недостижимая связь —
штатная тихая деградация на экране чек-листа, а не ошибка и не ложная
подсветка. Сломанный `Origin` — деградация ещё на уровне сбора данных
(исключение строки), а не на уровне клика.

**Priority:** Critical

### TC-005: Клик по реально отрендеренному пункту инбокса приводит к нужному тест-кейсу — проброс ID через URL и попадание в DOM

**Description:** Проверяет механику AC-07 (без визуального восприятия,

`TC-NNN`, восстановленный из `Origin` продуктового тест-плана, доходит от
РЕАЛЬНОГО клика по элементу, который рендерит `public/inbox.js`

правильный `[data-tc-id="TC-NNN"]` и инициирует именно его
прокрутку/подсветку, не трогая соседние тест-кейсы.

### TC-009: Поиск переживает перерендеры внутри визита, но не персистентен между визитами — в отличие от ролевого фильтра

**Description:** Проверяет AC-04 и BR-1, с двух сторон, которые легко
перепутать. AC-04 запрещает персистентность строго МЕЖДУ визитами
(следующее открытие экрана — снова полная сетка), но НЕ запрещает
запросу пережить перерендер В ПРЕДЕЛАХ одного визита — а лаунчер
перерендеривается не один раз за визит: `refresh()` красит экран сразу,
затем асинхронно догружает issues каждого проекта
(`loadProjectIssues()`) и полностью перестраивает DOM ещё раз
(`container.innerHTML = ""` + новый рендер), и то же самое происходит при
переключении роли в `.role-switch`. Поиск обязан пережить оба этих
перерендера — иначе поле будет неожиданно очищаться прямо во время
работы. Отдельно — сама неперсистентность между визитами должна быть
проверена не только по одному хранилищу: введённая строка не должна
всплывать ни в `localStorage`, ни в `sessionStorage`, ни в hash/URL
страницы. Это осознанное отличие от `.role-switch`
(`ROLE_STORAGE_KEY = "pf.role"`), который персистентен между визитами.

**Preconditions:**
- Раннер — `node --test tools/manual-test-ui/test/launcher.test.js`.
- Чистые `localStorage` и `sessionStorage` (фейковые storage-хранилища)
  на входе; фейковый/пустой `location.hash`.

**Steps:**

| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Смонтировать лаунчер, сразу (до завершения асинхронной догрузки issues, `await loadProjectIssues()`/аналог) ввести непустую подстроку поиска. Дождаться, пока догрузка завершится и вызовет свой перерендер (`ready`/эквивалентный промис). | Введённая строка и результат фильтрации сохраняются после перерендера — поле не очищается, список остаётся отфильтрованным. |
| 2 | На том же смонтированном лаунчере переключить роль в `.role-switch` (вызывает полный перерендер). | Строка поиска и результат фильтрации сохраняются и после этого перерендера — поиск переживает любой перерендер, инициированный самим приложением в рамках визита, не только первый. |
| 3 | Проверить содержимое `localStorage` и `sessionStorage` сразу после шагов 1–2. | Ни один ключ ни в одном из двух хранилищ не содержит введённую строку поиска (в отличие от `pf.role`, который меняется при переключении роли). |
| 4 | Проверить `location.hash`/query string страницы. | Введённая строка поиска не появляется ни в hash, ни в query — навигационный URL её не несёт. |
| 5 | Размонтировать лаунчер и смонтировать его заново с теми же (уже заполненными на шагах 1–2) `localStorage`/`sessionStorage` и тем же `location.hash`, эмулируя «следующее посещение». | Поле поиска пустое, сетка показывает все проекты — как при первом визите; ни одно из проверенных мест (два storage, hash/URL) не восстанавливает предыдущий запрос. |
| 6 | Повторить шаги 3–5, параллельно выставив непустой `pf.role` в `localStorage`. | Роль сохраняется между визитами (регресс существующего поведения), строка поиска — нет ни в одном из проверенных мест. |

**Expected Outcome:** Поиск — состояние текущего визита: оно переживает
любой перерендер, который сам визит порождает (асинхронную догрузку,
смену роли), но не восстанавливается ни из `localStorage`, ни из
`sessionStorage`, ни из URL при следующем визите.

**Priority:** High
