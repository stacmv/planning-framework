# Analysis: TC из `/pf-test-plan` не отслеживаются в `/pf-test`

**Issue:** 20260806-bug-test-plan-tc-untracked
**Дата:** 2026-08-10
**Тип:** bug · **Tier:** small

---

## Корневая причина

`/pf-test` Phase 3.2 ищет TC-ID **только в трёх местах**, все из которых —
конвенции JS/Python-фреймворков:

1. имя функции/метода содержит TC-ID (`test_TC001_`, `it_TC001_`), либо литерал
   `TC001` внутри вызова `it(...)`, `describe(...)`, `test(...)`;
2. комментарий **непосредственно над тестом**: `# TC-001` или `// TC-001`;
3. заголовок describe-блока, начинающийся с TC-ID.

Собственная конвенция bash-тестов этого репозитория не попадает ни в одно из
них. В `test/skills-role-matrix-static.sh` TC-ID живут:

- в **файловом** комментарии второй строки — `# test/skills-role-matrix-static.sh — TC-009, TC-014 (...)`
  — это не «комментарий непосредственно над тестом», и в нём **два** ID через
  запятую, чего форма `# TC-001` не описывает;
- в строковых аргументах хелперов — `pf_pass "TC-009 step 1: ..."`,
  `pf_fail "TC-009 step 1: ..."`;
- в `printf '=== TC-009: ...'`.

Функций в сьюте нет вовсе (`grep -E '^[a-z_]+\(\)'` не даёт совпадений) — это
линейный скрипт. Значит **карта TC-ID → тест из Phase 3.2 выходит пустой**.

Дальше цепочка отрабатывает ровно по написанному и молча:

| Фаза | Что происходит при пустой карте |
|---|---|
| 3.3 | сопоставлять нечего — ни один TC не получает pass/fail |
| 3.4 | «For rows not matched … leave the Status column unchanged» → все строки остаются `[ ]` |
| 4 | считает строки `Auto` + `✗`; их ноль → **гейт пройден** |
| 5 | чек-лист генерируется, стадия завершается успешно |

То есть `/pf-test` не падает и не предупреждает: он сообщает «0 mapped» и идёт
дальше. Ошибка всплывает много позже — на `/pf-qa`, чей Testing-гейт считает
необработанные `[ ]` строки и даёт FAIL, уже без связи с настоящей причиной.

## Два независимых дефекта той же связки

**Д2 — Phase 3.1 видит только изменённые на ветке файлы.** Область поиска —
`git diff --name-only develop...HEAD`, отфильтрованная по «похоже на тест».
TC, покрытый **уже существующим** тестом, невидим, даже если бы его конвенция
распознавалась. Для багфикса, который не добавляет тестовых файлов, а опирается
на имеющийся сьют, все Auto-TC остаются неотслеженными по этой причине —
отдельно от Д1.

**Д3 — Phase 3.3 сопоставляет с «именами тестов» из вывода раннера, которых у
bash-харнесса нет.** Phase 2 захватывает stdout/stderr целиком; структурного
списка имён тестов не существует. Даже непустая карта не имеет с чем
детерминированно сопоставляться.

## Воспроизведение

1. Взять issue, чьи Auto-TC покрыты bash-тестом по конвенции этого репозитория
   (`pf_pass "TC-NNN ..."`), например `test/skills-role-matrix-static.sh`.
2. Прогнать `/pf-test`.
3. Ожидаемо: строки этих TC в Status Tracker становятся `✓`.
   Фактически: остаются `[ ]`; в отчёте «0 mapped to TC-IDs»; гейт Phase 4
   пройден.
4. Прогнать `/pf-qa` → Testing-гейт FAIL с «unprocessed rows: N».

## Подтверждение на реальных данных

В `20260806-feat-role-matrix` TC-009/TC-014 в итоге стоят `✓` — но проставлены
**не** механизмом Phase 3.2. Коммит `b212e60` («test: status tracker + manual
checklist») одновременно *добавляет* `test/skills-role-matrix-static.sh` и
меняет обе строки трекера с `[ ]` на `✓`; его же сообщение фиксирует, что сьют
был написан прямо в том прогоне, потому что `implementation_plan.md` его не
запланировал. То есть отметку поставила сессия по собственному суждению, а не
документированное автосопоставление — которое на этом файле сработать не может.

## Влияние

- **Тихая потеря сигнала.** Auto-TC выглядят непрогнанными при зелёном сьюте;
  Phase 4 при этом пропускает дальше, потому что «нет `✗`» и «нет `[ ]`» — для
  него одно и то же.
- **Гейт `/pf-qa` ломается не в том месте.** FAIL приходит через две стадии
  после настоящей причины, что уже стоило одного разбора.
- **Задевает любой проект, чьи тесты не на JS/Python.** Баг-репорт пришёл из
  стороннего проекта — конвенция этого репозитория лишь воспроизводимый пример.
- **Не задевает** Manual-TC: они по дизайну не трогаются в 3.4 (это смежная,
  отдельно зафиксированная проблема `.qa-workflow.md`, не эта issue).

## Границы

Чинить нужно связку `/pf-test-plan` → `/pf-test`, а не только сканер: если
`/pf-test-plan` объявляет TC как `Auto`, должно существовать проверяемое
правило, по которому `/pf-test` его найдёт. Формат объявления соответствия
(явное поле в Status Tracker против расширения набора паттернов сканирования)
— предмет решения на стадии спецификации, не этого документа.
