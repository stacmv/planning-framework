# Analysis: TC из `/pf-test-plan` не отслеживаются в `/pf-test`

**Issue:** 20260806-bug-test-plan-tc-untracked
**Дата:** 2026-08-10
**Тип:** bug · **Tier:** small

---

## Корневая причина

`/pf-test` Phase 3.2 — не детерминированный сканер, а инструкция на естественном
языке, которую агент заново интерпретирует при каждом прогоне. Она называет
**три** конвенции, все из JS/Python-мира:

1. имя функции/метода содержит TC-ID (`test_TC001_`, `it_TC001_`), либо литерал
   `TC001` внутри вызова `it(...)`, `describe(...)`, `test(...)`;
2. комментарий **непосредственно над тестом**: `# TC-001` или `// TC-001`;
3. заголовок describe-блока, начинающийся с TC-ID.

Собственная конвенция bash-тестов этого репозитория буквально ни под одну из
них не подпадает. В `test/skills-role-matrix-static.sh` TC-ID живут:

- в **файловом** комментарии второй строки — `# test/skills-role-matrix-static.sh — TC-009, TC-014 (...)`
  — это не «комментарий непосредственно над тестом», и в нём **два** ID через
  запятую, чего форма `# TC-001` не описывает;
- в строковых аргументах хелперов — `pf_pass "TC-009 step 1: ..."`,
  `pf_fail "TC-009 step 1: ..."`;
- в `printf '=== TC-009: ...'`.

Функция в сьюте всё же есть — `check_order()` на строке 80
(`grep -nE '^[[:space:]]*[a-z_]+\(\)'` находит её с учётом отступа). Но это не
спасает совпадение по паттерну 1: имя `check_order` не содержит TC-ID, а
вызовы (`check_order "TC-014 step 1: ..." ...`, строки 105-106) — не
`it(...)`/`describe(...)`/`test(...)`.

**Д1 — Phase 3.2/3.3 не покрывают конвенцию этого репозитория.** Раз ни одна
из трёх названных конвенций буквально не совпадает, а инструкция не даёт
явного правила для конвенции без TC-ID в имени функции и без
it/describe-блоков, результат Phase 3.2 на этом файле — не гарантированно пустая карта, а
**ненадёжная, невоспроизводимая**: агент волен счесть «относящимся к делу»
файловый комментарий или баннер `printf`, а может и не счесть, и решение
способно отличаться от прогона к прогону. В худшем и, судя по всему, типичном
случае карта TC-ID → тест из Phase 3.2 пуста.

Тот же разрыв конвенций объясняет и Phase 3.3: она сопоставляет с «именами
тестов» из вывода раннера, а `pf_pass()` (`test/lib.sh:60-63`) печатает
переданную строку — включая TC-ID — целиком в stdout, который Phase 2
захватывает. Приём, который закрывает пробел Phase 3.2 (сканирование
строковых литералов, а не только имён функций и it-блоков), закрывает заодно
и Phase 3.3 — TC-ID из вывода `pf_pass` находится той же субстроковой
техникой. Это аспект Д1, а не отдельный дефект.

Дальше цепочка расходится не только по данным, но и по тексту самих фаз:

| Фаза | Что происходит |
|---|---|
| 3.3 | при пустой/ненадёжной карте сопоставлять нечего — ни один TC не получает pass/fail |
| 3.4 | «For rows not matched … leave the Status column unchanged» → строки Auto остаются `[ ]` |
| 4 | Failure Gate считает строки `Auto` + `✗`; их ноль → гейт **не срабатывает** |
| 5 | вход обусловлен собственным предусловием фазы: «all Auto-type TCs … have Status ✓, OR … no rows with Type Auto» (`pf-test/SKILL.md`). При `[ ]`-строках и наличии Auto-строк **ни одна половина условия не выполняется** |

**Д2 — незамкнутая ветка Phase 4 → Phase 5 в `pf-test/SKILL.md`.** Phase 4
прямо говорит «Do NOT proceed to Phase 5 when this gate triggers» — но гейт не
сработал (нет `✗`), так что по тексту Phase 4 управление отдаёт дальше. У
Phase 5, однако, своё предусловие не выполнено — и, в отличие от Phase 4, для
этой ветки в `pf-test/SKILL.md` **не описано никакого стоп-сообщения**. Что
происходит дальше — текстом skill'а не определено: это дефект самого
`pf-test/SKILL.md`, отдельный от Д1.

Наиболее вероятное практическое следствие (допущение, не факт из текста):
агент, столкнувшись с невыполненным предусловием без предписанного действия,
чек-лист не генерирует — `manual_test_checklist.md` не создаётся.
Downstream-эффект: `/pf-qa/SKILL.md`, строка 9, делает существование
`manual_test_checklist.md` **первым** предусловием и останавливается с
«Testing stage is not complete. Run /pf-test first.» — то есть `/pf-qa`
стопорится сразу, а не на Testing-гейте, который считает необработанные
строки `test_plan.md`.

## Д3 — Phase 3.1 ограничен диффом ветки

Phase 3.1 видит только изменённые на ветке файлы. Область поиска —
`git diff --name-only develop...HEAD`, отфильтрованная по «похоже на тест».
TC, покрытый **уже существующим** тестом, невидим, даже если бы его конвенция
распознавалась. Для багфикса, который не добавляет тестовых файлов, а опирается
на имеющийся сьют, все Auto-TC остаются неотслеженными по этой причине —
независимо от Д1.

## Воспроизведение

1. Взять issue, чьи Auto-TC покрыты bash-тестом по конвенции этого репозитория
   (`pf_pass "TC-NNN ..."`), например `test/skills-role-matrix-static.sh`.
2. Прогнать `/pf-test`.
3. Ожидаемо: строки этих TC в Status Tracker становятся `✓`.
   Фактически: карта Phase 3.2 пуста или ненадёжна → строки остаются `[ ]`;
   Failure Gate (Phase 4) пропускает дальше, потому что `✗`-строк нет; но
   предусловие Phase 5 не выполнено, и дальнейшее поведение в
   `pf-test/SKILL.md` не описано — по всей видимости, чек-лист не
   генерируется.
4. Прогнать `/pf-qa` → по всей видимости, остановка на первом же
   предусловии («Testing stage is not complete. Run /pf-test first.»), а не
   FAIL Testing-гейта по числу необработанных строк.

## Подтверждение на реальных данных

В `20260806-feat-role-matrix` TC-009/TC-014 в итоге стоят `✓`. Коммит `b212e60`
(«test: status tracker + manual checklist») одновременно *добавляет*
`test/skills-role-matrix-static.sh`, меняет обе строки трекера с `[ ]` на `✓` и
добавляет `manual_test_checklist.md`. Сам коммит не показывает, произошла ли
правка строк трекера внутри `/pf-test` или отдельной ручной правкой — то, что
«отметку поставила сессия по собственному суждению», это вывод из содержимого
коммита, а не наблюдение из него.

С учётом разрыва Phase 4 → Phase 5 (Д2, см. выше) есть более сильное
прочтение: если бы строки остались `[ ]`, Phase 5 не смогла бы стартовать по
собственному предусловию — а чек-лист в этом же коммите присутствует. То есть
проставление `✓` вручную было, вероятнее всего, не произвольным решением, а
необходимым шагом, чтобы удовлетворить предусловие Phase 5 и вообще дойти до
генерации чек-листа — а не случайным суждением сессии.

**Д4 — нарушение правила «Do not invent pass/fail status».** `pf-test/SKILL.md`
(Important Notes, строка 208) прямо требует: «Do not invent pass/fail status —
only update Status Tracker rows where you found a matching test in the runner
output. Leave unmatched rows as `[ ]`.» Документированного правила, по
которому совпадение для этих строк произошло бы в Phase 3.2, нет (Д1) — так
что `✓` не могли опираться на подтверждённое совпадение. Это нарушение того
же явного правила: самостоятельная находка-дефект, а не просто побочный
эффект пустой карты.

## Влияние

- **Тихая потеря сигнала (Д1).** Auto-TC выглядят непрогнанными при зелёном
  сьюте; Failure Gate (Phase 4) это не ловит, потому что для него «нет `✗`» и
  «нет `[ ]`» — одно и то же.
- **Незамкнутая ветка Phase 4 → Phase 5 (Д2).** При `[ ]`-строках и наличии
  Auto-TC у Phase 5 не выполнено предусловие, а стоп-сообщения для этого
  случая в тексте skill'а нет — поведение агента здесь не специфицировано.
- **`/pf-qa` останавливается на первом предусловии, а не на Testing-гейте.**
  Если чек-лист не сгенерирован (следствие Д2), `/pf-qa` (`SKILL.md:9`)
  стопорится с «Run /pf-test first» — а не на Testing-гейте, который в
  `.qa-workflow.md:44` считает необработанные строки `test_plan.md`
  (`grep -c '| \[ \] *|' ...`).
- **Задевает любой проект, чьи тесты не на JS/Python.** Баг-репорт пришёл из
  стороннего проекта — конвенция этого репозитория лишь воспроизводимый пример.
- **Не задевает** Manual-TC: они по дизайну не трогаются в 3.4 (это смежная,
  отдельно зафиксированная проблема `.qa-workflow.md`, не эта issue).

## Границы

Итого в связке обнаружено четыре дефекта. Д1, Д2 и Д3 независимы друг от
друга: Д1 (Phase 3.2/3.3 не покрывают bash-конвенцию), Д2 (незамкнутая ветка
Phase 4 → Phase 5), Д3 (Phase 3.1 ограничен диффом ветки). Д4 (проставление
статуса в обход правила «Do not invent pass/fail status») — производный:
он проявился только потому, что пустая карта Д1 и открытая ветка Д2 вместе
заставили кого-то вручную удовлетворить предусловие Phase 5, но при этом
нарушено отдельное явное правило, так что он отдельно фиксируется как
находка.

Чинить нужно связку `/pf-test-plan` → `/pf-test`, а не только сканер: если
`/pf-test-plan` объявляет TC как `Auto`, должно существовать проверяемое
правило, по которому `/pf-test` его найдёт. Формат объявления соответствия
(явное поле в Status Tracker против расширения набора паттернов сканирования)
— предмет решения на стадии спецификации, не этого документа.

В область входит и Д2 — разрыв Phase 4 → Phase 5 внутри самого
`pf-test/SKILL.md`: ветка, в которой предусловие Phase 5 не выполнено, а
стоп-сообщение для неё не определено, должна получить явное поведение
(стоп-сообщение по аналогии с Phase 4, либо иное явно специфицированное
действие). Это дефект того же skill'а, обнаруженный при анализе этой issue, и
его нужно закрыть в рамках того же фикса.

Д3 (диапазон поиска Phase 3.1) — отдельный, не вытекающий из Д1/Д2 разрыв в
той же связке; фикс этой issue должен закрыть и его, а не только сканер и
ветку Phase 4/5. Д4 отдельного фикса не требует: он производный от Д1+Д2 (см.
выше) и снимается автоматически, как только у Д1 появится проверяемое
правило сопоставления, а у Д2 — определённое поведение при невыполненном
предусловии.
