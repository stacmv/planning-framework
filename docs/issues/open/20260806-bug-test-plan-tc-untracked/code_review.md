## Findings

### P0 (Blocker)

**P0-1. Расширение области сканирования создаёт коллизию TC-ID между issue —
подтверждено на реальном прогоне.**

TC-ID в этом фреймворке не глобальны: нумерация начинается заново в каждой
issue. До фикса Phase 3.1 ограничивалась диффом ветки, что случайно защищало
от коллизий. Новый текст (`skills/pf-test/SKILL.md:35`) снимает ограничение, а
Phase 3.3 (`:52`) одновременно расширяется до «a TC-ID anywhere in captured
stdout … counts as a match for that TC» — сопоставление больше не привязано к
файлу из карты 3.2.

Проверено прогоном: `make test` печатает **девять** строк с `TC-001` из
несвязанных сьютов, в том числе:

- `test/converge-fresh.sh:15` — `printf '\n=== TC-001: convergence from a bare project (no-pf-bare)\n'`
- `tools/manual-test-ui/test/checklist-git.test.js:101` — `tcId: "TC-001"`
- `tools/manual-test-ui/test/prepare.test.js:35` — `CASE_IDS = ["TC-001", "TC-002"]`
- `tools/manual-test-ui/test/prepare-repo-state.test.js` — множественные вхождения

Активная issue объявляет собственные `TC-001`/`TC-002`. Ни 3.1, ни 3.2, ни 3.3
не вводят привязку найденного файла или строки к активной issue, и не задают,
что делать при нескольких несвязанных вхождениях одного TC-ID. Следствие —
тихая порча статуса TC у любой issue, чей номер уже занят где-то в дереве
тестов.

**P0-2. Правило «TC-ID должен вести строку» противоречит собственному
примеру.**

`skills/pf-test/SKILL.md:44` гласит: «The TC-ID must lead the string; a TC-ID
appearing later inside a message (e.g. `assert.ok(x, "TC-001 not parsed")`) is
not this convention and does not match.»

В строке `"TC-001 not parsed"` подстрока `TC-001` находится в позиции 0 — она
**ведёт** строку. Пример, приведённый как не-совпадение, по букве правила
является совпадением. Строка реальна:
`tools/manual-test-ui/test/checklist-ru.test.js:47`.

Абзац об исключении фикстур ниже (`:48`) усугубляет: он выводит исключение из
формулы «not a call to a test helper or an assertion», тем самым утверждая, что
вызовы assertion-функций **являются** валидной конвенцией — что снова
противоречит примеру в строке 44.

Агент, следующий инструкции буквально, не может непротиворечиво решить,
матчится ли `checklist-ru.test.js:47` — а это ровно тот пограничный случай,
который Task 2 должен был закрыть. Нужен другой критерий, чем позиция
подстроки: различать надо не «где стоит TC-ID», а «является ли строка
собственной меткой теста или текстом сообщения об ошибке».

### P1 (Important)

**P1-1. Исключение для фикстур не покрывает реальные промежуточные формы.**
Правило (`:48`) даёт две категории: вызов тестового хелпера/assertion (матч)
против фикстуры/тестовых данных (не матч). Реальные формы в репозитории не
укладываются ни в одну:

- `checklist-git.test.js:101` — `tcId: "TC-001"` как значение поля объекта в
  HTTP-запросе;
- `prepare-repo-state.test.js` — `const runs = [null, "TC-001", "TC-001", "TC-002", null];`
  и `prepareOk("TC-001")` — TC-ID как аргумент выбора кейса.

Ни «fixture/test data», ни «test helper or assertion» их не описывают.
