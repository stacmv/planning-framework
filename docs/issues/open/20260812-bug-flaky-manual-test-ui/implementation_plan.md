# Implementation Plan: падения `tools/manual-test-ui` — недетерминированности нет

## Overview

Две детерминированные причины из `analysis.md`, обе в тестовом коде.

**Причина 1** (Task 1-2): `fs.symlinkSync` в `buildFixture()` роняет `EPERM` на
все девять подпроверок TC-011 вместо одной. Симлинк уходит в свой шаг, в контекст
`t2`, и `EPERM` даёт видимый `t2.skip()`.

**Причина 2** (Task 3-4): `projects.json` пишется `printf`-ом с POSIX-путём как
есть. Заменяется на `cygpath -w` (где есть) плюс `node -e`-сериализатор; Task 3
заодно разносит сообщение шага 4 и добавляет `pf_note` для TC-006.

Task 5 — три ручные процедуры, кода не меняют. **`/pf-test` вне объёма:** после
фикса предсуществующих падений не остаётся, остановка гейта на любом `✗` снова
корректна, а смягчать её — значит завести гейт, который можно уговорить.

## Implementation Tasks

#### Task 1: Симлинк TC-011 — из фикстуры в собственный шаг, видимый skip

**Task Type:** code
**Mapped Test Cases:** TC-003
**Files:** `tools/manual-test-ui/test/read-paths.test.js` — `buildFixture()` (строка 73), `t.test("step 2: …")` (строки 148-157)

**Implementation Notes:**
- Убрать `fs.symlinkSync(...)` из `buildFixture()` и перенести внутрь
  `t.test("step 2: …", async (t2) => { … })` — **параметр `t2` надо добавить**,
  сейчас callback без него. В `try/catch`: `EPERM`/`EACCES` → `t2.skip(...)`,
  **никогда внешний `t`** (иначе пропадают все девять подпроверок — ровно тот
  баг, который задача чинит), плюс `console.error` с `EPERM`/`Developer
  Mode`/symlink и `return`. Другой код ошибки — `throw`. Прочие восемь
  подпроверок чинятся тем, что `buildFixture()` перестаёт падать.

**Acceptance Criteria:**
- [x] Среда без симлинков: восемь подпроверок `ok`, `step 2` — `# SKIP` с причиной
- [ ] Среда с симлинками: `step 2` реально выполняется, `ok` **без** `# SKIP` (это и есть TC-003)

#### Task 2: `test/manual-test-ui.sh` — TC-001/TC-002 на отдельном прогоне

**Task Type:** tests
**Mapped Test Cases:** TC-001, TC-002
**Files:** `test/manual-test-ui.sh` — новая секция после проверки `ui_rc`/`ui_out` (после строки 118)

**Implementation Notes:**
- **Не переиспользовать `ui_out`** — он покрывает весь glob, поэтому «вывод
  непуст» истинно, даже если `read-paths.test.js` не запускался. Снять свой
  захват: `node --test --test-reporter=tap
  tools/manual-test-ui/test/read-paths.test.js` — это и дословное требование
  `test_plan.md`, и фиксация TAP вместо догадок о репортёре. **Флаг только
  здесь, не в Makefile:** шаги 2-3 грепают рецепт регуляркой
  `node --test[[:space:]]+"?tools/` и сломались бы.
- Каждый шаг (и в Task 3-4 тоже) — `pf_pass`/`pf_fail` с литералом `TC-NNN step
  K: …` дословно из `test_plan.md`: единственная форма, которую видит Phase 3.2.
- Баннер `=== TC-001` от закрытой issue в этом же файле (строка 139) коллизии не
  даёт: Phase 3.2 исключает баннеры, живых меток `TC-001` в файле нет. Оставить
  комментарий с этим объяснением, иначе соседство «исправят» вслепую.
- Восемь подпроверок TC-001 ищутся по **дословным** именам `t.test(...)` (не по
  номерам строк — Task 1 их сдвинет). Успех = якорный
  `^[[:space:]]*ok [0-9]+ - <name>` **и** отсутствие `not ok` с тем же именем:
  наивный `grep -F` совпал бы и с `not ok`, засчитав провал за успех.
- TC-002 step 1 — те же якоря для `step 2: a symlink pointing out …`, три
  состояния: `# SKIP`, `ok` без `SKIP`, отсутствие обоих (→ `pf_fail`; **эта
  ветка и ловит исходный дефект**). Step 2: рядом `EPERM`/`Developer
  Mode`/symlink. Step 3: без `not ok`. Step 4: прочие восемь без `# SKIP`.

**Acceptance Criteria:**
- [ ] TC-001 passes
- [ ] TC-002 passes

#### Task 3: `projects.json` — сериализатор вместо `printf`, `TC-004` шаги, `pf_note`

**Task Type:** code
**Mapped Test Cases:** TC-004
**Files:** `test/manual-test-ui.sh` — шапка (строка 2), строки 348-350 (запись конфига), строки 385-392 (сообщение шага 4)

**Implementation Notes:**
- Заменить `printf '{"projects":…}' … >"$tc015_config"` на три шага.
  **Конвертация:** `command -v cygpath` → `repo_path="$(cygpath -w
  "$tc015_repo")"`, иначе `repo_path="$tc015_repo"` — Windows получает нативный
  путь, Linux POSIX как есть, ветвления по `uname` не нужно.
  **Зафиксировать `expected_path="$repo_path"` до записи** — Task 4 сравнивает с
  ним, это единственное значение, не прошедшее через файл.
  **Сериализация:** `node -e`, получающий имя, `repo_path` и путь конфига через
  `process.argv` (не интерполяцией в текст скрипта — кавычки и слэши сломают JS
  раньше `JSON.stringify`), пишущий `fs.writeFileSync(cfg, JSON.stringify(…))`.
- Затем прочитать `.projects[0].path` тем же способом в `written_path` и вывести
  двумя `pf_note` — печатаются они как `  ----  TC-015: …` (`test/lib.sh:84`), и
  TC-006 ищет эту форму вывода, а не вызов `pf_note`.
- Строки 385-392 разбить на два шага: `TC-004 step 1: server started` / `… did
  not start`; `TC-004 step 2: server listed the fixture project` / `… did not
  list …`. **Метка step 2 печатается всегда**, включая провал step 1 (тогда
  сразу `pf_fail`, без `curl`): молча пропущенный шаг оставил бы Auto-TC
  несопоставленным. При провале — лог и тело ответа в `>&2`.
- Обновить шапку файла: перечислить TC этой issue и назвать её ID — Phase 3.2
  квалифицирует файл по ID в тексте, а не по диффу. Прежний `step 4` TC-015 уходит под `TC-004`.

**Acceptance Criteria:**
- [x] TC-004 passes

#### Task 4: `TC-005` — JSON остаётся валиден и путь не искажается

**Task Type:** tests
**Mapped Test Cases:** TC-005
**Files:** `test/manual-test-ui.sh` — новая секция после Task 3, использует `$expected_path` и `$written_path`

**Implementation Notes:**
- Windows-ветке отдельная фикстура не нужна: `repo_path` уже со слэшами.
  **Ломают JSON не они, а несэкранированная запись** — валидность файла и
  сохранность значения суть два разных свойства, проверяются по отдельности.
- POSIX-ветка (`cygpath` нет): родительский каталог через `pf_mktemp_d` (**имя
  ему не задаётся** — генерируется `mktemp`; саму функцию не трогать, она общая и
  завязана на S-1…S-5), внутри `mkdir` подкаталог с `"` в имени и та же фикстура,
  что у TC-015 (`git init`, `symbolic-ref HEAD refs/heads/develop`,
  `pf_git_init`, `prompt.md` + `manual_test_checklist.md`) — без неё
  `/api/projects` не даст осмысленного ответа.
- Step 2: сырой файл через `JSON.parse` — валидность. Step 3: разобранный
  `written_path` сравнивается **побайтно** с `expected_path` из Task 3,
  зафиксированным **до** записи; сравнение с самим собой было бы зелёным при
  любом искажении. Step 4: поднять сервер на этом конфиге и завершить процесс.

**Acceptance Criteria:**
- [ ] TC-005 passes
