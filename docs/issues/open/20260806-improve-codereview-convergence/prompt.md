серьёзными замечаниями не должен проходить дальше по пайплайну.

## Выводы, обязательные к учёту

1. **Слепой потолок раундов отгрузил бы сломанный код.** Раунды 4-10 нашли
   реальные дефекты, включая 2 P0 в девятом. Ограничение «3 раунда → PASS»
   недопустимо.
2. **Настоящая причина — стадия ДО ревью.** 9 P0 + 9 P1 в первых двух раундах —
   это `/pf-execute`, сдавший неработающую реализацию. Раунды 5 и 8 нашли
   отсутствующую функциональность, то есть провал полноты implementation plan.
   Code review десять раундов работал механизмом дописывания реализации.
3. **Раунд 9 сломан фиксом раунда 8.** Значит «последний раунд — только
   верификация, новых findings не принимаем» опасно.
4. **Гейт фактически не удержал.** В отчёте прямо: «the user chose to stop the
   review/fix loop… No review has run against round 10's own diff in isolation» —
   и при этом записан `**PASS**`.
5. **P2 теряются.** Раунд 7 нашёл, что P2 из раунда 1 никто не починил.

## Что нужно сделать

### 1. Ledger findings

`code_review.md` становится append-only. Каждый finding: стабильный ID `CR-NNN`,
номер раунда, состояние (`open` / `fixed` / `accepted-risk` / `deferred` /
`wont-fix` / `duplicate-of CR-NNN`). В раунд N ревьюеру передаётся ledger с
инструкцией «эти уже разобраны, не повторяй; ищи новое, внесённое фиксами».

P2 обязаны иметь явное состояние на выходе PASS — молчаливое исчезновение
запрещено (вывод 5).

### 2. Бюджет раундов — триггер эскалации, НЕ потолок

Поле `review_rounds` в `prompt.md`, дефолт 3.

- **Ранний бросок назад:** если раунд 1 даёт ≥3 P0 — это диагноз «реализация не
  готова», а не результат ревью. В fix-цикл не входим: findings конвертируются в
  задачи `implementation_plan.md`, issue возвращается на `/pf-execute`.
- Раунд 2+ — дельта: диффы фиксов предыдущего раунда плюс верификация закрытия
  его P0/P1. **Новые findings принимаются всегда** (вывод 3).
- После исчерпания бюджета — не PASS и не бесконечный цикл, а возврат на
  `/pf-execute` с оставшимися findings как задачами. Незакрытый P0 не становится
  PASS никогда.
- **Каждый фикс-раунд обязан отревьюить собственный дифф.** Терминального «PASS
  без чистого раунда» не существует (вывод 4).

### 3. Рубрика блокирования и triage

P0/P1 требует конкретного сценария отказа: вход → неверный выход / креш /
регрессия / нарушение заявленного требования. Finding без сценария отказа — P2
по определению, независимо от severity, выданной ревьюером.

Технически: после сбора findings дешёвый triage-субагент размечает каждый
кандидат `blocking: yes/no` с однострочным обоснованием; блокирует только `yes`.
Это же снимает риск того, что широкое ведро `medium` у Codex (маппится в P1)
превращает придирки в блокеры.

P2 и `deferred` на выходе PASS выгружаются в `docs/planning/tech-debt.md` либо в
follow-up issue. Третья опция гейта — «вынести в follow-up issue» — доступна для
P1, никогда для P0.

### 4. Гейт полноты в `/pf-execute` до передачи в ревью

Механическая проверка: все чекбоксы `implementation_plan.md` отмечены И у
каждого заявленного поведения есть тест. Раунды 5 и 8 ловятся этим без единого
раунда ревью (вывод 2).

## Находки, всплывшие 2026-08-06 при работе над `20260715-bug-...`

Все четыре — тот же класс: **стадия рапортует об успехе, не выполнив работу.**

### 5. Codex-цепочка ревьюит пустой дифф и считает это чистым результатом

`skills/pf-check/SKILL.md`, шаг 2b вызывает
`codex-companion.mjs review --wait --scope branch --base <base-ref>`, то есть
ревьюит дифф ветки issue против родителя. Допущение: TARGET написан внутри ветки
issue. У `20260715-...` ветки не было — документы лежали в `develop`, дифф пуст.
Codex получил бы ничего, вернул бы «замечаний нет», `/pf-check` отчитался бы об
успешном ревью.

Нужно: пустой дифф — **ошибка стадии**, а не чистый результат. Различать
«нечего ревьюить» и «отревьюено, чисто». Когда ветки issue нет — ревьюить
документ по пути (шаг 4 цепочки), сообщая об этом. То же касается
`pf-codereview`: там `--base <base-ref>` предполагает то же самое.

### 6. `/pf` не отличает «проверку не запускали» от «запускали»

`/pf` роутит на `/pf-check`, если следующий документ отсутствует («check passed»
определён через готовность СЛЕДУЮЩЕГО документа). Определение циклично: план
реализации нельзя построить до проверки, а проверка засчитывается только когда
план готов. У `20260715-...` `/pf-check` уже прогоняли (коммит `d3f2b32`), но
`/pf` этого не видел.

Нужен явный признак пройденной проверки — запись в `session-log.md` issue или
файл-маркер, а не вывод по соседнему документу.

### 7. Субагентам недоступны `TaskGet`/`TaskUpdate`

`skills/pf-execute/SKILL.md`, раздел «For Each Task (Sub-Agent Instructions)»
предписывает субагенту первым шагом вызвать `TaskGet`, последним — `TaskUpdate`.
В реальном окружении этих инструментов у субагента нет; оба субагента волны 1
сообщили, что искали через ToolSearch и не нашли.

Хуже: один из них, лишившись `TaskGet`, ушёл читать `implementation_plan.md` и
взял задачу **по номеру** — а нумерация оркестратора не совпадала с нумерацией
плана. Он добросовестно выполнил не ту работу. Второй уцелел только потому, что
в его промпте было описано содержание задачи, а не только номер.

Нужно: либо починить доступность task-инструментов, либо переписать инструкцию —
задание субагенту обязано быть самодостаточным, ссылка на внешний идентификатор
недопустима. Это ровно «суждение по памяти», только про задание.

### 8. Родственные подтверждения того же класса

- `20260731-feat-pluggable-reviewers` был смерджен в `develop`, но `/pf-close`
  остановился после Phase 4: папка осталась в `open/`, в `session-log.md` записи

  любом `✗`, поэтому флакующий набор превращает гейт в шум. Отдельный issue.

## Приёмка

Прогон, эквивалентный `20260709-feat-dockerize`, должен сходиться за 2-3 раунда
либо явно вернуться на `/pf-execute` — но ни при каких условиях не выдавать
`PASS` при открытом P0 и не выдавать `PASS` по неотревьюенному финальному диффу.
