# Test Plan: Сходимость ревью и честность отчётов стадий

**Date:** 2026-08-12

## Overview

Предмет изменений этой issue — не UI и не библиотека, а **проза семи
`pf-*` skill-файлов** (`pf-codereview`, `pf-check`, `pf-execute`, `pf`,
`pf-close` — плюс справочные `pf-roles`/`pf-git`, не тронутые этой issue),
которую во время реального прогона интерпретирует LLM-агент. Бинарный
тест-раннер не может «запустить» `/pf-codereview` — он может только:

1. **Транскрибировать** механическое правило (бюджет раундов, словарь
   состояний ledger, гейт полноты плана) в bash-хелпер и прогнать его на
   фикстурах — и в том же TC, отдельным шагом, **сверить хелпер с реальным
   текстом `SKILL.md`** (drift-guard). Хелпер, согласный сам с собой,
   ничего не доказывает — доказывает только сверка с первоисточником. Этот
   урок стоил `20260806-feat-product-test-plan` живого прогона, в котором
   59 из 59 ассертов остались зелёными при живом дефекте формата, потому
   что каждый ассерт звал транскрибированный хелпер, а не текст скилла.
2. **Проверить форму, а не только присутствие** — там, где дефект является
   дефектом формы (порядок шагов, направление проверки, широта критерия),
   один `grep` на ключевое слово одинаково доволен и правильной, и
   сломанной версией текста. Ниже такие TC используют несколько независимых
   сигналов (несколько grep на разные обязательные свойства правила) или
   сравнение номеров строк, а не единственный неспецифичный grep.
3. **Честно объявить test-first drift-guard'ы красными.** Правила этой
   issue ещё не существуют в `skills/`, поэтому grep, ищущий их, обязан
   сегодня возвращать `FAIL` — это ожидаемо и диагностически ценно, а не
   брак теста. Каждый такой TC ниже прямо помечен «test-first, ожидаемо
   RED до реализации» и отдельно указывает, чем настоящий провал (правило
   не реализовано) отличается от брака тестовой инфраструктуры (фикстура
   отсутствует, `SKILL.md` не найден, скрипт хелпера падает с синтаксической
   ошибкой) — сообщение об ошибке в Auto-кейсах называет причину явно.

Живое поведение модели (реально ли ревьюер держит гейт, реально ли триаж
понижает важность находки без сценария отказа) никакой конечный тест не
доказывает с полной гарантией — это общее ограничение для каждого `Manual`
TC ниже, а не брак конкретного кейса; поэтому `Manual` зарезервирован для
того, что действительно недостижимо статическим аудитом текста или
фикстурой, и их количество сознательно минимизировано.

**Цель прогона** — подтвердить все 26 AC из `brd.md` (шесть user stories) и
акцептанс уровня issue: эквивалент `20260709-feat-dockerize` сходится за
2-3 раунда либо честно возвращается на `/pf-execute`; `PASS` никогда не
выдаётся при открытом P0/P1 или по неотревьюенному финальному диффу;
находка не исчезает молча; стадия, не сделавшая работу, не выглядит
чистой.

## Prerequisites

- Implementation по `implementation_plan.md` этой issue завершена:
  `skills/pf-codereview/SKILL.md`, `skills/pf-check/SKILL.md`,
  `skills/pf-execute/SKILL.md`, `skills/pf/SKILL.md`,
  `skills/pf-close/SKILL.md` обновлены.
- `test/lib.sh` доступен как есть — Auto-кейсы ниже следуют его конвенциям
  (`pf_setup_case`, `pf_repo_copy`, `assert_repo_untouched`,
  `HOME=$TMP_HOME`; правила безопасности S-1…S-5 в его заголовке
  load-bearing).
- **Каждый шаг каждого Auto-кейса отчитывается через `pf_pass "TC-NNN step K:
  …"` / `pf_fail "TC-NNN step K: …"`** — это единственная форма, которую
  распознаёт сканирование TC-ID в `/pf-test` (Phase 3.2, «label passed to a
  test-reporting helper»). Баннер `printf '=== TC-NNN …'` не считается меткой:
  он печатается независимо от исхода. Auto-строка Status Tracker, не давшая ни
  одной такой метки в выводе прогона, остаётся `[ ]` и **останавливает**
  `/pf-test` на его Phase 5 precondition — поэтому конвенция здесь
  предусловие, а не стилевое пожелание.
- Фикстуры под `test/fixtures/pf-codereview-convergence/…`, перечисленные
  в «Требуемые данные» каждого TC, созданы — задача реализующей стадии
  (`/pf-execute`), не этого документа.
- Для `Manual`-кейсов: рабочее дерево `D:/dev/planning-framework` чистое,
  тестировщик может создавать/удалять временные фикстур-issue под
  `docs/issues/open/zz-fixture-*/` и реально запускать `/pf-codereview`,
  `/pf-check`, `/pf-execute`, `/pf-close` в живой сессии Claude Code.
  Codex не требуется ни для одного TC ниже — все сценарии используют
  дефолтный `[claude]`-путь ревью; проверка `codex`/`both`-путей для этой
  конкретной фичи не входит в объём (роль резолвится тем же
  `pf-roles`-механизмом независимо от issue).
- **Уборка после каждого Manual-кейса обязательна.** Перед тем как считать
  TC-009/TC-019/TC-020/TC-027 завершёнными, тестировщик удаляет всё, что
  создал для этого конкретного кейса — конкретный набор команд зависит от
  того, как кейс разместил свою фикстуру (ни один из четырёх не коммитит
  фикстур-issue на `develop`, чтобы не пачкать трюнк): (a) фикстура закоммичена
  на отдельной ветке (TC-009, TC-020, TC-027) — `git checkout develop && git
  branch -D <branch>` убирает и ветку, и файлы разом (они не существуют на
  `develop`), плюс `git push origin --delete <branch>`, если стадия внутри
  теста успела запушить эту ветку; (b) фикстура лежит untracked прямо на
  `develop` (TC-019) — `git clean -fd docs/issues/open/zz-fixture-<name>/`
  обязателен отдельно, `checkout`/`branch -D` её не удаляют. Untracked- или
  забытые committed-остатки роняют `git status --porcelain`, который проверяет
  `/pf-qa` этой же issue при закрытии, а забытая ветка на origin копится через
  прогоны. Точное имя ветки/пути — в последнем шаге Steps каждого из четырёх
  кейсов ниже.

### TC-006: Закрытый словарь состояний находки

**Description:** Словарь состоит из **шести** значений, не пяти: `open` — начальное состояние, которое получает каждая новая находка при создании, плюс пять терминальных резолюций из AC-2.2 — `fixed`, `accepted-risk`, `deferred`, `wont-fix`, `duplicate-of CR-NNN`. AC-2.2 перечисляет именно терминальные резолюции; `open` — начальное состояние, а не резолюция, но словарь остаётся закрытым: ровно шесть значений и ни одного сверх. Придуманное седьмое значение отклоняется. Эта модель разрешает AC-2.4 (запрещено отсутствие записи, а не состояние `open`) и AC-3.4 (запрещён `PASS` при `open` у P0) непротиворечиво — TC-008 и TC-011 ниже проверяют её обе стороны.

**Preconditions:** Нет.

**Steps:**

| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Транскрибированный валидатор `pf_cr_valid_state(value)` на каждом из шести легальных значений — `open` плюс пять терминальных (для `duplicate-of` — с конкретным `CR-NNN`, например `duplicate-of CR-002`). | Все шесть приняты. |
| 2 | Тот же валидатор на придуманном значении `wontfix-later` (не входит в словарь). | Отклонено. |
| 3 | Drift-guard: `grep` в `skills/pf-codereview/SKILL.md` находит все пять терминальных литералов словаря рядом друг с другом (`fixed`, `accepted-risk`, `deferred`, `wont-fix`, `duplicate-of`). | Все пять присутствуют вместе, ни одно не подменено синонимом. Test-first: ожидаемо RED — понятие «состояние находки» сегодня в `pf-codereview/SKILL.md` отсутствует вовсе. |
| 4 | Drift-guard: отдельным `grep` в том же файле — `open` задокументирован как начальное состояние, присваиваемое находке при её создании (не как один из пяти терминальных). | Найдено, отдельно от пяти терминальных литералов из шага 3. Test-first: ожидаемо RED. |
