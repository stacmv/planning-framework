## Находка 1 (верификация, не починка) — входные гейты можно удовлетворить «по памяти»

Ручное тестирование прошлого issue (TC-048, шаги 6-7) показало: при **удалённом** `test_plan.md` / `implementation_plan.md` входные гейты `/pf-impl-plan` и `/pf-execute` **не отказали** — модель судила по копии документа, оставшейся в её контексте, а не по диску. Инструкция была написана верно, но не принуждала к вызову инструмента.

**Починка уже в коде** (коммит `d865899` из закрытого issue): в общее определение «стадия завершена» (`skills/pf-size-tiers/SKILL.md`) добавлен раздел «Evaluating it is a MECHANICAL check, never a memory exercise» с обязательным `ls -1 docs/issues/open/<ID>/` перед любым суждением; оба входных гейта (`skills/pf-impl-plan/SKILL.md`, `skills/pf-execute/SKILL.md`) предписывают этот вызов первым действием («Run the check, do not recall it» — подтверждено присутствие в обоих файлах на `836b04e`); пять статических проверок в `test/skills-static.sh` не дают потерять принуждение.

**Что нужно:** статический тест доказывает, что принуждение записано; что модель ему **подчиняется**, докажет только живой прогон в сессии Claude Code — удалить `test_plan.md`, запустить `/pf-impl-plan` (должен отказать), удалить `implementation_plan.md`, запустить `/pf-execute` (должен отказать). Ни один автотест этого не проверит.

**Актуальность повышена `/pf-autopilot`:** новый скил гонит issue к `/pf-close` автономно, без человека у экрана, — то есть ровно в сценарии, где гейт, отвечающий «по памяти», опаснее всего. Верификацию стоит гонять и под автопилотом.

## Находка 2 — `/pf-close` путает upstream-ветку с родительской

`skills/pf-close/SKILL.md:60` (Phase 3, «Detect Parent Branch»):

> Run `git config branch.issue/ISSUE-ID.merge`. If this returns a value such as `refs/heads/develop`, extract the branch name…

Но `branch.<name>.merge` — это **ветка отслеживания на remote** (upstream), а не родитель. Если ветку issue запушить с `-u` (что и делает `/pf-execute`/пользователь), команда возвращает `refs/heads/issue/<ID>` — **саму себя**. Скил, следуя инструкции буквально, попытался бы смержить ветку в неё же. Фолбэк на `develop` в Phase 3 не срабатывает — команда вернула значение, просто неверное. **Наблюдалось вживую** при закрытии `20260713-...` в этой сессии; пришлось определять родителя фактически через `git merge-base --is-ancestor develop HEAD`.

**Что нужно:** определять родителя не по upstream. Варианты: (а) конфиг `branch.<name>.pf-parent`, проставляемый `/pf-execute` при создании ветки; (б) фолбэк-детект — первая из `develop`/`main`, которая является предком HEAD (`git merge-base --is-ancestor`); (в) явный вопрос пользователю при неоднозначности. Проверить, не опирается ли `/pf-autopilot` на ту же сломанную Phase 3.

## Находка 3 — Manual Test UI: два дефекта парсинга (`tools/manual-test-ui`)

**3a. Экранированный пайп `\|` в ячейке таблицы ломается.** `lib/checklist.js:30` разбивает строку на ячейки по сырому `"|"`; комментарий на `:25` прямо признаёт: «Does not support escaped `\|` inside cells». `\|` — стандартное экранирование пайпа в GFM-таблице, и оно должно работать. UI превращает `\|` в `\ | `, ячейка разваливается, «Expected Result» уезжает в колонку «Result». **Наблюдалось вживую** на `manual_test_checklist.md` прошлого issue (шаг с `ls ~/.claude/skills/ \| wc -l`).

**3b. Секции, не являющиеся блоком `## TC-NNN`, не отображаются.** `lib/checklist.js:9` — `TC_HEADING_RE = /^##\s+TC-(\d+):/`; парсер (`:48-49`) пропускает любой заголовок, не совпавший с этим. Отдельная секция вроде «Общая подготовка» (не `## TC-…`) до тестировщика не доезжает — либо съедается в header-метаданные (если до первого TC), либо в предыдущий TC. **Наблюдалось вживую:** раздел подготовки был невидим, пока я не переименовал его в `## TC-000`.

**Что нужно:** (3a) распознавать `\|` при разбиении ячеек (замена `\|` на плейсхолдер перед split, восстановление после); (3b) решить, показывать ли не-TC секции отдельными карточками или хотя бы не терять их содержимое. Учесть локализованные заголовки (тест `checklist-ru.test.js` уже проверяет русские секции).

## Находка 4 — `make converge` не умеет передавать `--yes`

`Makefile`, цель `converge`:

```
converge:
	bash scripts/converge-to-v3.sh $(if $(TARGET),--target $(TARGET),)
```

Прокинуть `--yes` через `make converge` нельзя, поэтому цель **не автоматизируется из скрипта**: `make converge TARGET=…` при запуске не из терминала справедливо отменяется (`Converge cancelled — stdin is closed`). **Наблюдалось вживую** при подготовке фикстур ручного теста — пришлось звать `bash scripts/converge-to-v3.sh --target … --yes` напрямую. Прецедент проброса аргументов в самом `Makefile` есть — `make tui` использует `$(if $(TARGET),--target $(TARGET),)`.

**Что нужно:** добавить проброс флага, напр. `$(if $(YES),--yes,)`, чтобы `make converge TARGET=/tmp/x YES=1` работал неинтерактивно. Мелочь, но чинит автоматизируемость целевой команды фреймворка.

## Как воспроизвести

1. **Находка 1:** в мигрированном issue удалить `test_plan.md` → `/pf-impl-plan` должен отказать; удалить `implementation_plan.md` → `/pf-execute` должен отказать. Прогнать в живой сессии (и под `/pf-autopilot`).
2. **Находка 2:** запушить ветку issue с `-u`, запустить `/pf-close`; наблюдать, что Phase 3 возвращает саму ветку как «родителя».
3. **Находка 3:** открыть в Manual Test UI чеклист с ячейкой, содержащей `\|`, и с не-TC секцией между TC-блоками.
4. **Находка 4:** `make converge TARGET=/tmp/x < /dev/null` → отмена; нет способа передать `--yes`.
