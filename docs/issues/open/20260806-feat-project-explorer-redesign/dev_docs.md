# Project Explorer: редизайн — заметки для разработчика

Архитектурные решения, причины и известные ограничения редизайна `tools/manual-test-ui`. Пользовательская часть (что изменилось для тестировщика/разработчика/аналитика) — в `user_docs.md`; здесь — что нужно знать, чтобы дальше развивать этот код.

## Границы модулей

`app.js` больше не рендерит всё сам — он остался тонким роутером, решающим, какой из трёх ES-модулей смонтировать по `location.hash` (`#/`, `#/inbox`, `#/p/<project>`, `#/p/<project>/i/<issue>`), простым `switch`, без внешнего роутера (сохраняет «одна команда — работает», без сборки, `<script type="module">`). **Ловушка:** `package.json` намеренно **не** получил `"type": "module"` — с ним сломался бы `require()` во всех `server.js`/`lib/*.js`/`test/*.test.js` (CommonJS, не тронуты этим редизайном); `<script type="module">` в HTML достаточно для нативных ES-модулей в браузере и не требует этого поля вовсе. Не добавлять его при последующем рефакторинге модульной системы.

- `public/launcher.js` — уровень 1: карточки проектов, инбокс-карточка, ролевой переключатель.
- `public/workspace.js` — уровень 2: шапка, табы документов, содержимое, действие подготовки тестовых данных, human-tasks UI. Самый большой из трёх — унаследовал логику рендеринга документа из старого `app.js` почти без изменений.
- `public/inbox.js` — экран единого инбокса.

`public/workspace.js`'s разметка строится двумя разными способами намеренно, не по недосмотру: `renderChecklistPanel`/`renderTcPanelHtml`/`renderLooseSectionsHtml` — чистые функции, возвращающие HTML-**строку** (нужно для `test/workspace.test.js`'s TC-030 и для рендера в изолированном контексте); `renderChecklistBody`/`buildStepsTableNode`/`buildPrepareActionNode`/human-tasks-хендлеры — строят реальные DOM-узлы через `document.createElement`/`addEventListener`, потому что обработчик клика — замыкание, а не разметка, и в строку не сериализуется. Обе стороны переиспользуют одни и те же чистые под-функции для разметки, а не дублируют её — расхождение между «что показано» и «что интерактивно» здесь означало бы два независимых источника правды.

## Роль `human` и незавершённые задачи

`lib/roles-resolve.js` резолвит `roles.<key>` из `prompt.md` (алгоритм — `skills/pf-roles/SKILL.md` §4, тот же, что используют все `pf-*`-скиллы). Новое в этом редизайне: hard-stop на `kind: human` снят — резолвер возвращает структурный `{ kind: "human", ... }` вместо ошибки; **обработка** — на вызывающей стороне. `roles.<key>` также получил поле `mode: blocking | non-blocking` (дефолт `non-blocking`) — отдельное от `review.mode: parallel | sequential`, не путать.

Жизненный цикл: операция резолвится в `human` → появляется в `/api/inbox`'s `humanTasks[]` и в табе «Дела» → `POST .../human-tasks/:key/complete` (сервер проверяет, что артефакт существует и не заглушка, хеширует sha256, пишет маркер `[human-task done] <key> @ <ts> content-hash=<sha256>` в `session-log.md` issue) → если артефакт потом меняется на диске, пересчитанный хеш не совпадает — задача снова `[queued]`, помечена stale.

**`/pf-close`'s Phase 0 проверяет это независимо от `tools/manual-test-ui`** — это отдельный, не-JS алгоритм (skill-native, через Read/Bash), т.к. `pf-close`/`pf-autopilot` не должны зависеть от того, установлен ли и запущен ли этот инструмент. `pf-autopilot`'s work loop: если `/pf-close` останавливается на незавершённых human-задачах — снять cron (`CronDelete`) и завершиться отчётом, не пытаться повторить на следующем resume вхолостую.

**Список human-задач нигде не персистится — сервер пересчитывает его заново на каждый запрос инбокса**, пересканируя `prompt.md` всех настроенных проектов/issue целиком; статус живёт только в `session-log.md` (маркер + hash), отдельного реестра задач нет (`specs.md` §1). Это осознанное решение, не недосмотр: цена — пересчёт по всем проектам при каждом открытии инбокса, а выгода — невозможность рассинхронизации с `roles:` (то, что кеш неизбежно рано или поздно допускает). Если код на первый взгляд выглядит как «просто сканируем каждый раз без причины» — не «оптимизировать» кешем без переоткрытия этого компромисса заново.

**Известный, сознательно не закрытый здесь пробел: `/pf-execute` не обрабатывает `write: human`.** BRD допускает `roles.<key>.write: human` для любого ключа, включая `code`/`tests`, не только для документных стадий. Эта issue добавила обработку `kind: human` только в `pf-roles`/`pf-close`/`pf-autopilot` (`specs.md` G8/§4.1) — `/pf-execute`'s диспетчер (`claude` / не-`claude` через `codex-companion`) по-прежнему не умеет диспетчеризовать задачу с `write: human` на `code`/`tests`. Если `prompt.md` когда-нибудь выставит это вручную, `/pf-execute` эту ветку не обработает — см. `implementation_plan.md`'s «Known limitation» в разделе Dependencies.

## Действие «Подготовить тестовые данные» — на уровне issue и на уровне TC

`server.js`'s `prepareActionState(projectName, projectRoot, entry, options)` — единая функция для обоих уровней: без `tcId` в `options` считает verdict для всей issue, с `tcId` — для одного TC. Формы результата идентичны (`offered`/`enabled`/`reason`/`endpoint`/`checkout`), и это не совпадение: `GET .../checklist` вызывает её дважды — один раз для `parsed.prepare` (issue), и по разу на каждый `tc` в `parsed.tcs` (`tc.prepare`) — сервер уже отдавал оба уровня клиенту.

Клиент изначально читал только `parsed.prepare` (кнопка «Prepare test data for the whole issue» в `buildPrepareActionNode`, смонтированная на отдельной вкладке роли). `tc.prepare` уходил в браузер и терялся — регресс относительно дореформенного `app.js` (строка 933: `Prepare test data for ${tc.id}`), обнаруженный уже на стадии `/pf-user-docs` этой же issue, не раундом code review. Исправлено: `buildPrepareActionNode(item, runtime, tcId)` теперь принимает опциональный `tcId` (меняет текст кнопки, CSS-класс на `btn subtle`, добавляет `tcId` в тело POST-запроса), `renderChecklistBody` вызывает её на каждый `tc`, если у него есть `tc.prepare`. Один и тот же обработчик клика для обоих уровней — не два независимых пути к одному эндпоинту `POST .../prepare { confirm: true, tcId? }`.

## `looseSections` — известный, заведённый отдельно баг парсера

`lib/checklist.js`'s `parseChecklist()` возвращает `looseSections` — строки чек-листа между TC-блоками, не подошедшие ни под одну известную метку. Редизайн впервые показывает это поле в UI (`.loose-sections`, пунктирная рамка, заголовок «Дополнительные заметки») — раньше сервер его уже отдавал, но `app.js` никогда не читал. При этом сам парсер избыточно чувствителен: ветки «Предусловия»/«Требуемые данные»/таблица шагов не продвигают внешний цикл разбора корректно, из-за чего служебные строки самих TC-блоков иногда повторно попадают в `looseSections`. На реальном чек-листе этой же issue — 3 настоящих TC против 28 ложных записей `looseSections`. `specs.md` §1 сознательно выводит `lib/checklist.js` за скоуп этой issue (парсер существовал до неё) — баг заведён в `test_plan.md`'s Known Issues, не пофикшен здесь. `test/workspace.test.js`'s TC-030 проходит по своему буквальному контракту: рендерер корректно показывает то, что отдал парсер, вне зависимости от того, что парсер отдаёт лишнее.

## CSS-coverage guard и параллельные волны

`test/css-class-coverage.test.js` статически извлекает все CSS-классы, которые строит `launcher.js`/`inbox.js`/`workspace.js`, и проверяет, что для каждого есть правило в `style.css`. Полезная защита, но с последствием для параллельного исполнения: задача, пишущая новые классы в `workspace.js`, и задача, пишущая `style.css` **в той же волне**, диспетчеризуются одновременно — вторая не может знать о классах, которые первая ещё не написала на момент диспетчеризации. Результат — этот тест ловит «uncovered classes» на границе волны, не внутри одной задачи (случилось дважды за эту issue: волна 14 — Задача 29, `workspace.js`, новые классы vs. Задача 31, `style.css`, стилизующая по состоянию на момент диспетчеризации; волна 15 — та же коллизия между Задачей 30 и Задачей 31/32 набором). Задачи, пишущие в один и тот же файл (например 29/30/33/34, все — `workspace.js`), и так не диспетчеризуются в одной волне по правилу file-exclusivity — но `style.css` и `workspace.js` формально разные файлы, поэтому это правило само по себе коллизию не ловит; для новых классов из `workspace.js`-задачи нужен либо отдельный follow-up на стилизацию после волны, либо сознательный порядок волн, ставящий `style.css`-задачу позже, а не рядом.

## `code_review.md` — append-only ledger, не список

Находки живут в таблице `CR-NNN` (ID/Round/Priority/Description/Follow-up Issue/State), не в перезаписываемых секциях `### P0`/`### P1` — у списка нет стабильной идентичности между раундами, а строка таблицы не переписывается, только добавляется или у неё обновляется `State`/`Follow-up Issue`.

Два независимых пути к PASS-вердикту при открытых (не `fixed`) находках:
- **P2, `State: open`, без Follow-up Issue** — самый частый случай (`CR-007`…`CR-013` этой issue): Phase 3.6's порог блокировки — по приоритету (открытый P0/P1), не по `State`, так что открытый P2 не блокирует PASS сам по себе. Такие строки при PASS переносятся в `docs/planning/tech-debt.md` (BR-5) — не остаются видны только внутри `code_review.md`.
- **`State: deferred` с заполненным Follow-up Issue** — для находки, которую решено закрыть не фиксом, а отдельной issue (P1-находка `CR-014` этой issue — не блокер по `State`, несмотря на P1-приоритет; P2-находка `CR-015` туда же для трассируемости, хотя P2 и так не заблокировала бы PASS). `deferred`-строки в `tech-debt.md` не переносятся — это разные назначения одного и того же «не открытая P0/P1» состояния, не путать (`pf-git`/`pf-codereview` BR-5 явно разделяют их).

## Runbook: недетерминированный набор тестов

`tools/manual-test-ui/test/` не полностью стабилен, независимо от этого редизайна — известно с `prompt.md`: на нетронутом `develop` разные прогоны роняют разные тесты `prepare.test.js`, а `read-paths.test.js`'s TC-011 стабильно падает с `EPERM` на создании symlink (Windows-права). Чинится отдельной issue. Если локальный прогон `make test`/`node --test` показывает неожиданный красный тест из этих двух файлов — сначала перепроверить перезапуском, прежде чем считать это регрессией своих изменений.

## Известные ограничения и вынесенное за скоуп

- **Поиск по сетке карточек проектов** — `brd.md`'s AC-01a явно обещал, реализации нет (`launcher.js`/`index.html`: 0 совпадений на `search`/`filter`). Не регресс — фича никогда не строилась.
- **`ptcId`-несовпадение форматов** — продуктовый уровень (`docs/planning/test-plan.md`) использует `PTC-NNNN`, issue-локальный чек-лист — `TC-NNN`. CR-005's scroll-to-highlight при клике из инбокса в этом случае молча не срабатывает (основной переход — на правильную issue/таб — не затронут).
- Оба пункта вынесены в отдельную issue: `docs/issues/open/20260818-improve-project-explorer-launcher-search-and-tc-scroll/`.
- `looseSections`-баг парсера (выше) и P2-находки round 1/2 (`CR-007`…`CR-013`) — в `docs/planning/tech-debt.md`, не здесь: это `code_review.md`'s PASS-time остатки, а не результат `/pf-user-docs`/`/pf-dev-docs`.
