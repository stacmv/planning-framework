# Technical Specification: Редизайн Project Explorer (`tools/manual-test-ui`)

**Version:** 1.0
**Date:** 2026-08-17
**Status:** Draft
**Predecessor:** `brd.md` (v1.0, с правками /pf-check)

## 1. Обзор архитектурных решений

Существующий стек не меняется: raw `http` Node-сервер (`server.js`, без Express — design constraint «zero dependencies», см. `lib/roles.js` шапку), позиционная маршрутизация по `pathname.split("/")`, ванильный JS клиент (`public/app.js`, без фреймворка/сборки), `lib/roles.js` как единственный источник таблицы «роль → документы». Это issue **не переписывает** этот контракт — редизайн затрагивает навигационную оболочку (`.shell`/`.topbar`/`.sidebar`/`.content` в `style.css`/`app.js`/`index.html`), добавляет инбокс и human-очередь как новый слой поверх существующего API, и оставляет `lib/roles.js`, `lib/docstate.js`, `lib/checklist.js`, `lib/prepare.js`, `lib/markdown.js`, `lib/git.js`, `lib/memory.js`, `lib/instructions.js`, `lib/paths.js` содержательно нетронутыми (кроме точечных правок из §5/§6).

**Human-очередь резолвится на лету, не хранится отдельным файлом** (решение владельца при уточнении этого specs.md): сервер на каждый запрос инбокса сканирует `prompt.md` всех настроенных проектов/issue, резолвит роли по алгоритму `pf-roles/SKILL.md` §4, и строит список задач из тех точек, что резолвятся в `human`. Статус/хеш выполнения хранится в `session-log.md` соответствующей issue (append-only запись, как и остальные машиночитаемые маркеры пайплайна — `[pf-check PASSED]` и т.п.). Компромисс осознанный: пересчёт по всем проектам при каждом открытии инбокса, но без риска рассинхронизации между `roles:` в `prompt.md` и отдельным реестром.

## 2. Навигация — техническая структура

### 2.1 Уровень 1 — лаунчер (новый экран)

```
┌──────────────────────────────────────────────────────────────┐
│ .launcher                                                      │
│  ┌ .role-switch ─────────────────────────────────────────┐    │
│  │  [ Тестировщик ]  Разработчик   Аналитик                │    │
│  └───────────────────────────────────────────────────────┘    │
│  ┌ .inbox-card (клик → инбокс, AC-04d) ───────────────────┐    │
│  │  Инбокс — все проекты                          7 дел   │    │
│  └───────────────────────────────────────────────────────┘    │
│  .project-grid (карточки, поиск)                                │
│  ┌ .project-card ┐ ┌ .project-card ┐ ┌ .project-card ┐         │
│  │ planning-fw   │ │ codereview-…  │ │ tm-ritorika   │         │
│  │ 2 issue       │ │ 1 issue       │ │ 1 issue       │         │
│  └───────────────┘ └───────────────┘ └───────────────┘         │
└──────────────────────────────────────────────────────────────┘
```

- `.role-switch` на лаунчере хранит выбор в `localStorage` (`pf.role`), передаётся уровню 2 как дефолт (AC-01a: «роль выбирается здесь же»).
- `.project-card` рендерится из `GET /api/projects` (существует), без изменений формата ответа. BRD не требует счётчика дел на карточке проекта — AC-04d требует его только на единственной глобальной `.inbox-card`, а AC-06a вводит отдельный, project/issue-scoped счётчик только на уровне 2 (§2.2). Добавление ещё одного счётчика на каждую карточку проекта — расширение скоупа, которого BRD не просит, поэтому здесь его нет.
- Клик по карточке проекта → переход на уровень 2, с последней активной issue этого проекта (`localStorage` ключ `pf.lastIssue.<project>`, hash `#/p/<project>/i/<issue>`), либо на список issue данного проекта (hash `#/p/<project>`), если такой записи ещё нет.
- Клик по `.inbox-card` → отдельный экран инбокса (§3), не привязан к проекту.

### 2.2 Уровень 2 — рабочее пространство проекта (замена `.sidebar`+`.topbar`)

`lib/roles.js` партиционирует документы по ролям без пересечений (аналитик:
`prompt.md`/`brd`/`analysis`/`notes`/…; разработчик: `specs`/`impl_plan`/…;
тестировщик: `test_plan`/`manual_test_checklist`/`qa_report`/…) — ни одна роль
не объявляет одновременно `brd`, `specs`, `test_plan` и `impl_plan` (см.
шапку файла: «A role shows exactly what it declares and nothing else»,
проверяется `test/roles.test.js` TC-006). Поэтому `.doc-tabs` показывает
набор вкладок **текущей роли**, и этот набор меняется при переключении
`[Роль ▾]` — не единый ряд `brd│specs│test_plan│impl_plan` одновременно для
всех ролей. Ниже — пример для роли «Тестировщик»:

```
┌──────────────────────────────────────────────────────────────┐
│ .workspace-header                                               │
│  ← Проекты   planning-framework   [Issue ▾]   [Тестировщик ▾]   │
├──────────────────────────────────────────────────────────────┤
│ .doc-tabs (набор вкладок = roles.itemsOf("tester"))              │
│  test_plan │ manual_test_checklist │ qa_report │ Дела ③          │
├──────────────────────────────────────────────────────────────┤
│ .doc-panel (панели по AC-02f, во всю ширину)                    │
│  ...содержимое активного документа/вкладки...                   │
└──────────────────────────────────────────────────────────────┘
```

Переключение `[Роль ▾]` на «Разработчик» заменяет весь набор вкладок на
`specs │ implementation_plan │ Дела ③`; на «Аналитик» — на
`prompt.md │ brd │ analysis/notes │ Дела ③` (плюс project-doc-пункты каждой
роли, см. `lib/roles.js`). Документы, «живущие в разных ролях» (например
`brd` и `specs`), не видны одновременно ни в одном состоянии интерфейса —
каждый доступен только из своей роли, ровно как и сегодня в трёх списках
сайдбара; редизайн меняет визуальный контейнер (табы вместо списков), не
модель разделения.

- `.workspace-header`: «← Проекты» ведёт на уровень 1; `[Issue ▾]` — выпадающий список issue текущего проекта (замена `#issue-list`); `[Роль ▾]` — тот же переключатель роли, что на уровне 1 — его смена меняет одновременно и активную роль, и видимый набор `.doc-tabs`, описанный выше.
- **Переключение issue не меняет активный таб документа** (снимает P0 из `/pf-check`, AC-01e): если на `brd` для issue A и переключаешься на issue B — остаёшься на табе `brd` для issue B (или на ближайшем существующем документе, если `brd` для B ещё не создан — правило то же, что и сегодня для «not applicable»/«missing» состояний, `lib/docstate.js`). Это правило применимо только внутри одной роли — переключение роли уже само меняет набор вкладок, как описано выше.
- `.doc-tabs` рендерится из `roles.listRoles()`/`roles.itemsOf(roleId)` (существующий `GET /api/roles`) для текущей роли — источник данных не меняется (**`lib/roles.js` правок не требует**), меняется только визуальный контейнер (табы вместо трёх списков сайдбара) и то, что видимый набор вкладок теперь реагирует на переключатель роли в той же шапке, а не подразумевается фиксированным.
- Таб «Дела ③» — новый, есть в наборе вкладок каждой роли. Его счётчик — **не** только по этому issue: см. §3.4 ниже (AC-06a/AC-06b) — счётчик суммирует незакрытые дела по всем ролям **и по всем открытым issue текущего проекта**, независимо от того, какая issue/роль выбрана сейчас.

### 2.3 Компонентная граница в `app.js`

Текущий `app.js` (1086 строк) содержит рендеринг сайдбара, топбара и контента в одном модуле без явного разделения. Редизайн вводит три ES-модуля (без сборки — `<script type="module">`, уже допустимо для «нулевых зависимостей», это часть языка, не npm-пакет):

- `public/launcher.js` — уровень 1 (карточки проектов, инбокс-карточка, ролевой переключатель).
- `public/workspace.js` — уровень 2 (шапка, табы документов, содержимое) — наследует текущую логику рендеринга документа из `app.js` почти без изменений.
- `public/inbox.js` — экран инбокса (§3).

`app.js` остаётся тонким роутером: решает, какой из трёх модулей монтировать, на основе `location.hash` (`#/`, `#/inbox`, `#/p/<project>`, `#/p/<project>/i/<issue>`) — без внешнего роутера, простой `switch` по хешу, что сохраняет «одна команда — работает» (G7/AC-08a). `#/p/<project>` — проект выбран, для него ещё нет записи `pf.lastIssue.<project>` (§2.1): монтируется список issue этого проекта (не полноценное рабочее пространство уровня 2 — у него нет активной issue, а значит и активной роли/набора `.doc-tabs`).

### 2.4 Отображение `looseSections` чек-листа (G5/US-07)

Источник данных — уже существующий, ничего нового на сервере не требуется:
`GET /api/projects/:name/issues/:id/checklist` (реализован в `server.js`)
сегодня возвращает `parseChecklist()`'s результат целиком (`lib/checklist.js`),
включая поле верхнего уровня **`looseSections`** — массив
`{ afterTc, lineIndex, text }` (строки чек-листа, которые не подошли ни под
одну из известных меток — заголовок секции, «шаг», «данные», «заметки» —
между TC-блоками, см. `lib/checklist.js`, комментарий у объявления
`looseSections`). Сервер это поле уже отдаёт клиенту сегодня; проблема
только в том, что `public/app.js` его никогда не читает.

Где рендерится: в `.doc-panel` роли «Тестировщик», на экране документа
`manual_test_checklist.md` (`workspace.js`, наследующий текущую логику
рендеринга чек-листа). Новый блок `.loose-sections` добавляется **после**
последнего TC-`.panel` того же чек-листа, не внутри какого-либо TC-блока.
Элементы группируются по `afterTc` и рендерятся в порядке появления в файле
(`lineIndex`); элемент с `afterTc`, не совпадающим ни с одним отрендеренным
TC (не должно происходить при корректном документе, но защитно
обрабатывается), всё равно попадает в конец блока, а не отбрасывается —
принцип `lib/checklist.js` («don't let it vanish silently») переносится и на
UI.

Визуальное отличие от TC-блока (AC-07b): `.loose-sections` — не `.panel`.
Отдельный класс с иным фоном/бордером (например
`border: 1px dashed var(--border)` — пунктир вместо сплошной линии `.panel`,
и мягкий фон `color-mix(in srgb, var(--surface) 92%, var(--warn))`, тот же
приём, что и `.panel-table` в §5.2, но на базе `--warn`, а не `--accent`,
чтобы не читаться как акцентный заголовок обычной панели) и подписанным
заголовком **«Дополнительные заметки»** (не «TC-…» и не порядковый номер —
явно не тест-кейс), с короткой подписью под заголовком вроде «нераспознанный
текст между блоками чек-листа — не тест-кейс». Каждый элемент рендерится как
исходная строка `text` без markdown-разбора (сохраняется как есть, чтобы не
потерять то, что парсер и так не смог распознать) — это read-only
представление, как и весь остальной `.doc-panel` (Non-Goals: без ручного
редактирования содержимого документов пайплайна через UI).

## 3. Единый инбокс (US-04)

### 3.1 Источники данных

| Тип элемента | Источник | Фильтр |
|---|---|---|
| Ручной тест-кейс | `docs/planning/test-plan.md` каждого настроенного проекта (Status Tracker, формат из `20260806-feat-product-test-plan/specs.md`) | `Status == pending` |
| Human write/review-задача | `prompt.md` каждой открытой issue каждого проекта, `roles.<key>` резолвится в `human` (`pf-roles/SKILL.md` §4) | нет незакрытой отметки в `session-log.md` этой issue для данного `<key>` |

### 3.2 Новый API-эндпоинт

```
GET /api/inbox
  → {
      manualTests: [{ project, issueId, ptcId, area, testCase, priority, origin }],
      humanTasks:  [{ project, issueId, stageKey, operation, mode, artifactPath, instruction, status }],
      totalCount
    }
```

`manualTests[].issueId` — **обязательное** поле, не `issueId?`. Каждая
строка `docs/planning/test-plan.md`'s Status Tracker несёт колонку `Origin`
в формате `ISSUE-ID#TC-NNN` (формат зафиксирован в
`20260806-feat-product-test-plan/specs.md`, единственный путь, которым
строка вообще попадает в этот файл — перенос в `/pf-close` Phase 4.5,
которая всегда пишет `Origin` при переносе строки). `issueId` — это часть
`Origin` до `#`, распарсенная тем же построчным парсером, что читает
`Status`/`Priority`/`Area` (шаг 1 ниже); строка без валидного `Origin` —
признак повреждённого файла, а не легитимного случая «TC без issue», и
такая строка исключается из `manualTests[]` с предупреждением в серверном
логе, а не отдаётся клиенту с пустым `issueId`.

Реализация: серверная функция `collectInbox(projects)` в новом модуле `lib/inbox.js` (следует тем же design constraints, что `lib/roles.js`/`lib/markdown.js` — zero dependencies, чистые функции, без I/O на этапе загрузки модуля):
1. Для каждого проекта — прочитать `docs/planning/test-plan.md`, распарсить Status Tracker (переиспользовать парсер таблиц из `lib/markdown.js`, если он уже даёт построчный доступ к ячейкам; иначе — маленький построчный парсер по образцу `checklist.js`), собрать строки `Status: pending`, распарсив `issueId` из `Origin` как описано выше.
2. Для каждого проекта — перечислить открытые issue (`findChecklists`, уже существует), для каждой прочитать `prompt.md`, резолвить `roles.<key>` для всех ключей пайплайна (`brd`, `specs`, `test_plan`, `implementation_plan`, `code`, `tests`, `user_docs`, `dev_docs`) по алгоритму `pf-roles/SKILL.md` §4 в новом модуле `lib/roles-resolve.js` — **это не порт существующей логики**: сегодня в кодовой базе нет ни одного YAML-парсера, способного прочитать вложенную структуру `roles: { brd: { write: claude, review: [claude] } }` или `agents.yml`/`role-profiles.yml`. `lib/markdown.js` прямо документирует себя как «Deliberately not a YAML parser» и разбирает только плоские `key: value` пары фронтматтера (см. `parseFrontmatterLines`). `lib/roles-resolve.js` пишется с нуля как маленький построчный ридер, **намеренно ограниченный** узким подмножеством YAML, а не универсальный YAML-парсер:
   - вложенные мэппинги ровно в 2 уровня (`roles:` → `<key>:` → `write`/`review`/`run`/`skip`), не произвольная глубина;
   - flow-стиль объектов в одну строку — `{ key: value, key2: [a, b] }` — единственная форма, которую парсер обязан понимать; многострочный (block-style) вложенный мэппинг для одного `<key>` **не поддерживается** и является явным ограничением этой реализации;
   - flow-стиль списков в одну строку — `[a, b]`;
   - голые скалярные значения на уровне `<key>` — например `dev_docs: skip`.

   Это ограничение — не произвольное сужение: все примеры `roles:` в `pf-roles/SKILL.md` §1 и все реальные `prompt.md` этого репозитория уже написаны в этом однострочном flow-стиле построчно, по одному `<key>` на строку. Спецификация фиксирует это как явное **решение**, а не как временный пробел: `prompt.md`'s `roles:`-блок ограничен построчным flow-YAML-подмножеством, описанным выше; блок, написанный в ином (multi-line block) стиле, не гарантированно разбирается корректно, и `implementation_plan.md` заводит `lib/roles-resolve.js` отдельной, некрупной, но настоящей задачей — не разделом «переиспользовать существующее».
3. Для каждой пары `(issue, key)`, резолвящейся в `human` — проверить `session-log.md` issue на предмет отметки о выполнении/`stale` для этого `key` (маркер-конвенция — новая строка вида `[human-task done] <key> @ <ts> content-hash=<sha256>`, симметрично существующим `[pf-check PASSED]`).
4. Смёрджить оба списка, вернуть с `totalCount = manualTests.length + humanTasks.length`.

### 3.3 Разделение на секции (AC-04b)

Клиент (`inbox.js`) рендерит два раздельных блока/таба внутри экрана инбокса — «Ручные тесты» и «Человеческие задачи» — оба из одного ответа `/api/inbox`, без второго запроса. Раздел выбирается локальным табом, без изменения URL/хеша (не отдельные маршруты — не тот масштаб).

### 3.4 Счётчик «Дела» на уровне 2 (US-06, AC-06a/AC-06b)

BRD (AC-06a) требует: «Счётчик «Дела» на табе уровня 2 показывает сумму
незавершённых дел по всем ролям пользователя **в этом проекте**, а не
только по текущей выбранной роли». Это дословно **project-wide** значение —
сумма по всему проекту, а не только по открытой сейчас issue. Более ранняя
редакция этого specs.md сужала счётчик до «по всем ролям **этого issue**»
(§2.2, была строка «объединённый счётчик по всем ролям этого issue») — это
расхождение с BRD исправлено: счётчик — project-wide, вычисляется как
описано ниже.

Вычисление переиспользует ту же выборку, что и `collectInbox` (§3.2), без
отдельной серверной функции: клиент запрашивает `GET /api/inbox` (тот же
эндпоинт, что и экран глобального инбокса) и на клиенте фильтрует оба
списка (`manualTests`, `humanTasks`) по `project === текущий проект`; счётчик
таба «Дела» = сумма длин двух отфильтрованных списков. Поскольку ни
`manualTests[]`, ни `humanTasks[]` не несут поля «роль» (ручной TC —
всегда дело тестировщика по построению; human-задача привязана к
`stageKey`, не к роли-зрителю), фильтрация по проекту уже даёт сумму «по
всем ролям» без дополнительного шага — ни один элемент не относится к
конкретной *просматриваемой* роли, поэтому счётчик не меняется при
переключении `[Роль ▾]` (AC-06b: видно **до** переключения, поскольку
переключение роли этот счётчик вообще не трогает — он определяется только
текущим проектом). Повторного запроса при смене роли/issue внутри того же
проекта не требуется — набор данных инбокса не зависит ни от того, ни от
другого.

## 4. Актор `human` (US-05, US-06, G8)

### 4.1 Framework-скиллы — изменения вне `tools/manual-test-ui`

### 4.1a Human-task check в `/pf-close`/`/pf-autopilot` — независимый от `tools/manual-test-ui` алгоритм (AC-05b)

`/pf-close` и `/pf-autopilot` — markdown-скиллы, исполняемые LLM-агентом через
Read/Bash, работающие с одним проектом (cwd) и одной issue напрямую через
файлы. У них нет «настроенного списка проектов» и они не должны зависеть от
того, установлен ли и запущен ли `tools/manual-test-ui` — это отдельный,
опциональный dev-инструмент со своим `projects.json`. Поэтому проверка
человеческих задач в `/pf-close` **не** ссылается на §3.2 этого документа
(это серверная JS-функция `collectInbox`, другой рантайм) — у неё свой,
skill-native алгоритм, который `pf-close` выполняет сам через Read/Bash, без
JS и без обращения к `tools/manual-test-ui`:

1. Для активной issue прочитать `prompt.md` и резолвить `roles.<key>` для
   каждого ключа пайплайна (`brd`, `specs`, `test_plan`, `implementation_plan`,
   `code`, `tests`, `user_docs`, `dev_docs`, плюс `analysis`/`notes`, если
   применимо) по алгоритму `pf-roles/SKILL.md` §4 — тому же алгоритму, что уже
   выполняет каждый `pf-*`-скилл при резолвинге своей собственной роли, без
   нового кода, просто применённому здесь ко всем ключам сразу.
2. Отобрать ключи, резолвящиеся в `kind: human` (§2/§4 того же файла).
3. Для каждого такого ключа проверить `docs/issues/open/ISSUE-ID/session-log.md`
   на отметку `[human-task done] <key> @ <ts> content-hash=<sha256>` (§4.2
   ниже). Если отметка отсутствует — ключ не выполнен. Если отметка есть, но
   `sha256` артефакта на диске (тем же путём, что резолвится для этого `key`,
   см. §4.4) не совпадает с записанным `content-hash` — отметка `stale`, ключ
   тоже считается невыполненным.
4. Если хотя бы один резолвящийся в `human` ключ не выполнен (отсутствует
   отметка или она `stale`) — `/pf-close` останавливается с сообщением, какие
   именно ключи не закрыты.

**Место в фазах `pf-close`:** новый пункт 4 внутри существующей **Phase 0
(Prerequisite Checks)** — после сегодняшних трёх («QA report exists», «QA
verdict is PASS», «On correct branch»). Это prerequisite-проверка того же
рода (стоп до Phase 1's подтверждения пользователем), а не отдельная фаза —
согласуется с тем, что Phase 0 уже устроена как последовательность
«останавливаться немедленно при первом провалившемся пункте».

### 4.2 Жизненный цикл human-задачи

```
операция резолвится в human (pf-roles §4)
        │
        ▼
  [queued] ── появляется в /api/inbox, humanTasks[]
        │
        │  пользователь открывает задачу из инбокса или из таба «Дела»
        ▼
  [in progress] (чисто клиентское состояние — «открыл», не меняет статус на сервере)
        │
        ├── manual TC: заполняет Result по каждому шагу (существующий checklist-флоу)
        ├── human-review: пишет письменный вердикт (новая форма, AC-05d)
        └── human-write: создаёт/правит артефакт вне инструмента (только чтение — AC-05a/Non-Goals),
            затем помечает выполненным в инструменте
        │
        ▼
  POST .../human-tasks/:key/complete
    body: { verdict?: string }        // review: обязателен, "замечаний нет" — валидное значение
                                       // write: не нужен, только факт отметки
        │
        ▼  сервер проверяет: артефакт существует и не заглушка (AC-05e) →
           хеширует его содержимое (sha256) → пишет маркер в session-log.md issue
        │
        ▼
  [done, content-hash=X]
        │
        │  (позже) артефакт меняется на диске
        ▼
  при следующем построении инбокса: пересчёт хеша ≠ X → задача снова [queued], помечена stale (AC-05f)
```

### 4.3 Новые API-эндпоинты

```
GET  /api/projects/:name/issues/:id/human-tasks
  → [{ stageKey, operation, mode, artifactPath, instruction, status, contentHash? }]

POST /api/projects/:name/issues/:id/human-tasks/:key/complete
  body: { verdict?: string }
  422 invalid_verdict     — human-review без непустого verdict
  422 artifact_missing    — human-write, артефакт не найден/пуст на резолвленном пути
  200 { status: "done", contentHash }

POST /api/projects/:name/issues/:id/human-tasks/:key/reassign
  body: { actor: "claude" | "codex" | "haiku" | ... }   // валидируется против agents.yml
  Эффект: правит roles.<key>.write в prompt.md issue (AC-05g),
          дописывает запись о переназначении в session-log.md issue.
  200 { status: "reassigned", actor }
```

`:key` — один из ключей пайплайна (`brd`/`specs`/`test_plan`/`implementation_plan`/`code`/`tests`/`user_docs`/`dev_docs`), совпадает с ключами `roles:` в `prompt.md`.

**Механизм записи `roles.<key>.write` (AC-05g).** Тот же YAML-пробел, что и
у чтения (§3.2 п.2), только для записи — и здесь риск выше: полный
парсинг → мутация объекта → сериализация обратно легко портит форматирование,
комментарии или другие ключи `roles:`-блока, а полноценный YAML-writer вне
скоупа «нулевых зависимостей» этого инструмента. Поэтому `/reassign` не
делает parse-mutate-serialize круг, а выполняет **точечную построчную
текстовую замену**:

1. Прочитать `prompt.md` как текст (не как разобранную структуру).
2. Найти строку, соответствующую записи `<key>:` внутри `roles:`-блока —
   узкое построчное совпадение вида `^\s*<key>:\s*\{.*\}\s*$` (тот же
   однострочный flow-стиль, на который уже опирается §3.2 п.2 при чтении).
3. Внутри найденной строки заменить только подстроку `write: <старое>` на
   `write: <новое>` — регекспом, ограниченным этой одной строкой, не
   трогая `review`/`mode`/прочие поля той же записи и не трогая ни одной
   другой строки файла.
4. Записать файл обратно **байт-в-байт идентичным**, кроме этой одной
   заменённой подстроки — сохраняются переносы строк, отступы, соседние
   комментарии, порядок ключей.

**Ограничение, принимаемое явно.** Этот подход работает только если запись
`roles.<key>` уже написана в том же однострочном flow-стиле
(`<key>: { write: ..., review: [...] }`), которым сегодня написаны все
`prompt.md` этого репозитория (см. §3.2 п.2) — той же посылке, на которую
уже опирается чтение. Запись, разбитая на несколько строк (block-style
YAML), этим механизмом не находится и не правится; для такой issue
`/reassign` возвращает `409`/`501`-подобную ошибку с текстом «`roles.<key>`
записан в неподдерживаемом многострочном формате — переназначьте вручную
правкой `prompt.md`» вместо того, чтобы молча ничего не поменять или
испортить файл частичной заменой. Это принятое ограничение этой issue, не
дефект: полноценный YAML-writer — отдельная, более крупная задача, вне
скоупа «нулевых зависимостей».

### 4.4 Проверка выполнения — конкретика по типам (AC-05c/d/e)

- **Manual TC** (`mode` не применим — использует существующий checklist-флоу, не новый `/human-tasks` эндпоинт): существующая проверка непустого Result по шагам (`lib/checklist.js`) уже это делает — не меняется, только становится видна как часть инбокса, а не отдельного экрана.
- **human-review**: `POST .../complete` без непустого `verdict` → `422`. Текст «замечаний нет» — валидный непустой `verdict`, ничем не отличается от любого другого текста на уровне валидации (проверяется непустота, не содержание).
- **human-write, документные ключи** (`brd`/`specs`/`test_plan`/`implementation_plan`/`user_docs`/`dev_docs` — каждый резолвится ровно в один файл в папке issue): `POST .../complete` без тела (`artifactPath` берётся из самой задачи, не из запроса) — сервер читает файл по резолвленному `artifactPath` и проверяет три условия по порядку:
  1. **Существует и не пустой, не заглушка** — тот же признак, что `pf-size-tiers/SKILL.md`'s "Stage completion" уже использует для остальных документов пайплайна (непустое тело сверх заголовка, отсутствие маркера `TODO: Run /pf-`) — переиспользуется, не переизобретается.
  2. **Закоммичен в git (AC-05e)** — `lib/git.js` сегодня не даёт для этого готового метода (только `getCurrentBranch`/`isWorkingTreeClean`/`branchExists`/`showFile`/`listTreeNames`/`resolveDefaultBranch`/`checkoutBranch`), поэтому проверка описывается напрямую: `git status --porcelain -- <artifactPath>` (относительно корня issue-проекта) должен вернуть пустой вывод для этого пути — файл не числится ни неотслеживаемым, ни изменённым относительно последнего коммита. Непустой вывод (в том числе `??` — файл вообще не добавлен) → `422 artifact_not_committed`, отдельно от `artifact_missing` (файл физически существует и не пуст, но git о нём ещё не знает — разные причины отказа, разные коды).
  3. Если оба условия выполнены — хешировать содержимое (sha256) и писать маркер в `session-log.md`, как в §4.2.

  `422`-коды для этого пути: `artifact_missing` (условие 1 не выполнено), `artifact_not_committed` (условие 2 не выполнено).
- **human-write, `code`/`tests`** (`:key` = `code` или `tests`): эти два ключа не резолвятся в один файл-артефакт — `code` может затрагивать произвольный набор файлов реализации, `tests` — набор тестовых файлов, и требовать единственный `artifactPath` для них не подходит. Проверка выполнения здесь **другая**, не переиспользует путь выше:
  1. Определить родительскую ветку issue тем же способом, что `pf-close`'s Phase 3 (`git config branch.issue/ISSUE-ID.merge`, иначе `develop`/`main` — см. `skills/pf-close/SKILL.md`).
  2. Проверить, что ветка issue содержит хотя бы один коммит впереди родительской: `git rev-list --count <parent>..issue/<ISSUE-ID>` `> 0`.
  3. Проверить, что среди файлов этих коммитов (`git diff --name-only <parent>..issue/<ISSUE-ID>`) есть хотя бы один путь вне `docs/issues/` — для `code` любой такой путь считается; для `tests` требуется путь, дополнительно совпадающий с этим репозитория тестовой конвенцией (`test/*.test.js`, `node --test` — см. §7).
  4. Если оба условия (2) и (3) выполнены — задача считается выполненной; `contentHash` для этих двух ключей не файловый sha256, а sha1 текущего HEAD-коммита issue-ветки (`git rev-parse HEAD`) — «контент» здесь и есть состояние ветки, а не файл, так что stale-проверка (§4.2/AC-05f) сравнивает этот хеш при следующем построении инбокса точно так же, как файловый sha256 для остальных ключей.
  5. Если любое из условий не выполнено — `422 artifact_missing` (тот же код, что и для документных ключей — семантически то же самое: «результата ещё нет», источник неважен для клиента).

  `lib/git.js` не содержит готового метода ни для одного из шагов 1-4 — для этого пути пишутся новые небольшие функции по образцу уже существующих в этом файле (`tryGit`-обёртки), отдельная задача `implementation_plan.md`.

## 6. Клавиатурная доступность (US-03)

- Порядок `tabindex` — естественный DOM-порядок (не выставляется вручную), поэтому разметка `.role-switch` → `.inbox-card` → `.project-grid` → (на уровне 2) `.workspace-header` элементы → `.doc-tabs` → содержимое панели должна физически идти в этом порядке в HTML, не переставляться CSS-グリッдом/flex-order.
- `:focus-visible` (не `:focus`, чтобы не показывать рамку при клике мышью) — стиль `outline: 2px solid var(--accent); outline-offset: 2px`, контраст `--accent` к `--bg`/`--surface` уже покрыт AC-02b/токенами.
- Кнопки действий (`.human-task-actions`, чек-лист) — нативные `<button>`, не `<div onclick>` — клавиатурная доступность по умолчанию, без ARIA-костылей.

## 7. Совместимость и нефункциональные ограничения (G7, US-08)

- Ни одной новой записи в `package.json` (если он появится — сегодня `tools/manual-test-ui` его не имеет, см. `find` в начале спецификации; если для ES-модулей понадобится `"type": "module"`, это добавление поля в существующий `package.json` уровня `tools/manual-test-ui`, если он есть, либо не требуется вовсе, так как `<script type="module">` в HTML не требует `package.json`-декларации).
- Переключение на ветку issue (`lib/git.js`) — не трогается, вызывается из нового `workspace.js` тем же способом, что сегодня из `app.js`.
- Три состояния чек-листа (`missing`/`branch-only`/`on-disk`, `lib/docstate.js`) — не меняются, только рендерятся внутри `.doc-panel` вместо текущего контейнера.
- `test/` (существующие `node --test` сьюты) — сохраняются, дополняются новыми файлами по новым модулям (`lib/inbox.js`, `lib/roles-resolve.js`) без переписывания существующих. Известная недетерминированность `prepare.test.js`/`read-paths.test.js` TC-011 (BRD Non-Goals) — не в скоупе этой issue, не путать с новыми регрессиями.

## 8. Известные ограничения этой спецификации

- Формат парсинга `docs/planning/test-plan.md` (§3.2 п.1) предполагает Status Tracker-таблицу, описанную в `20260806-feat-product-test-plan/specs.md`; если этот формат к моменту реализации изменится, `lib/inbox.js` нужно свериться с актуальной версией того specs.md, а не с текстом здесь.
- Хеш-механизм stale-проверки (§4.2) — sha256 всего содержимого файла артефакта. Частичные/семантические diff'ы (например, «поменялись только пробелы») не различаются — любое байтовое изменение делает задачу stale. Осознанно просто; BRD (AC-05f) не требует более тонкой семантики.
