# Test Plan: Редизайн Project Explorer (`tools/manual-test-ui`)

**Version:** 1.0
**Date:** 2026-08-17
**Predecessors:** `brd.md` (v1.0), `specs.md` (v1.0)

## Overview

Инструмент (`tools/manual-test-ui`) сегодня тестируется исключительно на
уровне сервера/lib-модулей: `test/*.test.js` поднимает реальный HTTP-сервер
(`test/helpers/server.js`, форк `server.js` на эфемерном порту) и обращается
к нему через `fetch`, либо дёргает функции `lib/*.js` напрямую — без headless
браузера, без jsdom (проект намеренно zero-dependency, см. `lib/roles.js` и
`lib/markdown.js`). Этот план продолжает тот же принцип: подавляющее
большинство пунктов этой issue формулируются как проверяемые на уровне
API/lib/CSS-текста/git-состояния — числовые контрастные пороги, форма ответа
эндпоинтов, построчные git-проверки, разбор ограниченного YAML-подмножества.
`Manual` оставлен только для трёх случаев, которые действительно требуют
живого браузера или субъективного суждения владельца: подтверждение палитры
(AC-02k), визуальная приёмка панельной раскладки по референсу (AC-02f/02g),
и живая проверка табуляции/фокуса — в этом проекте нет headless-браузерного
харнесса, которым это можно было бы прогнать в CI.

### TC-003: Переключение issue сохраняет активный таб документа в рамках роли

**Description:** Проверяет правило specs.md §2.2 (снимает P0 из `/pf-check`): переключение issue в выпадающем списке не сбрасывает активный таб — если открыт `brd` issue A, переключение на issue B оставляет активным `brd` (или ближайший существующий документ, если `brd` у B ещё нет, по тем же правилам `missing`/`not_applicable`, что и сегодня). Это клиентское состояние, недостижимое через HTTP напрямую — тест предполагает, что `workspace.js` выражает это правило чистой функцией, экспортированной для тестирования (`require`d напрямую или загруженной через `node:vm`, как уже делает `test/roles.test.js` для клиентских модулей), например `resolveActiveTab(prevTabId, docsOfNewIssue)`, а не только вплетённой в обработчик клика.

**Preconditions:**
- Проект с двумя issue: issue A имеет `brd.md`, issue B — не имеет `brd.md` (документ `missing`).
- `public/workspace.js` экспортирует (или допускает загрузку через `node:vm` и последующий вызов) чистую функцию, реализующую правило «сохранить таб при смене issue» — задача на это должна быть заведена в `implementation_plan.md`, если модуль сейчас пишет это правило только внутри DOM-обработчика.

**Steps:**
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Вызвать `resolveActiveTab("brd", docsOfIssueA)`, где `docsOfIssueA` — ответ `GET .../docs` issue A (роль `analyst`, `brd.md` присутствует). | Возвращает `"brd"` — таб не меняется, когда документ есть у обеих issue. |
| 2 | Вызвать `resolveActiveTab("brd", docsOfIssueB)`, где `docsOfIssueB` — ответ `GET .../docs` issue B (`brd.md` отсутствует, `lib/docstate.js` классифицирует как `missing`). | Возвращает `"brd"` (таб остаётся тем же, документ рендерится в состоянии `missing`) — не переключение на другой документ автоматически, по тем же правилам, что и сегодня для `missing`/`not_applicable`. |
| 3 | Отдельно проверить: смена роли не проходит через `resolveActiveTab` — набор вкладок для новой роли берётся заново из `roles.itemsOf(newRoleId)` (TC-002 шаг 3), не из предыдущего активного таба. | Правило «сохранить таб» применяется только внутри одной роли при смене issue, не при смене роли. |

**Test Data:**
- `tools/manual-test-ui/test/helpers/fixtures.js` (две issue-фикстуры, у одной отсутствует `brd.md`)

**Expected Outcome:** Активный документ переживает смену issue внутри роли; смена роли — отдельная, независимая операция.

**Priority:** High

### TC-004: Клик-путь проект → документ — не больше двух/трёх кликов

**Description:** Проверяет M1/AC-01e: от карточки проекта на уровне 1 до документа последней активной issue — не больше двух кликов; переход к другой issue того же проекта — до трёх кликов (дополнительный клик за счёт `[Issue ▾]`, не нарушение). Клик-счёт проверяется не браузерным кликаньем, а числом хэш-переходов, которое порождает один клик — тест предполагает, что `app.js`/`launcher.js` выражают выбор целевого маршрута чистой функцией, экспортированной для тестирования, например `resolveLandingRoute(project, lastIssueByProject)`, возвращающей итоговый hash (`#/p/<project>/i/<issue>` или `#/p/<project>` для списка issue) за один вызов — если сейчас это решение вплетено только в обработчик клика, задача на экспорт функции должна быть в `implementation_plan.md`.

**Preconditions:**
- Фикстура значений `pf.lastIssue.<project>`: для проекта A запись есть, для проекта B — нет.

**Steps:**
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Вызвать `resolveLandingRoute("A", { A: "20260806-feat-example" })`. | Возвращает hash, ведущий напрямую на уровень 2 issue `20260806-feat-example` (без промежуточного списка issue) — один клик по карточке проекта уже приводит к этому вызову, второй — переход к самому документу: итог 2 клика (проект → документ). |
| 2 | Вызвать `resolveLandingRoute("B", {})` (записи `pf.lastIssue.B` нет). | Возвращает hash списка issue проекта B, не документ наугад и не пустой экран. |
| 3 | Смоделировать выбор другой issue того же проекта из выпадающего списка на уровне 2 как отдельный вызов роутера (не через `resolveLandingRoute` — это уже происходящая на уровне 2 операция). | Итоговый маршрут достигается за 3 перехода (проект → issue → документ) — специфицировано как ожидаемое поведение, не нарушение M1 (AC-01e). |

**Test Data:**
- не требуются

**Expected Outcome:** Хэш-роутинг (`#/`, `#/p/<project>/i/<issue>`) и `pf.lastIssue.<project>` дают ≤2 клика для уже активной issue и ровно на 1 клик больше при явном выборе другой issue.

**Priority:** High

### TC-006: Автотест контраста `test/contrast.test.js`

**Description:** Проверяет, что новый `test/contrast.test.js` существует, входит в стандартный `node --test`-прогон (`make test`/`make test-ui`), и падает при нарушении любого из порогов AC-02a–02c: `--text`↔`--surface` ≥7:1 (тёмная тема — около 10:1, не 15–21:1), каждый цвет текста (включая литералы) ↔`--bg` и ↔`--surface` ≥4.5:1, границы ≥1.5:1, ни чистого чёрного фона, ни чистого белого текста (M2).

Если сейчас парсер и вычисление контраста не разделены на вызываемые функции, задача на это должна быть в `implementation_plan.md`.

**Steps:**
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Запустить `node --test tools/manual-test-ui/test/contrast.test.js` как есть, против реального `public/style.css`. | Сьют завершается 0 (все пары проходят пороги) на текущем файле. |
| 2 | Вызвать `contrastRatio` для пары значений, где `--text`-подобный цвет заведомо даёт контраст <7:1 к `--surface`-подобному фону (inline-строки, не файл). | Функция возвращает значение <7, и обёрточная проверка (та же, что использует сьют на реальном файле) фиксирует нарушение — тест реально что-то проверяет, а не всегда зелёный. |
| 3 | Вызвать `parseRootTokens` на inline-CSS-строке, содержащей `color: #ffffff` как значение цвета текста, прогнать через ту же проверку «ни чистого белого текста». | Нарушение обнаружено на этой inline-фикстуре (AC-02c), реальный `public/style.css` не редактируется. |
| 4 | Убедиться, что `test/contrast.test.js` подхватывается стандартным раннером без отдельного вызова (лежит в `test/`, конвенция `node --test`). | Файл не требует правки `Makefile`/скриптов запуска. |

**Test Data:**
- `tools/manual-test-ui/public/style.css` (читается, не модифицируется)

**Expected Outcome:** M2 = 0 нарушений подтверждается автоматически и воспроизводимо, тест не является плацебо (шаги 2–3 доказывают чувствительность).

**Priority:** Critical
