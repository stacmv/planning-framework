# Business Requirements Document: Бюджет Manual-кейсов по size tier

## Overview

Сегодня `/pf-test-plan` требует пометить каждый тест-кейс как `Auto` или `Manual`, но никак не ограничивает их число и не создаёт давления в сторону автоматизации. На практике это приводило к тест-планам с 14-20 ручными кейсами на одну issue (см. `20260703-improve-scale-doc-complexity` — 20 Manual/0 Auto; `20260630-improve-add-testing-qa-close-phases` — 14 Manual/4 Auto), значительная часть которых — механически проверяемое содержимое сгенерированного документа, то есть по сути snapshot-тесты, ошибочно помеченные как ручные.

Это изменение вводит жёсткий бюджет числа Manual-кейсов по size tier, обязательное поле причины из закрытого словаря, автоматический проход по конвертации Manual→Auto при превышении бюджета, и гейт с явным решением пользователя, если после автоматизации превышение осталось.

## Goals

- Число Manual test case на issue ограничено по size tier: trivial 0-1, small ≤2, medium ≤3, large ≤5 — с жёстким потолком 5 при любом tier.
- Каждый Manual-кейс обязан нести причину `Manual reason` из закрытого словаря (`human-judgment`, `external-system`, `interactive-agent`, `cost`, `environment`); кейс без причины или с причиной, покрываемой существующим харнессом, не принимается.
- При превышении бюджета `/pf-test-plan` автоматически запускает проход конвертации: максимум возможных Manual-кейсов переводится в Auto, для остальных называется недостающий харнесс (а если харнесса нет — задача его построить попадает в `implementation_plan.md`).
- Если после автоматизации превышение сохраняется, пользователь получает явный выбор через `AskUserQuestion` из ровно трёх вариантов: разбить issue, поднять tier с записанным обоснованием, отложить избыток.
- Правило применяется ко всем запускам `/pf-test-plan` — включая уже открытые на момент этого изменения issue, а не только созданные позже.

## Non-Goals

- Продуктовый тест-план (`docs/planning/test-plan.md`), промоушен TC при закрытии issue, реестр невыполненного ручного долга и связанные гейты `/pf-qa`/`/pf-close` — отдельная issue `20260806-feat-product-test-plan`. Здесь эта половина дизайна не реализуется; вариант «отложить избыток» до появления той issue действует только как запись в текущей issue, без полноценного реестра.
- Изменение самого шаблона тест-кейса (структура Preconditions/Steps/Test Data) — не в охвате.
- Автоматическое построение недостающих test-харнессов — automation pass называет, что нужно построить, но не строит это сам; сама постройка харнесса — обычная задача `implementation_plan.md`, выполняемая на общих основаниях.
- Четвёртый вариант гейта («принять избыток как есть, без разбиения и без подъёма tier») — сознательно не вводится; «отложить избыток» уже покрывает потребность зафиксировать превышение без структурных действий.

## User Stories

1. **Как автор issue, запускающий `/pf-test-plan`**, я хочу, чтобы число ручных тест-кейсов было ограничено размером issue, чтобы объём QA-усилий соответствовал масштабу задачи, а не разрастался бесконтрольно.
2. **Как автор issue**, я хочу, чтобы каждый ручной кейс нёс явную, проверяемую причину из закрытого списка, чтобы «ручное, потому что лень автоматизировать» не проходило под видом легитимного ограничения.
3. **Как автор issue, чей тест-план превысил бюджет**, я хочу, чтобы система сама попыталась перевести лишние кейсы в Auto и назвала недостающий харнесс там, где перевод невозможен, чтобы не разбирать это вручную кейс за кейсом.
4. **Как автор issue, чей тест-план остался за бюджетом после автоматизации**, я хочу получить явный выбор (разбить / поднять tier / отложить), чтобы решение было осознанным и видимым в истории issue, а не молчаливым превышением.
5. **Как автор уже открытой issue** (созданной до этого изменения), я хочу, чтобы бюджет применялся и к моему повторному запуску `/pf-test-plan`, чтобы старые issue не оставались освобождены от дисциплины, которую ввели для новых.

## Business Rules

### Бюджет Manual по tier
| Tier | Бюджет Manual |
|---|---|
| trivial | 0-1 |
| small | ≤2 |
| medium | ≤3 |
| large | ≤5 |

Потолок 5 действует безусловно — `large` не даёт бюджету расти дальше вместе с масштабом issue.

### Закрытый словарь `Manual reason`
Обязателен для каждого Manual-кейса, одно из ровно пяти значений:
- `human-judgment` — визуальная/UX/эстетическая оценка;
- `external-system` — платное API, реальное устройство, сторонний аккаунт;
- `interactive-agent` — нужна живая сессия LLM как объект проверки (испытуемый и измерительный прибор — разные системы; кейс, где модель сама читает ожидаемый результат и сама же о нём отчитывается, не годится, независимо от заявленной причины — прецедент: `20260715-bug-gates-verification-and-tooling-fixes`, TC-002);
- `cost` — автоматизация технически возможна, но дороже пользы; требует оценки трудозатрат в самой причине;
- `environment` — нужное окружение недоступно в CI.

Кейс без `Manual reason`, либо с причиной, покрываемой существующим харнессом (вывод CLI, содержимое файла, текст сгенерированного документа — всё это механически проверяемо), не принимается как `Manual`.

### Automation pass при превышении бюджета
1. После генерации тест-плана оркестратор механически считает строки со статусом `Manual`.
2. Если счёт больше бюджета tier — запускается отдельный проход, единственная задача которого — перевести максимум возможных кейсов Manual→Auto и указать конкретный харнесс для каждого перевода.
3. Кейсы, которые остаются Manual после этого прохода, обязаны либо иметь харнесс, для которого автоматизация всё равно нецелесообразна (см. словарь причин), либо получить задачу на построение недостающего харнесса в `implementation_plan.md`.

### Гейт после automation pass
Если после automation pass бюджет всё ещё превышен, `AskUserQuestion` с ровно тремя вариантами:
- **разбить issue** — рекомендуется, когда избыток представляет собой один связный кусок функциональности;
- **поднять tier** — с обязательно записанным обоснованием в issue;
- **отложить избыток** — фиксируется как примечание в `test_plan.md` (раздел "Status Tracker" или близость к нему), перечисляя, какие кейсы отложены и почему; до появления реестра в issue `20260806-feat-product-test-plan` это остаётся чисто информационной записью, не обеспечиваемой никаким автоматизмом.

Никакого варианта «принять как есть без действия» не существует — превышение всегда требует одного из трёх решений выше.

### Применимость
Правило действует для каждого запуска `/pf-test-plan`, включая повторный запуск на issue, открытых до этого изменения. Ретроактивного пересчёта уже закрытых issue не производится.

## Acceptance Criteria

- AC-01: Тест-план объёмом, эквивалентным `20260703-improve-scale-doc-complexity` (20 Manual-кейсов; та issue предшествует появлению `size_tier` и не несёт этого поля), сгенерированный сегодня на issue любого объявленного tier, после прохождения `/pf-test-plan` либо укладывается в бюджет tier, либо явно останавливается на гейте с одним из трёх вариантов — не выдаёт 20 Manual-кейсов молча.
- AC-02: Каждая строка со статусом `Manual` в сгенерированном `test_plan.md` несёт непустое значение `Manual reason` из закрытого словаря пяти значений.
- AC-03: Повторный запуск `/pf-test-plan` на issue, открытой до этого изменения, тоже подчиняется бюджету — не только новые issue.
- AC-04: При превышении бюджета после automation pass пользователь получает ровно три опции гейта, без дополнительного варианта «принять как есть».
