Переделать Project Explorer (`tools/manual-test-ui`): двухуровневая навигация,
читаемое оформление, инбокс человеческих задач и очередь ручных тестов.

## Что не так сейчас

Измеримо, по `tools/manual-test-ui/public/`:

- `--bg: #0f1115` — почти чёрный фон;
- `font-size: 14px`, при этом `h1` — **15px**: заголовок неотличим от текста;
- `body { overflow: hidden }` — страница не скроллится, скроллятся только панели;
- навигация размазана по двум поверхностям: вкладки ролей сверху плюс три
  независимых списка (Project / Issue / Role items) в одном сайдбаре. Четыре
  измерения на двух поверхностях и три конкурирующие области прокрутки.

## Навигация — согласовано

**Уровень 1 — лаунчер.** Выбор роли, карточка глобального инбокса, сетка
карточек проектов. Роль выбирается здесь, вместе с проектом или инбоксом.

└──────────────────────────────────────────────────────┘
```

**Уровень 2 — рабочее пространство проекта. Сайдбара нет вообще.**

```
┌───────────────────────────────────────────────────────┐
│ ← Проекты   planning-framework    Issue ▾    Роль ▾   │
├───────────────────────────────────────────────────────┤
│  brd │ specs │ test_plan │ impl_plan │ Дела ③         │
├───────────────────────────────────────────────────────┤
│    # Technical Specification                          │
│    Содержимое во всю ширину, читаемая колонка.        │

Обоснование: с одной issue работают, пока она не закрыта, поэтому постоянный
список issue не нужен — выпадающий список в шапке. Документы переключаются
табами. Роль меняется выпадающим списком, места не занимает. «Дела» текущей роли
— такой же таб со счётчиком.

## Оформление

**Цветовая схема — Pine, выбрана.** Живёт в `D:/dev/dashboard`
(`www/assets/style.css`, слот `[data-theme="pine"]`):

    --bg #16241b  --surface #1e3126  --border #3c5c46
    --text #c6d5c8  --muted #96ac9c
    --ok #6ec97f  --fail #f08d84  --warn #e0b95c  --held #b6a0ef  --accent #5cc4d4

Правила, которые обязаны держаться при любой правке палитры:
- `--text` ≥ 7:1 к `--surface`; на тёмных темах держать около 10:1, не 15-21:1 —
  светлое на почти чёрном расплывается и утомляет за часы;
- **каждый** токен, используемый как цвет текста, ≥ 4.5:1 и к `--bg`, и к
  `--surface`. Это все они: по коду `color:` встречается 188 раз против
  `background:` 13. Именно этот порог был провален в пяти темах из шести;
- границы ≥ 1.5:1; ни чистого чёрного фона, ни чистого белого.

**Типографика и отступы — НЕ выбраны, это блокер стадии BRD.** Нужны референсы
от владельца: какие интерфейсы, приложения, издания нравятся визуально. Две
попытки подставить чужой вкус (мой и Codex) были отвергнуты; третью делать без
опоры бессмысленно. Известно только одно требование: моноширинный шрифт для
прозы — ошибка, гарнитуры для текста и для кода надо развести.

## Инбокс — две сущности в одной поверхности

Один инбокс, два типа элементов:

1. **Ручной тест** — из продуктового тест-плана со статусом `pending`. Источник
   данных даёт issue `20260806-feat-product-test-plan`.
2. **Человеческая задача** — write или review, назначенная актору `human`.
   Контракт ролей даёт issue `20260806-feat-role-matrix`; сам актор `human`
   реализуется **здесь**, поскольку вся его поверхность взаимодействия — этот
   интерфейс.

### Актор `human` — согласованный дизайн

Операция, зарезолвившаяся в `human`, скиллом не выполняется: она пишется задачей
в очередь (issue, стадия, операция, путь к артефакту, инструкция, статус).

**Два режима:**
- `mode: blocking` — пайплайн стоит, пока человек не выполнит;
- `mode: non-blocking` (дефолт) — пайплайн едет дальше, а `/pf-close` проверяет,
  что все human-операции выполнены, и **останавливается, если нет, в том числе
  под autopilot** (autopilot снимает себя с расписания и рапортует, а не крутится
  вхолостую).

**Проверка выполнения, а не декларации:**
- ручной TC — каждый шаг требует непустой текст в колонке Result, не только
  галочку; UI не даёт закрыть кейс с пустыми результатами;
- human-review — обязателен письменный вердикт, включая явное «замечаний нет»;
- human-write — артефакт существует, не заглушка, попал в коммит;
- **главный механизм:** завершение привязывается к хешу содержимого артефакта на
  момент отметки. Артефакт изменился после — операция становится `stale` и
  возвращается в очередь.

**Переназначение:** действие «отдать агенту» — задача переназначается на
llm-актора из `agents.yml`, `roles` в `prompt.md` правится, запись уходит в
`session-log.md` issue.

## Учесть при реализации

Парсер `tools/manual-test-ui/lib/checklist.js` был починен 2026-08-06 в
`20260715-bug-gates-verification-and-tooling-fixes`: экранированный `\|` теперь
парсится и корректно пишется обратно, а нераспознанные секции между TC-блоками
собираются в `parsed.looseSections` вместо того чтобы исчезать. **UI пока их
никак не показывает** — это надо доделать здесь, иначе починка парсера остаётся
невидимой пользователю.

Набор тестов `tools/manual-test-ui/test/` недетерминирован: на нетронутом
`develop` разные прогоны роняют разные тесты `prepare.test.js`, а
`read-paths.test.js` TC-011 стабильно падает с `EPERM` на создании symlink
(права Windows). Это чинится отдельной issue, но здесь об этом надо знать, чтобы
не принять чужой флак за собственную регрессию.

## Порядок работы

Сначала бриф на редизайн, потом критика и альтернативы от Codex, потом выбор
варианта владельцем, и только затем реализация. Codex может быть исполнителем —
это зависит от `roles.code.write`, см. `20260806-feat-role-matrix`.

## Приёмка

Тестировщик открывает интерфейс, за два клика попадает в нужный документ нужной
issue нужного проекта, видит свои невыполненные ручные тесты по всем проектам в
одном месте и не может отметить кейс выполненным, не записав фактические
результаты шагов.
