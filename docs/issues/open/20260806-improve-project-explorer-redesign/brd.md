# BRD: Редизайн Project Explorer (`tools/manual-test-ui`)

**Version:** 1.0
**Date:** 2026-08-17
**Status:** Draft

## Interview Notes

Постановка пришла развёрнутой (навигация, палитра, модель инбокса и актора `human` уже согласованы владельцем заранее) — уточнение в ходе `/pf-brd` касалось того, что сам owner явно пометил как блокер: типографика и отступы.

Ключевые высказывания и вскрытые ограничения:

- Референс на типографику/отступы дан не текстом, а двумя скриншотами старого проекта владельца (GLog v.0.7 — экран списка заявок и экран деталей анкеты). Две предыдущие попытки предложить типографику (от Claude и от Codex) были отвергнуты; третья без опоры на реальный референс не делалась.
- Из референса вытащены: панели с подписанным заголовком на каждую смысловую область экрана (а не сплошное полотно); контекстные действия и быстрые переходы видны сразу на экране, не спрятаны в меню/модалках; плотная, но не перегруженная подача — много деталей одновременно, но разбито по панелям; мягкая тональная заливка строк/панелей акцентным цветом вместо жёстких grid-линий; акцентный цвет для заголовков панелей, отличающий структуру от данных; заметная, но не драматическая разница заголовок/тело (фикс текущего бага, где h1 «15px» почти неотличим от body «14px»).
- Про сам зелёный цвет (уже выбранная палитра Pine) — прямое подтверждение от владельца: «зелёный — на него можно долго смотреть не уставая, тот самый компромисс между светлой и тёмной темой». Это не новое требование, а подтверждение уже принятого решения.
- Базовая клавиатурная навигация / видимый focus — явно включены как приёмочный критерий этого issue, по общему a11y-соглашению проекта (владелец подтвердил, а не просто не возразил).
- Инбокс: ручные тест-кейсы и человеческие write/review-задачи не сваливаются в одну ленту с одинаковыми на вид карточками — владелец прямо попросил раздельные секции/вкладки внутри инбокса, а не общий список с типовым бейджем.
- Переключение роли на уровне 2 (рабочее пространство проекта): счётчик невыполненных «Дел» должен быть по всем ролям сразу, не только по текущей — иначе владелец рискует не заметить свою же незавершённую human-задачу под другой ролью.
- Порядок работы над самим редизайном (бриф → критика и альтернативы от Codex → выбор владельцем → реализация) — явное требование к процессу, не к продукту; в этом BRD не порождает отдельного user story, но фиксируется как Non-Goal автоматической/безальтернативной реализации визуального решения.

## Executive Summary

Project Explorer (`tools/manual-test-ui`) сегодня — это набор из четырёх независимо прокручиваемых поверхностей (вкладки ролей + три списка в сайдбаре) на почти нечитаемой цветовой схеме. Issue переводит инструмент на понятную двухуровневую навигацию (лаунчер → рабочее пространство без сайдбара вообще), согласованную палитру Pine с проверенным контрастом, оформление по референсу владельца (панели, видимые действия, плотная подача) и объединённый инбокс, который впервые показывает не только ручные тесты, но и человеческие write/review-задачи, назначенные актору `human` — с проверкой их фактического выполнения, а не декларации.

## Problem Statement

Измеримо, по текущему `tools/manual-test-ui/public/`:

1. **Цвет и контраст.** `--bg: #0f1115` — почти чёрный фон, обесценивает саму идею тёмной темы (утомляет глаза при долгой работе) и не проходил ни одной из пяти прошлых попыток подобрать палитру.
2. **Типографика без иерархии.** `font-size: 14px` для тела, `h1` — 15px: заголовок неотличим от текста, читатель не видит структуру страницы.
3. **Навигация физически сломана.** `body { overflow: hidden }` — страница целиком не скроллится, скроллятся только отдельные внутренние панели, что рвёт ожидаемое поведение браузера.
4. **Навигация логически размазана.** Выбор роли (вкладки сверху) отделён от выбора project/issue (три независимых списка в сайдбаре) — четыре независимых измерения на двух разных поверхностях интерфейса, с тремя конкурирующими областями прокрутки одновременно.
5. **Инбокс не существует.** Ручные тест-кейсы со статусом `pending` и человеческие write/review-задачи, назначенные актору `human` (контракт даёт `20260806-feat-role-matrix`), нигде не собраны в одном месте — пользователь не может увидеть все свои незакрытые дела across projects.
6. **Починка парсера невидима пользователю.** `tools/manual-test-ui/lib/checklist.js` с 2026-08-06 умеет сохранять нераспознанные секции между TC-блоками (`parsed.looseSections`) вместо того, чтобы их терять, но UI их никак не показывает.

## Goals

| # | Goal |
|---|---|
| G1 | Тестировщик находит нужный документ нужной issue нужного проекта за два клика, без размазанной по двум поверхностям навигации |
| G2 | Цветовая схема и типографика проходят объективные контрастные пороги и субъективно узнаются владельцем как «удобно для длительной работы», а не как ещё одна отвергнутая попытка |
| G3 | Все незакрытые дела пользователя (ручные тесты + человеческие write/review-задачи) видны в одном инбоксе across projects, с чётким разделением двух типов |
| G4 | Актор `human` реализован до состояния, пригодного к использованию: задача пишется в очередь, выполнение проверяется по факту (хеш артефакта, непустой результат, письменный вердикт), а не по галочке |
| G5 | Нераспознанные секции чек-листа (`looseSections`), уже сохраняемые парсером, становятся видимы пользователю |
| G6 | Базовая клавиатурная доступность (навигация, видимый focus) присутствует как часть исходной реализации, а не как отложенный tech-debt |
| G7 | Инструмент по-прежнему не требует установки дополнительных зависимостей: одна команда запуска |

## Non-Goals

- Автоматическая или безальтернативная реализация конкретной визуальной раскладки: владелец явно потребовал порядок «бриф на редизайн → критика и альтернативы от Codex → выбор владельцем → реализация» — вопрос финального визуального решения не закрывается этим BRD в одностороннем порядке.
- Устранение недетерминированности `tools/manual-test-ui/test/` (`prepare.test.js`, `read-paths.test.js` TC-011) — известный tech-debt, чинится отдельной issue; здесь только требование не путать этот флак с собственной регрессией.
- Мультитемность (несколько цветовых схем на выбор) — палитра Pine уже выбрана владельцем как единственная целевая; переключение тем не запрашивалось.
- Полноценный воркфлоу-движок для актора `human` за пределами очереди/статусов, описанных в US ниже (например, уведомления, эскалации по SLA, назначение нескольким людям).
- Мобильная/адаптивная вёрстка — не упоминалась владельцем, целевая платформа — рабочая станция.
- Отдельная роль или интерфейс для внешнего тестировщика — адресат ролевых вкладок, как и в предыдущей итерации инструмента, владелец проекта в соответствующей роли.
- Редактирование документов пайплайна (brd/specs/test_plan/impl_plan/итд) из инструмента — только чтение, правка документов пайплайна остаётся вне UI.

## Users

| User | Context |
|---|---|
| Primary — владелец проекта, роль «Тестировщик» | Проходит ручные тест-кейсы; должен видеть все свои незакрытые дела across projects в одном месте и не может закрыть кейс без записанных фактических результатов |
| Primary — он же, роль «Разработчик» | Работает с impl-plan/code, получает и выполняет human-write/review задачи, назначенные ему как актору `human` |
| Primary — он же, роль «Аналитик» | Проверяет соответствие реализации требованиям; получает и выполняет human-задачи анализа/ревью |

## User Stories

### US-01: Как пользователь инструмента, я хочу двухуровневую навигацию без размазанного по двум поверхностям сайдбара, чтобы попадать в нужный документ за два клика.

**Acceptance Criteria:**
- AC-01a: Уровень 1 (лаунчер) даёт выбор роли, карточку глобального инбокса и сетку карточек проектов с поиском; роль выбирается здесь же, вместе с проектом или инбоксом.
- AC-01b: Уровень 2 (рабочее пространство проекта) не содержит постоянного сайдбара; issue выбирается выпадающим списком в шапке, роль — отдельным выпадающим списком там же.
- AC-01c: Документы issue (brd/specs/test_plan/impl_plan и т.д.) переключаются табами на уровне 2, во всю ширину доступного пространства, без конкурирующих областей прокрутки.
- AC-01d: «Дела» текущего issue — такой же таб, со счётчиком.
- AC-01e: От карточки проекта на уровне 1 до содержимого нужного документа — не больше двух кликов (проект → документ, при уже выбранной issue/роли по умолчанию последней активной).
- AC-01f: Страница скроллится штатно (не воспроизводится текущий баг `body { overflow: hidden }`).

### US-02: Как пользователь, я хочу оформление, проверенное на контраст и узнаваемое как удобное для долгой работы, чтобы не уставать глазами за часы использования.

**Acceptance Criteria:**
- AC-02a: `--text` даёт контраст ≥7:1 к `--surface`; на тёмных темах контраст держится около 10:1, не поднимаясь до 15–21:1.
- AC-02b: Каждый цветовой токен, применяемый как цвет текста, даёт контраст ≥4.5:1 и к `--bg`, и к `--surface` — без исключений по месту использования.
- AC-02c: Контраст границ ≥1.5:1; ни чистого чёрного фона, ни чистого белого текста нигде в интерфейсе.
- AC-02d: Используется палитра Pine (`--bg #16241b --surface #1e3126 --border #3c5c46 --text #c6d5c8 --muted #96ac9c --ok #6ec97f --fail #f08d84 --warn #e0b95c --held #b6a0ef --accent #5cc4d4`), без альтернативных цветовых схем на выбор.
- AC-02e: Разница в размере заголовок/тело заметна на глаз (фикс текущего h1=15px vs body=14px), но не драматическая — соответствует референсу владельца (скриншоты GLog v.0.7).
- AC-02f: Каждая смысловая область экрана — отдельная панель с подписанным заголовком (не сплошное полотно), заголовок панели — акцентным цветом, отличающим структуру от данных.
- AC-02g: Контекстные действия и быстрые переходы (например: выбор периода, переход к тому, что требует внимания, кнопки действий на экране записи) видны сразу на экране, не спрятаны в дополнительное меню или модальное окно.
- AC-02h: Таблицы и списки используют мягкую тональную заливку строк в рамках палитры Pine вместо жёстких grid-линий, сохраняя контрастные требования AC-02a–02c.
- AC-02i: Шрифт без засечек (sans-serif) для всей прозы интерфейса; моноширинный — только для фрагментов кода, не для основного текста (существующая договорённость, не меняется этим issue).

### US-03: Как пользователь, я хочу управлять интерфейсом с клавиатуры и видеть, где находится фокус, чтобы не зависеть от мыши.

**Acceptance Criteria:**
- AC-03a: Все интерактивные элементы (вкладки ролей, выпадающие списки issue/роли, табы документов, элементы инбокса, действия на чек-листе) достижимы по Tab в логичном порядке.
- AC-03b: Текущий элемент фокуса визуально виден (видимый focus-индикатор), контраст индикатора соответствует требованиям AC-02a–02c.
- AC-03c: Базовая клавиатурная навигация присутствует в исходной реализации этого issue, не выносится в отдельный tech-debt.

### US-04: Как пользователь любой роли, я хочу единый инбокс со всеми незакрытыми делами across projects, разделённый по типу дела, чтобы не искать их по отдельным проектам и не путать разные типы задач.

**Acceptance Criteria:**
- AC-04a: Инбокс собирает дела из всех настроенных в инструменте проектов, а не только из того, из которого инструмент запущен.
- AC-04b: Инбокс показывает два типа элементов в раздельных секциях/вкладках: ручные тест-кейсы (источник — продуктовый тест-план, статус `pending`, issue `20260806-feat-product-test-plan`) и человеческие write/review-задачи, назначенные актору `human` (контракт — `20260806-feat-role-matrix`).
- AC-04c: Для каждого элемента инбокса видно как минимум: проект, issue, что конкретно требуется (какой TC / какая стадия и операция), и куда вести пользователя дальше по клику.
- AC-04d: Карточка глобального инбокса на уровне 1 (лаунчере) показывает суммарное число дел across projects (пример: «Инбокс — все проекты, 7 дел»).

### US-05: Как разработчик или аналитик, я хочу, чтобы человеческая write/review-задача попадала в очередь и требовала от меня фактического выполнения, а не галочки, чтобы работа не считалась сделанной, пока она реально не сделана.

**Acceptance Criteria:**
- AC-05a: Операция, зарезолвившаяся в актора `human` (по правилам `20260806-feat-role-matrix`), не выполняется автоматически: она записывается задачей в очередь с полями issue, стадия, операция, путь к артефакту, инструкция, статус.
- AC-05b: Задача поддерживает два режима: `mode: blocking` (пайплайн останавливается до выполнения) и `mode: non-blocking` (дефолт — пайплайн продолжается; `/pf-close` проверяет, что все human-операции issue выполнены, и останавливается, если нет — в том числе под `/pf-autopilot`, который в этом случае снимает себя с расписания и рапортует, а не крутится вхолостую).
- AC-05c: Для ручного тест-кейса выполнение проверяется по непустому тексту в колонке Result у каждого шага — не только по галочке; UI не даёт закрыть кейс с пустыми результатами шагов.
- AC-05d: Для human-review выполнение требует письменного вердикта, включая явное «замечаний нет» — молчаливое согласие не засчитывается.
- AC-05e: Для human-write выполнение требует, чтобы артефакт существовал, не был заглушкой и попал в коммит.
- AC-05f: Завершение задачи привязывается к хешу содержимого артефакта на момент отметки о выполнении. Если артефакт меняется после отметки, задача переходит в статус `stale` и возвращается в очередь.
- AC-05g: Пользователь может переназначить human-задачу на llm-актора из `agents.yml` действием «отдать агенту»: `roles` в `prompt.md` соответствующей issue правится автоматически, запись о переназначении попадает в `session-log.md` этой issue.

### US-06: Как пользователь, я хочу видеть в рабочем пространстве проекта, сколько у меня незавершённых дел по всем ролям сразу, чтобы не пропустить свою же human-задачу под другой ролью.

**Acceptance Criteria:**
- AC-06a: Счётчик «Дела» на табе уровня 2 показывает сумму незавершённых дел по всем ролям пользователя в этом проекте, а не только по текущей выбранной роли.
- AC-06b: Переключение роли выпадающим списком в шапке не требует отдельного шага, чтобы увидеть, что счётчик включает дела других ролей — это видно до переключения.

### US-07: Как тестировщик, я хочу видеть нераспознанные секции чек-листа между TC-блоками, чтобы починка парсера (2026-08-06) была видна, а не только присутствовала в данных.

**Acceptance Criteria:**
- AC-07a: Секции, которые парсер `tools/manual-test-ui/lib/checklist.js` сохраняет в `parsed.looseSections` вместо того, чтобы терять, отображаются в UI на экране соответствующего чек-листа.
- AC-07b: Отображение `looseSections` не путается визуально с обычными TC-блоками — пользователь понимает, что это отдельная, не структурированная как TC часть документа.

### US-08: Как владелец проекта, я хочу, чтобы редизайн не требовал новых зависимостей и не ломал уже работающее (переключение веток, три состояния чек-листа), чтобы инструмент оставался «запустил и работаешь».

**Acceptance Criteria:**
- AC-08a: Инструмент по-прежнему запускается одной командой, без установки дополнительных зависимостей сверх текущего состояния.
- AC-08b: Переключение на ветку issue по явному подтверждению продолжает работать, как и три состояния чек-листа (доступен на диске / доступен только на ветке / отсутствует).
- AC-08c: Точечная запись отметок и заметок в чек-листе (правка одного пункта не затрагивает остальной документ) сохраняется без изменений.
