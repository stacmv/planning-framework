# Planning Framework v2.0 - Design Analysis

**Date:** 2024-01-27
**Status:** Design Complete - Ready for Implementation

## Executive Summary

Planning Framework v2.0 addresses critical issues with v1.0:
- **File growth problem** - Solves unbounded growth of implementation-plan.md and session-log.md
- **Multi-branch conflicts** - Issue-based workflow prevents planning doc conflicts
- **Multi-agent support** - Single PLANNING.md works for Claude/Gemini/Qwen
- **Complexity** - Dramatically simplified structure and templates
- **Issue tracking** - Built-in local issue tracker with defined workflow

## Key Changes from v1.0

### Structure Changes
| v1.0 | v2.0 | Rationale |
|------|------|-----------|
| CLAUDE.md | PLANNING.md | Multi-agent support, framework-specific name |
| All work in global plan | Issue-based workflow | Prevents file growth, branch conflicts |
| Large implementation-plan.md | Minimal global plan + issues | Bounded file sizes |
| No issue tracking | Built-in issue tracker | Structured feature/bug workflow |
| No QA workflow | .qa-workflow.md | Quality gates before closing issues |

### Philosophy Changes
- **From:** "Track everything in global files"
- **To:** "Global files for roadmap, issues for execution"

## Core Design Decisions

### 1. Issue-Based Workflow

**Issue Naming:** `YYYYMMDD-{type}-{slug}`
- Example: `20240127-feat-add-authentication`
- Date ensures uniqueness across branches
- Type visible at glance (feat/bug/improve)
- Slug provides human readability

**Issue Types (Default):**
- `feat` - New feature
- `bug` - Fix existing functionality
- `improve` - Enhance existing feature
- *Configurable per project in PLANNING.md*

**Branch Naming:** `issue/YYYYMMDD-{type}-{slug}`
- 1:1 mapping with issue folder
- Example: `issue/20240127-feat-add-authentication`

**Issue Locations:**
```
docs/issues/
├── open/           # Active issues being worked on
│   ├── 20240127-feat-add-auth/
│   └── 20240128-bug-fix-login/
└── closed/         # Completed and integrated issues
    └── 20240126-feat-user-dashboard/
```

### 2. File Structure

#### Global Planning Files (docs/planning/)

**implementation-plan.md** - Minimal, bounded size
- Current status (What's happening now?)
- Roadmap (Next 2-3 milestones)
- Active issues (Links to docs/issues/open/*)
- Planned issues (Not started yet)

**session-log.md** - Lightweight tracking
- One-line entries when issues close
- Format: `[Agent] ✓ [issue-id](link) - Brief description`
- Example: `[Claude Code] ✓ [20240127-feat-add-auth](../issues/closed/20240127-feat-add-auth) - Added JWT authentication`
- Ad-hoc work sessions (not tied to issues)

**decisions.md** - Architectural decisions
- Keep all significant decisions (permanent reference)
- Split by topic when too large (e.g., decisions-api.md, decisions-database.md)
- Decisions from closed issues get promoted here

#### Issue Files (docs/issues/open/YYYYMMDD-type-slug/)

**Required Files:**

1. **prompt.md** - Original user request
   - Exact user prompt that spawned issue
   - Preserves original intent

2. **analysis.md** - Agent's understanding
   - YAML frontmatter with metadata:
     ```yaml
     ---
     created: 2024-01-27
     type: feat
     branch: issue/20240127-feat-add-authentication
     status: open
     ---
     ```
   - Problem analysis
   - Proposed solution approach
   - Dependencies and considerations

3. **implementation-plan.md** - Detailed task breakdown
   - Step-by-step checklist
   - Component specifications
   - Progress tracking with checkboxes

4. **session-log.md** - Work progress
   - Session-by-session updates
   - Completed tasks
   - Blockers and notes
   - Next session priorities

**Optional Files (created if needed):**

5. **decisions.md** - Issue-specific architectural decisions
   - Only created if architectural decisions made
   - Significant decisions get promoted to global decisions.md on closure

6. **definition-of-done.md** - Completion criteria
   - Optional checklist
   - Acceptance criteria
   - Test scenarios

#### QA Workflow (.qa-workflow.md at repo root)

Defines quality gates before closing issues:
- Linting/formatting requirements
- Unit test requirements (pass existing + add new)
- Integration test requirements
- Documentation update requirements
- Bug-specific: failing test → fix → passing test

                         │

│    a. Merge branch to parent branch                            │
│    b. Move issue: open/ → closed/                              │

### 4. Session Management

**One Issue Per Session:**
- Agent focuses on single issue until closed or blocked
- Clear context boundaries
- Simpler state management

**Session Start (Issue Work):**
Agent reads in priority order:
1. `PLANNING.md` - Framework instructions
2. Issue-specific files (prompt, analysis, plan, session-log)
3. Global planning files (implementation-plan, decisions)
4. `.qa-workflow.md` - QA requirements

**Session End (Issue Work):**
Agent updates:
1. Issue `session-log.md` - What was done, blockers, next steps
2. Issue `implementation-plan.md` - Check off completed tasks
3. Commit changes with clear message

**Ad-Hoc Work (Not Issue-Based):**
- Small fixes, experiments, cleanup that don't fit into issues
- Agent asks user: "Should I create issue for this or work directly?"
- If direct work: Log in global session-log.md with agent name
- Format: `[Agent] YYYY-MM-DD: Brief description of ad-hoc work`

### 5. Context Reading Strategy

**Problem:** Large files consume too many tokens

**Solution:**
- Global files stay small (bounded by roadmap scope)
- Issues contain execution details (isolated context)
- Closed issues archived away (out of sight)
- Agent only reads relevant issue files

**Token Efficiency:**
- Old v1.0: Read entire implementation-plan.md (1000s of lines)
- New v2.0: Read minimal global plan + single issue folder (~200-300 lines)

### 6. Multi-Agent Support

**Single Config File: PLANNING.md**
- Replaces CLAUDE.md, GEMINI.md, QWEN.md
- Framework-specific name avoids conflicts
- Agent-agnostic instructions
- Agent-specific notes where needed (marked clearly)

**Agent Tracking:**
- Session log entries tagged with agent name
- Format: `[Claude Code]`, `[Gemini CLI]`, `[Qwen Code]`
- Helps debug agent-specific behaviors
- Git commits include Co-Authored-By line

### 7. Quality Assurance

**QA Workflow File:** `.qa-workflow.md` at repo root

**Default Requirements:**
```markdown
# QA Workflow

Before closing any issue, the following must pass:

## All Issues
- [ ] Linting/formatting passes
- [ ] All existing unit tests pass
- [ ] New unit tests added for new functionality
- [ ] Documentation updated (README, API docs, etc.)
- [ ] Code reviewed for security vulnerabilities

## Feature Issues (feat/improve)
- [ ] Integration tests pass (if applicable)
- [ ] User-facing documentation updated
- [ ] Examples added if needed

## Bug Issues
- [ ] Failing test created that reproduces bug
- [ ] Test now passes after fix
- [ ] Regression test added

## Project-Specific
[Add project-specific QA requirements here]
```

**QA Failure Handling:**
- If QA fails, agent attempts to fix
- If can't fix automatically, marks blocker in session-log
- Issue stays open until QA passes

### 8. Migration from v1.0 to v2.0

**Migration Strategy:**

**Phase 1: Setup v2.0 Structure**
1. Run interactive setup script: `./setup-planning-v2.sh`
   - Creates new folder structure
   - Generates PLANNING.md from templates
   - Creates .qa-workflow.md
   - Initializes minimal global planning files

**Phase 2: Convert Completed Work**
2. Convert completed sections of v1.0 implementation-plan.md to closed issues
   - Script: `./migrate-completed-work.sh`
   - Creates issue folders in docs/issues/closed/
   - Extracts prompts, summaries, decisions
   - Preserves historical context

**Phase 3: Convert Current Work**
3. Convert in-progress work to open issues
   - Manually create 1-3 issues for current priorities
   - Agent can help: "Analyze my current implementation plan and suggest issues"
   - Fill out prompt.md, analysis.md, implementation-plan.md

**Phase 4: Archive v1.0 Files**
4. Move v1.0 files to archive:
   - `docs/planning/v1.0-archive/`
   - Keep for reference but don't read in sessions
   - Update CLAUDE.md → PLANNING.md

**Phase 5: Commit Migration**
5. Commit changes: `git commit -m "Migrate to Planning Framework v2.0"`

**Migration Script Details:**

**Interactive Setup (`setup-planning-v2.sh`):**
```bash
# Prompts:
# - Project name
# - Issue types (default: feat/bug/improve)
# - QA requirements (linting, tests, docs)
# - Agent preference (Claude/Gemini/Qwen/All)

# Creates:
# - docs/issues/{open,closed}/
# - docs/planning/ (if not exists)
# - PLANNING.md (from template)
# - .qa-workflow.md (from template)
# - docs/planning/implementation-plan.md (minimal template)
# - docs/planning/session-log.md (empty)
# - docs/planning/decisions.md (empty if not exists)
```

## Design Validation

### Problem 1: File Growth ✓ SOLVED
**v1.0 Issue:** implementation-plan.md and session-log.md grow unbounded

**v2.0 Solution:**
- Global implementation-plan.md only contains roadmap + active issues (bounded)
- Global session-log.md only gets one-line entries when issues close
- Detailed execution tracked in issue folders
- Closed issues archived away from active context

### Problem 2: Multi-Branch Conflicts ✓ SOLVED
**v1.0 Issue:** Feature branches have conflicting planning docs

**v2.0 Solution:**
- Each issue has its own folder with planning docs
- No shared planning files between branches
- Global files only updated at merge time (sequential, no conflicts)
- Issue folders are branch-specific

### Problem 3: Multi-Agent Support ✓ SOLVED
**v1.0 Issue:** Separate CLAUDE.md, GEMINI.md files duplicate instructions

**v2.0 Solution:**
- Single PLANNING.md file with agent-agnostic instructions
- Framework-specific name (won't conflict with other tools)
- Agent name tracking in session logs

### Problem 4: Complexity ✓ SOLVED
**v1.0 Issue:** Complex templates, hard to understand

**v2.0 Solution:**
- Simplified file structure (4 required + 2 optional per issue)
- Clear workflow (7 phases)
- Interactive setup script (no manual template copying)
- Minimal global files

### Problem 5: No Issue Tracking ✓ SOLVED
**v1.0 Issue:** No structured way to track features/bugs

**v2.0 Solution:**
- Built-in issue tracker with defined workflow
- Issue types (feat/bug/improve)
- Definition of done
- QA gates

## Remaining Questions & Future Enhancements

### Future Enhancements (Not in v2.0)
1. **Issue Dependencies** - Track blocking relationships between issues
2. **Issue Labels/Tags** - Beyond type (priority, area, etc.)
3. **Closed Issue Archival** - Compress/archive very old closed issues
4. **Cross-References** - Standard format for linking issues
5. **Issue Search** - CLI tool to search issues by type/keyword
6. **Metrics/Reporting** - Issue velocity, cycle time, etc.
7. **Web UI** - Optional web interface for browsing issues

### Open Questions
1. **Issue slug uniqueness** - What if two issues same day/type have similar slugs?
   - *Proposed:* Agent checks for collisions, appends -2, -3, etc. if needed

2. **Very vague user requests** - What if slug can't be generated?
   - *Proposed:* Agent asks user for brief description to use as slug

3. **Issue reopening** - How to handle if closed issue needs more work?
   - *Proposed:* Create new issue referencing old one (e.g., "Continue 20240127-feat-add-auth")
