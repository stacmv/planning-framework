# QA Workflow

**Project:** Planning Framework
**Version:** 3.0
**Last Updated:** 2026-07-03

---

## Purpose

Quality assurance checklist that **must pass** before closing any issue.

Every item below is one of three kinds — no open-ended judgment calls:
- **[Automated]** — a shell command with a clear pass/fail exit code.
- **[AI check]** — a single yes/no question a QA agent answers by reading specific, named files (not "does it feel right," but "does file X contain/satisfy Y — yes or no").
- **[Human check]** — a single concrete action for a person, phrased as one thing to open/run plus one yes/no question.

**Rule:** If QA fails, fix and retry. Don't close issue until all checks pass.

## All Issues (Required)

### Code Quality

- [ ] **[Automated] Shellcheck passes** — `shellcheck scripts/*.sh` exits 0.
- [ ] **[Automated] No leftover debug output introduced** — `git diff develop...HEAD -- . ':!tools/' | grep -E "^\+.*(console\.log|debugger;|set -x)"` returns zero matches. Scoped to the diff (not whole-directory scan) so pre-existing example text in skill docs doesn't false-positive; `tools/` is excluded because internal CLI tooling (e.g. `tools/manual-test-ui`, `tools/onboarding-tui`) legitimately uses `console.log` as its actual terminal output, not leftover debug code.
- [ ] **[Automated] No unresolved TODOs introduced by this issue** — `git diff develop...HEAD | grep -E "^\+.*TODO"` returns zero matches (pre-existing TODOs elsewhere in the repo are not this issue's concern).
- [ ] **[AI check] No commented-out instruction blocks left in changed skill files** — read every file in `git diff --name-only develop...HEAD`; is there any line starting with `#` inside a `SKILL.md` that reads as disabled/old instruction text rather than an explanatory note? (Yes = fail, No = pass)

**Commands:**
```bash
shellcheck scripts/*.sh
git diff develop...HEAD -- . ':!tools/' | grep -E "^\+.*(console\.log|debugger;|set -x)"
git diff develop...HEAD | grep -E "^\+.*TODO"
```

### Testing

- [ ] **[Automated] Every TC in this issue's test_plan.md Status Tracker is marked done** — `grep -c '| \[ \] *|' docs/issues/open/<ISSUE-ID>/test_plan.md` returns `0` (no unchecked rows remain).
- [ ] **[Human check] Manual test checklist has been run** — open `docs/issues/open/<ISSUE-ID>/manual_test_checklist.md` — has every `[ ]` checkbox been marked `[x]` or `[ ]` with a Result recorded (none left blank)? (Yes/No)

**Commands:**
```bash
grep -c '| \[ \] *|' docs/issues/open/<ISSUE-ID>/test_plan.md
```

### Documentation

- [ ] **[AI check] Docs match the change** — read this issue's `prompt.md`/`brd.md` and the diff (`git diff --name-only develop...HEAD`) — if `prompt.md`/`brd.md` implies a user-facing doc (e.g. README) needs updating, was that file actually touched in the diff? (Yes/No — pass automatically if no such doc update was implied)

### Security

- [ ] **[Automated] No hardcoded secrets introduced** — `git diff develop...HEAD | grep -iE "^\+.*(api[_-]?key|secret|password|token)\s*=\s*['\"]"` returns zero matches.
- [ ] **[Automated] No unsafe remote-execution pattern introduced** — `git diff develop...HEAD | grep -E "^\+.*curl.*\|\s*(ba)?sh"` returns zero matches.

**Commands:**
```bash
git diff develop...HEAD | grep -iE "^\+.*(api[_-]?key|secret|password|token)\s*=\s*['\"]"
git diff develop...HEAD | grep -E "^\+.*curl.*\|\s*(ba)?sh"
```

## Feature Issues (feat, improve)

- [ ] **[AI check] Diff satisfies every acceptance criterion** — read this issue's `implementation_plan.md` (or `notes.md` for trivial-tier issues) — is every `- [ ] Acceptance Criteria` / `- [ ] Task` line checked off `[x]`? (Yes/No)
- [ ] **[AI check] Diff matches declared scope** — compare `git diff --name-only develop...HEAD` against the "Files to Create/Modify" list in `specs.md` (or `notes.md`) — is every changed file accounted for in that list, with no unexplained extra files? (Yes/No)

---

## Bug Issues (bug)

- [ ] **[Human check] Bug no longer reproduces** — follow the original repro steps recorded in `analysis.md` (or `notes.md`) against the fixed code — does the bug still occur? (Yes = fail, No = pass)
- [ ] **[AI check] Root cause addressed** — read `analysis.md`'s stated root cause and the diff — does the diff actually change the code path identified as the root cause? (Yes/No)

## Pre-Merge Checklist

- [ ] **[Automated] Working tree clean** — `git status --porcelain` returns empty output.
- [ ] **[Automated] Branch is up to date with parent** — `git merge-base --is-ancestor develop HEAD` exits 0.
- [ ] **[AI check] Commit messages are descriptive** — read `git log --oneline develop..HEAD` — does every commit message describe what changed (not "wip"/"fix"/"updates")? (Yes/No)
- [ ] **[AI check] No unrelated changes** — read `git diff --name-only develop...HEAD` — is every changed file traceable to this issue's `specs.md`/`notes.md` file list (same check as the Feature Issues item above, repeated here as the merge gate)? (Yes/No)

**Commands:**
```bash
git status --porcelain
git merge-base --is-ancestor develop HEAD
```

## Project Scope Guard

This repository has no application code, UI, database, or CI/CD pipeline — it is markdown skill-instruction files plus standalone bash scripts. Rather than listing "Performance / Accessibility / Browser / Database / Post-Merge CI" as perpetually-inapplicable checklist items, one automated guard enforces that this scope hasn't silently changed:

- [ ] **[Automated] No application-code or CI files introduced (outside internal tooling)** — `git diff --name-only develop...HEAD | grep -v '^tools/' | grep -E '\.(tsx?|jsx?|py|rb|go|sql)$|^\.github/workflows/'` returns zero matches. `tools/` is excluded because it's the established home for internal zero-dependency CLI tooling (e.g. `tools/manual-test-ui`, `tools/onboarding-tui`) — not application/product code. If this ever fails outside `tools/`, it means the repo's scope has expanded — restore the Performance/Accessibility/Browser/Database/Post-Merge/CI sections from `pf-qa-setup`'s default template at that point.

**Commands:**
```bash
git diff --name-only develop...HEAD | grep -v '^tools/' | grep -E '\.(tsx?|jsx?|py|rb|go|sql)$|^\.github/workflows/'
```

## QA Failure Handling

**If QA fails:**
1. **Don't close the issue** - Keep working until all checks pass
2. **Fix the failure** - Address the specific failing check
3. **Retry QA workflow** - Run checks again
4. **Document in session-log** - Note what failed and how it was fixed
5. **Mark blocker** - If blocked on external issue

**If repeatedly failing:**
- Consider if requirements need clarification
- Discuss with team/user
- May need to split into multiple issues

- No coverage/performance/accessibility targets are tracked — see Project Scope Guard above for why.
