# QA Workflow

**Project:** Planning Framework
**Version:** 3.0
**Last Updated:** 2026-07-03

---

## Purpose

Quality assurance checklist that **must pass** before closing any issue.

Every item below is one of three kinds — no open-ended judgment calls:
- **[Automated]** — a shell command with a clear pass/fail exit code.
- **[AI check]** — a single yes/no question a QA agent answers by reading specific, named files (not "does it feel right," but "does file X contain/satisfy Y — yes or no").
- **[Human check]** — a single concrete action for a person, phrased as one thing to open/run plus one yes/no question.

**Rule:** If QA fails, fix and retry. Don't close issue until all checks pass.

## All Issues (Required)

### Code Quality

- [ ] **[Automated] Shellcheck passes** — `shellcheck scripts/*.sh test/*.sh` exits 0. `test/` is in scope because the bash test harness (`test/lib.sh` and the per-group suites) is the gatekeeper that stops a test from running the convergence script against the developer's real `$HOME` — it is the last code in the repo that should go unlinted.
- [ ] **[Automated] No leftover debug output introduced** — `git diff develop...HEAD -- . ':!tools/' ':!test/' ':!docs/issues/' ':!.qa-workflow.md' | grep -E "^\+.*(console\.log|debugger;|set -x)"` returns zero matches. Four exclusions, each load-bearing:
  - `tools/` — internal CLI tooling legitimately uses `console.log` as its actual terminal output, not leftover debug code.
  - `test/` — the hand-built fixtures **impersonate real consumer projects**, so they deliberately contain a consumer's `src/main.js` with a debug print, and a consumer's own QA checklist telling its author to remove such prints. The gate was matching the scenery, not the code.
  - `docs/issues/` and **this very file** — a gate cannot scan the prose that *describes* it. The line you are reading names the trigger strings it hunts for; so does the `Commands` block below; so does any `qa_report.md` that quotes the command. Without these two exclusions, **every edit to a gate's own description trips that gate**, and the QA of the change that fixes a gate can never go green. Verified the hard way: this exact self-reference turned `make test` red once already.
- [ ] **[Automated] No unresolved TODOs introduced by this issue** — `git diff develop...HEAD -- . ':!docs/issues/' ':!test/' ':!.qa-workflow.md' ':!skills/pf/templates/' | grep -E "^\+.*TODO" | grep -v 'TODO: Run /pf-'` returns zero matches (pre-existing TODOs elsewhere in the repo are not this issue's concern). Four exclusions, each deliberate: the literal `TODO: Run /pf-` is the *stub-recognition rule* itself — the string a skill must grep for to refuse a placeholder document as a completed stage — so it legitimately appears in `skills/`, in planning documents and in test fixtures; `docs/issues/` is excluded because planning documents quote it; `test/` because fixtures deliberately embed a stub; and **this very file**, because a gate cannot scan the prose that describes it — the sentence you are reading contains the trigger literal, so without the exclusion any edit to this gate's own wording trips the gate; and `skills/pf/templates/` because it is a byte-for-byte mirror of `docs/planning/templates/` (kept in step by `test/pf-idea-templates-mirror.sh`) whose checklist templates contain lines *about* TODOs -- copies of text that already lives on the trunk, which the mirror turns into additions in every issue diff that first creates it. Note what is **not** excluded: `skills/` as a directory. A genuine stray marker in a skill file still fails this gate.
- [ ] **[AI check] No commented-out instruction blocks left in changed skill files** — read every file in `git diff --name-only develop...HEAD`; is there any line starting with `#` inside a `SKILL.md` that reads as disabled/old instruction text rather than an explanatory note? (Yes = fail, No = pass)

**Commands:**
```bash
shellcheck scripts/*.sh test/*.sh
git diff develop...HEAD -- . ':!tools/' ':!test/' | grep -E "^\+.*(console\.log|debugger;|set -x)"
git diff develop...HEAD -- . ':!docs/issues/' ':!test/' ':!.qa-workflow.md' ':!skills/pf/templates/' | grep -E "^\+.*TODO" | grep -v 'TODO: Run /pf-'
```

### Testing

- [ ] **[Automated] Every TC in this issue's test_plan.md Status Tracker is marked done AND none of them failed** — BOTH of these return `0`:
  - `grep -c '| \[ \] *|' docs/issues/open/<ISSUE-ID>/test_plan.md` — no row left unprocessed;
  - `grep -c '| ✗ *|' docs/issues/open/<ISSUE-ID>/test_plan.md` — no row failed.

  The second command is not decoration. `/pf-test` rewrites a processed row's Status from `[ ]` to `✓` **or `✗`** — so once it has run, zero `[ ]` remain *whatever the outcome*, and a gate that only counts `[ ]` goes green on a test plan full of failures. It would be meaninglessly green: passing precisely because the tests were run, not because they passed.
- [ ] **[Human check] Manual test checklist has been run** — open `docs/issues/open/<ISSUE-ID>/manual_test_checklist.md` — has every `[ ]` checkbox been marked `[x]` or `[ ]` with a Result recorded (none left blank)? (Yes/No)

**Commands:**
```bash
grep -c '| \[ \] *|' docs/issues/open/<ISSUE-ID>/test_plan.md
grep -c '| ✗ *|' docs/issues/open/<ISSUE-ID>/test_plan.md
```

### Documentation

- [ ] **[AI check] Docs match the change** — read this issue's `prompt.md`/`brd.md` and the diff (`git diff --name-only develop...HEAD`) — if `prompt.md`/`brd.md` implies a user-facing doc (e.g. README) needs updating, was that file actually touched in the diff? (Yes/No — pass automatically if no such doc update was implied)

### Version Bump

This project **is** the framework — there is no separate "product" to version alongside it, so the only version that ever moves here is `PF_VERSION` (`scripts/converge-to-v3.sh`). A consumer project that builds its own product *with* this framework tracks that product's version independently in its own `.qa-workflow.md` (see `pf-qa-setup`'s "Version Bump" section) — never conflate the two.

- [ ] **[AI check] CHANGELOG updated if framework-facing** — read `git diff develop...HEAD` — does it change skill behavior (`skills/*/SKILL.md`), the default schema a skill ships (e.g. `agents.yml`/`role-profiles.yml` default content defined in `pf-roles/SKILL.md`), or a script a consumer project runs (`scripts/converge-to-v3.sh`, `scripts/update-skills.sh`)? If yes, does `CHANGELOG.md`'s `## [Unreleased]` section contain a bullet describing this change? (Yes/No — pass automatically if the change is docs-only, test-only, or confined to `tools/`/`test/` internal tooling)

  **`PF_VERSION` itself is not bumped here, and that is correct, not an oversight.** Cutting a release (bumping `PF_VERSION`, syncing every `skills/*/SKILL.md`'s `version:` frontmatter, moving `[Unreleased]` under a dated heading) is a separate, occasional, deliberate act — not a per-issue default — see `CONTRIBUTING.md`'s "Cutting a Release" checklist.

**Commands:**
```bash
git diff develop...HEAD -- CHANGELOG.md
```

## Feature Issues (feat, improve)

- [ ] **[AI check] Diff satisfies every acceptance criterion** — read this issue's `implementation_plan.md` (or `notes.md` for trivial-tier issues) — is every `- [ ] Acceptance Criteria` / `- [ ] Task` line checked off `[x]`? (Yes/No)
- [ ] **[AI check] Diff matches declared scope** — compare `git diff --name-only develop...HEAD` against the "Files to Create/Modify" list in `specs.md` (or `notes.md`) — is every changed file accounted for in that list, with no unexplained extra files? (Yes/No)

## Bug Issues (bug)

- [ ] **[Human check] Bug no longer reproduces** — follow the original repro steps recorded in `analysis.md` (or `notes.md`) against the fixed code — does the bug still occur? (Yes = fail, No = pass)
- [ ] **[AI check] Root cause addressed** — read `analysis.md`'s stated root cause and the diff — does the diff actually change the code path identified as the root cause? (Yes/No)

## Pre-Merge Checklist

- [ ] **[Automated] Working tree clean** — `git status --porcelain` returns empty output.
- [ ] **[Automated] Branch is up to date with parent** — `git merge-base --is-ancestor develop HEAD` exits 0.
- [ ] **[AI check] Commit messages are descriptive** — read `git log --oneline develop..HEAD` — does every commit message describe what changed (not "wip"/"fix"/"updates")? (Yes/No)
- [ ] **[AI check] No unrelated changes** — read `git diff --name-only develop...HEAD` — is every changed file traceable to this issue's declared file list, with no unexplained extras? (Yes/No) Which document holds that list depends on the issue: for **feat/improve** issues it is `specs.md` (or `notes.md` at trivial tier) — same check as the Feature Issues item above, repeated here as the merge gate. For **bug** issues above trivial tier there is no `specs.md` and no `notes.md`, so the authoritative list is the "Files to Create/Modify/Delete" tables in `implementation_plan.md`; those tables are **normative** — a file touched but not listed there is either a mistake or a gap in the plan, and either way this gate fails.

**Commands:**
```bash
git status --porcelain
git merge-base --is-ancestor develop HEAD
```

## Project Scope Guard

This repository has no application code, UI, database, or CI/CD pipeline — it is markdown skill-instruction files plus standalone bash scripts. Rather than listing "Performance / Accessibility / Browser / Database / Post-Merge CI" as perpetually-inapplicable checklist items, one automated guard enforces that this scope hasn't silently changed:

- [ ] **[Automated] No application-code or CI files introduced (outside internal tooling and tests)** — `git diff --name-only develop...HEAD | grep -vE '^(tools|test)/' | grep -E '\.(tsx?|jsx?|py|rb|go|sql)$|^\.github/workflows/'` returns zero matches. `tools/` is excluded because it's the established home for internal zero-dependency CLI tooling (e.g. `tools/manual-test-ui`, `tools/onboarding-tui`) — not application/product code. `test/` is excluded for the same reason: the bash test harness and its hand-built fixtures (which contain `.js` files precisely because they impersonate real consumer projects) are test material, not product code. If this ever fails outside `tools/` and `test/`, it means the repo's scope has expanded — restore the Performance/Accessibility/Browser/Database/Post-Merge/CI sections from `pf-qa-setup`'s default template at that point.

**Commands:**
```bash
git diff --name-only develop...HEAD | grep -vE '^(tools|test)/' | grep -E '\.(tsx?|jsx?|py|rb|go|sql)$|^\.github/workflows/'
```

## QA Failure Handling

**If QA fails:**
1. **Don't close the issue** - Keep working until all checks pass
2. **Fix the failure** - Address the specific failing check
3. **Retry QA workflow** - Run checks again
4. **Document in session-log** - Note what failed and how it was fixed
5. **Mark blocker** - If blocked on external issue

**If repeatedly failing:**
- Consider if requirements need clarification
- Discuss with team/user
- May need to split into multiple issues
